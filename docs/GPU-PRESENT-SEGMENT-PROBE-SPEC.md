# 同一プロセス内の全画面準備待ち比較

## 判断対象

[前回の0／1ms比較](GPU-PRESENT-WAIT-PROBE-RESULTS-2026-09-09.md) は別起動ごとの全画面変動が大きく、待ちの効果を確定できなかった。同一プロセス・同一スワップチェーン内で待ち要求を切り替え、起動ごとの状態差を減らす。順序依存・時間経過・切替後の影響は依然残るため、逆順も比較する。

独立GPU試作のみ。split、Spout位相4ms、Spout mutex要求8ms、公式WinSpoutDXreceiver、monitor index 1を固定する。合成・送信周期、GPU device、swapchain、共有画像pool、sender、準備通知の保持状態は区間境界で再作成・リセットしない。待ち上限1ms、GPU完了確認、期限見送りは前回通り。

## 区間モデル

`--present-wait-plan fixed|abba|baab` を追加し、既定fixedは既存の `--present-wait-ms` を使用する。abbaは0,1,1,0ms、baabは1,0,0,1ms。試験全長を4等分し、予定QPCから区間を選ぶ。実行が遅れた周期はその予定時刻の区間を選び、飛ばした区間を追いかけない。同じ値の隣接区間も区別して記録する。

非fixedは全画面を含み、静的な `--present-wait-ms` は0を要求する。各区間長は `2*Warmup` より長くなければならない。区間境界は `origin + (long)(index * (Seconds / 4) * frequency)`。各区間の計測窓は開始+Warmup以上、終了-Warmup未満。

manifestへ区間の番号、要求値、開始・終了秒とQPC、計測窓を記録する。GPU周期先頭で区間が変わる時に `present.wait.segment` を一度記録し、readinessイベントの待ち要求をその周期の区間設定で検証する。保持済み準備通知を次区間へ持ち越せるので、解析側も区間境界で準備状態をリセットしない。

## 実行と評価

親が実装レビュー、Debugビルドと管理テストを確認してから実機を直列実行する。まず1080p/windowedでABBA、全32秒・区間8秒・Warmup2秒。正常終了と区間解析を確認後、4K生成キャンバスでABBA全128秒、次にBAAB全128秒を各1回実行する。各区間32秒のうち22秒を評価する。途中で異常終了・記録不整合があれば次の実機を開始しない。

4K各runの窓は[5,27)、[37,59)、[69,91)、[101,123)秒。各窓ごとに既存の合成／Present成功／Spout公開頻度、画像年齢、間隔、コピー見送り、準備未完了・実測準備確認時間、期限見送りを集計する。混在run全体の平均を0msまたは1ms単独の結果として扱わない。指標ペアと所有権は窓外を含む全ログで照合する。

0msで見送りがある状態から1msへ移って改善し、逆向きの変化でも整合するかを評価する。1msで未準備が発生せず、確認が即時に戻るだけのケースは待ちによる救済の直接証拠とはしない。時間経過や一度待った影響が後続区間へ残る可能性も評価する。問題が再現しなければ未確定とし、要求上限やswap設定を自動変更しない。

表示先の実描画寸法は1080pで、物理4K60の評価ではない。API成功・GPU完了と受信機の生存は、異なる画像の実受信を証明しない。既存ログ・AGENTS.md・通常設定・他アプリを保持し、自分が起動したプロセスのみ終了する。WPR/UACのGPU記録、GPUリセットは行わない。本体統合・mpv・hwdec・GPUプレビュー・保留中のSpout問題へ広げない。
