# Spout mutex待ち4ms／8msの比較

2026-09-09。ユーザーの「次に進んでください」を受け、[受信機の対照実証](GPU-RECEIVER-CONTROL-PROBE-RESULTS-2026-09-09.md)に続いて送信側の待ち予算を比較する。親が設計・レビュー・実機評価、サブエージェントが試作とハーネスの実装を担当する。

実装・比較は完了。[結果](GPU-MUTEX-8MS-PROBE-RESULTS-2026-09-09.md)を参照。8ms条件はSpout59.68〜59.95Hz、公開画像の平均年齢5.35〜5.66msとなり、公開空白の改善が2試行で再現した。次の比較基準を待ち8msとするが、CLI既定0msと本体未統合は維持する。

## 目的

公式受信機を伴う条件では、送信側のmutex取得失敗と公開空白が残る。取得待ち指定を4msから8msへ増やした場合、公開の抜けを減らせるか、その代わりに画像年齢や表示準備未完了が増えないかを確認する。受信機の処理やGPU内部原因を確定したという前提にはしない。

## 変更と不変条件

試作の `--mutex-wait-ms` とハーネスの許容範囲を整数0〜8msへ拡大する。既定値0msを維持し、8msより長い待ちは追加しない。新しい実行ファイルで4msの基準条件も取り直す。

実効WaitOne指定は設定値と次周期までの残り整数ms（切り捨て）の小さい方。次回期限は位相を含むスケジューラー自身のDueQpcを使う。1回だけ取得を試し、再試行や追いつき送信を行わない。取得後に期限・停止要求を再確認し、取得できていても無効なら一度だけ返却して送信しない。OSの復帰時刻は指定msを超える可能性があるため、実測区間と期限超過を記録する。

画像選択、コピー、共有画像の使用権返却、送信後のGPU完了確認、外側mutex返却の順序を維持する。GPU命令の発行後に次周期の期限へ達しても、使用中の画像を強制的に解放しない。通常終了・明示的な強制終了の方針、Present設定、スレッド構成、送信位相は変更しない。

## 検証

管理テストでは8msの入力、9ms拒否、残り7.999msで7msへ制限されること、高fpsでの予算制限、遅れた取得成功・停止時の返却を確認する。解析器も設定／実効値0〜8へ揃え、実効値が設定や期限予算を超えるログを拒否する。旧ログ・受信機対照・位相計測との互換性を維持する。

親レビューとテスト後、公式受信機あり・1080p・8ms待ち・12秒・warmup2秒の短いスモークを直列実行する。正常終了とログを確認して4Kへ進む。

4K比較はsplit／both、送信位相4ms、公式WinSpoutDXreceiver、GPU生成3840×2160、60Hz、32秒、warmup5秒、解析窓 `[5,27)` の22秒。Debug / x64、既存の1920×1080実表示先を維持。A=4ms、B=8msとしてA→B→B→Aを直列実行する。

平均公開Hzに加えて、最長公開間隔、1秒区間最小公開数、画像年齢の平均・p99・最大、mutex取得失敗と連続回数、実際の取得区間、期限超過、コピー見送り、全画面の表示準備未完了を見る。成功画像の年齢だけから、公開されない時間の受信画像の新しさを保証しない。改善しない場合に、8msより長い待ちへ自動的に広げない。
