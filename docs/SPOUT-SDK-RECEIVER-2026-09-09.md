# Spout SDK受信サンプルでの検証（2026-09-09）

ユーザー指定の`WinSpoutDXreceiver.exe`を使い、製品SpoutOutputの4K60送信プローブを30秒ずつ2回実行した。両回とも送信停止は再現せず、2回目には受信画面の表示変化も確認した。過去のSpout無効化の根本原因は未解決であり、この結果から標準OBSプラグインが原因だと断定しない。

## 入力と条件

作業ブランチは`refactor/session-lifecycle`、開始時HEADは`c8f0db4`。既存の未追跡AGENTS.mdを保持し、製品コード・DLL・100ms期限・hwdec既定を変更せず、再ビルドもしていない。

保存画面は明るいグレー→暗いグレー→明るいグレーと変化した。3枚の表示領域には目視で異なる明るさの混在を認めなかった。ただし縮小表示した受信窓の疎な3標本であり、4K共有画像の全画素・全フレームの一致、60fps受信継続、同期精度は未検証である。画像001と003のSHAは同じ、002は異なる。

## 保全と限界

各rootに実行スクリプト、入力hash、所有PID／起動時刻、原始sender.jsonl、診断ログ、observations、resultを保存した。2回目にはPNG3枚と取得helperも保持している。採取前後の入力SHA256は1回目7件・2回目8件すべて一致した。各receiverは所有PIDが一致するHWNDへWM_CLOSEを送り終了し、送信側は自然終了した。通常OBS設定・元の動画やプロジェクトは操作していない。

04:50:55 JSTの`post-test-state.json`で関連試験プロセス0・WPR停止を確認した。

今回の判定は、このSDK受信サンプルを使う30秒×2回ではSpout無効化が再現せず、2回目の3画面で表示変化を確認した、という範囲に限る。過去のWPR付き試験とは観測負荷も異なり、受信アプリの差だけを原因として比較できない。長時間の安定性と無効化の原因追跡は引き続き必要である。

## 主な受信先としての採用と診断範囲

ユーザーの指定に従い、今後の送信安定性検証ではこのSDK受信サンプルを主な受信先にする。提供されたEXEと同梱DLLの組み合わせを保持する。SDKの公式サンプルであることを、実機での無欠陥・全画像の整合性の保証には置き換えない。

送信無効化の調査は製品プローブの各送信QPC／前後状態、Warning／例外、失敗checkpointのTransfer段階・mutex／poll時間・最終応答・DeviceRemovedReason・PID／OS TIDを使用する。停止位置から根本原因を絞る際はGPU／CPUのETLが別途必要になる。通常の送信一覧は計測終了後に保存されるため、失敗ログに到達する前のnative停止では記録が欠ける。checkpointの書込み失敗・不完全JSONも考慮する。

受信側の全フレーム到達・同期精度については、現状の画像3色と疎なPNGでは不足する。実接続先、固有フレームID、受信または表示時刻、連続した欠落・重複・画素観測が必要である。既存サンプル自身の内蔵ログ機能の有無は未確認であり、「ログ機能がない」とは断定しない。定量測定が必要な場面では、元サンプルを変更せず、別の計測手段で補う。
