# Spout SDK受信サンプルでの検証（2026-09-09）

ユーザー指定の`WinSpoutDXreceiver.exe`を使い、製品SpoutOutputの4K60送信プローブを30秒ずつ2回実行した。両回とも送信停止は再現せず、2回目には受信画面の表示変化も確認した。過去のSpout無効化の根本原因は未解決であり、この結果から標準OBSプラグインが原因だと断定しない。

## 入力と条件

作業ブランチは`refactor/session-lifecycle`、開始時HEADは`c8f0db4`。既存の未追跡AGENTS.mdを保持し、製品コード・DLL・100ms期限・hwdec既定を変更せず、再ビルドもしていない。

指定文字列のバージョン前にあったフォルダー区切りは、実ファイルではアンダースコアだった。Downloads内に存在する次の同名サンプルを使用した。

`C:\Users\<user>\Downloads\Spout-SDK-examples_2-007-017\Spout-SDK-examples\Examples_2-007-017\SpoutDX\WinSpoutDXreceiver.exe`

- 受信EXE SHA256: `AEAC163C6D029ACBABA6A9E6642B4F5378E28DB1B1F09650B9D8F986C155AE69`
- 受信側同梱SpoutDX.dll: `2004188DA4F77B871D02CD7A03D46972FE659F000A629703C8CE967DAE390CC7`
- 製品送信側SpoutDX.dll: `BBCEE6F0031F6BD1A6461585C53F3F8F3CECBF006B486661BCDE6413E2ADDEF5`
- 製品DLL: `E910DF35C0A20F56B1E91CB85EADE5DB99EAD3C7D9EFBA1FA01CA74B46CF907B`
- プローブDLL: `9E6DDF78705F483BF8088E2968EC693CF27AABE18F0CC3AF3CBDB9496CB7876F`

受信側は指定フォルダーからそのまま起動し、同梱DLLを置き換えていない。送信元は計測前に作成した3840×2160のBGRA画像3枚（各B/G/R=64、128、192、A=255）を60Hzで切り替える。MP4・mpv・LTCは使わない。OBS・WPR・別の音声／GPU負荷試験は併走させず、各試験の前に関連プロセスなし・WPR停止を確認した。

1回目はWindowsがSetForegroundWindowを許可せず、対象窓の画面保存を3回ともskipした。送受信プロセスの正常終了と、画面確認の未達を区別する。1件の遅延WarningはCompletedで、mutex14.0371ms、SendImage2.1949ms、poll1.4114ms、transfer内部合計17.6641ms。外側SendFrameの28.7548msと同一の区間ではない。

2回目は別rootのランナーを使い、PrintWindow(2)で所有する受信HWNDだけを保存した。取得は所有する別プロセスに分け、各5秒の期限を設けた。受信窓の前面化は不要で、他アプリの画面は取得していない。スクリーンショット取得は計測中の追加負荷なので、純粋な送受信のみの性能測定とは区別する。

保存画面は明るいグレー→暗いグレー→明るいグレーと変化した。3枚の表示領域には目視で異なる明るさの混在を認めなかった。ただし縮小表示した受信窓の疎な3標本であり、4K共有画像の全画素・全フレームの一致、60fps受信継続、同期精度は未検証である。画像001と003のSHAは同じ、002は異なる。

独立担当が両runの`audit.json`で全送信のslot・QPC・有効状態・summaryの会計整合を確認した。2回目の`audit-client-roi.json`ではタイトルと枠を除く画像領域（x=8〜647、y=51〜410、640×360）を検査し、各230,400画素がそれぞれRGB=192／128／192の一色だった。領域外の画素hashは3枚で一致した。これは画像領域の変化と、その3標本に異なるグレーの混在がない証拠である。同じ色のフレーム間の混在、送信元名とフレーム番号の厳密な対応は、この方法では検証できない。

## 保全と限界

各rootに実行スクリプト、入力hash、所有PID／起動時刻、原始sender.jsonl、診断ログ、observations、resultを保存した。2回目にはPNG3枚と取得helperも保持している。採取前後の入力SHA256は1回目7件・2回目8件すべて一致した。各receiverは所有PIDが一致するHWNDへWM_CLOSEを送り終了し、送信側は自然終了した。通常OBS設定・元の動画やプロジェクトは操作していない。

04:50:55 JSTの`post-test-state.json`で関連試験プロセス0・WPR停止を確認した。

今回の判定は、このSDK受信サンプルを使う30秒×2回ではSpout無効化が再現せず、2回目の3画面で表示変化を確認した、という範囲に限る。過去のWPR付き試験とは観測負荷も異なり、受信アプリの差だけを原因として比較できない。長時間の安定性と無効化の原因追跡は引き続き必要である。
