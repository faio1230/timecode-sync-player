# T11: V3 の測定素材のキーフレーム間隔を現場相当（1 秒）にして測り直す

**利用者の決定（2026-09-16、案 A）**: 一般的なキーフレーム間隔の素材で V3 を判定する。
長いキーフレーム間隔の結果も記録として残す。

---

## 1. 経緯（T10 で確定した事実）

- 60fps クリップのシークで、ロード発行から最初のフレームまで **264ms**（24fps 91ms、29.97fps 122ms）
- 内訳は **ロード 11.6ms + 直前のキーフレームからのデコード 254.6ms**
- 同一クリップ内の対照: 目標 3.680（キーフレームから 221 フレーム先）は 277.7ms、
  目標 4.240（キーフレーム直後）は **1.5ms**
- 素材の生成（`tests/TimecodeSyncPlayer.Tests/Helpers/AccuracyVideoFixture.cs` の `EncodeAsync`）は
  `-g` を指定していないため **libx264 の既定 250 フレーム**。60fps では **4.17 秒に 1 枚**しかキーフレームが無い
- 現場の素材は 1〜2 秒間隔、または ProRes のような全フレーム独立が一般的。**いまの素材は現実より厳しい**

## 2. 直すこと（テスト側だけ。製品コードは触らない）

1. `EncodeAsync` に**キーフレーム間隔 1 秒**を指定する
   - `-g <1 秒あたりのフレーム数>`、`-keyint_min` も同じ値、`-sc_threshold 0`（内容によるキーフレーム挿入を止め、間隔を確定させる）
   - フレーム数は各クリップの fps から出す（24 → 24、29.97 → 30、60 → 60）。端数は四捨五入し、根拠をコメントに書く
2. **環境変数 `TCS_V3_GOP` で上書きできるようにする**（未設定なら 1 秒）。記録用に長いキーフレーム間隔でも測れるようにする
3. `fixture.json` に、クリップごとの **キーフレーム間隔（フレーム数と秒）** を残す
4. 生成後の検証に**キーフレーム位置の確認**を足す。`ffprobe -select_streams v -show_frames` で
   `key_frame=1` のフレーム番号を数え、**間隔が指定どおりであること**を確かめる（違えば例外）
5. 既存の生成時間が伸びすぎないこと（`ultrafast`・`crf 18` はそのまま）

## 3. 測る（実機。**親の合図を待つこと**）

1. **新しい素材で Smooth 3 本**: `scripts/run-v3-accuracy.ps1 -Backends gst -Label t11-<SHA> -Repeats 3`
   条件は T9 と同じ（gst / `outputBackend=1` / LTC 25 / Debug / 出力トレース有効 / 先行補償は既定 off）
2. **記録用に、長いキーフレーム間隔で 1 本**: `TCS_V3_GOP=250` を設定して `-Label t11-gop250-<SHA>`
3. 出すもの（合否は書かない）:
   - 定常誤差の平均・p50・p5・p95・p95-p5（run 別と 3 本結合）
   - **±80ms への収束時間（フェーズ別、全 run）**。150ms・250ms の行も
   - `analyze-v3-seek-breakdown.py` の `b→c`（ロード発行 → 最初のフレーム）をクリップ別に
   - `app-stderr.txt` の `load.attempt` の内訳（T10 と同じ表）
   - 粗い同期シークの回数、上限 0.20 への切り替え回数
4. 比較として T9 の 3 本（`t9-4fd56dd-ltc25-gst-1..3`、GOP 250）を並べる

## 4. 期待（これは仮説であって、合否ではない）

1 フレームあたりのデコードは実測で 1.13〜1.38ms。キーフレーム間隔 1 秒なら 60fps でも 3.08 秒の要求で
**約 60 フレーム ≈ 83ms** になる見込み。着地の遅れが 264ms → 100ms 前後に縮めば、
±20% の窓で 1 秒以内に収まるはず。**そうならなかった場合は、数字をそのまま報告すること。**

3. 実機を使う前に親へ一報する（別のエージェントが E2E で長く使っている）
