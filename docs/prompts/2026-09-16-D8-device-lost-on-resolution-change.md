# D8: 解像度が変わるトラック切替で GPU デバイス消失が起き、復旧後に再生が進まない

**出荷構成（GStreamer + GPU 合成）でだけ出る欠陥。** R1 の E2E で発見（2026-09-16）。
既定が mpv + CPU 合成だったため、これまで誰も踏んでいなかった。

---

## 1. 事実（実装側の報告、3/3 再現）

- テスト: `GStreamerBackend_SurvivesRepeatedTrackSwitches`。main（mpv + CPU 合成）では合格、
  出荷構成（`1e9bf86`）で失敗。単独で 3 回とも再現（13:29:37 / 13:32:00 / 13:32:08）
- 症状の順序:
  1. 最初の Next 切替で GStreamer のロードが走る（**1080p60 → 720p25**、解像度が変わる）
  2. 直後に `OutputEngine: GPU デバイス消失`
  3. 約 60ms で「GPU 復旧が完了」のログ
  4. **その後、再生クロックがほぼ停止**（`playbackRate=0.13〜0.18`）。以降トラックのロードが起きない
  5. UIA の Invoke が COM エラー（`0x8000FFFF` / `0x80040201`）で失敗し、テストが落ちる
- 今日のログでデバイス消失が出たのはこのテストだけ（他は 0 件）。**D5 の切替テスト（同素材）では出ない**
- 実装側の仮説（未確定）: 解像度変更を伴う切替で共有リングを作り直す際にデバイス消失が起き、復旧しても再生が戻らない

## 2. 依頼: まず原因を測って切り分ける（直すのはその後）

**当て推量で直さないこと。** 次の順で materials を集める。

1. **shim の stderr を取る。** `9b82070` で E2E のアプリ起動時に `app-stderr.txt` / `app-stdout.txt` を
   保存できるようになっている。この経路をこのテストでも有効にし、`load.attempt` / `ring` / `device` 関連の行を回収する
2. **どこでデバイス消失が判定されたかを特定する。** `OutputEngine` の device lost 経路
   （`GpuDeviceLostException` を投げている箇所）に対し、**直前に実行していた操作**（共有リングの再オープン、
   テクスチャ生成、フェンス待ちなど）をログで確定させる。`HRESULT` を必ず残す
   （`DXGI_ERROR_DEVICE_REMOVED` / `DXGI_ERROR_DEVICE_RESET` / それ以外を区別する）
3. **本当にデバイスが消失したのかを確かめる。** `ID3D11Device::GetDeviceRemovedReason` の値を出す。
   0（S_OK）なら**デバイスは生きていて、別の失敗をデバイス消失として扱っている**ことになる
4. **再生クロックが止まっている先を切り分ける。** 復旧後に
   - shim 側のパイプラインは進んでいるか（`gst.delivery` の間隔、`tcs_player_get_time_pos` の値）
   - 合成側は回っているか（`compose.publish` の間隔）
   - アプリ側の状態（`playbackRate` の由来）
   の 3 つを同じ時間軸で並べる
5. **解像度変更が引き金かを確かめる。** 同じ切替を「解像度が同じクリップ同士」でも試す
   （E2E の素材を差し替えるか、手動で 2 クリップのプロジェクトを作る）。
   **解像度が同じなら起きないことを確かめてから**「解像度変更が原因」と言うこと

## 3. 報告に入れるもの

- 上の 1〜5 の数字とログの抜粋（`HRESULT`、`GetDeviceRemovedReason`、各段の時間間隔）
- 「デバイス消失の判定が正しいか」「復旧後に何が止まっているか」の結論
- 直し方の案（実装はまだしない。**親が承認してから**）
