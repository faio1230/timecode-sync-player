**自分のワークツリー（`C:\Users\<user>\Documents\timecode-sync-player-wt-output-engine-20260911-1247`）で作業すること。**

不変条件は `docs/OUTPUT-GPU-INVARIANTS.md`。実機の前に一声かけること。
**合否判定は書かないこと。** 採否は親と利用者が決める。

## なぜこれをやるか

V8 の「落ち」（`present.scanout` の間隔 > 25ms）は GStreamer で 40 秒に **1〜5 回**。
原因は次まで絞れている（利用者の解析）:

- 落ちた tick の合成は**ほとんど予定どおりに始まっている**（起床遅れ 0.2〜0.6ms）。
  vblank まで約 **5ms の余裕**があった（一部だけ合成自体が 5〜8ms 遅れて起床）
- **出力スレッドが OS に数 ms 待たされて、その余裕を使い切ったときに落ちている**
- ProRes の CPU デコード（`avdec_prores`）でも外部 CPU 負荷 12 本でも落ちは増えない。**重さの問題ではない**
- **出力スレッドの優先度を上げる処理（MMCSS 等）は今のコードに無い**

**つまり「OS に待たされる」ことが直接の原因なので、優先度を上げれば消える可能性がある。**
消えれば V8 は基準「落ち 0」のまま合格できる。

## 依頼

### 1. GPU worker の優先度を上げる変更を、切り替え可能な形で入れる

- **対象は表示を担う GPU worker スレッド**（合成 → present を回しているスレッド）
- 手段は任せる。Windows なら **MMCSS（`AvSetMmThreadCharacteristics` の "Pro Audio" / "Playback" など）**か
  `Thread.Priority` / `SetThreadPriority` が候補。**選んだ理由をコミットメッセージに書くこと**
- **有無を切り替えられること。** 環境変数でよい（例 `TCS_OUTPUT_THREAD_PRIORITY=high`）。
  **既定は現状のまま**（＝優先度を上げない）にしておくこと。採否は測ってから決める
- 失敗したときに落ちないこと（API が使えない環境でも起動できること）。失敗はログに 1 回だけ

### 2. 同じセッションで対比を測る

**GStreamer 4K、50 秒、DISPLAY1 全画面、Spout ON**（既存の V8 と同じ条件）で:

- **変更なし 3 本・変更あり 3 本**
- **同じセッション内で交互に回さず、まとめて 3 本ずつでよい**が、間に再起動を挟まないこと

出す表:

| 条件 | 落ち（`present.scanout` 間隔 > 25ms） | `display.vblank.wait.end` の `outcome=compose` |
| --- | --- | --- |
| 変更なし | | |
| 変更あり | | |

### 3. 悪化していないことも確認する

優先度を上げると他が割を食う可能性がある。**次の 3 つが悪化していないことを数字で示すこと**:

- **UI の応答**（ボタン操作から反応までの時間、または UI スレッドのハング有無）
- **LTC 受信**（音声スレッド。取りこぼし・デコード失敗が増えていないか）
- **CPU 使用率**（プロセス全体）

### 4. 結果の読み方（親と利用者が判断する材料）

- **落ちが 0 になれば**、V8 は基準「落ち 0」のまま合格にできる
- **変わらなければ**、実測の上限に余裕を持たせた回数と
  **「連続した落ちが無いこと」**を基準にする案を出してほしい（数字の案も添える）。
  **判断は利用者がする**

> **V8 の基準は固定値で書く。** mpv は v0.4 で除去するため、mpv との比較はもう使えない。
