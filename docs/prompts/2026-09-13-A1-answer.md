# A1 設計案への回答（親、2026-09-13 09:30 JST）

**案 1（ソーステクスチャの読み戻し＋`compose.publish` の QPC＋既存 env で有効化）の「境界」を承認する。**
ただし下記の条件を満たすこと。解析スクリプト側の `preview-frame` 受理と
`unknown-trace-event-type` / `trace-event-count-mismatch` の解消も承認する。

## なぜ案 1 の境界か（案 3 を採らない理由）

この計測の目的は **mpv の基準値と比較して「GStreamer が同等以下か」を判定する**ことにある。
mpv の基準値（平均絶対 59.7ms、p95 118.6ms、p99 146.7ms、最大 160.0ms、測定 1741/1741）は
**「LTC 受信 → レンダラが公開したフレームの画素」**という境界で測った。

案 3（合成後キャンバスを読む）は実際の表示に近く、計測としてはより良い。しかし**境界が mpv の基準値と異なる**ため、
比較が成立しなくなる。配置・スケール後の画素を読むと合成段階の遅延が加わり、mpv の数字と並べられない。
**今は「より良い計測」より「比較できる計測」が要る。** 案 3 は将来の改善候補として記録に残す。

案 2 を採らないのは、**黒判定を合成状態から推定する**と測っているものが変わるため。
CPU 経路は画素そのものから黒を判定していた。推定に置き換えると、同じ指標として並べられない。

## 条件 1: 読み戻しが計測対象を歪めていないことを数値で示す

1080p BGRA のフル読み戻しは 1 枚 約 8.3MB、60Hz で約 500MB/秒。**この読み戻し自体が合成や配信を
遅らせるなら、測っているのは製品ではなく計測器になる。**

同一素材で **計測 ON と OFF の run を対で取り**、次を並べて報告すること:

| | 計測 OFF | 計測 ON |
| --- | --- | --- |
| 実フレーム/秒 | | |
| 合成 p99 | | |
| 生成→走査 | | |
| error / exit | | |

**ON 側が明確に劣化するなら、その数字で精度を語ってはいけない。** その場合は条件 2 へ。

## 条件 2: 読み戻しを減らす場合も、黒は画素で判定する

コストが問題になったら、読み戻す範囲を**マーカー帯＋フレーム内部の数点**に絞る。
内部の数点を読めば黒かどうかは画素で判定できる。**合成状態からの推定には置き換えないこと**（案 2 の弱点）。
Probe の意味を CPU 経路と同一に保つことが、比較可能性の条件。

## 条件 3: 既定経路のゼロコスト

`SyncAccuracyTrace.Current.IsEnabled` が false のときに合成 tick へ分岐や読み戻しが一切増えないこと
（不変条件 I4 の趣旨）。上の表の「計測 OFF」列が、現行の実測値（実フレーム 60/秒、合成 p99 1ms 前後、
生成→走査 4〜6ms、error 0）と同等であることで示す。

## 検証計画について

提示された計画（`backend=1`/`outputBackend=1` と `backend=0`/`outputBackend=1` の両方で COMPLETE、
計測 OFF の通常 run、非E2E 全件、全 E2E 58/0/4）で良い。これに上記の ON/OFF 対比を追加すること。

**`backend=0`（mpv）+ `outputBackend=1` も必ず測ること。** mpv 削除前に、GPU 経路での mpv の値を残す必要がある。
既に取ってある mpv の基準値は `outputBackend=0`（mpv 本来の経路）のものなので、**別物として扱い混同しないこと**。

実機・E2E の実行前には一声かけること。
