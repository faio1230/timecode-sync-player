# V3 拡張: LTC のフレームレート 4 種すべてで測る

利用者の指示（2026-09-15）:

> タイムコードのフレームレートは実際は 24fps、25fps、29.97fps、30fps の種類があります。
> V3 ではこれ全部テストしてください。どれも現場で使われる可能性があります。

現在の V3 は **LTC 25fps 固定**（`fixture.json` の `ltcFps: 25`）。4 種に広げる。

---

## 1. 現状の対応状況（親が確認済み）

| 層 | 状況 |
| --- | --- |
| `LtcTestSignalGenerator.Generate(..., **double fps**, ...)` | **対応済み。** 非整数を受けられる |
| 同 `bits[10] = tc.DropFrame` | **ドロップフレームのビットは実装済み** |
| `LtcSignalPlayer`（ラッパー） | **`int fps` で縛っている。ここが唯一の制約** |
| `TimecodeFpsSelector` | **対応済み。** `Fixed24 / Fixed25 / Fixed29_97 / Fixed30` と自動検出（`30000.0/1001.0`） |
| `AccuracyFixture` | `ltcFps` が固定値。パラメータ化が要る |

**つまり直すのは `LtcSignalPlayer` の `int fps` → `double fps` と、フィクスチャのパラメータ化だけ。**
生成器とアプリ側は既に揃っている。

## 2. 測る組み合わせ

LTC 4 種 × 既存の 6 フェーズ。素材は現行のまま（clip1 24fps / clip2 29.97fps / clip3 60fps）。

| # | LTC fps | 備考 |
| --- | --- | --- |
| 1 | 24 | |
| 2 | 25 | 現行。過去の測定と直接比較できる |
| 3 | **29.97**（30000/1001） | 非整数。`double` 経路の確認も兼ねる |
| 4 | 30 | |

**GStreamer のみでよい**（利用者の指示: mpv は削除前提なので基本 GStreamer だけ見る）。
**各 3 本、同一セッション内で LTC fps を交互に回す**（24→25→29.97→30→24→…）。
V8-D と V3 でこの方法が効いている。間に再起動やビルドを挟まない。

**先行補償（D7-a）は無効のまま**（`TCS_SEEK_LATENCY_COMPENSATION=off`）。二重補正になるため。

## 3. 併せて記録すること

- **各組み合わせの許容差（デッドゾーン）。** `max(1/videoFps, 1/tcFps) × 6` なので LTC fps で変わる。
  LTC 24 + clip1 24fps なら 250ms、LTC 30 + clip3 60fps なら 200ms。**フェーズごとに実際の値を出すこと**
- **`TimecodeFpsSelector` の自動検出が当たっているか。** 起動ログの
  `mode="Auto" detectedFps=... dropFrame=... resolvedFps=...` を run ごとに拾う。
  **外した組み合わせがあれば、それ自体が不具合**
- 自動検出が外れる場合に備え、**固定指定（`Fixed24` 等）でも 1 本ずつ確認**できると良い。
  外れなければ不要

## 4. ドロップフレームは今回の範囲外（理由を明記する）

29.97 には drop-frame（DF）と non-drop（NDF）があり、現場では DF も使われる。
ただし **DF は「フレーム番号の付け方」だけが違い、レートは同じ**。
DF は毎分の先頭で番号 00・01 を飛ばす（10 分ごとを除く）ので、
**分をまたがない測定では DF と NDF は完全に同一の信号になる。**

現行の V3 は 00:00:00 付近の 35 秒しか使わないため、**このままでは DF を試験できない**。
DF を本当に測るなら、**分境界をまたぐ開始タイムコード**（例 00:00:59:00 から）の
別フィクスチャが要る。**今回はやらない。** 利用者へ別途提案する。
