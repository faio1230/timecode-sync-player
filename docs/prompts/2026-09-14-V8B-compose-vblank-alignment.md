**4K の 6 run すべてで、落ちの回数と `display.vblank.wait.end` の `outcome=compose` の回数が一致する。**

| run | 落ち（`present.scanout` 間隔 > 25ms） | `wait.end` の `compose` | `wait.end` の `target` |

**落ちは例外なく「vblank 待ちが target ではなく compose で終わった」ときに起きている。**
これは OS の揺らぎという説明より具体的で、**共有の出力エンジンの、合成を先にする経路**を指している。

**したがって「mpv 固有」とは言えない。** 同じ出力エンジンを GStreamer も使う。

### 利用者の追加観測（親は再現できていない。定義を揃えること）

利用者から「mpv 4K-1 では `compose.start` が vblank の 14ms 以降に 157 回入っていた（他の run は 0〜1 回）」
という指摘があった。

**親が「直前の `present.scanout` から 14ms 以降」で数えると、全 run で 2000 件超**になり再現しない。
合成リードが約 2.5ms なので、**「直前 vblank から 14ms 以降」は通常の状態**である。

**利用者が見ていたのは別の基準のはず**（予測された次の vblank を基準にした遅れ、
`wait.end` からの遅れ、あるいは target vblank を過ぎてからの開始など）。
**まずこの量の定義を決め、定義を明記した上で数え直すこと。** 定義が違うまま議論しても噛み合わない。

## 依頼

### 1. `outcome=compose` で待ちが終わるのはどういうときか

コードで確定させる。`display.vblank.wait` が `target` ではなく `compose` を返す条件は何か。
**どの状態がそろうとそうなるのかを、コードの引用付きで説明すること。**

### 2. mpv 4K-1 で位置合わせが崩れた原因

- 514 回（約 19 秒間）も `compose` で終わり続けたのはなぜか
- **`mpv-4k-3` は合成時間が同程度なのに正常。** したがって「合成が重いから」では説明できない。
  **重さ以外の何が違うのかを数字で示すこと**
- 崩れ始めた瞬間の前後（数十 tick）の各段階の時刻を並べた表を出すこと
- **一度崩れると戻らないのか、戻る run もあるのか**

### 3. GStreamer でも起こしうるか — ここが v0.4 の判断に効く

**合成が重く、かつ時間が揺れる条件を GStreamer で作って試すこと。** 例:

- **CPU デコード（ProRes など）** で合成 tick に負荷と揺らぎを与える
- 4K 素材 + Spout + 全画面の同時
- 他プロセスの負荷を意図的に載せる

**GStreamer でも `outcome=compose` が増える条件が見つかれば、v0.4 の出荷リスクである。**
見つからなければ、定常の 3〜5 回だけが残る。

### 4. 定常の 3〜5 回はどう説明されるか

`outcome=compose` が 3〜5 回起きること自体は、上の「崩れ」と同じ機構の軽い版なのか、別物なのか。
