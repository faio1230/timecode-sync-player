# V8-D 差し戻し: 「既定で有効」が「明示的に high」より悪い

**統合できない。** 既定を有効にした状態の落ちが **6 / 9 / 7** で、
利用者が確定した基準「**40 秒で 5 回以下**」を満たしていない。

実装そのものは良い（失敗フック・無効化スイッチ・起動ログ・E2E）。**問題は結果が説明できないこと。**

---

## 数字（親の独立検証。`present.scanout` の間隔 > 25ms、5〜45 秒）

素材は全 run 同じ（`v1_h265_4k60.mp4`）、DISPLAY1 全画面、Spout ON、LTC 送出あり。

| 条件 | scanout レート | 落ち |
| --- | ---: | ---: |
| V8-C `high`（環境変数で明示） | 59.954 / 59.979 / **60.006** | **0 / 2 / 3** |
| V8-C `none` | 59.884 / 59.902 / 59.954 | 4 / 5 / 3 |
| **V8-D `default`（既定 ON）** | **59.803 / 59.828 / 59.879** | **6 / 9 / 7** |

**V8-D は全 run で scanout レートが最も低い。** ばらつきではなく系統的な差である。

アプリログには `mode=mmcss/Pro Audio source=default` が出ているので、
**MMCSS 自体は適用されている**。それでも結果が「優先度なし」より悪い。

---

## 依頼: 同一セッションで 3 条件を並べて測る

**いま必要なのは新しい機能ではなく、この食い違いの説明。**

**1 セッションの中で、間に再起動を挟まず**、次の 3 条件を各 3 本、**交互に**回すこと。

| 条件 | 指定 |
| --- | --- |
| A | `TCS_OUTPUT_THREAD_PRIORITY=off` |
| B | **指定なし（既定 = ON）** |
| C | `TCS_OUTPUT_THREAD_PRIORITY=high`（V8-C と同じ明示指定） |

**交互に回す**のは、時間帯やマシンの状態の影響を分離するため（A→B→C→A→B→C→…）。

### 見てほしいこと

1. **B と C は同じ結果になるか。** ならなければ**実装の欠陥**である。
   既定を解決する経路と環境変数を解決する経路で、**適用のタイミングや対象スレッドが違っていないか**を
   コードで確認すること（例: 既定の解決が worker スレッド生成より後に走っている、
   別のスレッドに適用している、複数回登録している、など）
2. **A が V8-C の `none`（4/5/3）と同水準に戻るか。** 戻らなければ、
   V8-C と V8-D の間で**環境が変わった**ことになる（その場合は何が変わったかを探す）
3. **`on_new_sample: frame_lock busy; waiting` の出方**も記録すること。
   ペインに大量に出ていた。落ちとの時間的な相関があるかを見る

### 補足

- `mode=... source=default` と `source=env:high` のログで、どちらの経路を通ったかは区別できる。
  **各 run のログでそれを確認して表に載せること**
- `app-log-tail.txt` は**日次ログの末尾 400 行**で複数 run が混ざる。
  **run の開始時刻で絞って読むこと**（親も過去に同じ誤りをした）

## 60 分 run について

60 分の run は完走したようだが、**上の食い違いが解けるまで V6 の判定には使わない**。
**生データは消さずに残しておくこと。** 食い違いが解けた後、必要なら測り直す。

## 守ること

1. **製品コードの変更は最小限に。** いま足りないのは説明であって機能ではない
2. 非E2E が全て通ること
3. **実機は 1 本ずつ。自分の PID のみ終了**
4. **合否判定は書かないこと**
