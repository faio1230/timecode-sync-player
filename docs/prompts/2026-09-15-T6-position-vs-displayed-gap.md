# T6: 「プレイヤーの報告位置」と「画面に出ている絵」の 74ms のずれを分解する

**推測をやめて計測で切る。** 親は仮説を 2 回外している（`thread-type=frame`、`max-buffers`）。
今回は原因を当てにいかず、**内訳を測って残った場所を特定する**。

---

## 1. 何が分かっているか

T5 の測定（`TestResults/v3/t5-smooth-c1-ltc25-gst`）で、同一 run の 2 つの量を比べた。

| 測っているもの | 平均 |
| --- | ---: |
| **アプリ内部の残差**（`sync.evaluate` の `delta` = `ltc - playbackSeconds`） | **+15.6ms** |
| **実測の表示誤差**（`accuracy-samples.csv` の `signedErrorMs`） | **-58.5ms** |
| **差** | **-74.1ms** |

**`Smooth` は内部残差を ±30ms に収束させている。制御は成功している。**
しかし画面の絵は 74ms 遅れており、補正ループはそれを見ていない。

`max-buffers` を 4 / 8 / 16 / 32 で振っても差は 85.8 / 92.1 / 66.7 / 78.4 と動かなかった（**原因ではない**）。
むしろばらつきは 155.3 → 183.7 と悪化した。

## 2. 分解したい区間

```
[A] LTC 受信時刻
     ↓
[B] GetTimePos が返す再生位置（= sync.evaluate の playbackSeconds）
     ↓  ← ここに 74ms がある
[C] その瞬間に公開されていた合成画像が表す素材時刻（= accuracy の測定対象）
```

**[B] と [C] の差がどこで生まれるかを、既存のトレースから段ごとに出す。**

段の候補（すべて `output-trace` の events.jsonl に材料がある）:

| 段 | 意味 | 使うイベント |
| --- | --- | --- |
| B1 | `GetTimePos` の値と、その時点で shim が持っている最新フレームの PTS の差 | `sync.evaluate` の `playback=` と `gst.delivery` の PTS |
| B2 | shim が最新フレームを持ってから、合成が取得するまで | `gst.delivery` → `compose.acquire` |
| B3 | 取得から公開まで | `compose.acquire` → `compose.publish` |
| B4 | 公開から、accuracy が「その時点の公開画像」と見なすまで | `compose.publish` → accuracy サンプルの `frameTicks` |

## 3. 依頼

1. **既存データで分解する。実機は要らない。**
   `TestResults/v3/t5-smooth-c1-ltc25-gst` と `t5-smooth-c2/c3` を使う
2. 上の B1〜B4 について、**中央値と p95** を出す。合計が 74ms に近くなるか確認する
3. **合計が 74ms に届かない場合**、どこにも現れない差が残る。その場合は
   「材料が足りない区間はどこか」を報告する。**埋めるための追加トレースを提案してよい**（実装はまだしない）
4. フェーズ別にも出す。**連続再生（`freeze-sweep`）とシーク後で内訳が変わるか**が要点。
   V3 のばらつきはこの 2 つの差（-18〜-43ms 対 -106〜-169ms）が作っている
5. `scripts/analyze-v3-spread-stages.py` が近い分解をしているので流用してよい

## 4. 読み方の注意

- **`gst.delivery` の間隔は変換を含む**（V11-h で判明）。所要時間として読むときは注意する
- accuracy の `signedErrorMs` は「LTC 受信時点で公開されていた画像」を基準にしている。
  **公開してから次の公開までの間はずっと同じ画像**なので、最大 1 合成周期（16.7ms）の粗さが乗る
- `playbackSeconds` は `GetTimePos`（`gst_element_query_position`）の値。
  **これがパイプラインのどの時点を指すのかは未確認**。B1 がそこを測る

## 5. 守ること

1. **実機を使わない。** 既存データの解析のみ
2. 製品コードを変更しない
3. 合否判定は書かないこと
4. **原因を断定しないこと。** 数字を出して、どこに残ったかを示すだけでよい

## 追記（2026-09-16）: 分解の結果と、B1 を確定させる 3 案

### 既存データでの分解結果（`TestResults/v3/t6-gap-decompose.txt`、Smooth c1〜c3）

| 段 | 中央値 | p95 |
| --- | ---: | ---: |
| B1（`GetTimePos` と最新 delivery PTS の差） | 13.9 | 36.8 |
| B2（delivery → acquire） | 5.5 | 29.1 |
| B3（acquire → publish） | 0.3 | 0.4 |
| B4（publish → accuracy の基準時点） | 1.1 | 1.9 |
| **合計** | **27.6** | **74.1** |

**合計の中央値 27.6ms に対し、表示誤差との差は 74ms。46ms が内訳に現れていない。**
p95 が 74.1ms と一致するので、**74ms は常にあるずれではなく裾の厚さ**である可能性がある。
フェーズ別ではシーク後（seek-a 47.4、seek-back 34.5）に B1 と B2 が揃って大きくなる。

### B1 の意味が確定していない

`playbackSeconds` は `gst_element_query_position` の値だが、**それがパイプラインのどの時点を指すか未確認**。
B1 が最大の段なので、ここを確定させないと先へ進めない。

障害: **アプリ実行時は shim の stderr がアプリログ（Serilog）に乗らない**ため、shim 内で 1 行出しても回収できない。

実装側（同期エージェント）の 3 案:

| 案 | 内容 | 製品コード | C ABI |
| --- | --- | --- | --- |
| **案 1** | E2E ハーネスでアプリの stderr をファイルへリダイレクトして回収 | 不変（テスト側のみ） | 不変 |
| 案 2 | shim に診断用の取得口を足し、`sync.evaluate` の detail に `pos=` と `latestPts=` を並記 | 変更 | **追加（承認が要る）** |
| **案 3** | shim の `tcs_player_get_time_pos` 内で、既存 trace 経路（`gst.delivery`）に「同時点の position」イベントを 1 行足す | 変更 | 不変（既存イベント種別の拡張） |

実装側の見立て: **案 1 が最小**。ただし B1 の確定を測定と同一ビルドで見るなら **案 3 が確実**。
**親の判断は未決**（2026-09-16 時点）。

### 同時に入れる追加トレース（3 点）

1. `compose.acquire` に、タイムライン位置ではなく**取得画像のスタンプ PTS** を記録
2. B4 を全標本で厳密結合する
3. `gst_element_query_position` の値と、同時点の最新 delivery PTS を 1 行で比較するログ（**上の 3 案のどれか**）

### 前提の変化

T6 を出した後、4K software の真因（CPU 色変換）が判明し `f9d381c` で GPU へ移した。
**配信のタイミングが変わったので、74ms にも影響しうる。** 追加トレースは統合後の `main`（`9c92d5a` 以降）で測ること。
