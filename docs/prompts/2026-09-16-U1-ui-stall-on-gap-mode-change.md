# U1: ギャップ動作の切替で UI スレッドが約 1.5 秒滞る件を切り分ける

作成: 2026-09-16 20:45、親。担当: 同期担当（`w5:p3`、作業ツリー `timecode-sync-player-wt-a`、ブランチ `agent-a`。**新しいセッション**）。
基点: **main の最新**（`68ff1e2` 以降）を `agent-a` へ通常マージしてから始める。

## 1. 事実（T2 段 3 の測定で見つかった。`docs/GSTREAMER-GPU-VALIDATION-PLAN-2026-09-12.md` の「T2 段 3」節）

- V3 の精度ハーネスが black-sweep → freeze-sweep のフェーズ切替でギャップ動作のコンボ（Black → Freeze）を変えた直後、
  LTC フレームの処理が **約 1.5 秒**遅れて UI スレッドに届いた（`LtcSyncController` の age 範囲外警告 `age=1500ms` 前後、各 run 1 回）
- 音声スレッド側の age は通常（約 50ms）だったので、遅れは **UI スレッドの `Dispatcher` キューの滞り**。コンボ変更の後ろに LTC フレームが並んだ
- T2 の age クランプ（0〜0.5 秒）が守るので同期値は壊れないが、**ライブ中に設定を触った瞬間に 1.5 秒固まる**のは現場では困る
- 何が 1.5 秒かかっているかは未確認（保存？ ギャップ状態の再評価？ フリーズ用テクスチャの確保？ プロジェクトの書き出し？）

## 2. 依頼: 測って切り分ける（直すのはその後）

1. コンボ変更のハンドラから先の呼び出しを読み、UI スレッドで同期的に走る重い処理の候補を列挙する（ファイル I/O、設定保存、GPU 資源の確保、`Task.Wait` など）
2. 候補ごとに所要時間が分かるログ（`Stopwatch`、`Debug` レベル）を足し、E2E か手動で 1 回再現して数字を取る。
   再現は V3 ハーネス（`scripts/run-v3-accuracy.ps1 -Repeats 1`）の black-sweep → freeze-sweep の境目で起きる。**実機を使う前に一報**
3. 1.5 秒の内訳を報告する。**製品の変更はまだしない**（直し方の案だけ: 非同期化、遅延書き出し、事前確保など、選択肢＋根拠）

## 3. 報告に入れるもの

コンボ変更 → 復帰までの内訳（ms）、どの処理が支配的か、同じ滞りが他の操作（モード切替、プロジェクト保存、フルスクリーン切替）でも起きるかの見立て、直し方の案。**合否は書かない。**
