worktree `C:\Users\codea\Documents\timecode-sync-player-wt-output-engine-20260911-1247`（cwd 固定）。

**まずはコード修正と非E2E までにとどめること。** 利用者が PC を使う時間帯があるため、
E2E・実機 run・アプリ起動は親が「再開してよい」と伝えてから実行する。

## 事実（親の V5 計測、2026-09-13 05:22〜05:25 JST、`TestResults/v5`）

同一プレイリスト（`v1_h264_1080p5994.mp4` ＋ 25／29.97／TS／HEVC の 4 本）を、
同じ操作列（next/prev を 2 秒間隔で 20 回、index 経路 `0,1,2,3,4,3,2,1,0,…`）で
GStreamer と mpv の両方に流し、`compose.acquire` の `NotReady`（＝合成が Held を出した tick）を数えた。

| | GStreamer | mpv |
| --- | ---: | ---: |
| 切替回数 | 20 | 20 |
| `compose.sourceNotReady` の tick 数 | **577** | 108 |
| Held のクラスタ数（起動後） | **10**（連続切替で融合） | 20（切替ごとに 1 回） |
| Held の合計 | **21.90 秒** | 1.97 秒 |
| 1 切替あたり | **2.19 秒** | **0.098 秒** |
| 最大 | **4.40 秒** | 0.167 秒 |
| 合成 p99 | 0.95ms | 1.23ms |
| error / exit | 0 / 0 | 0 / 0 |

黒フレームは出ておらず（Held が出続ける）、Spout も 59〜60/秒を維持しているので不変条件 I7 は守られている。
**問題は遅さそのもの。** 2 秒間隔で切り替えると次の切替が来ても前の切替が終わっておらず、
出力がほぼ止まりっぱなしになる。ライブでキューを送る用途では致命的で、
v0.4 は「GStreamer を既定にする版」なので、この差を残したまま既定にはできない。

関連する既知事項として **E2: 起動時に同じファイルを 2 回ロードしている**（`--open` の初回ロードの
約 2.6 秒後にプレイリスト初期化でもう一度）も記録済み。`docs/GSTREAMER-GPU-VALIDATION-PLAN-2026-09-12.md` を参照。

## 依頼

1. **原因を計測で特定する。** ロード 1 回の内訳（pipeline 生成／要素生成／状態遷移 NULL→READY→PAUSED→PLAYING／
   最初のフレーム到達）を時刻付きで出し、2.19 秒がどこに消えているかを示すこと。
   shim 側と C# 側のどちらが支配的かを分けること。
2. **短縮する。** 方針は実装側で設計してよいが、**不変条件に触れる変更（デバイス構成・スレッド構成・
   バッファリング方針・破棄規則・終了順序）は親に質問する**こと。
   参考になりうる観点（採否は計測で決めること）:
   - パイプラインを毎回破棄せず再利用する（`filesrc location` の差し替え＋flush seek など）
   - 要素生成やプロファイル探索の結果をキャッシュする（同じコーデックなら探索をやり直さない）
   - 次トラックの先読み（プリロール）を別パイプラインで行い、切替時に差し替える
3. **E2（起動時の二重ロード）もこの機会に直してよい**。直す場合は製品挙動が変わらないことを示すこと。

## 合格条件

- 同じ V5 の操作列（next/prev 20 回、2 秒間隔）で、**1 切替あたりの Held が 0.3 秒以下**、
  クラスタが切替ごとに 1 回ずつ分離していること（融合しない）。mpv の 0.098 秒に近いほど良い。
- 黒フレームなし、Spout 59/秒以上、error 0、exit 0、合成 p99 1ms 前後を維持。
- 回帰: `tcs-shim-test` v1 全素材＋TS 3 本 failures=0、非E2E 全件成功、全 E2E 58 成功・0 失敗・4 スキップ。
- 通常再生（切替なし 50 秒）の指標が現状と同等（実フレーム 60/秒、合成 p99 1ms 前後、生成→走査 4〜6ms）。
- 1 コミット。

報告は コミット／変更ファイル／非E2E 件数／計測（上の表と同じ形）／設計差異（不変条件との照合）／未検証。
