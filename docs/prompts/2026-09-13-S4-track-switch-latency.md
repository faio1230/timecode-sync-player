**問題は遅さそのもの。** 2 秒間隔で切り替えると次の切替が来ても前の切替が終わっておらず、

関連する既知事項として **E2: 起動時に同じファイルを 2 回ロードしている**（`--open` の初回ロードの
約 2.6 秒後にプレイリスト初期化でもう一度）も記録済み。`docs/GSTREAMER-GPU-VALIDATION-PLAN-2026-09-12.md` を参照。

## 依頼

1. **原因を計測で特定する。** ロード 1 回の内訳（pipeline 生成／要素生成／状態遷移 NULL→READY→PAUSED→PLAYING／
   最初のフレーム到達）を時刻付きで出し、2.19 秒がどこに消えているかを示すこと。
   shim 側と C# 側のどちらが支配的かを分けること。
2. **短縮する。** 方針は実装側で設計してよいが、**不変条件に触れる変更（デバイス構成・スレッド構成・
   バッファリング方針・破棄規則・終了順序）は親に質問する**こと。
   参考になりうる観点（採否は計測で決めること）:
   - パイプラインを毎回破棄せず再利用する（`filesrc location` の差し替え＋flush seek など）
   - 要素生成やプロファイル探索の結果をキャッシュする（同じコーデックなら探索をやり直さない）
   - 次トラックの先読み（プリロール）を別パイプラインで行い、切替時に差し替える
3. **E2（起動時の二重ロード）もこの機会に直してよい**。直す場合は製品挙動が変わらないことを示すこと。

# 撤回（親、2026-09-13 05:50 JST）

**この差し戻しは取り下げる。上の計測の解釈が誤っていた。**

実装側の指摘（`compose.acquire` の `NotReady` は「その tick に新しいフレームが無い」状態であり、
表示より遅い素材では正常）を、親が既存データで独立に確認した。**切替を一切行っていない V1 の定常再生 run**
（`TestResults/v1-d347673`、解析窓 12〜42 秒）での `compose.acquire` に対する `NotReady` の割合:

| 素材（切替なし） | compose.acquire | NotReady | 割合 | 理論値 (60-fps)/60 |
| --- | ---: | ---: | ---: | ---: |
| H.264 1080p **25fps** | 1800 | 1050 | **58.3%** | 58.3% |
| H.264 1080p **29.97fps** | 1800 | 900 | **50.0%** | 50.0% |
| H.264 1080p 59.94fps | 1800 | 3 | 0.2% | 0.1% |
| H.264 1080p60＋AAC | 1800 | 0 | 0.0% | 0% |

理論値と一致する。つまり V5 の GStreamer run で数えた 577 tick の大半は、
プレイリストに含まれる 25fps・29.97fps クリップの**通常再生**によるもので、切替の停止時間ではない。

さらに、この指標は**バックエンド間で比較できない**。mpv 経路は同じ低 fps クリップでも NotReady が
108 tick しか出ておらず、ソース側が tick ごとに「新フレームあり」として振る舞っている可能性が高い。
同一素材・同一操作でも意味が揃っていない指標を並べた時点で、比較として成立していなかった。

**したがって「GStreamer の切替は mpv の 20 倍遅い」という主張は根拠を失う。撤回する。**

## 正しい設問と指標

切替の速さを測るなら、**`BtnNextTrack` の invoke から、新しいトラックの最初のフレームが実際に表示
（present）されるまでの時間**を測る。これはバックエンドに依存しない定義で、利用者の体感と一致する。
実装側が追加した `load.attempt` / `load.summary` / `loadfile elapsedMs` / `--load-bench` は、
その内訳を見るうえで有用なので残す。
