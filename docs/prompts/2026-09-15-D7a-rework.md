# D7-a 差し戻し: 補償する場所がずれている（実機測定の前に直す）

実装そのものは良い。`SeekLatencyCompensator` の構造（決定 QPC と発行の分離、sequence による
旧フレームの除外、EMA、クランプ、警告ログ）は仕様どおりで、単体テストも筋が通っている。

**問題は、この補償が効く経路と、V3 で遅れが出ている経路が違うことである。**
このまま測ると D7-a はほぼ無効果に出る。実機は貴重で、**mpv の基準値は今回が最後の機会**なので、
先に直す。

---

## 1. 根拠（コードで確認した事実）

### 事実 A: 遅れの主因は「シーク」ではなく「ロード」

`ContinueOnTrackCoordinator.cs` のトラック切替経路:

```csharp
if (onTrackDecision.Action == ContinueOnTrackAction.SwitchTrack)
{
    bool success = _effects.LoadFile(track.FilePath, mediaPos);   // ← 着地位置はここで決まる
    if (success)
    {
        _effects.SetLoadedTrackId(track.Id);
        _syncService.BeginFileLoad(mediaPos, ...);                 // ← ここで Reset()
        ...
    }
    return success ? SyncRequestResult.Complete : SyncRequestResult.Deferred;   // ← Seek は発行しない
}
```

**この経路では `ReportSeekSent` が呼ばれない。** つまり補償器は arm されず、
`CompensateTarget` も通らない。着地位置は `LoadFile(path, mediaPos)` の `mediaPos` そのままである。

これは検証記録の読みとも一致する:

> フェーズごとの定常オフセットは、フェーズ先頭の着地でほぼ決まる。
> gst の seek-c は **load→着地 288ms**、着地誤差 -282ms、その後の定常平均 -274ms とほぼ一致。
> 伸びているのは **load 発行後の最初のフレーム到着待ち**。

### 事実 B: `Reset()` が、学習が要る瞬間に学習を捨てている

`BeginFileLoad` が `Reset()` を呼ぶ。そして **V3 の seek 系フェーズは全てトラック切替を伴う**。

`SyncAccuracyE2ETests.cs` のフェーズ定義:

```
black-sweep   black   start=0   duration=35
freeze-sweep  freeze  start=0   duration=35    ← clip1・clip2・clip3 を全て通る
seek-a        freeze  start=3   duration=5     ← clip1
seek-b        freeze  start=15  duration=5     ← clip2
seek-c        freeze  start=27  duration=5     ← clip3
seek-back     freeze  start=3   duration=5     ← clip1
```

LTC が跳ぶ → プレイリストが別クリップを選ぶ → `SwitchTrack` → `LoadFile` → `BeginFileLoad` → **`Reset()`**。
**測りたいフェーズの先頭で必ず L=0 に戻る。**

### 事実 C: 仮に seek 経路に乗っても、EMA が 1 フェーズ内に収束しない

`α=0.25` で 0 から始めると、真値に対して 1 回目 0.25 倍、2 回目 0.44 倍、3 回目 0.58 倍。
一方 1 フェーズは 5 秒で、`ShouldSuppressSeek` は `HasReachedSeekTarget` か 2 秒のタイムアウトまで
`Pending` を返すため、**1 フェーズに入るシークはせいぜい 2 回**。収束しない。

## 2. 直す方向

### (1) ロード位置も補償する

`LoadFile(track.FilePath, mediaPos)` の `mediaPos` を `mediaPos + L` にする。
ここが遅れの主因なので、ここを直さないと効かない。

`BeginFileLoad` の時点で測定を arm し（開始＝`LoadFile` を発行した QPC）、
新しい世代の最初の Ready フレームで着地を観測する。
シーク経路の arm（`MarkSeekSent`）は今のまま残してよい。

### (2) 学習をトラックごとに保持し、切替で捨てない

**`Reset()` を「全消し」から「トラック単位の引き当て」に変える。**
L はトラック（またはクリップの fps）をキーにした辞書で保持し、**トラック切替では消さない**。

理由は 2 つ:

- 着地遅延は素材で決まる（60fps 255ms、24/29.97fps 91〜121ms）。**トラックごとに覚えるのが正しい単位。**
- **V3 の run では `freeze-sweep`（0〜35 秒）が clip1・clip2・clip3 を全て通る。**
  つまり seek-a/b/c に入る前に、各クリップの L を 1 回は観測できている。
  トラック単位で保持すれば、**測りたいフェーズの時点で既に値がある。**

現場の運用でも同じクリップが繰り返し呼ばれるので、保持する方が実態に合う。

### (3) 最初の 1 標本は EMA を通さない

あるキーの**最初の観測は α=1.0**（観測値をそのまま採用）とし、2 回目以降を α=0.25 の EMA にする。
1 回の観測で使える値になる。上限 400ms・下限 0 のクランプと警告ログはそのまま。

### (4) 細かい硬化（任意）

`_pendingDecisionQpc` が arm 後にクリアされない。現状 `ReportSeekSent` の呼び出し元は
同期経路 2 か所だけなので実害は無いが、`MarkSeekSent` の中で 0 に戻しておくと、
将来 `ReportSeekSent` が別経路から呼ばれたときに古い決定 QPC を拾わない。

## 3. 守ること

1. **実機はまだ使わない。** 上記を直して単体テストを通してから、親の合図を待つこと
2. テストを先に書く。特に次を明示的に固定すること:
   - トラック切替で L が**消えない**
   - 別トラックの L が**混ざらない**
   - 最初の 1 標本がそのまま採用される（α=1.0）
   - ロード位置が `mediaPos + L` になる
   - L=0 のとき現行と完全に同一の行き先になる
3. 合否判定は書かないこと
4. デッドゾーン（`ToleranceFrames = 6.0`）と `HasReachedSeekTarget` の上下限は**今回も変えない**
5. 疑問があれば 測定の前に聞くこと
