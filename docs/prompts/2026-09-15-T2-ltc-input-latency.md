# T2: LTC 入力遅延の直接測定（送出 → デコード完了）

利用者の承認済み（2026-09-15）。**LTC fps マトリクスの測定が終わってから着手すること。**

## 1. なぜ要るか

V3 が測っているのは「**デコード済み LTC の受信時刻**を基準にした映像側の誤差」で、
`docs/SYNC-ACCURACY.md` の冒頭どおり **LTC 経路そのものの遅延は測っていない**。
現場での総遅れは「V3 の数字 ＋ LTC 経路の遅延」になる。

親の推定では **40〜90ms**（フレーム完成 40ms ＋ バッファ 0〜50ms、25fps の場合）だが、
**バッファ分は受信間隔の量子化からの推定**であって実測ではない。
現場基準の ms を定めるなら、ここを実測して内訳を確定させる。

## 2. すでに揃っているもの

`SyncAccuracyTrace.RecordLtc`（`SyncAccuracyTrace.cs:82`）が**受信時刻を QPC で記録済み**。

```csharp
long ticks = Stopwatch.GetTimestamp();
Enqueue(new LtcEvent("ltc", ticks, frame.Timecode.ToRealSeconds(_referenceLtcFps), _referenceLtcFps));
```

**足りないのは送出側の時刻だけ。**

## 3. 依頼

### 3-1. 送出側の基準時刻を残す

`LtcSignalPlayer` が LTC 波形の再生を開始した時点の QPC と、開始タイムコード・fps を
run ディレクトリへ書き出す（例 `ltc-emission.json`）。

```json
{ "playbackStartQpc": 123456789, "startSeconds": 0.0, "ltcFps": 25.0, "qpcFrequency": 10000000 }
```

アプリとハーネスは別プロセスだが、**QPC はシステム全体で一貫**するので突き合わせられる。

### 3-2. 解析

トレースの各 `ltc` イベントについて:

```
emissionQpc = playbackStartQpc + (ltcSeconds - startSeconds) * qpcFrequency
latency     = receiptQpc - emissionQpc
```

**LTC fps ごとに、最小・中央値・p95・最大**を出す。

### 3-3. 内訳の分解（この測定の肝）

遅延は 2 つの成分に分かれる。

| 成分 | fps 依存 |
| --- | --- |
| **80 ビットフレームの完成待ち** | **1/fps に比例**（24fps 41.7ms、25fps 40ms、29.97fps 33.4ms、30fps 33.3ms） |
| 音声バッファ（送出・受信） | **fps に依存しない定数** |

したがって **LTC fps 4 種の測定を横に並べ、遅延を 1/fps に対して回帰**すれば、
**傾きが 1 に近いことでフレーム完成分を確認でき、切片がバッファ分**になる。
**4 種を測る今回の構成でそのまま分解できる。**

これを必ずやること。単一 fps の 1 点だけでは内訳が出ない。

## 4. この測定の限界（報告に必ず書くこと）

- **VB-CABLE のループには送出側（WASAPI レンダー）のバッファが含まれる。**
  実機で本物のケーブルから LTC を受ける場合、この分は存在しない。
  **したがってこの測定値は現場の遅延の上限**であって、そのままの値ではない
- `playbackStartQpc` は再生を**要求した**時刻であって、最初のサンプルが実際に
  デバイスから出た時刻ではない。その差も送出側バッファに含まれる
- 下限は「フレーム完成 1/fps ＋ 受信側バッファ」。**上限と下限の両方を報告すること**
