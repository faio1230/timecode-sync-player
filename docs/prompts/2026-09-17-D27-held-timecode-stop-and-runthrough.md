# D27: タイムコードが「止まった」とき（値が進まない保持 LTC）も、停止モードは動画を止め、ランスルーは走らせる

作成: 2026-09-17 17:30、親。担当: 同期担当（`w5:p3`）。S-4 のゲート修正の後、D24/D25 の前に。
基点: **main の最新** を `agent-a` へ通常マージし、shim を自分のツリーでビルドしてから。
仕様（利用者、2026-09-17 17:20）: 「タイムコードが止まった時に動画も停止するか、走り続けるか。**ランスルーは走り続けて、停止は止まる**」。
**製品コードの変更。同期の目標・補正（Smooth/Jump、サンプル時計）には触らない。信号断の判定と、そのときの再生の扱いだけ。**

## 1. 現状（親のコード読み）

- 信号断（`LtcSignalLossMode` Stop / RunThrough、`LtcSignalLossTimeoutMs` 既定 250ms）は **LTC フレームが解読されなくなった（無音）とき**だけ発火する
- 同じ値が繰り返される LTC（`TimecodeFrameDiagnosticStatus.Duplicate`、保持）は信号断ではないので、Stop モードでも動画が走り続ける（シナリオ E2E の S-2 で観測: 保持 8.0 中に位置が 11.3 まで進む）
- 既存の E2E（`LtcHardwareLoopE2ETests`）は無音による信号断を Stop / RunThrough の両方で確認している。**値が止まった保持 LTC は両モードとも未確認**

## 2. 直すこと

- 「タイムコードが止まった」の判定に **保持（値が進まない）を含める**: 解読は続いているが値が `LtcSignalLossTimeoutMs` の間進まなければ、信号断と同じ扱い（`LtcSignalLossAction`）にする。無音と保持で表示文言を分けてよい（例: 「信号断で停止中」/「タイムコード停止で停止中」）
- **Stop モード**: 保持に入ったら動画を一時停止する。位置は保持値に同期した位置（D20-b の 1 回適用の結果）で止まる。値が動き出したら（Normal または Jump）復帰して再同期（既存の信号復帰の経路）
- **RunThrough モード**: 保持中も動画は走り続ける。値が動き出したら再同期（既存どおり）
- 復帰の判定は既存の「有効フレーム N 枚」の規則を流用。保持からの復帰では Duplicate → Normal/Jump の変化を「復帰」とみなす
- ギャップ中（Black / Freeze）の保持は、既存の「信号断はギャップ回復後に評価」（`CableLoop_StopMode_SignalLossDuringGap_IsEvaluatedAfterGapRecovery`）と同じ扱い

## 3. テスト

- 単体: 信号断判定に「保持で発火」「保持から Normal/Jump で復帰」を追加。既存の無音の判定は不変
- E2E（`LtcScenarioE2ETests` に 4 本追加、ID は R-1〜R-4。VB-CABLE、`LtcSignalPlayer.PlayHeld`）:
  - R-1 Stop + 保持: Continue、LTC を 8s から送出し 12s で 3 秒保持 → 保持開始から `LtcSignalLossTimeoutMs` + 1 フレーム以内に一時停止し、位置が 12.0 ±1 フレームで止まる（3 秒間動かない）。画面は赤系（A 本文）
  - R-2 Stop + 復帰: R-1 の後、LTC を 12s から再送出 → 再生が再開し、位置が LTC ±0.3 に追従
  - R-3 RunThrough + 保持: 同じ送出で、保持中も位置が進み続ける（3 秒で +2.5 秒以上）
  - R-4 RunThrough + 復帰: 再送出後、位置が LTC ±0.3 に再同期（ジャンプで戻る）
- S-2 の期待を **モードに合わせて**直す: Stop なら保持中は位置が保持値 ±0.3 で止まる（現行の期待）、RunThrough なら着地だけを見る。S-2 は Stop モードで回す（`LtcSignalLossModeCombo` の選択を明示）
- 回帰: `LtcHardwareLoopE2ETests` 14 本（無音の信号断の挙動が不変）、シナリオ 18 + 4、V3 を 1 本（信号断の判定を触るため）。実機は一報のうえ親の合図
