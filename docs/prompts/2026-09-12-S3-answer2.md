# S3 の 2 回目の質問への回答（親、2026-09-12 20:10 JST）

計測の報告（方式 5 は着地 +3〜+14ms で正確、しかし到達 1.7〜2.8 秒。原因は `appsink sync=true` の
クロック待ちで、デコード自体は 170ms で target に到達している）を受けた判断。

## 採るのは 2（シーク後のクロック再基準化）

理由: 待っているのは**デコードではなく時計**だと計測で分かった。飛び先（snap したキーフレーム）から target までの
区間を実時間でなぞっているだけなので、その区間を「もう過ぎた時間」にすれば消える。これは qtdemux の ACCURATE
シークが内部でやっていること（segment.start = target にして、それ以前のバッファをシンクが待たずに捨てる）と
**意味論的に同じ**であり、新しい挙動を発明するわけではない。

### 実装の指定

1. 方式 5 の着地ロジック（`KEY_UNIT | SNAP_BEFORE` で飛び、pts < target を配信せず捨てる）は**そのまま残す**。
   着地 +3〜+14ms は合格。
2. フラッシュシークの完了後（`async-done`）に、**target の running time が「今」になるよう base_time を補正する**
   （`gst_element_set_base_time` によるパイプライン単位の補正。sink 個別の `ts-offset` を使う場合は
   **映像と音声の両方に同じ値**を当てること）。補正後、snap〜target のバッファは遅延扱いで一気に流れ、
   既存の破棄ロジックが捨てる。以降は通常のペースで再生される。
3. 補正は **snap back が発生したシーク（＝MPEG-TS の経路）だけ**に適用する。MP4／MOV は ACCURATE が
   1ms 台で着地しており catch-up が要らないので触らない。
4. `step` は `GST_EVENT_STEP` 化してよい（500ms 予算を満たすなら）。ただし着地精度は同じ基準で測ること。
5. C# と C ABI は変更しない。合成側（表示ゲート・lead）には触れない（**I3・I10 は親の管轄**）。

### 必ず測って報告すること

- **到達時間**（シーク発行 → 新世代フレームの取得）: TS と MP4。**目標 500ms 以下**。
- **着地誤差**（`post-seek lease pts` − target）: TS と MP4。1 フレーム未満。
- **A/V 同期**: 音声付き素材（`v1_h264_1080p60_aac.mp4`）と、音声付き TS を 1 本作って、
  **シーク後に音と映像がずれないこと**。測り方は任せるが、数値で示すこと（例: 音声シンクの位置と映像 pts の差）。
  音声だけが取り残される／先に飛ぶ実装は不可。
- **通常再生への影響が無いこと**: 実機 1 本で実フレーム 60/秒、合成 p99 1ms 前後、error 0。
- **連続シークで補正が累積しないこと**: 10 回連続シーク（V5 を想定）で着地誤差と到達時間が悪化しないこと。

## 1・3・4 を採らない理由

- **1（tsdemux のパッチ／更新）**: **親が確認したところ、インストール済みの GStreamer は 1.28.2（現行最新）**。
  つまり上流更新では直らず、パッチ版 DLL の恒久保守と LGPL 配布設計を製品に抱えることになる。費用対効果が合わない。
  ただし**放棄はしない**: 2 が A/V 同期で行き詰まった場合の次善として残す。その際は上流への報告（issue／MR）も検討する。
- **3（Held 2〜3 秒を許容）**: V3 の基準は「mpv 経路と同等以下」。mpv は TS でも 100〜200ms で着地するので満たせない。
  ライブでキュー変更のたびに 2〜3 秒静止するのは製品として不可。
- **4（SNAP_AFTER）**: GOP 依存で着地が最大 +1 GOP ずれる。1 フレーム未満の基準を満たさない。
  `GST_EVENT_STEP` の方は上記 4 のとおり採用してよい。

## 行き詰まった場合

2 の A/V 同期がどうしても取れない、または通常再生のペーシングが崩れる場合は、**実装を止めて計測値とともに再質問する**。
その数字を見て、1（パッチ版 DLL）の採否、あるいは v0.4 では方式 5 のまま「TS のシークは 2〜3 秒」を
既知の制限として文書化し v0.5 で直す、という判断を親が行う。**合格条件を実装側で緩めない。**
