# D34（解析）: キャッシュ済みプロファイルの速いロード（110〜150ms）の後に、尺・位置・フレームが来ないことがある

作成: 2026-09-18、親。担当: 同期担当（`w5:p3`、作業ツリー `timecode-sync-player-wt-a`、ブランチ `agent-a`。版上げの 2 コミットは agent-a にそのまま置く）。
基点: main の最新（`17f7bcf` 以降）を `agent-a` へ通常マージ。**コード変更なし（解析のみ）。実機は使わない。**

## 1. 観測（検証機、候補 5 = 0.4.2+3a122b5、実素材。時刻は検証機ローカル）

| 件 | 観測 |
| --- | --- |
| b G-5 | `03:43:43.434 Gst loadfile <M1> start=null paused=false rc=0 elapsedMs=151.8` → `Playlist track loaded index=0` の後、**15 秒間 FetchMetadata 行なし**。テストの details: `timeLabel=0:00:00:00 / 0:00:00:00`、`metaLine` は前トラック（M3）のまま、`playButton=⏸`。直前の M5（828ms）・M3（437ms）のロードでは FetchMetadata が 2 行ずつ出ている |
| b G-6 | `A の再生位置が追従; ltc=10.640; position=0.000; loaded=0`（ロード後、位置が 0 のまま） |
| c C-2 c2-10 | 切替のたびに開始位置つきロード。M1 のロードが 1050ms / 1056ms（通常、8 プロファイル試行）のときは着地するが、`04:00:28.573 loadfile <M1> start=14.9366 paused=false rc=0 elapsedMs=110.6` の後は **position=14.000 のまま**（要求 14.937 の 0.9 秒手前）で 4.6 秒動かない |
| 候補 2 | 「トラック N のメタデータ取得」時間切れ 4 件はすべて elapsedMs 113〜224 のロード（383 回中、FetchMetadata が出なかったのは 5 回で、そのうち 4 回がこれ） |

M1 = ProRes 4K60 10bit（CPU デコード、prores-cpu）。通常は不一致プロファイル 8 件（各 101〜311ms）の後に成功して 1,000ms 超。**速いロードはキャッシュ済みプロファイルの経路**と見られる。開発機（生成素材、プロファイルが即決まる）では再現していない。

## 2. 調べること（ファイル:行つきで）

1. shim のロード（`tcs_player_load*` 系）で、プロファイルのキャッシュ（前回成功したプロファイルの再利用）がどう働くか。キャッシュ経路と通常経路で **rc=0 を返す時点**（プリロール完了前か後か）、`load.summary` の内容、失敗時のフォールバック（キャッシュのプロファイルで負の結果になったとき通常の試行へ戻るか）の違い
2. ロード直後に尺（`tcs_player_get_duration` 相当）・位置・フレームが来ない状態になり得る経路: 例えばキャッシュ経路で状態遷移が非同期のまま返り、パイプラインがエラー／ASYNC 待ちで止まっても `rc=0`・`Playlist track loaded` になる／`seek_boundary_expect` や世代の初期化が通常経路と違う／開始位置つきロードのキャッシュ経路で seek が送られない（c C-2 の 14.000 = 直前のセグメント位置？）
3. アプリ側: `FetchMetadata` が 15 秒出ない条件（`_duration > 0` の待ち。尺が 0 のまま = shim が尺を返さない）と、D33-b の予約が効かない理由
4. 検証機に依頼している shim ログ・トレースの抜粋が届いたら突き合わせる。届く前に、コードから「速いロードだけ」に固有の経路を列挙する

## 3. 報告

該当コードの箇所、キャッシュ経路と通常経路の差分表、疑わしい順の仮説、確認のために検証機のログで見るべき行。**コードは変えない。素材名・絶対パスは書かない。**
