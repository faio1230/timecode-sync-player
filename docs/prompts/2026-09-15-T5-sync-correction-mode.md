# T5: 同期補正モード（フィードバック / ジャンプ）

利用者の指示（2026-09-15）:

> フィードバック補正モードとフラッシュシークでピョンと正しい位置にジャンプさせる
> ２つのモードは持っておきたい。デフォルトはフィードバック補正。
> これは Preference などの設定ページで設定するようにする。

**v0.4 の範囲に入れる。これが V3 の最後の構造的課題。**

---

## 1. 直す対象（実測で確定済み）

LTC 4 種 × 3 本（`TestResults/v3/v3fps-*`）で、**4 種すべて同じ構造**が出ている。

| | 誤差 |
| --- | ---: |
| 連続再生（`freeze-sweep`） | **-34〜-45ms** |
| **シーク後**（`seek-a/b/back/c`） | **-42〜-157ms** |

シーク後の着地誤差は**デッドゾーン（`max(1/videoFps, 1/tcFps) × 6` = 200〜250ms）の中**に収まるため、
`SyncDecisionEngine.Decide` は `None` を返し続け、**誰も補正しない。着地点がそのまま定常値になる。**

**ばらつき 151〜175ms の正体はこの「連続再生とシーク後の差（約 110ms）」**であって、揺れではない。

`SyncOffsetMs`（T3）は全体を一律にずらすので、**この差は消せない。**

## 2. 仕様

### 設定

`AppSettings` に **`SyncCorrectionMode`** を追加。

| 値 | 挙動 | 既定 |
| --- | --- | --- |
| **`Smooth`** | 残差をレート微調整で徐々に 0 へ寄せる | **既定** |
| `Jump` | 残差をフラッシュシークで即座に合わせる | |

**Preference（設定ページ）の UI から選べること。** 現場で選ぶ設定なので settings.json のみにしない。

### 共通の判定

どちらのモードでも、**デッドゾーンの内側**で残差 `e = effectiveLtcSeconds - playbackSeconds` を見る。
現行の粗いデッドゾーン（6 フレーム）は**大きな不連続を拾う役目として残す**。今回はその内側に補正を足す。

- **デッドバンド**: `|e|` が小さいときは何もしない。**ms で置く**（実時間で吸収する設計思想に合わせる）。
  初期値の提案は **20ms**。実装側が測定で詰めてよい。
  **40ms にすると連続再生の系統誤差（-34〜-45ms）がデッドバンド内に入って補正されない**ため、
  それより小さく取る。小さすぎるとハンチングするので、比例制御と併せて測定で決める
- 補正中の再評価が発振しないよう、**ヒステリシス**を持つこと

### `Smooth`（既定）

**レート偏差の上限は ±10%**（利用者の判断、2026-09-15）。

> ±10%くらい詰めちゃっていいかなと思います。基本的には音は別のマシンで出して
> 同期取る形になるのでピッチが変わってもいいんですが、将来的にピッチが変わらないように
> 補正かけてもいいかもしれません

#### なぜ ±0.5% ではだめか（算数）

残差を詰めるのにかかる時間は `残差 ÷ レート偏差`。

| 残差 | ±0.5% | **±10%** |
| ---: | ---: | ---: |
| 150ms | **30 秒** | **1.5 秒** |
| 40ms | 8 秒 | 0.4 秒 |

**V3 のシークフェーズは 5 秒**なので、±0.5% では 25ms しか詰まらず**収束しない**。
±10% なら 1.5 秒で詰まる。

#### 制御則

**比例制御にする。一定倍率で突っ込んでデッドバンドで止める方式（bang-bang）にしない。**
オーバーシュートとハンチングの原因になる。

```
r    = clamp(e / T, -0.10, +0.10)     // T = 収束の時定数。初期値 1.0 秒
rate = 1 + r
```

誤差が縮むほど補正が緩むので、デッドバンドへ滑らかに入る。

| 残差 e | レート（T=1.0s） |
| ---: | --- |
| 150ms | 1.10（上限） |
| 50ms | 1.05 |
| 10ms | 1.01 |

`T` と上限は**測定で詰めてよい**。初期値から始めて、収束時間とオーバーシュートを見る。

#### そのほか

- **シークを発行しない。** 絵が飛ばない
- ずれが**どちら向きでも**効く（予測が要らない。D7-a が失敗した理由がここ）
- **shim の改修が要る**: `tcs_player_set_rate_instant`（`GST_SEEK_FLAG_INSTANT_RATE_CHANGE`）。
  **C ABI は承認済み**（2026-09-15）。条件は shim 側で PAUSED を防御すること、
  ヘッダに契約を明記すること、失敗を操作者に見える形にすること
- **`Smooth` のレートが 1.0 でない状態で `Jump`・手動シーク・手動速度へ移ると、その倍率を引き継ぐ。**
  移る前にアプリ側で `tcs_player_set_rate_instant(player, 1.0)` を呼ぶこと（実装側が指摘、shim では強制しない）

#### 音声への影響（記録しておくこと）

±10% は音程で**約 165 セント（約 1.65 半音）**。**このアプリから音を出している場合は明確に聞こえる。**

- 利用者の運用では**音は別マシンで出す**ため許容
- **将来、ピッチ補正（タイムストレッチ）を入れる余地がある**（利用者コメント、v0.4 の範囲外）
- **このアプリで音を出す構成では、`Smooth` のレート上限を下げるか `Jump` を使う**方が良い可能性がある。
  V2 の音声条件で実際にどう聞こえるかを確認し、**報告に残すこと**

### `Jump`

残差がデッドバンドを超えたらフラッシュシークで合わせる。

- 既存のシーク経路をそのまま使える（新しい配管が要らない）
- **発振に注意。** シークの着地自体が誤差を持つ（実測 -42〜-157ms）ので、
  補正シークがまた誤差を生んで再発火する可能性がある。
  **着地後の待ち（settle）とヒステリシスで必ず止めること。**
  `TimecodeSyncSeekState` の既存の settle 機構を使う
- **1 回のシークで収束しない場合の上限**を設ける（例: 連続 3 回で諦めてログを出す）。
  無限に飛び続けるのが最悪

## 3. 測定との関係

- **V3 の判定は両モードで測る。** 既定が `Smooth` なので、そちらが出荷基準
- `SyncOffsetMs = 0` で測る（T3 と同じ理由）
- 見る指標は、**連続再生とシーク後の差が縮んだか**。プールの p95-p5 が
  現在の 151〜175ms からどこまで下がるかが成否

## 4. 依頼

1. **まず C ABI の案を出す**（`Smooth` のレート変更をどう shim へ渡すか）。親の承認を待つ
2. 単体テストを先に書く。最低限:
   - 既定 `Smooth` で、残差がデッドバンド外のときレートが動く
   - デッドバンド内でレートが 1.0 へ戻る
   - **`Smooth` ではシークが 1 回も発行されない**
   - `Jump` で補正シークが発行される
   - **`Jump` で発振しない**（連続発火の上限が効く）
   - 残差が 0 のとき、どちらのモードでも現行と完全に同一の挙動
   - ずれが正・負どちらでも対称に効く
3. 実装する
4. Preference の UI を足す（AutomationId 付き）
5. `docs/SETUP.md` に両モードの説明と既定を書く
6. 非E2E を全て通す
7. 実機は親の合図を待つ

## 5. 守ること

1. **粗いデッドゾーン（`ToleranceFrames = 6.0`）は変えない。** その内側に足す
2. **`Smooth` で毎フレーム・毎 LTC ごとにシークを発行しない**（利用者が明確に避けたい設計）
3. 合否判定は書かないこと
4. `main` へ書き込まない
5. C ABI は承認前に実装しない
