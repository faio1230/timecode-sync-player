# T10: 60fps クリップだけロードから最初のフレームまで 264ms かかる原因を測る

**測って切る。原因を当てにいかない。** 直すかどうかは、内訳が出てから親が決める。

---

## 1. 分かっていること（T9 の 3 本、`4fd56dd`）

`scripts/analyze-v3-seek-breakdown.py` の `b→c`（ロード発行 → 新しい位置の最初のフレーム到着、中央値 / p95）:

| フェーズ（素材） | b→c |
| --- | ---: |
| seek-a（clip 1、24fps） | 90.6 / 93.1ms |
| seek-b（clip 2、29.97fps） | 121.5 / 125.4ms |
| **seek-c（clip 3、60fps）** | **263.9 / 264.8ms** |
| seek-back（clip 1、24fps） | 91.9 / 143.6ms |

V3 の収束基準（1 秒以内に ±80ms）に対し、T9 の実測は seek-a 0.15〜0.66 秒、seek-b 0.41〜0.76 秒に対し
**seek-c は 1.22〜1.72 秒**。着地が 264ms 遅れ、その分をレートで詰めるので時間が足りない。
素材は 3 本とも 1080p H.264（`d3d11h264dec`）で、違いはフレームレートと長さだけ。

## 2. 依頼

### 2-1. shim の内訳ログを回収できるようにする（テスト側だけの変更）

shim は 1 回のロードごとに内訳を stderr に出している（`tcs_gstreamer.cpp` の `log_attempt`）:

```
[tcs-gst] load.attempt path=... profile=h264-gpu result=ok teardown_ms=.. build_ms=.. set_state_ms=..
          preroll_ms=.. first_frame_ms=.. audio_prime_ms=.. pause_ms=.. seek_ms=.. duration_ms=.. total_ms=.. frames=..
```

アプリ実行時はこれがどこにも残らない。**E2E のアプリ起動で stdout / stderr をファイルに保存する**ようにしてほしい。

- `Invoke-AppGpuTrial`（`scripts/GpuOutputProbeHarness/`）が同じことをしている（`app-stdout.txt` / `app-stderr.txt`）。書き方はそれに合わせてよい
- 保存先は run ディレクトリ（`TIMECODE_ACCURACY_REPORT_DIR`）。ファイル名は `app-stderr.txt` / `app-stdout.txt`
- **読み取りを止めないこと**（パイプが詰まるとアプリ側の書き込みが止まる）。非同期で読み続けて書き出す
- 製品コードは変更しない。E2E のアプリ起動経路（`Helpers/E2EAppRunner.cs` など）だけ

### 2-2. 測る

1. V3 を 1 本（`scripts/run-v3-accuracy.ps1 -Backends gst -Label t10-<SHA>`）。条件は T9 と同じ
2. `app-stderr.txt` から `load.attempt` の行をすべて拾い、**クリップごと**に内訳（`teardown_ms` / `build_ms` /
   `set_state_ms` / `preroll_ms` / `first_frame_ms` / `audio_prime_ms` / `pause_ms` / `seek_ms` / `total_ms`）を表にする
3. 同じ run の `analyze-v3-seek-breakdown.py` の `b→c` と突き合わせ、**264ms のうちどの区間が長いか**を示す
4. 素材の条件も並べる: 各 clip の fps・長さ・GOP（キーフレーム間隔）・音声トラックの有無・ファイルサイズ。
   `ffprobe` があれば `-show_frames` でキーフレーム位置を数え、**要求位置 3.08 秒の直前のキーフレーム**がどこかを出す
5. 60fps だけ長い理由の候補を、**測った数字で支持されるものだけ**挙げる。支持されない候補は挙げない

### 2-3. 参考: 同じ素材を `gst-launch-1.0` で測る（アプリ経由と比べる）

アプリ側の作りが原因か、GStreamer の素の性能かを分ける。
**出口の caps をアプリと同じにすること**（`video/x-raw(memory:D3D11Memory),format=BGRA`）。
`fakesink sync=false` だけで測ると変換もバックプレッシャーも消えて別物になる（2026-09-15 に親が踏んだ罠）。

## 5. 測定結果（2026-09-16、`t10-9b82070-ltc25-gst`）

1 本のみ（13:12:12〜13:14:06）。条件は T9 と同じ（gst / `outputBackend=1` / LTC 25 auto / Debug / 出力トレース有効 / 先行補償は未設定＝既定 off）。
`app-stderr.txt` の回収を入れたコミットは `9b82070`（テスト側のみ）。
参考の定常誤差: n=1067、平均 -27.5ms、p50 -25.0、p5 -66.7、p95 +6.7、p95-p5 73.3ms。±80ms への収束は seek-a 811 / seek-b 914 / seek-c 1264 / seek-back 858ms。

### 264ms の内訳

| フェーズ | clip | b→b'（ロード） | b'→c（ロード後の最初のフレームまで） | b→c |
| --- | --- | ---: | ---: | ---: |
| seek-a | 1 | 7.8 | 83.7 | 91.5 |
| seek-b | 2 | 11.5 | 113.9 | 125.4 |
| **seek-c** | **3** | **11.6** | **254.6** | **266.2** |
| seek-back | 1 | 10.7 | 81.5 | 92.2 |

**266.2ms = ロード 11.6ms + ロード後のデコード 254.6ms。** ロード自体は 60fps でも遅くない。

### 同一クリップ内の対照（clip 3）

| シーク先 | 直前キーフレーム | 直前キーフレームからのフレーム数 | b'→c |
| ---: | ---: | ---: | ---: |
| 3.680s | 0.000s | 221 | 277.7ms |
| 4.240s | 4.167s | 約 5 | 1.5ms |

同じファイル・同じデコーダで、キーフレームからのフレーム数だけが違う。所要時間を支配しているのはフレーム数であることを直接示す。

### 1 フレームあたりの所要

| clip | b'→c | フレーム数（直前キーフレームから 3.08s まで） | 1 フレームあたり |
| --- | ---: | ---: | ---: |
| 1 | 83.7ms | 74 | 1.13ms |
| 2 | 113.9ms | 93 | 1.22ms |
| 3 | 254.6ms | 185 | 1.38ms |

60fps はフレーム数が約 2.5 倍で、1 フレーム単価も約 22% 高い。単価差が bitrate の差（16.4 / 19.8 / 35.6Mbps）によるものか、デコード負荷によるものかは、この 1 本のデータでは分離できない。

### データが支持する候補

1. **GOP 250 固定による「直前キーフレームからのフレーム数」**。同じ 3.08s でも 24fps は 74 フレーム、60fps は 185 フレーム。同一ファイル内の 3.68s（221 フレーム、277.7ms）と 4.24s（キーフレーム直後、1.5ms）の対照が直接支持する。
2. **1 フレーム単価の差**（1.13 → 1.38ms）が上乗せ要因。フレーム数の効果に比べると小さい。
3. ロード経路は原因ではない（60fps のロード内訳は他と同等、`audio_prime_ms=0`）。

### データが支持しない候補

- **ファイルサイズそのもの**: 同一ファイル内でサイズが同じでも、キーフレーム直後のシークは 1.5ms。
- **音声プライム**: 3 クリップとも音声トラックなし（`-an`）で、`audio_prime_ms=0.0`。
- **ロード（open / build / set_state / preroll / first_frame）**: 60fps で増えていない（`total` 7.6〜11.5ms）。
