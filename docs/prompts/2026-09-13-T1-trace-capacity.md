## 背景（親の V6 で判明、利用者が対応を指示）

`src/TimecodeSyncPlayer/Output/OutputTrace.cs` の `Capacity = 1_000_000` により、
**60Hz では約 8.3 分でトレースが打ち切られる**。親の V6（60 分連続再生）では
`events.jsonl` が 169.5MB／1,000,000 行で、**最初の 498.5 秒しか残らなかった**。
そのため V6 の中心項目である「欠落 0」と「到着→取得の遅れが鋸歯（H-3 の 21ms 閾値で 1 枚破棄→4ms 台へ）」を
60 分全体について確認できず、**V6 は部分合格にとどまっている**。

さらに問題なのは、**打ち切りが静かに起きたこと**。親は解析してみるまで気づかなかった。
`dropped` カウンタは既にあるので、これを見える形にする。

## 依頼

1. **上限を可変にする。** 既存の設計に合わせて環境変数で与える
   （例 `TIMECODE_SYNC_PLAYER_OUTPUT_TRACE_CAPACITY`）。**既定値は現行の 1,000,000 のまま**変えないこと。
   不正値・未設定は既定にフォールバックする。
2. **打ち切りを見えるようにする。**
   - 最初に 1 件破棄した時点で警告ログを 1 回出す（例: 「出力トレースが上限 N に達しました。以降のイベントは記録されません」）
   - `summary.json` に `droppedEvents` と `capacity` を必ず出す（既に出ていれば、親の
     `app_run_summary.py` / `analyze_probe.py` から確認できる位置か確かめる）
3. **メモリの見積もりを README か該当文書に書く。** イベントはメモリに溜めて停止時に一括書き出しする設計なので、
   上限を上げるとその分常駐する。1,000,000 件で約 170MB、60 分 60Hz 相当（約 730 万件）で約 1.2GB という
   実測値を根拠に記載する。
4. 製品の既定挙動は変えない。トレースは環境変数を与えたときだけ有効という現行の性質も変えない。

## 合格条件

- 既定（環境変数なし）で現行と同一の挙動。非E2E 全件成功（現状 1712 件）、全 E2E 58 成功・0 失敗・4 スキップ。
- 上限を小さく設定した短い run（例 capacity=2000）で、警告が 1 回出て `summary.json` に
  `droppedEvents > 0` と `capacity` が出ることを示す。
- 上限を上げた run で `events.jsonl` の行数が上限まで伸びることを示す。
- 1 コミット。

実機は 1 プロセスずつ、開始前に時刻を報告。報告は コミット／変更ファイル／非E2E 件数／E2E／確認した挙動／設計差異／未検証。
