worktree は現行のまま（`codex/d2-paused-seek-20260913`）。**統合は保留**。

## 事実（親の検証、2026-09-13 14:50〜16:17 JST）

D2 のビルド（`e2048a5`）で `tcs-shim-test` を v1 の 13 素材に連続実行したところ、
**`v1_h264_1080p60.ts` で 86 分間ハングした**（親が PID を確認のうえ終了）。

| 観測 | 値 |
| --- | --- |
| 経過 | 14:50:10 開始、16:16 時点で応答なし（**86 分**） |
| CPU 時間 | **27.5 秒のみ**（＝計算していない。待機している） |

ハング時点のログ全文は親の手元にある（`PASS: ring evict: empty -> -1` まで進み、
`create (internal device)` → TS の demux pad → ring 作成 の直後で停止）。

## なぜ差し戻すか

**ハングは出荷可否に直結する。** ライブ運用でこれが起きると映像が止まったまま復帰しない。
テストの失敗より重い。断続的なので「通ったから大丈夫」とは言えない。

D2 の非同期 pump は**一時的に PLAYING へ遷移させ、bus スレッドが tick して PAUSED へ戻す**設計で、
状態遷移とスレッドが増えている。TS は S3 で `KEY_UNIT|SNAP_BEFORE` 着地＋目標まで破棄という
別経路を通るため、pump と組み合わさったときの競合が疑われる（**推測。計測で確かめること**）。

## 依頼

1. **再現させる。** `tcs-shim-test v1_h264_1080p60.ts` を繰り返し実行して発生率を出す
   （バッチの連続実行で出たので、単発より連続の方が出やすい可能性がある）。
   `short\v1_h264_ffmpegmux.ts` と `short\v1_h264_ts_dumpextra.ts` でも試すこと。
2. **どこで待っているかを特定する。** 37 スレッドすべてが待機していたので、
   ロックの取得順序かイベント待ちの取りこぼしが疑われる。`frame_lock`、pump のスレッド、
   bus スレッド、GStreamer の状態遷移待ちの関係を明らかにすること。
3. **直す。** 設計を変える場合は親に提案すること。
   **`tcs_player_seek` の非ブロッキング性（0.1〜0.2ms で戻る）は維持すること**（不変条件 I6）。
4. D2 の本来の効果（一時停止シークの目標 pts 到着が中央値 119.5ms）は維持すること。

## 合格条件（D2 の元の条件に追加）

- **`tcs-shim-test` を v1 の 13 素材で 3 周連続実行して、ハングも失敗も 0**。
  各素材の出力を保存し、失敗時は内容を示すこと。
- 上記 1 の発生率の計測結果（修正前と修正後）を示すこと。
- ハングの原因を説明できること（「直ったようだ」では受け取らない）。

### 再現スクリプトの注意（実装側の不具合）

`& powershell -File ... | Select-Object` の形だとタイムアウトが効かず、90 秒指定でも
1 時間以上ブロックした。**`Start-Process -PassThru` ＋ `$p.WaitForExit(ms)`、false なら `$p.Kill()`** を使うこと。
待ちが外れないとハング調査自体が止まる（実際に止まり、親のメッセージもキューに溜まったまま処理されず、
利用者がインタラプトして解除した）。

これがあったから「同一事象」と判定できた。可能ならダンプも取る。
