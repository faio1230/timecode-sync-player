# 同期精度の測定

今回の目的は、既定設定の同期精度を数値で把握すること。許容幅・シーク頻度を変更して見かけ上の結果を改善する作業は含めない。

## 測っているもの

VB-CABLEで25fpsのLTCを送り、アプリが受信した時刻と、映像をWriteableBitmapへ書き込んだ時刻を同じ単調増加時計で記録する。動画にはフレーム番号とクリップ番号のマーカーを埋め込み、実際に渡した画像のピクセルから読み取る。再生位置表示やmpvの位置プロパティだけで精度を判定しない。

各LTC受信時点の最後の公開画像と、LTCが指定する動画位置を比較する。画像更新が止まっていても測定は続く。正しいクリップの有効マーカーから数値化できた標本、別クリップ、不明画像、未公開は分けて報告する。定常区間の集計では開始直後とクリップ変更後の1秒を除外するが、それらも全標本CSVと復帰・境界測定に残す。

誤差の符号は、プラスが映像の先行、マイナスが遅れ。フレーム開始時刻との差に加え、目標時刻がその画像の表示区間に入っている場合を0とする「フレーム区間からの誤差」を扱う。例えば24fps映像の1枚は約41.67msを占めるので、同じ画像に対応する目標時刻には幅がある。

これは**LTCのデコード通知到着を基準とした、アプリ内の出力画像の測定**である。音声を送った瞬間からの遅延、VB-CABLEのバッファ遅延、Windowsの画面合成、モニター、Spout受信側は測っていない。時刻をmsで記録しても1ms精度を保証しない。入力は40ms刻み、動画は約16.67/33.37/41.67ms刻みで、受信通知にはバッファ処理による揺れもある。

## 試験条件

- 入力: LTC25fps、VB-CABLEのCABLE Input → CABLE Output。
- 映像: 1920×1080、24/1・30000/1001・60/1fps、H.264、フレーム番号付き生成素材。
- 配置: 各映像の最初の10秒を0/12/24秒に配置し、途中に2秒の空白を設ける。
- BlackとFreezeそれぞれで0秒から35秒連続再生。その後3/15/27/3秒へ飛ばして各5秒測る。
- 復帰: 正しいクリップで区間誤差80ms以内、250ms以内をそれぞれ0.5秒継続するまでの時間。戻らない場合も結果として記録する。
- Blackは実際の黒画素、Freezeは前クリップ末尾のフレーム番号を確認する。

既定の同期許容幅は映像とLTCのうち長い方のフレーム時間×6。今回の入力では24fps映像で250ms、29.97/60fps映像で240msとなる。これは再シークを決める内部条件であり、実画像誤差の上限保証ではない。シークの待機・抑制もあるため、実測して判断する。

## 再実行と準備

Windowsの操作可能なデスクトップ、.NET 8、PowerShell 7.2以降、Python 3、ffmpeg/ffprobe、mpv DLL、VB-CABLEが必要。このPCでは利用可能。試験中は対象アプリを操作せず、PCをロック・スリープさせない。既存のプロジェクトや動画を準備し直す必要はない。

```powershell
./scripts/run-timecodesyncplayer-accuracy.ps1
```

通常のテストでは専用の実機試験をスキップする。専用実行ではスキップ・強制終了・記録欠落を成功と扱わない。生成動画、測定ログ、CSV、集計、アプリログ追記分、バイナリハッシュを結果フォルダへ保存する。

解析器は記録の完全性と同期精度を別々に扱う。すべて測定できても大きなずれがある場合は、その値をそのまま出す。品質として許容できる誤差の合格基準は、この基準測定の後に決める。

## 2026-09-07 の測定結果

**現状は、常に1フレーム以内に追従する状態ではない。** シーク後の大きな遅れと、Freezeが末尾より前の画像を保持するケースを実画像で確認した。今回は測定機能の追加と原因調査までで、同期制御は変更していない。

同じビルドで2回実施した。VB-CABLEは48kHz・32bit・2ch、アプリのLTC設定はFixed25、Spout送信は無効。各動画の符号化後の全1,368フレームを読み戻してマーカー・フレーム数・fps・開始時刻を検証した。

| 回 | 結果フォルダ（TestResults/accuracy 配下） | 記録 | 監視込み時間 |
| --- | --- | --- | ---: |
| 1 | 20260907-171342-0f370eb0 | 完全：LTC 2,243件、画像公開2,968件、drop/error 0 | 114.13秒 |
| 2 | 20260907-171647-dc95e3a2 | 不完全：Freeze開始付近でLTC欠落を検出。記録キューのdrop/errorは0 | 113.52秒 |

「完全」は記録が解析条件を満たす意味で、同期精度の合格ではない。以下の数値は**1回目だけ**を用いる。2回目を都合よく除去した集計や、合格するまでの再試行はしていない。

### 誤差

各試験開始・クリップ切替から1秒を除外した標本の、フレーム区間からの絶対誤差。動画の1枚が占める時間を考慮しても残るずれである。除外後も復帰が終わっていない場合があり、「完全に安定した再生だけ」の集計ではない。

| 区間 | 数値化できた標本 | 平均絶対誤差 | 95%点 | 最大 |
| --- | ---: | ---: | ---: | ---: |
| Black連続再生 | 672 | 71.2ms | 143.3ms | 793.3ms |
| Freeze連続再生 | 669 | 94.5ms | 150.0ms | 1,111.7ms |
| 全区間（シーク試験を含む） | 1,735 | 121.5ms | 521.0ms | 1,111.7ms |

全区間の99%点は880.0ms。区間誤差80ms超は790標本・観測間隔合計約31.68秒、250ms超は141標本・約5.64秒だった。これは受信標本からの時間推計で、すべての瞬間を直接観測した継続時間ではない。

最大の遅れはFreeze試験のLTC1.32秒時点。24fps動画のフレーム4（PTS約0.167秒）を出していた。フレーム開始時刻との差は約1,153.3ms、フレーム区間を考慮しても約1,111.7ms遅れていた。

全2,243標本のうち、正しいクリップの有効マーカーを数値化できたのは1,817件。残りはGapの正しい画像221件、Gapの誤った画像29件、動画区間で黒画像65件、別クリップ111件。これらを「誤差0」として平均へ混ぜていない。1秒除外後にも黒画像5件が残る。未知マーカーと未公開は0件だった。

### シーク後の復帰

最初の対応LTC受信から、正しいクリップかつ指定誤差以内を0.5秒連続して観測できた区間の開始まで。各試験は5秒なので、復帰未観測は「その試験時間内に条件を満たさなかった」という意味。

| ジャンプ先 | 80ms以内への復帰 | 250ms以内への復帰 |
| --- | ---: | ---: |
| 24fps・TC3秒 | 未観測 | 約1,219ms |
| 29.97fps・TC15秒 | 未観測 | 未観測 |
| 60fps・TC27秒 | 約1,271ms | 約1,271ms |
| 24fps・TC3秒へ戻す | 未観測 | 約2,030ms |

29.97fpsの試験では、末尾付近でも同じ画像番号205が保持され、遅れが増える様子を記録した。単発で目標付近へ到達することと、連続して追従し続けることを区別する必要がある。

### Black / Freeze

Blackは各境界の最初のLTC受信から、黒画像公開まで約3.9 / 25.6 / 11.3msだった。入力の基準そのものは40ms刻みであり、物理画面までの遅延ではない。

Freezeの24fps末尾は最初のGap受信時点ですでに正しい画像だったため、遅延の正確な値は測れない（出力では下限打切りの0ms）。29.97fps末尾は約7.2ms。60fps末尾は期待するフレーム599に到達しなかった。TC34.00秒では590、34.04〜34.96秒では591を保持し、末尾より8フレーム、約133ms前の画像で止まっていた。検査では末尾1フレーム分の許容も設けているが、その範囲にも入らない。

同じ時点のアプリログは「最終フレームを取得済み」と記録していた。コードはmpvの位置とファイル一致を確認しているが、公開された画像がその位置のフレームかまでは確認していない。位置情報の到達を、画像の到達と同一視できないことが今回の計測で明確になった。古い画像がどの処理段階で残ったかは追加調査が必要。

### 2回目の不完全測定

Freeze試験のLTC0.84→0.96秒で0.88/0.92秒の通知がなく、通知間隔は152.237msだった。解析器は入力欠落と長い通知間隔を検出し、不完全として非ゼロ終了した。欠落区間を補間して合格扱いにしていない。原因が送出・受信・デコードのどこにあるかは、この計測では確定できない。

この回でも60fpsのFreeze末尾は593から594へ進んだ後に止まり、期待599より5フレーム前の画像を保持した。29.97fpsへのシークも5秒以内に250ms条件で復帰しなかった。1回目の現象を補強する観察だが、完全な再測定として数値を合算していない。

### 測定の健全性と次の調査

両回ともアプリは正常終了し、ERR/FTLログは0。1回目の画像マーカー解析時間は平均約0.009ms、95%点約0.015ms、最大約0.579ms。キュー投入やログ書込みの費用はこの値に含まれず、計測を有効にする影響が完全にゼロと証明したものではない。

内部テスト1,305件、解析器テスト24件、計測無効時の既存起動・再生操作E2E6件が成功。専用測定を指定しない場合のスキップも確認した。独立レビューは、画像番号・誤差計算・記録件数・2回目の欠落を生ログから再照合した。今回、既存E2E全50件の再実行はしていない。

次は、Freezeで実際の末尾画像の到達を確認する処理と、シーク後に古い画像が残る経路を優先して調査する。許容幅を小さくするだけでシーク回数を増やす前に、この2点を解消して同じ測定で比較する。

実行時のソース基準HEADは461c321に今回の計測変更を加えた状態。実際に実行したEXE/DLLのSHA-256は各結果フォルダのenvironment.jsonに保存されている。原プロジェクト・原動画は使用・変更せず、生成fixtureだけで実施した。

監視のTimeoutMinutesは実機テストを対象とし、解析器には別途60秒の上限がある。異常時の強制終了では途中のtraceが失われる場合があるが、その場合は不完全として扱う。
