# 同期精度の測定

既定設定の同期精度を実画像で測り、Freeze画像確定とシーク後の追従修正を同じ条件で比較する。許容幅・除外条件・解析の閾値は変更していない。最新結果は「修正後の測定」、変更前の記録は「基準測定」に分けて残す。

Spout受信を含む追加検証とGPU・CPU方式の比較は、[Spoutデコード比較](SPOUT-DECODE-COMPARISON.md)を参照。以下の測定はアプリ内の出力画像が対象。

## 測っているもの

VB-CABLEで25fpsのLTCを送り、アプリが受信した時刻と、映像をWriteableBitmapへ書き込んだ時刻を同じ単調増加時計で記録する。動画にはフレーム番号とクリップ番号のマーカーを埋め込み、実際に渡した画像のピクセルから読み取る。再生位置表示やmpvの位置プロパティだけで精度を判定しない。

各LTC受信時点の最後の公開画像と、LTCが指定する動画位置を比較する。画像更新が止まっていても測定は続く。正しいクリップの有効マーカーから数値化できた標本、別クリップ、不明画像、未公開は分けて報告する。定常区間の集計では開始直後とクリップ変更後の1秒を除外するが、それらも全標本CSVと復帰・境界測定に残す。

誤差の符号は、プラスが映像の先行、マイナスが遅れ。フレーム開始時刻との差に加え、目標時刻がその画像の表示区間に入っている場合を0とする「フレーム区間からの誤差」を扱う。例えば24fps映像の1枚は約41.67msを占めるので、同じ画像に対応する目標時刻には幅がある。

これは**LTCのデコード通知到着を基準とした、アプリ内の出力画像の測定**である。音声を送った瞬間からの遅延、VB-CABLEのバッファ遅延、Windowsの画面合成、モニター、Spout受信側は測っていない。時刻をmsで記録しても1ms精度を保証しない。入力は40ms刻み、動画は約16.67/33.37/41.67ms刻みで、受信通知にはバッファ処理による揺れもある。

## 試験条件

- 入力: LTC25fps、VB-CABLEのCABLE Input → CABLE Output。
- 映像: 1920×1080、24/1・30000/1001・60/1fps、H.264、フレーム番号付き生成素材。
- 配置: 各映像の最初の10秒を0/12/24秒に配置し、途中に2秒の空白を設ける。
- BlackとFreezeそれぞれで0秒から35秒連続再生。その後3/15/27/3秒へ飛ばして各5秒測る。
- 復帰: 正しいクリップで区間誤差80ms以内、250ms以内をそれぞれ0.5秒継続できた区間の開始までの時間。戻らない場合も結果として記録する。
- Blackは実際の黒画素、Freezeは前クリップ末尾のフレーム番号を確認する。

既定の同期許容幅は映像とLTCのうち長い方のフレーム時間×6。今回の入力では24fps映像で250ms、29.97/60fps映像で240msとなる。これは再シークを決める内部条件であり、実画像誤差の上限保証ではない。シークの待機・抑制もあるため、実測して判断する。

## 再実行と準備

Windowsの操作可能なデスクトップ、.NET 8、PowerShell 7.2以降、Python 3、ffmpeg/ffprobe、mpv DLL、VB-CABLEが必要。このPCでは利用可能。試験中は対象アプリを操作せず、PCをロック・スリープさせない。既存のプロジェクトや動画を準備し直す必要はない。

```powershell
./scripts/run-timecodesyncplayer-accuracy.ps1
```

通常のテストでは専用の実機試験をスキップする。専用実行ではスキップ・強制終了・記録欠落を成功と扱わない。生成動画、測定ログ、CSV、集計、アプリログ追記分、バイナリハッシュを結果フォルダへ保存する。

解析器は記録の完全性と同期精度を別々に扱う。すべて測定できても大きなずれがある場合は、その値をそのまま出す。品質として許容できる誤差の合格基準は、この基準測定の後に決める。

## 2026-09-07 の修正後の測定

Freezeの末尾画像の誤確定と、シーク後に古い画像が残る経路を修正した。最終版の完全測定では24/29.97/60fpsすべての末尾画像が正しく、4か所のシークは約151〜203msで「正しいクリップかつ区間誤差250ms以内を0.5秒継続」の条件に復帰した。**常時1フレーム以内や1ms精度を保証する結果ではない。**

### 変更内容と原因

- mpvの描画処理がUIの位置取得を待たないよう、native callbackから専用スレッドへ直接描画を予約する。制御されたnative比較では、UI待ちの方式は29.97fpsの5シーク中4件で600ms以内に新画像が来ず、位置取得にも約199〜207msの待ちがあった。独立した描画処理では5件すべてで新画像を取得した。
- native用とUI用の画像バッファを分離し、コピーした待機画像を最大1枚に制限する。UIが使用中の画像を上書きせず、古い画像が後から届いて新しい画像を戻さないよう順序を検査する。描画1回ごとに待ち行列へ処理を戻し、60fpsの連続通知が明示的な再描画を待たせ続ける問題も修正した。
- Freezeは停止・シーク完了・ファイル・位置を描画前後に確認し、実際の画像コピーが成功した場合だけ確定する。途中の再生・シーク・Gap再進入、コピー失敗、タイムアウトを確定済みキャッシュにしない。最後の通知がシーク中に来てもタイマーから再試行・公開する。最終画像からさらに1枚進めるframe-stepは削除した。
- Freezeの確定待ちは現在の公開画像を維持する。過去の別クリップの静止画へ差し替えず、実際のキャッシュと確定状態が揃ってから末尾画像を公開する。描画要求の処理自体は待機中も継続する。
- 同じクリップの同期判定ではnativeシーク中の位置を到着済みとして扱わない。別クリップへの切替・Gap退出は引き続き新しい要求へ切り替えられる。
- 現在のSW描画方式の既定デコードを`auto-copy`から`no`へ変更した。同じnative比較で、29.97fpsの新画像到達はハードウェアコピー124〜398msに対しソフトウェア35〜76ms、60fpsでは230〜267msに対し49〜57msだった。描画側だけを直した実機反復でもハードウェア方式のシーク復帰が不安定だったため、今回の設定を採用した。

mpvは描画処理から通常APIへの待ち依存を避けることを要求し、シーク中のtime-posは要求位置を表す場合がある。一次資料: [render API契約](https://raw.githubusercontent.com/mpv-player/mpv/master/include/mpv/render.h)、[再生位置取得の実装](https://raw.githubusercontent.com/mpv-player/mpv/master/player/playloop.c)。使用DLLはmpv v0.41.0-524-g5921fe50b。計測用の画像マーカーは製品の同期判定に使っていない。
