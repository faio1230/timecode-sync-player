## v0.5.0: HAP の GPU 直接対応

**狙い**: VJ で使われる HAP を、CPU で展開して 33MB/コマ を転送する形ではなく、
**圧縮テクスチャのまま GPU へ渡して展開する**形で再生できるようにする。

### 根拠（測定済み）

[docs/analysis/2026-09-20-hap-gpu-probe.md](analysis/2026-09-20-hap-gpu-probe.md) の試作で、合格条件 3 つをすべて満たした。
- 4K60 HapQ（実写）で 1 コマ 中央 2.00ms / 最大 5.7ms（予算 中央 8ms・最大 12ms）
- 60 秒 × 48 条件で落ちコマ 0（1 条件だけ 7 件出たが再現せず）
- 読み出しは最悪ケース 475MB/s に対し 3,577MB/s
- qtdemux は 272〜363 コマ/秒（必要量の 4.5〜6 倍）

### 入れるもの

1. **shim に HAP の分岐**（`video/x-hap` の拒否をやめる）
   - いまは `on_video_pad` で明示的に拒否し、`avdec_hap`（CPU 展開）へ流れないようにしてある
   - 新しい経路: `demux → queue → appsink（video/x-hap）` で圧縮フレームを受け、
     **Snappy 展開 → BC テクスチャへ転送 → シェーダで BGRA へ展開 → 既存の `copy_ring_locked` でリングへ**
   - **リングとフェンスの仕組みには触らない**（壊れる範囲を shim の中に収める）
2. **HAP の解析と Snappy 展開**（`include/tcs_hap.h`、純粋なデータ処理）
   - かたまり分割（並列展開できる形式）にも対応。**実データで固定する**（ffmpeg の `-chunks` で作れる）
3. **対象は HapQ（Scaled YCoCg DXT5）と Hap1（DXT1）**
   - HapM / HapA / Hap7 / HapH は今回の対象外。**読み込み時に「未対応」として扱い、黙って壊れないようにする**
4. **推奨外コーデックの警告（0.4.7）への追加**: HAP をどう分類するかを実測で決める
   （H.264＝推奨 / ProRes＝可 と同じ枠組み。**測る前に決めない**）
5. **既定は無効から始める**（環境変数で切替）。検証機で全条件に通ってから既定で有効にする
6. **文書**: 現場準備ガイド（HAP の扱い・必要な読み出し帯域）、設定リファレンス、リリースノート

### 同乗させる整理（振る舞いを変えない削除のみ）

外部レビュー（Codex、2026-09-20）の指摘のうち、**消すだけで振る舞いが変わらないもの**を入れる。
- **転送するだけのクラスの削除**: `ProjectSaveExecutor`（受け取った関数を呼ぶだけ）、
  `WindowLoadedUiInitializer`（4 つの Action を順に呼ぶだけ）。付随するテストも整理
- **古いキーフレーム警告の経路の削除**（`TCS_LONG_GOP_WARNING`）。
  判定方式が誤っていると自分でコメントに書いてあり、読み込み時のスキャン（0.4.5）に置き換わっている

**残すもの**: `TCS_SEEK_COST_HINT`。棚上げ中の「キーフレーム列を見て着地先を選ぶ」の比較対象で、
**どちらを採るか決まっていない**。決着した時点で、勝った方だけ残して消す。

### 進み方（開発機、2026-09-20）

| 段階 | 状態 | 根拠 |
| --- | --- | --- |
| 1. HAP の解析と Snappy 展開 | **済** | shim のテスト 24 件（実データ 4 通り。C# の実装と検査和が一致） |
| 2. 最小再生 | **済** | 1080p Hap1 / Hap Alpha / 4K HapQ が絵として出る（画面で確認） |
| 3. シーク・未対応変種 | **済** | シーク 3 回とも目標位置へ着地。Hap 7 / Hap HDR は読み込みを理由つきで失敗させる |
| 4. 性能（実機） | **済** | 4K60 HapQ を 20 秒: 2 秒あたり 120〜122 コマ（期待 120〜121）、落ちコマ 0、エラー 0 |
| 5. 既存の形式への影響 | 確認中 | 非E2E 2086 合格（素材の要る 2 件は素材を置いて再実行）、E2E を実行中 |
| 6. 検証機での確認 | 未 | 候補ビルドを送る段階 |

**対応する変種**: Hap（DXT1）・Hap Alpha（DXT5）・Hap Q（Scaled YCoCg DXT5）。
**Hap 7（BC7）と Hap HDR（BC6H）は未対応**として読み込みを失敗させる。テクスチャとしては作れてしまうが、
色の戻し方が違うため**黙って違う絵を出すより断る**。素材が手に入って絵を確認できたら足す。

### 完了の条件（検証機）

1. いつもの一式（シナリオ 22 × 3 周 + L-1 × 6）が v0.4.7 と同等
2. **HAP の実素材が再生できる**（絵が正しい・音がある素材なら音も）。HapQ と Hap1 の両方
3. **4K60 の HAP で、試作と同じ合格条件**（1 コマの時間・落ちコマ 0）を実機で満たす
4. HAP でシーク・トラック切替・LTC 同期が、ほかの形式と同じように動く
5. **未対応の変種（HapM ほか）で、黙って壊れない**（警告を出して再生しない、など決めた動きになる）
6. 既存の形式（H.264・ProRes・VP9・AV1）の挙動が変わっていない

### 入れないもの（v0.5.0 の範囲外）

- **NotchLC**: GStreamer にも同梱 ffmpeg にもデコーダが無い。対応するなら自前実装からで、素材を作るにも Notch 本体が要る。**別途、実現性の調査から**
- HAP の書き出し（エンコード）
- 圧縮テクスチャのままリングに流す経路（試作で差が 0.05ms 以内だったため、**約束を変えない方を採る**）

## v0.5.1: 整理と地固め

**狙い**: 0.5.0 で先送りにした「振る舞いに触る整理」を、**検証 1 回でまとめて**片付ける。

### 入れるもの

1. **同期の取得結果の一体化**（Codex 指摘 2）
   - `ReadSyncTimePos` が取得結果をフィールドに保存し、`ReadSyncPositionSample` が取り出して消す。
     **「この順で呼ぶ」という暗黙の約束**が 2 つの関数に分かれている
   - 同じ取得で得た再生秒数と位置サンプルを**1 つの戻り値**にする
   - **同乗先があればそちらへ前倒しする**: 交番の修正（`steady-delivered-basis`）、
     自動化用に「LTC と位置を 1 回で読む口」を足す作業（L-1 の M4 の根治）。どれも同じ場所を触る
2. **ギャップのフリーズ確定処理の整理**（Codex 指摘 3）
   - `TryCaptureGapFreezeFrameAsync` は実際には待たず、条件判定を `Task.FromResult` で返すだけ。
     画像の保存は GPU 側（`ComposeLayer.SaveFreeze`）が担当しており、名前と構造が役割に合っていない
   - 同期的な状態遷移として整理する。**古い世代・古い捕捉要求を拒否する判定と、GPU 側の画像保持は残す**
3. **長時間試験で出た課題**（2026-09-20 に検証機で実施中の Single 4 時間・Continue 周回・切替集中）
   - 出た問題の大きさによっては、hotfix（0.4.x）へ回す

### 完了の条件

1. いつもの一式が v0.5.0 と同等
2. **ギャップの出入り・トラック切替が、整理の前後で同じ挙動**（Continue の周回ソークで確認）
3. 同期の誤差の分布が v0.5.0 と同等（L-1、`sync.evaluate` の delta で判定）
