# GPU出力の初回実証結果

2026-09-09。独立GPU試作の実装と初回比較を完了した。親が設計・レビュー・実機評価、サブエージェントが実装を担当。作業場所は `session-refactor` worktree、ブランチ `refactor/session-lifecycle`、HEAD `b66d12b`。既存変更と未追跡AGENTS.mdを保持し、コミットしていない。

## 判断

GPU生成画像からDirect3D全画面とSpout SendTextureへ渡す経路は動作した。ただし、今回のSpout公開方式では安定60Hzに達していない。共通スレッド／Spout分離の本体採用は保留する。

- 4Kキャンバスの合成は全8回で60.00Hz。表示は共通スレッドで全回60.00Hz、分離版の併用再試験だけ59.82Hzだった。
- Spoutは併用でcommonが37.55／42.59Hz、splitが38.59／37.32Hz。どちらも公開間隔に長い空白がある。
- 主な見送り理由は、外側のSpout access mutexを待ち時間ゼロで取得できなかったこと。スレッド分離だけでは解消しなかった。
- splitの生成開始から送信公開までの経過時間は平均約17.5ms。commonは約0.93〜1.07ms。ただし成功した公開だけの年齢であり、公開が途切れている間に受信側が保持する画像の古さを表さない。
- 次は独立試作のまま、mutex取得方式と送信予定時刻の関係を小さく比較する。本体のGPU全面移行、mpv接続やGPUプレビュー追加はこの結果を理由に開始しない。

## 実装したもの

詳細な契約は [初回実証仕様](GPU-OUTPUT-PROBE-SPEC.md)、操作・ビルド方法は [試作README](../scripts/GpuOutputProbe/README.md)、実行・解析は [ハーネスREADME](../scripts/GpuOutputProbeHarness/README.md)。

独立した.NET 8 / WPF / x64 / Debugアプリに、D3D11/HLSLの動く色帯と24bit画像ID、最新画像プール3枚、送信用保持画像へのGPUコピー、Direct3Dの全画面表示、Spout送信、共通／分離ワーカーを実装した。分離版は同じアダプター上の別デバイスで共有画像を開く。双方ともコピー完了後に元画像の使用権を返してから送信する。GPU完了確認にはEVENT queryを使用し、CPU読み戻しは送信側の表示経路に含めない。

WPF操作画面は出力処理・終了待ちから独立。終了選択中は出力を続け、通常終了は所有スレッドで完了待ちと解放を行う。明示的な自プロセス強制終了ボタンも実装した。今回の実機確認は時間満了による通常終了であり、実GPUハングや強制終了の注入試験は行っていない。

本体のBlack/Frozen/Buffered、キャンバス設定、クリップ配置、テストカードの操作モデルをこの試作へ接続したわけではない。GPU生成パターンは出力経路を検証するための入力である。

## 条件と表示寸法

- NVIDIA GeForce RTX 3070、driver `32.0.15.9186`、アダプターLUID `72428`。送信側の全デバイスで同一LUIDを確認した。
- 3840×2160 / BGRA8 UNORM / 不透明SDRのGPU生成画像、目標60Hz、32秒、解析窓 `[5,27)` の22秒。百分位はnearest-rank。
- 表示先は `monitor-index=1`（DISPLAY2）。実スワップチェーンは1920×1080、VSync interval 1、flip-discard、2バッファ、最大frame latency 1。WPF操作画面が重なる可能性をmanifestに残した。
- 受信機は指定の公式WinSpoutDXreceiver。隣接DLLを交換せず、専用作業ディレクトリからHiddenで起動。性能比較中に画面キャプチャはしなかった。実受信画像の確認は別の1080p試験で行った。
- アプリ・受信機は1回ずつ親が直列実行。既存設定・表示設定・他アプリを変更せず、自分の受信機だけをWM_CLOSEで終了した。比較8回はすべて双方exit 0、強制終了なし。GPU異常、ログ欠落、画像ID逆行はなかった。

DXGIとCIMの寸法差を調べたところ、表示倍率による誤報ではなく、デスクトップ描画寸法と出力信号寸法の違いだった。PerMonitorV2を検証したCPU専用QueryDisplayConfig／EnumDisplaySettingsExで次を確認した。

| 表示先 | デスクトップ／source mode | targetの出力信号 |
| --- | --- | --- |
| DISPLAY1 / HDP-V104 | 1920×1080 | 3840×2160・60Hz |
| DISPLAY2 / FH-DP4K | 1920×1080 | 1920×1080・60Hz |

証跡は `TestResults/gpu-display-modes-20260909-191443/`。今回の全画面は4Kキャンバスを1080pへ縮小した評価であり、物理的な4K画素の表示試験ではない。試作には明示的なPerMonitorV2 manifestと実コンテキストの確認を追加した。列挙には `dotnet <dll>` ではなく生成されたEXEを使用する。

公式受信機の[公開ソース](https://github.com/leadedge/Spout2/blob/master/SPOUTSDK/SpoutDirectX/SpoutDX/Windows/Receiver/WinSpoutDX.cpp)はReceiveImageによる読み戻しとGDI描画を行う。この受信機の負荷を含む結果であり、受信側までGPUだけで処理する構成の性能ではない。

## 受信画像の確認

別の1080p / split / windowed試験で、自分の公式受信機のみ一時表示し、PrintWindowでclient領域を2枚保存して元の非表示状態へ戻した。親が色帯・動く目印・画像IDの変化を確認した。

- 試験: `TestResults/gpu-output-visual-20260909/20260909T101752681Z-split-both-02df15ffcb6a402c950f68c121ce8b9d/`
- 画像・QPC・所有PID: `TestResults/receiver-evidence/receiver-evidence-20260909T101803029Z-0fa4f32c8ea54a56b99b25f9d6e2deae/`
- 24bitセルの中央を読み取った画像IDは581と660。各IDに対応するsend.publishが撮影完了時刻より前の送信ログに一意に存在した。

これにより、この確認試験で試作の異なる画像が公式受信機に届いたことを確認した。全フレームの実受信率、性能試験8回それぞれの接続先、4K画像の実受信率、物理走査の証明ではない。runnerの `receiverBindingVerified=false` は自動検証していない意味のまま保持した。

先行の撮影補助は長い作業ディレクトリのため起動に失敗した。アプリ・受信機は通常終了しており、その試験は比較表から除外した。短い証拠保存先で撮影を成功させ、その後補助プロセスの作業ディレクトリをスクリプト配置先に固定した。失敗時の記録も保持した。

## 次の実証で切り分けること

最初にSpout access mutexの取得方式を比較する。現在は毎回の予定時刻に待ち時間ゼロで1回だけ試し、失敗すると次の周期まで送らない。受信側と同じ周期で取得機会が重なることが連続欠落を作る可能性がある。今回のログだけでは、1回の長い占有と短い占有の反復を区別できない。

候補は「現行の即時スキップ」と「次の予定時刻を越えて古い仕事を蓄積しない、小さい取得待ち予算」の比較。取得待ち・実際の超過時間・取得成功率・表示への影響を記録する。時間指定がOSによって厳密に守られると仮定しない。GPU完了前に共有画像やmutexを返す変更はしない。

その後、splitの送信予定時刻と合成完了の関係を別に比較する。mutex方式と位相を一度に変更して結果の原因を混ぜない。CPUアップロードやmpvを加えるのは、GPU生成入力での公開境界を評価した後とする。以上は次段階の提案であり、今回の比較途中に適用していない。
