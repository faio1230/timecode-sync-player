## 2. 版ごとのブランチの流れ（規則）

1. 版ごとにブランチを切る: `main` から `v0.X.Y`（例 `v0.5.3`）。作業ツリーも版ごと（`timecode-sync-player-v05` の流用可。切るときは `git worktree` で）。
2. その版の作業はすべてそのブランチへ。担当エージェントのブランチ（`agent-a` / `agent-b`）は版ブランチから切り、版ブランチへ統合する。
3. 合格（1 節）→ 版番号を上げる → `main` へ `--no-ff` で統合 → タグ `v0.X.Y` → 公開（**公開は利用者の許可で止まる**。3 節）。
4. 公開したら次の版のブランチを `main` から切る。使い終わった作業ツリーは `git worktree remove` で消す（成果物で膨らむ）。
5. タグとブランチが同名になるため、push は refs を明示する（`git push origin refs/heads/v0.5.3`、`git push origin refs/tags/v0.5.3`）。
6. 0.4.x／0.5.x の公開後の不具合は `hotfix/<版>-<件名>` ブランチで、同じ合格条件の縮小版（該当シナリオ + 標準 3 通り 1 回）で公開する。

## 3. 止まって利用者に聞く地点

- **公開**（`gh release create`）: 候補が合格したら「公開してよいか」で止める。公開前に配布物の時刻と SHA-256 を見る（成果物は候補を跨いで溜まる）。
- **挙動を変える判断**: 仕様の解釈が分かれる修正、既知の制限に落とす判断、推奨素材の変更。設計書の「利用者に諮る」欄に書いて止まる。
- **範囲の変更**: 想定外の欠陥で版の計画（1 節）を変えるとき。
- **検証機の物理操作**: スリープ復帰、素材の追加、GPU の切替、ドライバ更新。
- **同じ欠陥で候補が 3 回連続で落ちた**、または**前の版で通っていた項目が落ちた（回帰）**: 統合を止めて報告。

これ以外（実装の指示、レビュー、統合、候補作成、Taildrop、検証機への依頼、結果の分類、記録）は止まらず進める。

## 4. 守ること（既存の規則の要点）

- 親は製品コードを書かない（設計・検証・記録）。実装は担当エージェント、判定は親、証拠は trx とログ。
- 途中ビルドは版を据え置き SHA で識別。版は合格してから上げる。
- 実機は直列 1 本、自分の PID だけ止める。候補を検証機へ送る前に開発機で重い素材セットを通す。
- main への書き込みは統合のみ。stash/reset/clean 禁止。コミットは日本語。push は gh 認証情報。
- 素材名・ローカルパスを公開文書に書かない（M1〜M7 / A〜C）。日時は `date` を見て書く。
- 記録は `docs/STATUS.md` と計画文書への 1 追記に絞る。版の公開ごとに引き継ぎを更新し、コンテキストが 60% を超えたら交代する。
- 1 回の合格を証拠にしない。狙った指標だけでなく壊れた側も数える。結論を測定の前に書かない。0 件は率を当ててから読む。守りを足したら平常時の発火回数を数える。
- 着地や追従の遅れが、復号速度から説明できる量（GOP 長 × フレーム時間 + 4K のフレーム時間、実測 100〜300ms）を明らかに超えたら、素材・解像度・デコーダではなく同期経路の時間ベースの門（保留の時間切れ、位置信頼の再確認、シークのゲート、確認窓）の足し算を疑い、製品側の欠陥候補として起票する。失敗の分類で「4K だから」「重い素材だから」と書く前に、ログのシーク発行時刻と LTC 到着時刻の差を復号上限と比べる（利用者の規則、2026-09-26、TSP-Fable 経由）
