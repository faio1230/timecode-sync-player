# 外部出力の単独・併用条件の比較

今回の固定4K MP4では、Spoutのみ／全画面のみは各2回ともBitmap公開平均60.000fps、併用は56.182／56.500fpsだった。native描画終了後に用意できたsnapshotが、併用時だけ公開待ちとmailbox差替えを生じた。今回の差はMP4の単独デコード不足だけでは説明しにくく、出力併用時の待ち・競合を支持する。ただし、どのGPU内部処理が原因か、Spout送信側とSDK受信側のどちらが寄与したかまでは特定していない。

今回は依頼の1〜2、出力条件の固定比較と段階時間・未公開画像の照合までを実施した。製品コード・DLL・デコード設定は変更せず、修正・新規ビルド・テスト追加は行っていない。安定60fps全般、画像混在、LTC同期精度の解決報告ではない。

## 固定条件

基点コミットは `d12a36c`、Debug/x64、製品DLLのSHA256は `B69DAEC0A697988F3D0D8A9509556450F6B16D22736C38B6DC1B22E69E1372C7`。前回v2のDLLをそのまま使用し、`hwdec=no`を維持した。入力は既存 `synthetic-4k60-changing.mp4`（3840×2160、60fps、30秒、SHA256 `1F8D01C4B0801F0D57C90FA80940424F2FAB3D7AD537FBACA2931D6175557F2F`）。LTC OFF・消音・専用settings・メイン窓1076×680、位置(156,156)。OBS・音声入力・WPR・画像採取を併走させず、実機はroot担当が直列実行した。

S=Spout＋公式SDK受信、F=全画面のみでSpout OFF、B=両方。順序はS,F,B,B,F,S、各条件2回、各回32秒のうち開始後5秒以上27秒未満の22秒を解析した。測定中はUIAを使わず、1Hzのプロセス・ネイティブ窓確認を行った。

全画面の実測範囲は全回 `WinDisc` 2080×1017・96dpi。入力と外部用Bitmapは4Kだが、物理4Kモニター表示の試験ではない。Sの主画面プレビュー上限は30Hz、F/Bは10Hzで、全画面による遮蔽も異なる。特にF対BはSpout送信とSDK受信の両方を追加する比較であり、送信処理だけの独立効果ではない。

| --- | ---: | ---: | ---: | ---: |
| 01-S | 60.000 | 60.000 | 59 / 61 | 19.673 / 21.826 / 24.163 |
| 02-F | 60.000 | 無効 | 60 / 60 | 19.365 / 20.711 / 22.831 |
| 03-B | 56.182 | 56.182 | 52 / 59 | 22.744 / 27.204 / 31.028 |
| 04-B | 56.500 | 56.500 | 54 / 59 | 21.798 / 26.276 / 31.214 |
| 05-F | 60.000 | 無効 | 60 / 60 | 19.368 / 21.184 / 22.851 |
| 06-S | 60.000 | 60.000 | 59 / 61 | 19.213 / 21.087 / 24.428 |

Bitmap公開は `frame/kind=normal`、Spoutは `spout/call-returned` の終了時刻で数えた。Sの平均60fpsも各1秒窓が常に60回という意味ではない。外部用BitmapとSpout送信サイズは3840×2160、プレビューは960×540。プレビュー実測はS 21.091／21.364fps、F 9.136／9.136fps、B 8.591／8.636fpsだった。

Bitmap.Lock平均はS 0.010／0.012ms、F 0.027／0.027msに対し、Bは5.460／5.349ms。Bitmapコピー＋dirty領域指定はF 4.654／4.762ms、B 4.142／4.174msで、Bitmap時間増加の主部はLock呼出しの経過時間だった。公開全体平均はS 11.254／9.764ms、F 4.760／4.865ms、B 15.477／15.770ms。BのSpout区間平均は5.789／6.159msだった。

段階時間は開始・終了の両方が解析窓内の記録、分位値はnearest-rankで集計した。別途、境界を跨ぐ段階もrawから保持し、長い待ちを単に解析から消していない。FのSpout OFF呼出しも `disabled-call-returned` として平均0.004ms程度の基底費を記録しており、計測欠落ではない。`preview-prepare`はBitmap参照の通知だけで、タイマー内の縮小・コピー・プレビューLockの費用はこのtraceから個別に分離できない。

## native終了から公開・差替えまでの照合

native-render→snapshot-copyは `(sessionId, generation, attemptId)`、snapshot以後のpublish／discardは `(sessionId, generation, sequence)` で結合した。解析窓内にnative-renderを終了した群から、窓外も含む全traceを使って各画像の行方を追った。別にsnapshot-ready終了時刻で選ぶ群も集計した。6回とも重複・対応欠落・時刻逆転は0、行方不明のterminalは0だった。

全回、native終了群1,320件は全てsnapshotの準備まで進んだ。S/Fは各1,320件とも公開された。Bの03は1,237公開＋83件mailbox差替え、04は1,244公開＋76件差替えだった。Bitmapの時刻窓内公開数はそれぞれ1,236／1,243件で、群の選択時刻との境界差がある。公開数との差をそのまま欠落数にしない。

公開された群のsnapshot-ready→publish開始待ちは、S平均0.479／0.491ms、F 0.240／0.233ms、B 5.575／5.633msだった。Bのp95は14.205／13.736ms、最大20.051／17.673ms。この待ちにはmailbox滞在、UI callback、gate等が含まれ、Dispatcher単独の待ち時間ではない。描画終了後の公開待ちが増え、まだ公開されないsnapshotが新しいものに置き換わっている。

| Bのnative終了群に属する差替え | 総数 | 別のpublish親区間中 | うちSpout子区間中 | Bitmap.Lock子区間中 | publish区間外 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 03-B | 83 | 56 | 55 | 0 | 27 |
| 04-B | 76 | 42 | 39 | 0 | 34 |

重なりはdiscard記録時刻と各区間の半開区間で照合した。publishはSpoutやBitmapの親なので、親子の件数・時間を加算しない。Spout中に多数の差替えが起きたことは、その時点でUI公開が占有されていた観測であり、Spout単独が根本原因という証明ではない。Lock中の差替え0も、Lock待ちの影響がないという意味ではない。区間外の差替えを未計測のプレビュー処理などへ推定で割り当てない。

## 終了・警告・限界

6回ともplayer／所有SDK受信（S/B）／ハーネスはexit0、強制終了なし、trace欠落・エラー0、素材hashは不変。rootの終了後確認で関連プロセスは残っていなかった。原始データと既存ログを保持した。

01-SのWarning7件は全てSpout slow sendで、`Stage=Completed`、`SendSucceeded=true`、所要16.9604〜19.1761ms。送信終了QPCは測定開始後29.542〜31.678秒で、7件全て解析窓外だった。隠さず保存し、解析窓の性能低下とは区別する。他5回はWarning0。Spout無効化の再現や解決とは扱わない。

native-renderはmpv描画API全体の時間で、デコードだけの時間ではない。1,320回のnative終了やBitmap平均60fpsも、60枚の異なるMP4画像のデコード・Spout到達・物理表示を保証しない。今回の素材には一意なフレーム番号マーカーがなく、画像整合、実受信の連続更新、LTC同期精度は未判定。GPU内部原因の確定、timeout変更、出力処理の修正へは今回の範囲を広げていない。
