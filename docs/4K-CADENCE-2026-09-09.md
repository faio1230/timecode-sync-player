# 4K動画の公開頻度とBitmap待ちの調査

Spoutの途中無効化は保留し、動画の更新頻度を調査する。外部出力（Spout・フルスクリーン）の解像度と更新頻度を優先し、プレビューの軽量化は許容する。`hwdec=no`、Debug/x64、mpvソフトウェア描画経路を維持する。

## 固定条件と判定範囲

原始データは Git 管理外の `TestResults/obs-clean/4k-cadence-20260909-050717/`。基点は `19fb888`。`app-baseline/` と `app-diagnostic/` に比較用バイナリを保存した。動画は既存の `synthetic-4k60-changing.mp4`（3840×2160、60fps、30秒、SHA256 `1F8D01C4B0801F0D57C90FA80940424F2FAB3D7AD537FBACA2931D6175557F2F`）。原動画・プロジェクトは変更しない。

各回32秒、開始後5秒以上27秒未満の22秒を解析。新規の試験用settingsでLTC OFF、消音、メインウィンドウ外形1076×680・位置(156,156)。OBS・音声入力・GPU記録・スクリーンショットを併走させず、公式SDK `WinSpoutDXreceiver.exe` を受信側に使う。ハーネスは測定中にUIAを呼ばず、1Hzのプロセス・ネイティブウィンドウ採取のみ行う。試験は直列に実施する。

ここでのfpsは **アプリがBitmapへ公開した回数**。素材にフレーム番号マーカーがなく、native-render回数も一意なデコード画像数ではない。受信側の全画像更新、物理画面の60Hz表示、画像混在、LTC同期精度の合格とは分ける。間隔のp95/p99はnearest-rankで求める。

| --- | ---: | ---: | ---: | ---: |
| run-001-off | 60.000 | 60 / 60 | 19.121 / 20.324 / 22.751 | 0 |
| run-002-sdk | 55.955 | 37 / 59 | 23.421 / 31.119 / 49.357 | 89 |
| run-003-off | 60.000 | 60 / 60 | 19.284 / 20.410 / 21.339 | 0 |
| run-004-sdk | 57.091 | 55 / 60 | 21.612 / 25.499 / 36.584 | 63 |

native終了群は各1,320回。未公開群は準備済みsnapshotのmailbox差替えと対応する。群の開始・終了境界と公開時刻は異なるため、公開数との差をそのまま欠落数とはしない。OFFでは公開60fpsを維持し、SDK受信ありでは公開処理が平均16.1〜16.4msに増えた。デコードだけが間に合わないとする証拠にはならない。

公開終了からlease-release記録までの平均はSDKの2回で0.141 / 0.134ms、p95は0.239 / 0.233ms。最大の公開間隔は、先行フレームのSpout処理と次フレームのBitmap処理が直列に重なる区間に対応した。lease-release記録後の実際のpool返却時間はこの値に含めない。

## Lock・コピー・Unlockの追加診断

`FrameRenderer` の通常画像公開に `bitmap-lock`、`bitmap-copy-dirty`、`bitmap-unlock` を追加した。親のsession/generation/sequenceと結び付け、記録キューへの追加はUnlock試行後に行う。診断無効時は追加QPCやイベントを生成しない。

`diagnostic/run-001-off`、`diagnostic/run-002-sdk` はいずれも正常終了、trace記録欠落・エラー0。公開頻度は60.000 / 57.364fps。SDKの1秒窓は53〜59回、間隔p95 21.348ms・p99 26.461ms・最大29.517ms。

| UI側処理 | OFF 平均 / p95 ms | SDK受信あり 平均 / p95 ms |
| --- | ---: | ---: |
| Bitmap.Lock | 0.027 / 0.055 | 6.694 / 9.805 |
| 画素コピー＋AddDirtyRect | 4.952 / 6.466 | 4.138 / 6.568 |
| Unlock | 0.036 / 0.054 | 0.038 / 0.068 |
| Bitmap全体 | 5.042 / 6.551 | 10.899 / 13.469 |
| Spout | 無効 | 5.304 / 10.566 |
| 公開全体 | 5.051 / 6.557 | 16.217 / 20.896 |

段階時間は開始・終了の両方が解析窓内にある記録を採用し、p95は既存監査の `floor(0.95*(n-1))` 番目（0始まり）を使用する。間隔のnearest-rankとは方式が異なる。

SDK条件で増えたBitmap時間の主部はLock呼び出しであり、画素コピーの増加ではない。Lockの経過時間にはスケジューリング等も含まれ、GPU内部の根本原因まで特定したものではない。[WPFのLock仕様](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.imaging.writeablebitmap.lock)にも描画スレッドとの競合でUIがブロックし得ることが記載されている。

メインプレビューとフルスクリーンは同じWriteableBitmapを共有している。この画像を単純に間引くとフルスクリーンも落ちるため、外部出力を維持する比較候補を評価する。診断追加時点のDebugビルドは警告・エラー0、非E2Eテスト1,421件成功（失敗・skipとも0）。


## フルスクリーンの基準測定

`fullscreen-harness/` は既存試験ハーネスのコピーに `--fullscreen` を追加したもの。所有PIDと正確なタイトルで全画面HWNDを特定し、測定中1Hzで表示・非最小化・寸法・モニター・DPIを確認する。実測画面は `WinDisc`、2080×1017、96dpi。入力は4Kだが物理4Kモニターでの表示試験とはしない。メインプレビューは残り、全画面窓による他の窓の遮蔽もあるので、通常窓条件との数値差を単独の効果とは呼ばない。

`fullscreen-baseline/run-001-sdk` は公開55.818fps、1秒窓51〜60回、間隔p95 23.012ms・p99 27.494ms・最大35.416ms。native終了群1,320回中未公開93回。trace完全・記録欠落とエラー0、player/SDK受信ともexit0、強制終了なし。

診断版の通常窓条件のプロセス採取（約5〜26秒、22標本）は、playerのCPU消費がOFF 3.406 / SDK 3.883論理コア相当。Working SetはOFF 825.68→830.52MiB、SDK 919.49→929.42MiB。SDK受信プロセスを含めたシステム全体のCPUではない。採取開始・終了QPCを記録した上で中点差を計算した値であり、短区間1回ずつの比較からリークは判断しない。


基準反復 `fullscreen-baseline-repeat/run-001-sdk` は56.091fps、1秒窓51〜59回、間隔p95 22.862ms・p99 27.075ms・最大38.332ms。未公開群86回、正常終了・trace完全だった。

## 不採用: 2枚のBitmap交互利用

4K以上の完全フレームを2枚で交互公開し、Lock/コピー/Unlock後に表示先を切り替える候補を試した。部分更新・Black/Freeze・サイズ変更・通知中再入拒否を含む非E2Eテスト1,436件成功、Debugビルド警告・エラー0。

しかし `candidate-sdk/run-001-sdk` は公開 **50.273fps**、1秒窓28〜57回、間隔p95 24.410ms・p99 27.805ms・最大485.153msへ悪化。Lock平均は0.028msに減った一方、copy-dirtyは7.764ms、Spoutは10.062ms、公開全体は18.019msへ増加。player Working Setは984.62→990.88MiB、最大993.35MiB（解析窓内標本）。新たなSpout無効化やtrace欠落・エラーはなく、player/受信とも正常終了した。

Lock待ちだけの短縮では全体改善にならなかったため、この候補は製品に採用しない。コード・テストは `rejected-double-buffer/`、実行ファイルは `app-double-buffer-rejected/`、原始データは上記runに保管する。候補のフルスクリーン試験は未実施。


## 未採用: Spoutを先に送信する順序変更

1枚方式へ戻し、通常公開パイプラインだけをSpout→Bitmap→統計→Freezeコピーの順にした候補を比較した。pin/lease・mutex・GPU完了待ち・hwdecは不変。Debugビルド警告・エラー0、非E2Eテスト1,426件成功。Spout例外ならBitmapを更新せず、Bitmap例外ならSpout呼出し済みになる境界もテストした。

| 条件 | 公開fps | 1秒窓の最小／最大 | 間隔p95 / p99 / 最大 ms | 未公開native群 |
| --- | ---: | ---: | ---: | ---: |
| reordered-sdk/run-001-sdk | 57.773 | 56 / 60 | 21.046 / 24.357 / 32.000 | 49 |
| reordered-fullscreen/run-001-sdk | 57.227 | 51 / 60 | 21.348 / 26.205 / 33.979 | 61 |

通常窓ではLock平均0.039msへ減少したが、copy-dirty 5.592ms・Spout 10.737ms・公開全体16.476msとなった。待ちの箇所を移しても公開全体の負担は十分に減っていない。フルスクリーンは同じWinDisc 2080×1017/96dpi。両回trace完全、記録欠落・エラー0、player/SDK受信exit0、強制終了なし。

基準値との差はあるが各条件1回であり、反復・一意画像到達の改善を実証したものではない。安定60fpsには未達なので順序変更も採用しない。`reordered-publish/` に変更前・候補source/tests、`app-reordered-unadopted/` に実行ファイルを保存し、製品は診断追加のみへ戻した。2枚候補から戻したFrameRendererのソースSHAは旧診断時点とbyte一致していない（改行差を含む）。`rejected-double-buffer/restoration.json` に不一致を明記し、最終diffが元の診断追加43行のみであることを確認した。

## 今回の結論と残る検証

- **ビルド・終了:** 各段階のDebugビルド成功。今回の実機12回はすべてplayer/所有SDK受信を正常終了し、素材・設定・元ログを保持した。GPU記録・LTC・OBSは起動していない。
- **公開性能:** 基準のSpout OFFは2回とも全22個の1秒窓で60回。公式SDK受信ありは55.955 / 57.091fps、追加診断で57.364fps。フルスクリーン併用基準は55.818 / 56.091fps。目標の安定60fpsは未達。
- **確認できた遅延:** SDK受信ありでBitmap.Lockの経過時間が増え、UI側の公開が詰まり、準備済みsnapshotの差替えが発生する。今回の候補ではLock時間が短くなる一方、コピー・Spout時間が増えた。デコードライブラリの自作が必要、またはGPU内部の故障が原因と結論づける証拠ではない。
- **画像・同期:** 一意な受信画像の連続更新、混在、物理4K60表示、LTC同期精度は今回未測定。Spout呼出しreturn数とBitmap公開数も分けて `comparison-final-with-restored.json` に記録した。call-returnedは画像到達の保証ではない。
- **次の候補:** 外部出力とプレビューを分け、プレビューの解像度・更新頻度を抑えて外部出力への待ちを減らす設計を検討する。現在は同じBitmapなので、単純な間引きではフルスクリーンも低下する。分離の改善効果は未検証。外部出力の画質を落とす変更やGPU描画への全面変更は今回行わない。

Spout途中無効化、OBSの混在、LTC欠落・同期誤差、長時間メモリ保持の課題は、この結果で解決済みとしない。


## 復元後の最終確認

製品・テストを強制Rebuildし、診断追加のみの最終コードで **1,421件成功、失敗・skipとも0**、ビルド警告・エラー0。最初の復元後incremental実行は保存元の更新日時により候補テストassemblyが残り1,426件となったため、`final-diagnostics.trx` は最終コードの検証証拠に採用しない。正式結果は `tests/final-diagnostics-rebuilt.trx`。

最終製品DLL SHA256は `0349DD1DFAD9E4C48EF447887A8B10C8827A9564F50014C80FFC0839A7241A26`。`final-diagnostic-sdk/run-001-sdk` でこのDLLを実行し、player/SDK受信exit0・強制終了なし、trace完全・記録欠落とエラー0、条件検査・素材ハッシュ不変を確認した。

**この最後の測定は52.545fpsまで低下**した。1秒窓46〜56回、間隔p95 25.641ms・p99 29.990ms・最大37.821ms、native終了群1,320回中未公開163回。低下した結果も保持し、初期55〜57fpsだけを代表値として選ばない。関連プロセス・素材・設定・窓を固定していても、保持したユーザーの他アプリを含むマシン全体の負荷・スケジューリングを固定した試験ではない。元診断版とのソースbyte差もあるため、変動要因の単独原因は未確定。候補の小さな数値差を改善と断定しない判断を維持する。
