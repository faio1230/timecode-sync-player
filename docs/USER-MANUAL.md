# TimecodeSyncPlayer 現場準備ガイド

本番前に確認しておくと、同期が安定する項目をまとめます。
**ここに書いた数値はすべて実測です。** 測っていないことは「測っていない」と明記します。

---

## 1. 素材の推奨形式

**どれも「読めないと困る」形式ではありません。** 読めますが、外れると同期が不安定になります。

| 項目 | 推奨 | 外れたときに起きること |
|------|------|----------------------|
| **キーフレーム間隔** | **1〜2 秒** | **これがいちばん効きます。**下の 1-1 を参照 |
| コーデック | **H.264**（GPU デコード） | ProRes は可、AV1 は非推奨（1-2） |
| 素材の fps | **タイムコードの fps と揃える** | ずれが一定量残る（1-3） |
| 解像度 | 4K60 まで実測で問題なし | — |
| ビットレート | **測っていません**（1-4） | — |

### 1-1. キーフレーム間隔（最重要）

**同期が不安定になる原因の大半はこれです。** 解像度でもビットレートでもありません。

同期のずれを詰めるときプレイヤーはシークしますが、**シークは直前のキーフレームから目標位置まで復号する**ので、
キーフレーム間隔がそのまま所要時間になります。しかも**二重に効きます**。

実測（同じ 4K60 の素材どうしの比較）:

| キーフレーム間隔 | 追従開始のずれ | 追い付くまで | 補正シーク |
|----------------|--------------|------------|-----------|
| **0.5 秒** | 5.78 秒 | **1.4 秒** | **0 回** |
| **6.6 秒** | 小さい | **16 秒** | 複数回 |

- **シーク自体が遅くなる**: 間隔 6.633 秒の素材で、キーフレーム直後へのシークは 244ms、
  次のキーフレーム直前へのシークは **2,164ms**（約 9 倍）
- **シークのあと再生が戻るまでも遅くなる**: 間隔 6.633 秒 → 0.79 秒、0.501 秒 → 0.15 秒、
  0.017 秒 → 0.10 秒。**間隔に比例します**

**書き出しの例**（`-g` は「何フレームごとにキーフレームを置くか」）:

```
# 60fps の素材を 1〜2 秒間隔にする
ffmpeg -i input.mov -c:v libx264 -g 120 -keyint_min 60 -sc_threshold 0 out.mp4

# 30fps なら
ffmpeg -i input.mov -c:v libx264 -g 60 -keyint_min 30 -sc_threshold 0 out.mp4
```

書き出した素材を確認するスクリプトを同梱しています（`ffprobe` があれば動きます）:

```
powershell -File scripts\inspect-gop.ps1 -Path D:\media
```

### 1-2. コーデック

- **H.264**: 実測してきた経路です。GPU でデコードします。**これを推奨します**
- **ProRes**: 使えます。全フレームがキーフレームなのでシークは速いですが、
  帯域を食います（読み出しが間に合わない環境では別の問題が出ます）
- **VP9**: **推奨しません。** 4K60 では、2 秒単位で数えたときの約 5 回に 1 回、デコードが
  追いつかなくなりました（実測。1080p60 では起きていません）
- **AV1**: **推奨しません。** デコードできますが、**キーフレーム間隔の警告が出ません**（解析に使う
  パーサが AV1 のキーフレームを立てないため）。不安定な素材でも気づけない、という意味で危険です。
  **どうしても AV1 を使う場合は、下の `inspect-gop.ps1` で事前に確認してください。**
  こちらは `ffprobe` を使うので AV1 でも正しく読めます（実測: 3840x2160 の AV1 で
  キーフレーム 12 枚・最大間隔 1.000 秒を正しく検出）
- **HAP**（v0.5.0 から）: 使えます。GPU で展開するので、4K60 でも CPU の負担はほとんどありません。
  詳しくは下の「1-5. HAP」を見てください

### 1-3. タイムコードと素材の fps

**揃えるのがいちばん良いです。** 揃っていれば、ずれのばらつきは**ほぼゼロ**になり（25fps の素材と 25fps のタイムコードで実測 0.00ms）、
残る誤差は映像 1 フレームぶんの固定値だけになります。

実測（ばらつき = p95 − p5）:

| 素材 | タイムコード | ばらつき |
|------|------------|---------|
| 25fps | 25fps | **0.00 ms** |
| 60fps | 30fps | 約 17 ms |
| 60fps | 25fps | 約 27 ms |

比が 1 から離れるほど大きくなります。上の表の範囲（最大 27ms、映像 2 フレーム弱）なら目で見て分かる量ではありませんが、揃えられるなら揃えてください。

### 1-4. ビットレートについて

**測っていません。** 同期の安定性に効くかどうか、こちらで確かめたデータがありません。
「4K60 の 15GB 程度の素材で問題なかった」以上のことは言えません。
キーフレーム間隔を推奨どおりにしてもまだ不安定な場合は、ご連絡ください。

### 1-5. HAP（v0.5.0 から）

HAP は圧縮したまま GPU へ渡して展開します（CPU では展開しません）。全フレームがキーフレームなので、
シークは ProRes と同じく速い形式です。

- **設定は要りません。** そのまま読み込めます。止めたいときだけ、起動前に環境変数 `TCS_HAP=off` を
  設定します（止めている間は HAP の素材は読み込みに失敗します。CPU で展開する経路には流しません。
  4K では間に合わないためです）
- **使える種類**: Hap（DXT1）・Hap Alpha（DXT5）・Hap Q（Scaled YCoCg DXT5）
- **使えない種類**: Hap 7（BC7）・Hap HDR（BC6H）。**読み込み時に理由を出して失敗します**
  （黙って違う色の絵を出すより、断るほうを選んでいます）。Hap 7 の代わりに Hap Q か Hap を使ってください
- **Hap Q Alpha は未保証です。** 実際のソフトで書き出した素材で確かめるまで、動作を保証しません
  （手元の ffmpeg ではこの形式を書き出せないため）。素材が手に入りしだい確認して対応します
- **読み出しの速さ**: HAP はファイルが大きくなります。4K60 の Hap Q で毎秒 数百 MB を読み続けるので、
  **素材は内蔵の SSD（NVMe）に置いてください。** 外付けの HDD や USB 接続のドライブでは読み出しが
  間に合わないことがあります
- 実測（v0.5.0 の検証機、4K60 の Hap Q・Hap と 1080p60 の Hap Alpha を CPU 内蔵の GPU と RTX 3080 の両方で）:
  2 秒あたり 120〜121 コマ届き、「デコードが追いついていません」は一度も出ませんでした。
  絵は ffmpeg で展開したものと同じで、色の差は 1/255 未満です。1 コマの展開と転送は、開発機で中央 2.0ms・最大 5.7ms です

## 2. タイムコード信号

現場ではアナログ回線で受けることを想定しています。

- **判断材料は SNR（信号対雑音比）です。** 実測では、これだけで復号の成否が決まりました
- **ハムノイズ（50/60Hz）はホワイトノイズより 3〜4 dB 強いところまで耐えます。**
  ハムは特定の周波数に集中するため、広い帯域に散るノイズより影響が小さいです
- **分配してレベルが下がっても、SNR が保たれていれば問題ありません**
- **速度のずれ（±100ppm 程度）では影響が出ませんでした**（実測。これより大きいずれは測っていません）
- **一瞬の途切れ**（ケーブルを踏む・抜ける）は、ランスルー設定で乗り切れます

## 3. 「キーフレーム間隔が長い」警告について

素材を読み込むと、プレイヤーがキーフレーム間隔を調べ、長すぎる場合に
**ステータス行とプレイリストに警告**を出します。再生は止めませんし、エラーにもしません。

| 最大間隔 | 表示される文言 |
|---------|--------------|
| 5 秒以下 | （表示なし） |
| **5 秒超** | キーフレーム間隔が長い区間があります（最大 ○.○ 秒、推奨 1〜2 秒） |
| **10 秒超** | **⚠** キーフレーム間隔が ○.○ 秒の区間があります。同期が不安定になる可能性があります（推奨 1〜2 秒） |

10 秒超は `⚠` が付きます。**どちらも再生は止まりません。**素材の差し替えを検討する合図としてお使いください。

- 判定は**ファイル全体の最も長い間隔**で行います。平均ではありません。
  実素材に、間隔の中央値が 0.7 秒なのに**最大 6.7 秒の区間**を持つものがありました。
  その区間にシークすると実際に遅くなります
- 素材の**先頭**（0 秒〜最初のキーフレーム）と**末尾**（最後のキーフレーム〜終端）も対象です。
  末尾が 3.9〜6.0 秒ある実素材があり、終端付近へのシークが遅くなります
- 解析は**コンテナを読むだけでデコードしません**。再生とは別に、低い優先度で動きます

**解析にかかる時間**（ローカルの SATA SSD で実測）:

| ファイル | 初回 | 2 回目以降 |
|---------|------|-----------|
| 928 MB | 0.3 秒 | — |
| **13.4 GB**（実素材） | **22.8 秒** | **5.8〜6.3 秒** |
| 300 GB（見込み） | **8 分程度** | — |

2 回目が速いのは OS のファイルキャッシュです。**NAS や外付けの場合は測っていません**（もっと遅くなるはずです）。

**解析を止めたいとき**は、環境変数 `TCS_GOP_SCAN=off` を設定してから起動してください。
300GB 級の素材で初回の読み切り（8 分程度の見込み）を避けたいときや、素材が推奨どおりだと
分かっているときに使えます。**止めると上の警告も出なくなります**（判定の材料が無くなるため）。

**解析中も、再生への影響は測った範囲では見られませんでした**（ローカルの SATA SSD での実測: 13.4GB の解析が追従の最初の 8.2 秒に重なった実行で、
2 秒あたりの表示 119.9 コマ・同期のずれ 0.08〜0.09 秒と、重ならなかった実行と差がありませんでした）。

## 4. 推奨外の形式・デコードの遅れの表示

### 4-1. 推奨外の形式

H.264・ProRes 以外の形式（VP9・AV1・H.265 など）を読み込むと、ステータス行とプレイリストに
「推奨外の形式」と表示します（プレイリストの印は `⚠ 形式`）。**再生は止めません。**
判定は「推奨に合っているか」だけで、ビットレートなどは見ていません。

### 4-2. 「デコードが追いついていません」

再生中に、2 秒あたりに届いた映像のコマ数が、本来届くはずの数の 9 割を下回ると、
ステータス行に次のように表示します。

```
⚠ デコードが追いついていません（2 秒で 74 / 120 枚、この素材で 3 回）
```

- **表示するだけで、同期の動きは変えません。** 最後に起きてから 10 秒で消えます
- 表示が出ると、そのあと同期が一時的に 0.3〜0.7 秒ずれることがあります（取り戻しの行き過ぎ）
- シーク・一時停止・速度の切替・読み込みの直後、ギャップの中、素材の終わり近くでは判定しません
  （そこでコマが減るのは正常なため）
- 速度ボタンで 2×・4× にしたときは、その速度で届くはずのコマ数と比べます。重い素材では
  4× で出ることがあります（試験では、4K60 の ProRes は 4× にしても約 3 倍速ぶんしか届かなかった）。
  同期中の速度はほぼ 1× なので、本番で気にするのは 1× で出る場合です
- 起きた時刻と数字はログにも残ります（`Decode behind:` の行）

**出たときにすること:** 本番前のリハーサルで出るなら、その素材は差し替えを検討してください。
推奨どおりの素材（H.264・キーフレーム間隔 1〜2 秒）では、実測で一度も出ていません。
推奨どおりの素材で出る場合は、ログを添えてご連絡ください。

## 5. うまくいかないときの確認順

1. **警告が出ていないか** — 出ていれば、まず素材をキーフレーム間隔 1〜2 秒で書き出し直す
2. **素材とタイムコードの fps が揃っているか**
3. **タイムコードのノイズ** — ハムやホワイトノイズが乗っていないか
4. それでも直らない場合は、ログ（`logs\timecodesyncplayer-YYYYMMDD.log`）を添えてご連絡ください

## 6. 既知の制限

- **CPU 内蔵の GPU では、4K60 の素材を実時間で復号しきれないことがあります。** そのあいだ同じ絵が
  0.3〜0.8 秒出続け、長く続くと同期も一時的にずれます（v0.4.8 の検証機で、内蔵 GPU では 1650 秒に
  16〜37 回。外付けの RTX 3080 では 0 回）。4K60 の素材は**外付けの GPU で動かしてください**。
  - アプリは「全画面の出力先に選んだディスプレイがつながっている GPU」を使います
  - 出力先を選ばない（Spout だけで使う）ときは Windows の既定の GPU を使います。ノート PC では
    内蔵の GPU になることが多いので、Windows の「設定 → システム → ディスプレイ → グラフィック」で
    アプリを「高パフォーマンス」にしてください
  - **Spout の受け手のソフトも同じ GPU にそろえてください。** Spout は GPU をまたいで共有できません
- キーフレーム間隔が長い素材では、再生中のシークの着地が 1〜3 秒遅れることがあります
- 同じ素材で追従中にずれが生じた場合、絵を止めずに再生速度で詰めるため、
  解消まで数秒から十数秒かかることがあります（ずれ 1 秒あたり約 10 秒）
- トラックを切り替えてから最初の絵が出るまで、4K60 の実素材で 0.7〜0.8 秒かかります。
  ギャップを挟む切替では画面が黒のため見えませんが、**挟まない切替では前の絵が残ります**
- **切り替えた直後は、新しいトラックが頭から始まります。**読み込みにかかった時間ぶん
  タイムコードより手前から始まり、1 秒前後かけて追い付きます。遅れの量は素材で変わります
  （実測: 推奨どおりの素材で 0.05〜0.24 秒、キーフレーム間隔が長い 4K60 の素材で最大 1.08 秒）。
  キーフレーム間隔が長い素材では、追い付きに 10 秒以上かかることがあります
- デコードが一時的に追いつかなくなると、そのあと同期が 0.3〜0.7 秒ずれることがあります
  （上の「デコードが追いついていません」が出る場面です）。いずれも数秒で戻ります。
  以前「10 分の連続追従で数回ずれる」と書いていたものも、同じ現象でした（ずれた時刻と
  デコードが遅れた時刻が、10 分間ですべて一致しました）
- ビットレートが非常に高い ProRes 4K60（1.7 Gbps 程度）では、まれに読み込みやシークが数秒遅れます
  （シークのあと新しい位置の絵が 2 秒以上来ない: 自動試験で 59 回中 9 回、日によって 0〜27%。
  読み込みが終わらない: 同じ素材で数回）。原因は分かっていません。以前の版から同じです
- タイムコードが範囲外へ出てクリップの端で止まるとき、ふだんは端から 2〜3 フレーム先で止まりますが、
  まれにもう少し先（実測で 0.18 秒）の絵で止まることがあります
