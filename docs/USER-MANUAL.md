# TimecodeSyncPlayer 現場準備ガイド

本番前に確認しておくと、同期が安定する項目をまとめます。ここに書いた数値はすべて実測です。測っていないことは「測っていない」と明記します。

---

## 1. 素材の推奨形式

どれも「読めないと困る」形式ではありません。読めますが、外れると同期が不安定になります。

| 項目 | 推奨 | 外れたときに起きること |
|------|------|----------------------|
| キーフレーム間隔 | 1秒を目安、長くても2秒 | 影響がいちばん大きい。下の1-1を参照 |
| コーデック | H.264（GPUデコード）、ProRes（NVIDIAのGPUで推奨） | AV1・VP9・H.265は推奨外（1-2） |
| 容器 | mp4・mov | mkv・webm・aviは開けない（1-6） |
| 素材のfps | タイムコードのfpsと揃える | ずれが一定量残る（1-3） |
| 解像度 | 4K60まで実測で問題なし | — |
| ビットレート | 測っていません（1-4） | — |

### 1-1. キーフレーム間隔（最重要）

同期が不安定になる原因の大半はキーフレーム間隔です。解像度でもビットレートでもありません。

同期のずれを詰めるときにプレイヤーが行うのはシークです。シークは直前のキーフレームから目標位置までデコードするので、キーフレーム間隔がそのまま所要時間になります。しかも二重に影響します。シーク自体が遅くなることと、シークのあと再生が戻るまでも遅くなることです。

実測は、同じ4K60の素材どうしの比較です。

| キーフレーム間隔 | 追従開始のずれ | 追い付くまで | 補正シーク |
|----------------|--------------|------------|-----------|
| 0.5秒 | 5.78秒 | 1.4秒 | 0回 |
| 6.6秒 | 小さい | 16秒 | 複数回 |

シーク自体の遅れは、間隔6.633秒の素材で、キーフレーム直後へのシークが244ms、次のキーフレーム直前へのシークが2,164ms（約9倍）でした。シークのあと再生が戻るまでの時間は、間隔6.633秒で0.79秒、0.501秒で0.15秒、0.017秒で0.10秒と、間隔に比例します。

書き出しの例です。`-g`は「何フレームごとにキーフレームを置くか」で、1秒を目安にします（長くても2秒）。

```
# 60fps の素材を 1 秒間隔にする
ffmpeg -i input.mov -c:v libx264 -g 60 -keyint_min 30 -sc_threshold 0 out.mp4

# 30fps なら
ffmpeg -i input.mov -c:v libx264 -g 30 -keyint_min 15 -sc_threshold 0 out.mp4
```

書き出した素材を確認するスクリプトを同梱しています（`ffprobe`が必要です）。

`ffprobe`は4.1以上を使ってください。MP4に入ったAV1を読めるのが4.1からです。

```
powershell -File scripts\inspect-gop.ps1 -Path D:\media
```

### 1-2. コーデック

H.264は実測してきた経路で、GPUでデコードします。推奨する形式はこれです。

ProResはNVIDIAのGPUで推奨します。GPUでデコードし、全フレームがキーフレームなのでシークは速いですが、帯域の消費は大きいです。読み出しが間に合わない環境では別の問題が出ます。ほかのGPUでは既定でCPUデコードになります。詳しくは下の「7. GPUとProResのデコード」を見てください。

VP9は推奨しません。4K60では、2秒単位で数えたときの約5回に1回、デコードが追いつかなくなりました（実測。1080p60では起きていません）。

AV1は推奨しません。デコードできますが、キーフレーム間隔の警告が出ません。解析に使うパーサがAV1のキーフレームを立てないためです。不安定な素材でも気づけない、という意味で危険です。どうしてもAV1を使う場合は、上の`inspect-gop.ps1`で事前に確認してください。こちらは`ffprobe`を使うのでAV1でも正しく読めます（実測: 3840x2160のAV1でキーフレーム12枚・最大間隔1.000秒を正しく検出）。

H.265（HEVC）は推奨しません。GPUでデコードはできますが、同期の安定性を測っていません。

HAP（v0.5.0から）は使えます。GPUで展開するので、4K60でもCPUの負担はほとんどありません。詳しくは下の「1-5. HAP」を見てください。

### 1-3. タイムコードと素材のfps

揃えるのがいちばん良いです。揃っていれば、ずれのばらつきはほぼゼロになり（25fpsの素材と25fpsのタイムコードで実測0.00ms）、残る誤差は映像1フレームぶんの固定値だけになります。

実測のばらつき（p95 − p5）は次のとおりです。

| 素材 | タイムコード | ばらつき |
|------|------------|---------|
| 25fps | 25fps | 0.00ms |
| 60fps | 30fps | 約17ms |
| 60fps | 25fps | 約27ms |

比が1から離れるほど大きくなります。上の表の範囲（最大27ms、映像2フレーム弱）なら目で見て分かる量ではありませんが、揃えられるなら揃えてください。

アプリの「LTC fps」の設定は、本番ではタイムコードの発生器と同じ値に固定してください。「自動（Auto）」は、つないだタイムコードのfpsが分からないときに当たりを付けるための補助の設定です。自動のままだと、信号が乱れた瞬間に追従が一時的に遅れることがあります。

### 1-4. ビットレートについて

測っていません。同期の安定性に影響するかどうか、こちらで確かめたデータがありません。「4K60の15GB程度の素材で問題なかった」以上のことは言えません。キーフレーム間隔を推奨どおり（1秒を目安）にしてもまだ不安定な場合は、ご連絡ください。

### 1-5. HAP（v0.5.0から）

HAPは圧縮したままGPUへ渡して展開します（CPUでは展開しません）。全フレームがキーフレームなので、シークはProResと同じく速い形式です。

設定は要らず、そのまま読み込めます。止めたいときだけ、起動前に環境変数`TCS_HAP=off`を設定します。止めている間はHAPの素材は読み込みに失敗し、CPUで展開する経路には流しません。4Kでは間に合わないためです。

使える種類はHap（DXT1）・Hap Alpha（DXT5）・Hap Q（Scaled YCoCg DXT5）です。Hap 7（BC7）とHap HDR（BC6H）は使えず、読み込み時に理由を出して失敗します。理由を出さずに違う色の絵を出すより、断るほうを選んでいます。Hap 7の代わりにHap QかHapを使ってください。

Hap Q Alphaは未保証です。実際のソフトで書き出した素材で確かめるまで、動作を保証しません。手元のffmpegではこの形式を書き出せないためです。素材が手に入りしだい確認して対応します。

HAPはファイルが大きくなります。4K60のHap Qで毎秒数百MBを読み続けるので、素材は内蔵のSSD（NVMe）に置いてください。外付けのHDDやUSB接続のドライブでは読み出しが間に合わないことがあります。

実測（v0.5.0の検証機、4K60のHap Q・Hapと1080p60のHap AlphaをCPU内蔵のGPUとRTX 3080の両方で）では、2秒あたり120〜121コマ届き、「デコードが追いついていません」は一度も出ませんでした。絵はffmpegで展開したものと同じで、色の差は1/255未満です。1コマの展開と転送は、開発機で中央2.0ms・最大5.7msです。

### 1-6. 容器の対応

推奨する容器はmp4とmovです。コーデックの推奨は上の1-2のとおりです。

| 容器 | 拡張子 | 開けるか |
|------|--------|---------|
| MP4（推奨） | .mp4 | 開ける |
| QuickTime（推奨） | .mov | 開ける |
| MPEG-TS | .ts・.m2ts・.mts | 開ける |
| MXF | .mxf | 開ける |
| Matroska・WebM | .mkv・.webm・.mka | 開けない |
| AVI | .avi | 開けない |

「開けない」容器は、同梱のGStreamerに、その容器を読む部品（demux）が入っていないため読み込みに失敗します。ファイルを選ぶ画面では今は.mkvと.aviも選べますが、選べても開けません。mp4かmovに書き出し直してください。

## 2. タイムコード信号

現場ではアナログ回線で受けることを想定しています。

判断材料はSNR（信号対雑音比）です。実測では、これだけでデコードの成否が決まりました。ハムノイズ（50/60Hz）は、ホワイトノイズより3〜4dB強いところまで耐えます。ハムは特定の周波数に集中するため、広い帯域に散るノイズより影響が小さいです。分配してレベルが下がっても、SNRが保たれていれば問題ありません。速度のずれ（±100ppm程度）では影響が出ませんでした（実測。これより大きいずれは測っていません）。

一瞬の途切れ（ケーブルを踏む・抜ける）は、ランスルー設定で乗り切れます。頭だけLTCで合わせて走らせる使い方も可能です。ランスルー設定で、LTCを頭の1秒ほど当てて位置を取れば、その後LTCが止まっても映像はそのまま走り続けます。止まっている間は位置を合わせ直さず、LTCが戻ったときに1回だけ合わせ直します。

## 3. 「キーフレーム間隔が長い」警告について

素材を読み込むと、プレイヤーがキーフレーム間隔を調べ、長すぎる場合にステータス行とプレイリストに警告が出る仕組みです。再生は止めませんし、エラーにもしません。

| 最大間隔 | 表示される文言 |
|---------|--------------|
| 5秒以下 | （表示なし） |
| 5秒超 | キーフレーム間隔が長い区間があります（最大 ○.○ 秒、推奨 1〜2 秒） |
| 10秒超 | `⚠` キーフレーム間隔が ○.○ 秒の区間があります。同期が不安定になる可能性があります（推奨 1〜2 秒） |

10秒超は`⚠`が付きます。どちらも再生は止まりません。素材の差し替えを検討する合図としてお使いください。表示の文言にある「推奨 1〜2 秒」は、本書の推奨（1秒を目安、長くても2秒）の範囲を示します。

判定はファイル全体の最も長い間隔で行います。平均ではありません。実素材に、間隔の中央値が0.7秒なのに最大6.7秒の区間を持つものがありました。その区間にシークすると実際に遅くなります。素材の先頭（0秒〜最初のキーフレーム）と末尾（最後のキーフレーム〜終端）も対象です。末尾が3.9〜6.0秒ある実素材があり、終端付近へのシークが遅くなります。解析はコンテナを読むだけでデコードしません。再生とは別に、低い優先度で動きます。

解析にかかる時間は、ローカルのSATA SSDでの実測で次のとおりです。

| ファイル | 初回 | 2回目以降 |
|---------|------|-----------|
| 928MB | 0.3秒 | — |
| 13.4GB（実素材） | 22.8秒 | 5.8〜6.3秒 |
| 300GB（見込み） | 8分程度 | — |

2回目が速いのはOSのファイルキャッシュです。NASや外付けの場合は測っていません（もっと遅くなるはずです）。

解析を止めたいときは、環境変数`TCS_GOP_SCAN=off`を設定してから起動してください。300GB級の素材で初回の読み切り（8分程度の見込み）を避けたいときや、素材が推奨どおりだと分かっているときに使えます。止めると上の警告も出なくなります。判定の材料が無くなるためです。

解析中も、再生への影響は測った範囲では見られませんでした。ローカルのSATA SSDでの実測では、13.4GBの解析が追従の最初の8.2秒に重なった実行で、2秒あたりの表示119.9コマ・同期のずれ0.08〜0.09秒と、重ならなかった実行と差がありませんでした。

## 4. 推奨外の形式・デコードの遅れの表示

### 4-1. 推奨外の形式

H.264・ProRes・HAP以外の形式（VP9・AV1・H.265・VP8・MPEG-2・MPEG-4など）を読み込むと、ステータス行とプレイリストに「推奨外の形式」と表示します。専用のデコーダを持たない形式を汎用のデコーダで読んだときも「その他の形式」として表示します。プレイリストの印は`⚠ 形式`です。再生は止めません。判定は「推奨に合っているか」だけで、ビットレートなどは見ていません。形式の名前が判定できないときは表示しません。

### 4-2. 「デコードが追いついていません」

再生中に、2秒あたりに届いた映像のコマ数が、本来届くはずの数の9割を下回ると、ステータス行に次のように表示します。

```
⚠ デコードが追いついていません（2 秒で 74 / 120 枚、この素材で 3 回）
```

表示するだけで、同期の動きは変えません。最後に起きてから10秒で消えます。表示が出ると、そのあと同期が一時的に0.3〜0.7秒ずれることがあります（取り戻しの行き過ぎ）。シーク・一時停止・速度の切替・読み込みの直後、ギャップの中、素材の終わり近くでは判定しません。そこでコマが減るのは正常なためです。

速度ボタンで2×・4×にしたときは、その速度で届くはずのコマ数と比べます。重い素材では4×で出ることがあります（試験では、4K60のProResは4×にしても約3倍速ぶんしか届かなかった）。同期中の速度はほぼ1×なので、本番で気にするのは1×で出る場合です。起きた時刻と数字はログにも残ります（`Decode behind:`の行）。

本番前のリハーサルで出たときは、その素材の差し替えを検討してください。推奨どおりの素材（H.264・キーフレーム間隔1〜2秒）では、実測で一度も出ていません（推奨を1秒目安に変えた後の値も同じ範囲です）。推奨どおりの素材で出る場合は、ログを添えてご連絡ください。

## 5. うまくいかないときの確認順

1. 警告が出ていないか。出ていれば、まず素材をキーフレーム間隔1秒（長くても2秒）で書き出し直す
2. 素材とタイムコードのfpsが揃っているか
3. タイムコードのノイズ。ハムやホワイトノイズが乗っていないか
4. それでも直らない場合は、ログ（`logs\timecodesyncplayer-YYYYMMDD.log`）を添えてご連絡ください

## 6. 既知の制限

CPU内蔵のGPUでは、4K60の素材を実時間でデコードしきれないことがあります。そのあいだ同じ絵が0.3〜0.8秒出続け、長く続くと同期も一時的にずれます（v0.4.8の検証機で、内蔵GPUでは1650秒に16〜37回。外付けのRTX 3080では0回）。4K60の素材は外付けのGPUで動かしてください。

アプリは起動時に、保存されている全画面の出力先ディスプレイがつながっているGPUを使います。出力先が保存されていない（Spoutだけで使う）ときや見つからないときは、Windowsの既定のGPUを使います。ノートPCでは内蔵のGPUになることが多いので、Windowsの「設定 → システム → ディスプレイ → グラフィック」でアプリを「高パフォーマンス」にしてください。出力先やこの設定を変えたらアプリを再起動します。どのGPUを使ったかは、ログの`OutputEngine: 初期化完了`の行の`adapterLuid=`で分かります。Spoutの受け手のソフトも同じGPUにそろえてください。SpoutはGPUをまたいで共有できません。

ギャップに入ったとき、まれに画面のプレビューだけが黒にならないことがあります。全画面の出力とSpoutは黒になります（v0.5.0の検証で数回。原因を調査中）。起きたときはログに`Preview stalled:`が残ります。

キーフレーム間隔が長い素材では、再生中のシークの着地が1〜3秒遅れることがあります。同じ素材で追従中にずれが生じた場合、絵を止めずに再生速度で詰めるため、解消まで数秒から十数秒かかることがあります（ずれ1秒あたり約10秒）。

トラックを切り替えてから最初の絵が出るまで、4K60の実素材で0.7〜0.8秒かかります。ギャップを挟む切替では画面が黒のため見えませんが、挟まない切替では前の絵が残ったままです。切り替えた直後は、新しいトラックが頭から始まります。読み込みにかかった時間ぶんタイムコードより手前から始まり、1秒前後かけて追い付きます。遅れの量は素材しだいです（実測: 推奨どおりの素材で0.05〜0.24秒、キーフレーム間隔が長い4K60の素材で最大1.08秒）。キーフレーム間隔が長い素材では、追い付きに10秒以上かかることがあります。

デコードが一時的に追いつかなくなると、そのあと同期が0.3〜0.7秒ずれることがあります（上の「デコードが追いついていません」が出る場面です）。いずれも数秒で戻ります。以前「10分の連続追従で数回ずれる」と書いていたものも、同じ現象でした。ずれた時刻とデコードが遅れた時刻が、10分間ですべて一致しました。

ビットレートが非常に高いProRes 4K60（1.7Gbps程度）では、まれに読み込みやシークが数秒遅れます。シークのあと新しい位置の絵が2秒以上来ないことが自動試験で59回中9回（日によって0〜27%）、読み込みが終わらないことが同じ素材で数回ありました。原因は分かっていません。以前の版から同じです。

タイムコードが範囲外へ出てクリップの端で止まるとき、ふだんは端から2〜3フレーム先で止まりますが、まれにもう少し先（実測で0.18秒）の絵で止まることがあります。

## 7. GPUとProResのデコード

前提は外付け（RTX級）のGPUです。映像の合成と出力にはDirect3D 11.4が必要で、対応していないPCでは起動時にそのことを知らせ、再生だけを無効にします。CPU内蔵のGPUでは4K60の素材のデコードが間に合わないことがあります（6節）。

ProResは同梱のプラグイン（gst-prores-d3d11）でGPUデコードします。検証して推奨しているのはNVIDIA（RTX級）のGPUです。プラグインはDirect3D 11の汎用のシェーダーで動くので、v0.6.5からは既定（自動）でどのGPUでもGPUデコードします。NVIDIA以外は、検証機のCPU内蔵のGPU（AMD）で確かめた範囲です。内蔵のGPUでは4K60のProResのデコードがCPUより追いつかないことがあり、そのときは画面の「ProRes の GPU デコード」を「無効」にしてください。自動・有効・無効の変更は、アプリの再起動後に反映されます。

GPUデコードに1回失敗すると、その起動の間はProResをCPUでデコードします（アプリの再起動でGPUをまた試します）。どちらで開いたかの手がかりは、画面のメタデータ行のデコーダ名です。`V:proresd3d11dec`ならGPU、`V:avdec_prores`ならCPUです。理由はshimのログ（`logs\tcs-gst-YYYYMMDD.log`）の`prores-gpu:`と`load.skip`・`load.fail`の行に出ます。

GPUデコードのプラグインに必要なのは、Microsoft Visual C++ v14再頒布可能パッケージ（x64）14.50以上（旧称 Microsoft Visual C++ 2015-2022）です。インストーラーは入っていないか古いときだけ導入し、その途中で一度だけ管理者の確認（UAC）が出ます。入っていないときはCPUでデコードします。

4KのProResをCPUでデコードすると、アプリだけで1.5〜1.7GBのメモリを使います（GPUでは約0.7GB）。システムのコミットの空き（タスクマネージャーの「コミット済み」の上限との差）は4GB以上を確保してください。空きが尽きるとデコードのメモリの確保に失敗してアプリが終了することがあります。
