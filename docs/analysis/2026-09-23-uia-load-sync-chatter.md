# UIA 50ms 監査の失敗: 復号の一時的な遅れが同期補正の揺れに増幅される（0.4.8）

作成: 2026-09-23、親。検証機の再現（v0.4.7、LTC 30fps、Continue、ギャップなし、M1/M4/M7、
使用尺 1220/180/250 秒、Spout ON、外部 Spout 受信監査、UIA 読み取り 50ms と 250ms）を、
出力トレース（`events.jsonl`）・精度トレース（`ltc-dispatch`）付きで取り直したものから。

## 症状（UIA 50ms だけで出る）

- `rate catch-up` の開始と終了の反復（前回 31〜91 回）
- 位置停止 100ms 以上、`Playback perf` の 5 秒超の欠落（10〜21 秒）
- 同じ内容の再送 250ms 以上（最長 530ms 前後）
- Spout の受信停止・送信の不足・切断・カウンタの巻き戻りは無い（送信は続いているが中身が変わらない）

UIA 250ms では同じ素材・同じ区間で何も起きない（Codex の A/B/A 3 本ずつ、取り直し 1 本ずつ）。

**UI スレッドは詰まっていない。** 起点は shim 側の復号・コピーの遅れで、UIA 50ms の負荷はその引き金を
引きやすくしているだけ（機構は未特定。下の「残っていること」）。

## UIA の読み取りに副作用は無い

- LTC 表示・位置表示は VM の文字列をそのまま返す（`TextBlock` のバインド）
- 開発機の E2E（`UiaReadSideEffectE2ETests`）: 3 秒間の連続読み取りで、位置照会・シーク・同期判定は
  読まない区間と同じ回数（位置照会 208→212、シーク 0、同期判定 0）。合成 tick・配信・新フレームの採用も同じ
- ただし連続読み取りは UI スレッドの低優先度の処理を遅らせることがある（開発機の 20 秒測定で位置照会が 1231→183）。
  合成・配信は UI スレッドに依存しない

## なぜ揺れが続いたか（増幅の仕組み）

1. **位置の交番**: 復号が追いつかずオーディオが詰まると、パイプラインの位置照会が
   「止まったオーディオ位置」と「クロックから補間した位置」を返し分ける。
   これは 2026-09-19 の [位置の交番](2026-09-19-position-alternation.md) と同じ現象
2. **ゲートの外れ値採用**: `SeekDecisionGate` は弾くたびに系列を消していたため、弾いた直後の外れ値が
   無条件に採用され、1 つおきに外れ値が入った（D37-a/c の守りは単発の跳ねを想定しており、
   持続的な交番には効かない、と 09-19 にも書いてある）
3. **補正が負担を増やす**: 残差に従って速度を 1.1 倍にすると、復号の負担がさらに増える
4. **性能監視の窓**: `PlaybackPerformanceStats` は位置が戻ると黙って窓を作り直していたので、
   交番が続く間は 2 秒の窓が一度も閉じなかった

## 直したこと（0.4.8）

| 変更 | 内容 |
| --- | --- |
| `PlaybackPositionContinuity` | 同じ系列（乱れの回数・世代）の中では位置を後退させない。10ms を超える後退を「不安定」として数える。0.5 秒を超える後退は前の値を外れ値とみなして受け入れる |
| 補正の停止 | 最後の後退から 1 秒間は Smooth 補正を止めて倍率を 1.0 に戻す（停止と再開をログに 1 行ずつ） |
| `SeekDecisionGate` | 弾いた直後のサンプルを無条件に採用しない。弾く前の系列とつながれば続け、弾いた値とつながれば新しい系列（本物の跳びへの反応は従来と同じ 1 サンプル遅れ） |
| `PlaybackPerformanceStats` | 位置が戻っても窓を作り直さない。単調時計。戻りは `Playback position went backward` で別に数える |
| `OutputHoldCounter` | 前の絵を出した tick を「フェンス待ち」「新しいフレーム無し」に分けて、100ms 以上の窓で `Output held:` を出す |
| 終了順 | 出力の停止（GPU worker の停止とリース返却）が確認できないうちは shim を破棄しない |

### 09-19 の案 2（配信 PTS を基準にする）との関係

09-19 は「定常追従中も配信 PTS を基準にする」を案 2 として `steady-delivered-basis` ブランチに
既定 off で置いた（main には入っていない）。今回は**どちらの系列が正しいかを選ばず、交番している間は
補正しない**ことにした。理由:

- 今回の 50ms 回では、配信 PTS そのものが LTC から 170〜270ms 遅れていた（復号が遅れている）。
  配信 PTS を基準にすると補正は 1.1 倍へ振れ、復号の負担をさらに増やす
- 交番が害を出す経路は速度補正（09-19 で「直すのは補正経路の 1 か所」と確定）なので、そこを止めれば増幅は起きない
- 粗い判定（シーク）は後退させない位置で続ける。このトレースで再生すると残差は最大 139ms（許容 200ms の内側）で、余計なシークは出ない

## 残っていること

- **復号が遅れる引き金の機構**: 250ms 回でもフェンス待ち 50ms 以上は 543 回（最長 194ms）あり、
  検証機では M1（59.94fps）の復号がもともと限界近く。50ms で長引く理由（CPU か GPU デコードエンジンか）は
  候補の検証で機材負荷を記録して切り分ける
- 候補でも、フェンス待ちによる Held そのものは機材の余裕しだいで出うる。
  判定は、それが同期の揺れ（catch-up の反復・位置停止・perf の欠落）に波及しないかで見る
