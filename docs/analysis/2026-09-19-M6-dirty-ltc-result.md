# M6 の結果: ダーティーな LTC の限界点（2026-09-19）

**指示書**: `docs/prompts/2026-09-19-M6-dirty-ltc-margin.md`、**設計**: `docs/analysis/2026-09-19-M6-dirty-ltc-design.md`
**方法**: 1 run = 1 条件。レベルは phase で切替、各 run 先頭の clean を基準に**相対判定**。
限界近傍（A の 5/4.5/4dB、C の全幅）は **2 本ずつ**。加工はテスト側のみ、**製品コードは無変更**。

## 0. 結論サマリ（数字）

| 条件 | 試した範囲 | 壊れ始め | 落ち方 | clean 実測（run 内基準） |
| --- | --- | --- | --- | --- |
| A ノイズ | SNR 40 → 4 dB | **4.5 dB**（5.0dB は 100%、4.5dB は 0.8%、4.0dB は 0%） | **急**（0.5dB 幅で約 99 ポイント低下） | 99.6% / 99.2%（r1/r2） |
| B レベル | +3 dBFS → −60 dBFS | **なし**（−60dBFS まで 99.4〜100%） | - | 99.8% |
| C 欠落 | 10 / 50 / 200 / 600 ms・5 秒毎 | **10ms で既に −2pt**（幅に比例、崖なし） | 緩 | 100.1% / 100.0%（r1/r2） |
| D レート | 44.1k→48k、96k→48k | **なし**（clean と同一） | - | 100.2% / 100.0%（r1/r2） |
| E ppm | ±50 / ±100 ppm | **なし**（clean と同一） | - | 100.0% |

**「全条件で問題なし」ではない**: A は明確に壊れ、その位置と形（崖）が 2 run で再現した。

## 1. A ノイズ（付加ノイズ）

- **限界は SNR 5.0 dB と 4.5 dB の間**。r1/r2 とも同じ:
  - clean 99.6 / 99.2% → SNR40〜5dB は 99.0〜100.2%（低下なし）
  - **SNR 4.5 dB: decode 0.8%、clean 0.2%（両 run）**。届いた数フレームは値が完全に化け（誤差 −6×10⁶ms 級）、ギャップ最大 6.1 秒
  - **SNR 4.0 dB: decode 0%（両 run）**
- **壊れ方 = 崖**。SNR 5.0dB（499/500）→ 4.5dB（0〜5/500）→ 4.0dB（0/500）で、成功率がほぼ一段で落ちる。
  デコーダ単体のオフライン探索でも 5.0dB=499/500、4.5dB=5/500、4.0dB=0/500 と同じ崖を確認。
- **現場条件との距離**: 崖は「ノイズ RMS が信号 RMS の約 60%」の水準。現場の SNR 実測値は未取得なので距離は数字では出せない
  （**試した範囲は SNR 40〜4 dB**）。
- 参考: 高 SNR 側 40/30/20/12/6dB はすべて clean と同等で、**6dB（ノイズ RMS ≈ 信号の半分）でも 100%**。

## 2. B レベル（−60dBFS まで余裕）

- clean 99.8% → +3dBFS 99.8%、−6dBFS 99.4%、−20dBFS 99.8%、−40dBFS 100.0%、−60dBFS 99.8%。
  **−60dBFS（振幅 0.001）まで劣化なし**。この範囲ではアプリの捕捉（float32）がそのままデコードする。
- −6dB の 2 サンプルだけ値の跳び（1 フレームが −120 秒相当に化けた）が出たが、p5/p95 は clean と同一で、
  D37-a のゲートにより同期には届いていない（gate_rejected 増加なし）。
- **+3dBFS はクリップしない**: 再生経路（VB-CABLE / 共有モード）がピークを約 0.985 に正規化するため、
  アプリは振幅 1.0 相当のクリーンな信号を受け取る（アプリのログ rms 0.985）。**この経路ではクリップ条件は作れない**（環境の性質）。

## 3. C 欠落（5 秒ごとの無音）

無音幅にほぼ比例して LTC フレームが失われる。**値の化けは増えず、届いたフレームの同期誤差は clean と同一**（p95 36〜43ms、|err|>許容 0%）。

| レベル | clean%（r1 / r2） | ギャップ最大 ms（r1 / r2） |
| --- | --- | --- |
| clean | 100.1 / 100.0 | - |
| 10ms | 98.0 / 98.0 | 154 / 153 |
| 50ms | 97.1 / 96.9 | 153 / 154 |
| 200ms | 94.0 / 93.9 | 305 / 354 |
| 600ms | 85.5 / 86.0 | 710 / 758 |

- 落ち方は**緩**（崖なし、幅に比例）。0.5 秒の外挿上限を超える 600ms でも、復帰後に値の化けは残らない。
- 周期挿入のため 10ms でも各欠落で 1〜2 フレーム失い、−2pt から始まる。

## 4. D サンプルレート不一致（44.1k→48k、96k→48k）

- **両レベルとも clean と同一**（r1 100.2/100.2/99.8%、r2 100.0/100.0/100.0%、跳び 0、gap 0、gate 0）。
  テスト側で 44.1k / 96k の波形を 48k へリサンプル（共有モード変換のモデル）して送出した。
- **「壊れない」が結論**。アプリはレート不一致を検知していない（`LtcAudioMonitor.cs:49` は `new WasapiCapture()` の既定形式をそのまま使用）ため、
  **この結果は「検知機能が無いままでも実害が出ない」ことの根拠**になる。
- 注意: これは OS の SRC そのものの再現ではなく、「変換が挟まっても同期は保たれる」ことの確認。

## 5. E ppm（わずかな速度差）

- ±50 / ±100 ppm とも **clean と同一**（100.0%、跳び 0、gap 0、gate 0、誤差 p95 40〜42ms）。
- 比例制御の理論（一定速度差は吸収され、残差は 50〜100µs = 25fps の 1/400〜1/800）と整合。**試した範囲（±100ppm）で劣化なし**。

## 6. 壊れ方と「手前で警告できるか」

- A は**急**（5.0→4.5dB で 100%→0.8%）、B/C/D/E は**緩または劣化なし**。
- A の崖の手前には**成功率のなだらかな低下が無い**（5.0dB は満点）。デコード率だけでは事前警告は作れない。
- 一方、アプリは既に `LTC audio stats ... peak= rms=` を 2 秒ごとに記録している。
  **crest factor（peak/rms）**はスケール不変で、clean の矩形波は 1.0 付近、ノイズが乗るほど上がる
  （A のログ実測: SNR6dB で peak 0.985 / rms 0.59 → 約 1.67）。**崖の手前を測れる既存量**があり、
  0.4.5-C と同種の警告の材料になり得る（実装は別作業）。
- C は幅に比例して静かに落ちる。欠落幅は既存のギャップ検出で見えるため、警告の必要性は別判断。

## 7. 限界・注意

- ノイズ/レベルは**デジタル波形へ付加**。外部機器・アナログ経路は範囲外（指示書 §6）。
- 判定は各 run の clean 実測基準。clean 自身も窓境界で 1 フレーム前後が欠ける（99.2〜100.2%）。
- トレースは実秒のみで、生の HH:MM:SS:FF を持たない。値の化けは「跳び」で代理測定。
- 現場の SNR・欠落幅・ppm の実測値は手元に無い。余裕の定量には現場側の 1 回の測定が要る。
