# キーフレームを見て着地先を決める（実装計画）

作成: 2026-09-19 03:30、親。前提は `docs/analysis/2026-09-19-seek-cost-endpoint.md`
（コストモデルの回帰: 傾き 0.419 / 切片 0.023 / 残差 RMS 0.032、n=8）。

**0.4.5 には入れない。** 候補 6 は基準を満たしており（M3 4/4 で 4.50〜4.94 秒、上限 5 秒）、
これは 0.4.6 の作業。ただし M3 ×8 で 5 秒超が出た場合は、**これが候補 7 になる**。

## なぜこれ以外に手が無いか

候補 6 の M3 の内訳を検算すると、ゲート待ち 4.90 秒の中身はシーク 3 本
（+0.53 / +1.08 / +3.54 秒）だけで、**速度補正は一度も関与していない**。
したがって:

- **±20% の窓を延ばす案は、この素材では効かない**（速度補正が使われていないため）
- **学習値の優先順位を変える案も、単独では効かない**（1 回目の行き過ぎが原因なので）

効くのは**シークの本数と各シークのコストを減らすこと**、つまり着地先の選び方だけ。

## 数学

`cost(t) = c × (t − k(t))`、`k(t)` は t の直前のキーフレーム、`c ≈ 0.42`。
着地したときの誤差は `error(t) = t − (ltc + cost(t))`。

区間 `[k_i, k_{i+1})` の中で `error` は **傾き (1 − c) = 0.58 の単調増加**。
連続かつ単調なので、区間ごとに見るのは **3 つ**:

| 候補 | 値 |
| --- | --- |
| **厳密解** `t* = (ltc − c·k_i) / (1 − c)` | その区間に入っていれば `error = 0`。入っていれば即採用 |
| `t = k_i`（キーフレーム直上） | `error = k_i − ltc` |
| `t → k_{i+1}⁻`（次のキーフレーム直前） | `error = k_{i+1} − ltc − c × gap_i` |

**厳密解を先に見ること。** `error` は区間内で連続なので、端点の符号が変わるなら**内部に厳密解がある**。
（当初この文書は「候補は端点だけで尽きる」と書いていたが誤り。端点は `error` の範囲を与えるだけで、
0 がその範囲に入るなら内部に解がある。）

厳密解がどの区間にも入らないことはありうる。`error` が区間の境目で不連続に跳ねるためで、
M3・ltc = 7.411 がまさにそれ。そのときだけ端点の中から `|error|` 最小を選ぶ。**同点なら負（足りない側）。**

M3・ltc = 7.411（キーフレーム 3.000 / 9.633）での検算:

- `t = 9.633` → error = **+2.222**（行き過ぎ）
- `t → 9.633⁻` → error = 9.633 − 7.411 − 0.42 × 6.633 = **−0.564**（足りない）

**選ばれるのは後者。** いまの `ltc + maxGap × 0.42 = 10.197` は前者側に落ちるので +2.5 秒行き過ぎる。

## 実装

### 1. shim: キーフレーム列を返す

`tcs_scan_gop` は `GopScanCtx::key_times` を集めてから統計に畳んでいる。列を捨てずに返す。

**既存の `tcs_scan_gop` は変えない**（アプリ側に `EntryPointNotFoundException` の
フォールバックがあり、署名を変えると黙って壊れる）。新しい輸出を足す:

```c
/* out_times に最大 capacity 個のキーフレーム時刻（秒、昇順）を書き、
 * 実際の数を out_count に返す。capacity を超える場合は out_count に必要数を返し、
 * out_times には何も書かない（呼び出し側が諦めるか、確保し直す）。 */
TCS_GST_API int tcs_scan_gop_ex (const char* utf8_path, int32_t budget_ms,
                                 TcsGopScan* out,
                                 double* out_times, int32_t capacity,
                                 int32_t* out_count);
```

**密な素材の扱い**: ProRes は全フレームがキーフレーム（4K60 の 12 秒で 720 枚、
300GB なら数千万枚）。列を返しても意味が無い（どこへ飛んでもコストがほぼ 0）。
**上限は 65536 枚**とし、超えたら列を返さない。アプリ側は「列が無い = 密 = 先行量 0 でよい」
と解釈する。中央値ギャップが小さい素材では、そもそも先行補償が要らない。

### 2. アプリ: 列を持ち回る

- `GopScanResult` に `double[] KeyframeTimes`（空配列可）を足す
- `GopScanCache` はそのまま（record に足すだけ）
- `MainWindow.UpdateGopScanWarning` で `_syncService.SetSeekKeyframes(times)` を呼ぶ
  （`SetSeekCostHintSeconds` と同じ場所・同じガード）

### 3. 目標選択を純関数にする

```csharp
internal static class SeekTargetPlanner
{
    /// 着地誤差が最小になる目標を返す。列が空なら null（呼び出し側は従来の見積もりを使う）。
    internal static double? Choose(double ltcSeconds, IReadOnlyList<double> keyframes,
                                   double costPerGapSecond);
}
```

**純関数なので単体テストが書ける。** 受け入れ試験は M3 の実測キーフレーム列
（0.000, 3.000, 9.633, 12.867, 13.317, 13.784, 16.100…）と ltc = 7.411 で、
**戻り値が 9.633 のすぐ下、誤差 −0.564 になること**。

### 4. 呼び出し側

`TimecodeSyncService` の先行量計算を差し替える。**列があれば `Choose`、無ければ従来どおり**。
`SeekTargetLookaheadSeconds` は「LTC への加算値」なので `Choose(...) − ltc` を渡す。

## 注意

- **`MaxSeekCostHintSeconds` の上限は不要になる**。コストが推定値でなく計算値になるため
- **係数 `c` は素材ごとに違う可能性がある**。M3 の 1 本でしか回帰していない。
  腕の長い M2 / M4 で 2 本取ってから確定する（検証機に依頼済み、0.4.5 の後）
- **`error` が最小でもゼロにはならない**（不動点が存在しないため）。残差は速度補正で詰める。
  **ここで初めて `LandingWindow` の延長が効く** — この 2 つは対で入れること
- 目標が**現在位置より後ろ**になる場合がある（行き過ぎている状態）。後ろ向きシークは高くつくので、
  その場合は速度補正（減速）で済ませられる大きさかを先に見る
