# 位置の交番（再生速度が ±10% で往復する件）

作成: 2026-09-19 04:15、親。検証機の実測（候補 6・M3・4 回目、`sync.evaluate` 231 件 /
`gst.position` 1,585 件）から。**利用者が以前から報告していた「20 Hz くらいのレートのふらつき」
「18 秒ほど 10% くらい速い」に対応する現象**。

## 症状

同期判断に使う位置が、**数ミリ秒差で 0.4 秒ちがう 2 つの値を交互に返す**。

```
時刻        位置       LTC-位置  reason            shadowRate
2932.051   52.844157                               （配信PTS 52.483）
2932.055   52.592492                               ← 4 ms で 0.25 秒 戻る
2932.149   52.945445                               （配信PTS 52.500）
2932.156   52.615721                               ← 7 ms で 0.33 秒 戻る
```

8.4 秒で **50ms 以上戻った問い合わせが 1,585 件中 140 件**（戻り幅 中央 0.426 秒・最大 0.704 秒）。
結果、残差が交番し、再生レートが **0.90 と 1.10 を往復**して誤差が 0.313 → 0.553 秒と積み上がる。
**その 8.42 秒のうちレート ≥1.09 が 46%、≤0.91 が 30%、ほぼ等速は 12% だけ。**

同じ条件の 8 回のうち **2 回で発生、合格した 6 回には符号反転が 1 件も無い。**

## 否定された説明

| 説 | 実測 |
| --- | --- |
| LTC が揺れている | **否定**。8.42 秒で 0.9989 倍速・単調増加、逆行なし（231 サンプル） |
| 出所が切り替わっている（パイプライン位置 ↔ 配信 PTS） | **否定**。`evalBasis` は 231 件すべて `pipeline`、世代も全件一致 |
| `positionFallback` が絡む | **否定**。当該 8 秒間に 1 件も無い（実行全体でも 5 件、時刻が離れている） |
| 絵が止まっている | **否定**。`compose.publish` 510 件、間隔 中央 16.7ms・最大 23.5ms、33ms 超のギャップ 0 件 |
| レート変更のセグメント書き換えが位置をずらす | **判定できない**。レート変更は 50ms 刻みで常時起きており、どの逆行も「直前 70ms 以内にレート変更がある」ことになる。**検定として成立しない**（下の節を参照） |

## 診断

**注意: 最初に書いた「音声シンクとの差 0.25 秒」は誤りだった。撤回済み。**
最初の 2 点（PTS+0.11 と PTS+0.36）だけを見て「2 つの固定された出所の差」と読んだが、
検証機が分布を取り直したところ:

| 系列 | 実測 |
| --- | --- |
| **低い側** | PTS + 0.106〜0.116。**中央 0.102、四分位 0.094〜0.110 で安定**。ただし**同じ値が 50〜160 ms 据え置かれてから飛ぶ**（フレーム境界に量子化） |
| **高い側** | **一定オフセットではない**。中央 0.548、**四分位 0.428〜0.636**。0.2 秒で +0.331 → +0.497 と**単調に伸びる**（低い側の約 1.85 倍の速さで離れる） |

**固定値でない以上、「2 つの固定された出所」では説明できない。2 点から機構を決めたのが誤り。**

現在の読み（検証機と一致）:

- **低い側 = バッファ由来**（最後に届いたフレームの時刻。フレーム境界に量子化される）
- **高い側 = クロックからの外挿**（`最後の同期点 + 経過 × レート`）

basesink は位置をこの形で外挿する。**レートを 50 ms ごとに変えている**ため、外挿の基準点と
レートの組み合わせ次第で値が走る。**同じシンクが問い合わせのたびに「外挿値」と
「最後のバッファの値」を返し分けている**形でも説明がつく。ビンが複数シンクの答えを
畳み込んでいる可能性も否定はできないが、**どちらにせよ「外挿している側」が悪さをしている。**

なお shim は位置を `player->pipeline`（ビン）に問い合わせている（`get_time_pos_locked`）。
映像シンクへの参照 `player->appsink` は既にあるので、問い合わせ先を絞るのは 1〜2 行で済む。

### レート変更との時間対応は検定にならない

「逆行の直前にレート変更があるか」を数えても意味がない。**レート変更は 50 ms 刻みで常時
起きており（1,609 サンプル中 534 件が 1.000 以外）、何を選んでも直前 70 ms 以内に入る。**
「最初のレート変更より前に逆行があるか」も、追従開始直後からレート補正が始まるため分離できない。
**この問いの立て方が悪かった。**

### 実害: 8 秒間ずっと 10.2% 速い

**指標の取り方に注意がいる。**「PTS の進み ÷ 実時間」を**追従全体で平均すると 1.00 に埋もれる**
（速い区間と遅い区間が打ち消し合う）。**8 秒のスライド窓の最大値**を見ること（検証機の指摘）。

| 候補 6・M3 | 符号反転 | 逆行 | 全体の比 | **最悪 8 秒の比** |
| --- | --- | --- | --- | --- |
| 4 回目（失敗） | 64 | 163 | 0.9983 | **1.1015** |
| 3 回目（合格） | 0 | 0 | 0.9987 | 1.0016 |
| 7 回目（失敗） | 0 | 4 | 1.0046 | 1.0251 |

**失敗回は 8 秒間ずっと 10.2% 速く流れている。**全体平均の 0.9983 を見ていたら見逃していた。
`compose.publish` は 16.7 ms 間隔・33 ms 超のギャップ 0 件なので、**絵は滑らかなまま速い**。

**利用者の「10% くらい速い」は体感ではなく、実際の再生速度だった。製品の欠陥として明確。**

（当初ここには「1.049 倍速」と書いていた。8.45 秒の固定窓での平均で、**窓の取り方に依存する弱い数字**
だった。スライド窓の最大に差し替えた。）

## 直し方の候補（0.4.6）

**環境変数では届かない。** フェーズ 2（`TCS_SYNC_POSITION_FEEDBACK`）は `unlanded` のときだけ
配信 PTS を使い、**着地済み＝定常追従中は `sample.Seconds`（交番している値そのもの）**を返す。

検証機が既存トレースで裏を取った（候補 6・4 回目の全 1,609 サンプル）:

```
pipeline   1517 件   うちシーク発行から 2.5 秒以内: 74 件 (5%)
delivered    92 件   うちシーク発行から 2.5 秒以内: 92 件 (100%)
```

**`delivered` は 92 件すべてがシーク直後。** 交番が起きている定常追従中は 100% `pipeline`。

| | 内容 | 難点 |
| --- | --- | --- |
| 1 | shim の位置問い合わせを、ビンではなく `player->appsink` に絞る（参照は既にある。1〜2 行） | **外挿しているのがどの要素かまだ分かっていない。**appsink は `sync=true` なので位置の意味はあるが、basesink 自身も外挿するので直るとは限らない |
| 2 | **定常追従中も配信 PTS を基準にする**（フェーズ 2 の枝を着地後にも広げる） | 配信 PTS は 17.0 ms 刻みで単調と実測できており**入力としては確実**。ただし外挿の上限（フレーム 2 枚 = 33ms）が定常でも妥当かは別途詰める |

**2 のほうが確実。** ただしどちらも全条件の再検証が要るので 0.4.5 には入れない。

## 0.4.5 との関係

**この欠陥は 0.4.5 で入ったものではない。** 根拠は 2 つ:

1. 位置の問い合わせ（`gst_element_query_position(pipeline, ...)`）は以前からこの形
2. **速度補正（Smooth）は v0.4.0 から既定**（`6307ec5`、2026-09-15。`git tag --contains` で
   v0.4.0 / v0.4.1 / v0.4.2 に含まれることを確認）。振動の経路は 0.4.5 より前から存在する

ただし **D37-b で「追従中の実際のずれを、シークではなく速度補正で詰める」ようにした**ため、
**速度補正を通る場面が増えている**。同じ測定の揺れが**以前より表に出やすくなっている**可能性はある
（そこは未測定。0.4.3 で同じ素材を回さないと言えない）。

0.4.5 では**既知の制限として書き、直さない**。環境変数では届かず（フェーズ 2 は着地未確認の間だけ）、
直すには定常追従中の位置の出所そのものを変えることになり、全条件の再検証が要るため。

**フェーズ 2（`TCS_SYNC_POSITION_FEEDBACK`）では直らない。** `PlaybackPositionFeedback` は
`unlanded` のときだけ配信 PTS を使い、**着地済みは `sample.Seconds`（交番している値そのもの）**を返す。
検証機の「`evalBasis` は 231 件すべて `pipeline`」が、その枝に一度も入っていないことを示している。

## 0.4.6 の設計: 開発機の実測で方針が固まった（2026-09-19 04:25 追記）

**開発機で V3 精度ハーネスを回し、同じトレースで比べた。交番は開発機では起きていない。**

| | 開発機（V3、720p/1080p、短 GOP） | 検証機（M3、4K60、最大ギャップ 6.6 秒） |
| --- | --- | --- |
| 位置 − 配信 PTS | **中央 0.001 s**（p25 0.001 / p75 0.004 / 最大 0.043） | 低い側 +0.102 / 高い側 +0.55（四分位 0.428〜0.636） |
| 50ms 以上の逆行 | **10 件。いずれも約 9.9 秒＝シーク由来**（V3 は 10 秒跳ぶ位相を含む） | **140 件**、戻り幅 中央 0.426 s |

（`gst.position` 9,724 件。`value` は `RunningNs / 1000` なので**マイクロ秒**。単位を間違えると全部 0 に見える。）

### これで分かること

1. **交番は常時起きているのではない。** 健全な条件では位置と配信 PTS は **1ms 以内で一致**する
2. **したがって「配信 PTS とパイプライン位置の間に約 0.1 秒の一定のずれがある」は一般には成り立たない。**
   前の版でここに「先に 0.1 秒が何かを測れ」と書いたが、**その 0.1 秒自体が異常時だけの値**だった
3. **案 2（定常追従中も配信 PTS を基準にする）の副作用は小さい。**
   健全なときは両者が 1ms 以内で一致するので**切り替えても何も変わらず**、
   異常時だけ「まともな側」を選ぶことになる

**案 2 を採る。** 残る設計上の詰めは外挿の上限（いまはフレーム 2 枚 = 33ms）が定常でも妥当かだけ。
配信は 16.7ms 間隔なので、上限 33ms は「1 回分の取りこぼしまで許す」形で妥当に見える。

### 開発機で再現しない以上、直したことの確認は検証機でしかできない

**開発機では交番が出ないので、修正の効果は開発機では測れない。**
0.4.6 では「直した候補を検証機で M3 に当てて、符号反転と最悪 8 秒の比が落ちるか」で見る。
**開発機で緑なのは前提条件であって、効果の証拠にはならない。**

  これが無ければ「絵が止まる欠陥」として全く違う方向を掘っていた

- D37-a/c の「中央値＋連続超過」は**単発の跳ね**を想定した守りで、
