# ダーティーな LTC 信号に対する現状の耐性（コード確認、2026-09-18）

**きっかけ（利用者、2026-09-18）**: 「DAW の実装ではタイムコードで速度を出す実装になっているという話がありました。
いまは内部でタイムコードを生成したかなりクリーンな状態でテストを行なっていて、現場だとダーティーな信号が来る
可能性も考えられます。そのような場合で速度を出すのを実装していた場合効果は発揮されますか？」

**この問いは正当である。** 0.4.5 で「LTC の速度推定（案 1）を実施しない」と決めた根拠（M2）は、
**LTC 生成と受信が同じ PC クロックを共有する VB-CABLE ループ**での測定であり、
**外部機器・アナログ経路・ノイズを一切含まない**。

---

## 1. 速度推定が効きうる場面を 3 つに分けて検討する

### 1-1. 外部機器と PC の時計がずれている → 速度推定は要らない（計算で言える）

制御則は `rate = 1 + clamp(誤差 / 1.0秒, ±10%)`。相手が `d`（分数速度）ぶん速い場合、
定常状態は「レート補正 = ドリフト」で釣り合うので、**残る誤差は `d` 秒**。

| 相手のずれ | 残る定常誤差 | 25fps の 1 フレーム（40ms）比 |
| --- | ---: | ---: |
| 50 ppm（民生クリスタル相当） | **50 µs** | 1/800 |
| 100 ppm（かなり悪い） | **100 µs** | 1/400 |

**比例制御は一定の速度差を自動的に吸収する。** 速度推定が消せるのはこの数十 µs だけ。
**この結論はクリーンな測定に依存しない**（制御則からの帰結）。

### 1-2. 信号が途切れる → すでに同等の仕組みがある

Ardour のフライホイールに相当するものとして、**サンプルクロック基準の外挿（上限 0.5 秒）**と
信号断の扱い（Stop / RunThrough）がある。違いは外挿に使う速度が「実測値」か「1.0」か。

**相手が 1.0 倍で走る限り、0.5 秒の外挿での差は 25 µs**（50 ppm の場合）。
差が出るのは**相手が 1.0 倍以外で動くとき**（DAW のスクラブ、バリスピード、テープの立ち上がり）。
これは精度ではなく**機能**の問題で、「その用途を支えるか」という別の判断になる。

### 1-3. ビット化けした値が来る → 現場リスクだが、対策はすでにある

#### 現状のデコーダの防御（`LtcDecoder.cs` 確認）

| 段 | 内容 | 実装 |
| --- | --- | --- |
| 1 | **同期ワード 0xBFFC の一致**（16 ビット） | `:55`、`:165` |
| 2 | **範囲チェック**（フレーム ≤ 29、秒 ≤ 59、分 ≤ 59、時 ≤ 23） | `TryParseFrame` |
| — | パリティ検査 | **無し**（SMPTE 12M のそれは極性補正用で誤り検出力はほぼ無いため妥当） |
| — | 連続性の検査 | **無し** |

**したがって「範囲内に収まる 1 ビット化け」は素通りする。**
例: フレーム値の bit 3 が化けると 1 → 9 になり、25fps で **320ms** ずれた値が有効として通る。

#### その先で止まる（D37-a）

D37-a の物理的妥当性フィルタが、**LTC 40ms の間に位置が動ける上限（約 88ms）**を超える変化を弾く。
320ms の跳びは同期判定に届かない。加えて中央値フィルタがあるので、**1 枚の化けた値ではシークが出ない**。

DAW が「速度の妥当性で弾く」のと**同じことを誤差側で実装済み**、という関係になっている。

## 2. 結論

**速度推定を実装しても、1-1〜1-3 のどれも改善しない。**
1-1 は比例制御が吸収し、1-2 は既存の外挿で足り（1.0 倍前提の範囲で）、1-3 は D37-a が等価の防御を持つ。

**ただし、指摘の本質は「速度推定」ではなく「ダーティーな信号を一度も試していない」ことにある。そこは穴である。**

## 3. 試していない失敗モード

| # | 内容 | 現状 |
| --- | --- | --- |
| A | **ノイズでデコードが間欠的に失敗する** | 未測定。信号断の試験は**きれいな信号を人為的に切って**行っている |
| B | レベルが低い／歪んでいる | 未測定 |
| C | **サンプルレートの不一致**（共有モード WASAPI のリサンプリング） | **アプリは検知していない**（`LtcAudioMonitor.cs:49` は既定のまま） |
| D | 表示用タイムコードに化けた値が一瞬出る | 生値を表示。同期は守られるが表示は守られていない |
| E | 外部機器のアナログ経路 | 未測定（実機が要る） |

**A〜D はソフトウェアで作れる**（ノイズ付加、レベル操作、間引き、±ppm のリサンプリング）。
E だけ外部機器が要る。

**推奨: 速度推定を推測で実装するより、ダーティー信号試験を回して何が実際に壊れるかを見る。**
既存の計器は使える（D37-a の「弾いた標本数」、デコード成功率、`decodedFrames`/2 秒）。
