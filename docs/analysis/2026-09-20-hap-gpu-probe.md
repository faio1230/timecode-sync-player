# HAP を GPU 直接経路で扱えるか（試作の測定、2026-09-20）

[docs/HAP-GSTREAMER-INVESTIGATION-2026-09-11.md](../HAP-GSTREAMER-INVESTIGATION-2026-09-11.md) の「次にやるなら 1」。
**製品コードには触れていない。**試作は `scripts/HapProbe`（独立した実行ファイル）。

## 結論

**3 つの合格条件をすべて満たした。本実装へ進んでよい。**

| 合格条件（測定前に決めたもの） | 結果 |
| --- | --- |
| 1 コマの「展開＋GPU への転送」が中央 8ms 以下・最大 12ms 以下 | **中央 0.2〜2.2ms / 最大 0.5〜5.7ms**（4K60 の最悪条件で中央 2.0ms） |
| 60 秒連続で落ちコマ 0・描画間隔の最大 20ms 未満 | **48 条件中 47 条件で落ちコマ 0**（下の「一度だけ出た詰まり」参照） |
| 読み出しが 60fps に追いつく | **必要 475MB/s に対し 3,577MB/s（7.5 倍）**。キャッシュを通さない読み出しで測定 |

**推奨する構成**: **shim の中で BGRA に展開してから既存のリングへ載せる**（経路 1）、転送は **DEFAULT テクスチャへ直接書く**（UpdateSubresource）。
経路 2（圧縮のままリングに流す）との差は 1 コマあたり 0.05ms で、**測定上ほぼ差が無い**。それなら、リングと合成の約束を変えない経路 1 のほうが、壊れる範囲が shim の中に収まる。

## 測ったもの

| 条件 | 内容 |
| --- | --- |
| 素材 | ノイズ（圧縮が効かない＝1 コマが最大）と実写（Snappy が効く＝展開が最も重い）の 2 系統 |
| 解像度・変種 | 4K60 / 1080p60 × HapQ（YCoCg+BC3）/ Hap1（BC1） |
| 経路 | 1: GPU で BGRA に展開してからキャンバスへ合成 / 2: 圧縮テクスチャのまま合成でサンプリング |
| 転送 | DEFAULT へ直接（UpdateSubresource）/ 中継バッファ経由（STAGING に Map → CopyResource） |
| 展開 | 単体 / 並列（かたまり分割がある素材のみ効く） |
| 長さ | 1 条件 60 秒（3,600 コマ）、合計 48 条件 |
| 機材 | RTX 3070 / NVMe SSD |

**表示は 60Hz を自前で刻んだ**（画面のリフレッシュレートに左右されないため）。締め切りに間に合わなかったコマを落ちコマとして数えた。

## 1 コマあたりの時間（中央値 / 最大値、ミリ秒）

| 素材 | 1 コマの大きさ | 展開 | 転送 | 1 コマ合計 |
| --- | --- | --- | --- | --- |
| 4K60 HapQ（ノイズ） | 7.91 MB（圧縮なしで格納） | 0.50 / 1.5 | 0.52 / 1.9 | 1.06 / 3.5 |
| 4K60 HapQ（実写） | 0.92 MB → 7.91 MB | **1.41 / 3.9** | 0.53 / 1.8 | **2.00 / 5.7** |
| 4K60 Hap1（ノイズ） | 3.96 MB | 0.24 / 1.7 | 0.26 / 1.6 | 0.56 / 2.8 |
| 1080p60 HapQ（実写） | 0.21 MB → 1.98 MB | 0.32 / 1.4 | 0.14 / 1.0 | 0.51 / 2.1 |
| 1080p60 Hap1（ノイズ） | 0.99 MB | 0.06 / 0.6 | 0.07 / 0.4 | 0.18 / 1.0 |

- **ノイズ素材は「1 コマが大きい」最悪ケースだが、「展開が重い」最悪ケースではない。** 圧縮が効かないため二段目が「無圧縮」で格納され、展開はメモリのコピー（7.91MB を 0.50ms＝毎秒 15.8GB）になる。**展開時間の最悪ケースは実写**（0.92MB から 7.91MB を 1.41ms＝毎秒 5.5GB）
- 経路 1 と経路 2 の差は 1 コマ 0.05ms 以内。転送の直接と中継の差も 0.05ms 以内
- **並列展開は効果が測れていない。** ffmpeg が作る HAP は 1 コマ 1 かたまりで、分割された素材が手元に無いため

## 読み出し（キャッシュを通さない測定）

| 素材 | 1 コマ | 60fps に必要 | 実測 | 余裕 |
| --- | --- | --- | --- | --- |
| 4K60 HapQ（ノイズ） | 7.91 MB | 475 MB/s | 3,577 MB/s | 7.5 倍 |
| 4K60 HapQ（実写） | 0.95 MB | 57 MB/s | 2,058 MB/s | 36 倍 |
| 4K60 Hap1（ノイズ） | 3.95 MB | 237 MB/s | 4,151 MB/s | 17 倍 |

**HAP は絵柄によって必要な帯域が 8 倍変わる**（実写 57MB/s、ノイズ 475MB/s）。**最悪ケースの 475MB/s は、HDD では足りない。**

## GStreamer 側（qtdemux）の速度

試作は GStreamer を通していないので、**分解（qtdemux）が 60fps に追いつくか**を別に測った。
帯域の最悪ケース（ノイズ 4K60 HapQ、1 コマ 7.91MB、180 コマ＝3 秒ぶん 1,424MB）を
`filesrc ! qtdemux ! fakesink sync=false` で流し切った時間:

| 回 | 所要 | コマ/秒 | MB/s |
| --- | --- | --- | --- |
| 1 回目（キャッシュに乗っていない） | 0.66 秒 | 272 | 2,153 |
| 2 回目 | 0.51 秒 | 355 | 2,809 |
| 3 回目 | 0.50 秒 | 363 | 2,875 |

**必要な 60 コマ/秒（475MB/s）に対して 4.5〜6 倍**。分解は律速にならない。

**それでも残る未確認**（速度の問題ではなく、つなぎ込みの問題）:
- appsink で受けたバッファをそのまま展開に渡せるか（余計なコピーが増えないか）
- 分解・展開・合成を別スレッドで回したときの受け渡しと、リングへの書き込み
- シーク（HAP は全コマがキーフレームなので軽いはずだが、未確認）

これらは測定ではなく**最小の実装を通して確かめる**のが早い。本実装は「まず最小の経路を shim に通して、同じ合格条件で実機で測る」形から始める。

## 一度だけ出た詰まり

48 条件のうち 1 条件（4K60 HapQ 実写・経路 1・直接転送・単体展開）で、**3,600 コマ中 7 コマが締め切りに間に合わず、1 コマの最大が 107.81ms** になった。
- その回の展開の最大は 3.62ms、転送の最大は 1.38ms で、**時間はどちらでもない場所（合成・表示・実行環境）で消えている**
- **同じ条件を 60 秒 × 8 通り測り直すと、落ちコマは 0 件**だった。再現しない
- 原因は特定していない。本実装のあと、長めの連続再生で改めて見る

## 絵が正しいことの確認

速度だけでは足りないので、合成した絵を PNG に書き出し、参照（同じ素材を ffmpeg で展開したもの）と比べた。**色バー・斜めのグラデーション・焼き込みのタイムコードが一致**し、HapQ の YCoCg の戻し方も正しいことを確認した。

この確認の過程で、試作側の誤りが 2 つ見つかっている。**どちらも速度には影響しないため、絵を見なければ「合格」と報告していた。**
1. 表示（Present）の後に読み戻していた（FlipDiscard では表示後の中身が保証されない）→ 真っ黒
2. 全画面クアッドの面の向きが裏になり、既定の設定で捨てられていた → 真っ黒

## 本実装へ持ち越す注意

- **かたまり分割のある素材で測れていない。** 解析は実装済みだが、実データで通していない。本実装では、分割された素材を入手して確かめる
- **HapM / HapA / Hap7 / HapH は測っていない。** まず HapQ と Hap1 を対象にする
- **GPU 側の所要時間は分離して測っていない。** 「1 コマが 16.7ms に収まる」ことは確認したが、内訳のうち GPU の取り分は未測定
- 試作は GStreamer を通していない（コマは `gst-launch` で事前に切り出した）。**本実装では demux・時計・シークが加わる**
- 機材は RTX 3070 と NVMe。**現場の機材が弱い場合は、この余裕がそのまま縮む**

## 手順の記録

```powershell
# 素材（ノイズ＝帯域の最悪ケース）
ffmpeg -f lavfi -i "nullsrc=s=3840x2160:r=60" -vf "geq=random(1)*255:random(1)*255:random(1)*255" `
  -frames:v 60 -c:v hap -format hap_q src.mov
# 素材（実写＝展開の最悪ケース）は手持ちの動画を scale して同じように書き出す
# 圧縮されたコマを 1 コマ 1 ファイルに切り出す（GStreamer が HAP を分解できることの確認も兼ねる）
gst-launch-1.0 -q filesrc location=src.mov ! qtdemux ! multifilesink location=frames/f%05d.hap
# 測定（48 条件で約 48 分）
dotnet run -c Release --project scripts\HapProbe -- --frames <frames の親> --seconds 60
dotnet run -c Release --project scripts\HapProbe -- --frames <frames の親> --diskread
dotnet run -c Release --project scripts\HapProbe -- --frames <frames の親> --set 1080_hapq_real --dump <出力先>
```
