### 提案の前提との差（重要）

| 提案文の前提 | 実際 |
| --- | --- |
| 入力サンプル位置とコールバック到着時刻から LTC の時刻を推定する | **実装済み**（`LtcAnchorFilter`。ただし WASAPI のタイムスタンプではなく自前の最小値フィルタ） |
| 受信後の経過時間を加えて現在位置を推定する | **実装済み**（`age`。100ms タイマーの再送時も取り直す） |
| 小さなずれをレート変更で補正する | **実装済み**（比例制御 ±10%、着地直後のみ ±20%） |
| 大きなずれをシークで補正する | **実装済み**（粗いデッドゾーンと Jump の 2 段） |
| 音声入力は NAudio の WasapiCapture | **そのとおり**（バッファ長・共有/排他はコードで指定しておらず NAudio 既定） |
| 再生は GStreamer | **そのとおり** |

**つまり「LTC をサンプル位置で時刻付けし、経過時間で外挿する」段は終わっている。** 足りないのは次節。

## 3. 他システムが何をしているか（一次資料で確認したもの）

### Ardour の LTC スレーブ（`libs/ardour/ltc_slave.cc`、`transport_master.cc`）

| 論点 | Ardour の実装 |
| --- | --- |
| 時刻付け | **エンジンの単調サンプル位置**。libltc が返す `off_end + 1` を採用。ソース中のコメントが「これは LTC が表している時刻ではなく、自分のオーディオクロック由来だ」と明示 |
| 位置 | デコード完了時点でそのフレームは過ぎているので、**次のフレームへ進めてから**換算（逆再生時は戻す） |
| 速度 | **2 点の差分商だけ**。`ltc_speed = (ltc_sample − current.position) / (cur_timestamp − current.timestamp)`。**PLL も PID も移動平均も無い**。あるのは「1.0 から 0.1% 以内なら 1.0 に丸める」デッドゾーンと、「10 倍を超えたら 0 にする」クランプのみ |
| 受け渡し | `(position, timestamp, speed)` の 3 つ組をロックフリーで渡し、**消費側が `pos = position + (now − timestamp) × speed` で外挿**する |
| ロック判定 | fps 検出済み かつ 連続 2 フレーム受信でロック（マニュアル）。内部は `delayedlocked < 5` |
| 不連続 | 次に来るはずのフレームと比較して外れたら検出 → 位置を保ったままリセット |
| 信号ロス | **1 秒**のフライホイール。超えたら「**位置は動かさない**」とコメントして return |
| 遅延補償 | **入力側のみ**。`ltc_sample += 入力レイテンシ`。再生側は明示的に無視（`if (playback) return;`）。TV 規格ごとのフレーム境界補正も別途 |

### WASAPI の入力タイムスタンプ（Microsoft）

- `IAudioCaptureClient::GetBuffer` は **パケット先頭の `devicePosition`（ストリーム先頭からのフレーム数）と `qpcPosition`（100ns 単位に換算した QPC）** を返す
- 妥当性はフラグで示される。`TIMESTAMP_ERROR`（時刻が不確か）、`DATA_DISCONTINUITY`（前パケットと位置が連続しない。Windows 7 以降は**取りこぼし検出**に使える）、`SILENT`
- パケットが無いときは **これらの出力変数に書き込まれない**
- ドライバの責務として「Windows に推測させず、実際のストリーム位置のタイムスタンプを提供すること」「DSP を挟む機器では、転送時刻ではなく実際の遅延を織り込むこと」と明記。**機器・ドライバ依存**
- 共有モードの既定バッファは Windows 10 以降 **10ms**。`IAudioClient3` でより小さい周期を選べる
- **NAudio の `WasapiCapture` は 2 引数の `GetBuffer` を呼んでおり、この 2 つを捨てている。** ただし `AudioCaptureClient` には 4 引数のオーバーロードが public で存在し、`MMDevice.AudioClient` から到達できる → **自前のキャプチャループを書けば取得できる**

### Nuendo / Cubase（Steinberg）

- 同期を **speed / position / phase の 3 要素**として定義
- **LTC は「位置情報に使うもの」**。速度と位相に使うのは「他にクロック源が無い場合の最後の手段」と明記
- 速度の基準は**単一でなければならない**（ワードクロック、映像基準信号）。劇場の実例では「位置は 9-Pin / MTC、速度はワードクロック」と経路が分かれている
- ASIO の低遅延設定と「外部クロックに従う」設定は**別の設定項目**（ドライバ側でクロック源を選ぶだけでは足りず、ホスト側にも通知が要る）

**このアプリは「外部ワードクロックが無い」構成に該当する。** したがって位置合わせは LTC でできるが、**長時間の速度一致はソフト側の補正に頼らざるを得ない**。これは Ardour のマニュアルが「サンプルクロックが同期していないなら varispeed で調整するしかない」と述べているのと同じ構造。

## 4. 改善案（重要度順）

### P1. LTC を「位置・時刻・速度」の 3 つ組にする（最優先）

- **事例**: Ardour の `SafeTime`（position / timestamp / speed）と、消費側の外挿 `pos = position + (now − timestamp) × speed`。速度は差分商のみでフィルタ無し
- **考え方**: 「いま何秒か」だけでなく「**どれだけの速さで進んでいるか**」を持つ。入力の揺れは速度の推定値に吸収させ、制御は速度と位置の差に対して行う
- **現状との差**: いまは速度を持たず、外挿は暗黙に速度 1.0。残差の比例制御だけなので、**入力の揺れと本当のドリフトを区別できない**（実測 D の往復はこれ）
- **期待できる改善**: 往復の抑制、長時間ドリフトの可視化（PC と LTC 源の時計差が ppm で出る）、停止・ジャンプ・ロックの判定を 1 か所に集約できる
- **解決しないこと**: 表示側の遅れ（G）、フレーム量子化（C の 60fps -13ms）
- **負担**: 中。推定自体は数行だが、状態（ロック・フライホイール・不連続）の扱いを整理する必要がある。**Ardour がフィルタを使っていない**点は重要で、凝った制御は不要
- **採用判断に必要な計測**: 速度推定値の分布（定常で 1.0 ± 何 ppm か）、10 分・60 分のドリフト、ジャンプ後の追従時間

### P2. 表示済みフレームの PTS を同期へ戻す（または定常遅れの自動測定）

- **事例**: Ardour は**入力側のレイテンシのみ**補償し、出力側は補償しない（明示的に無視）。Steinberg は phase（フレーム境界との整合）を別要素として扱う
- **考え方**: 制御ループが見ている量（プレイヤーの報告位置）と、現場が見ている量（画面の絵）は別物。**どちらを合わせるかを決める**
- **現状との差**: PTS はリースに載っていて計測用トレースには出るが、**同期には戻っていない**。実測 C の遅れはループの外
- **期待できる改善**: 現場のオフセット調整を減らせる。定常遅れを自動で測って `SyncOffsetMs` の初期値を提案する形なら、制御則を変えずに済む
- **解決しないこと**: フレーム量子化、表示機器側の遅れ（LED プロセッサなど）
- **負担**: 小〜中。**まず「測って提案する」形**にして、ループに入れるかは後で判断するのが安全（ループに入れると遅れの変動が制御に入り、不安定化の余地がある）
- **計測**: 報告位置基準と表示 PTS 基準を同時に採り、**固定遅延と変動遅延を分ける**

### P3. 出力フレームの選択を「次の表示予定時刻」基準にする

- **事例**: 一般的な映像出力の設計（目標表示時刻に最も近い PTS を選ぶ）。Steinberg の phase（フレーム境界との整合）も同じ問題意識
- **考え方**: 「いつ出すか」だけでなく「**どれを出すか**」を目標時刻で決める
- **現状との差**: 合成は常に最新 1 枚（H）。vblank 予測と compose lead は既にあるので、**目標時刻はすでに手元にある**
- **期待できる改善**: 24fps 素材を 60Hz で出すときの重複・欠落が規則的になり、誤差の量子化が減る（実測 C の 60fps -13.2ms はこの範疇）
- **解決しないこと**: 入力側の揺れ、デコードの遅れ
- **負担**: 中〜大。リングに複数枚を保持して選ぶ必要があり、**遅延が 1 枚ぶん増える可能性**がある。不変条件（I1〜I13）に触れるので慎重に
- **計測**: 現状の重複・欠落の分布（24fps 素材 × 60Hz）、変更後の同じ分布と遅延

### P4. WASAPI の入力タイムスタンプを直接使う

- **事例**: Microsoft の `GetBuffer` が返す `devicePosition` / `qpcPosition` と、妥当性を示すフラグ
- **考え方**: 推定ではなく**ドライバが報告する対応関係**を使う。取りこぼしとタイムスタンプ不定を検出できる
- **現状との差**: 自前の最小値フィルタ（J）。取りこぼしを知る手段が無い（I）
- **期待できる改善**: anchor の推定誤差が消え、glitch を速度推定から除外できる。**P1 の速度推定の質が上がる**
- **解決しないこと**: デバイス時計と QPC のドリフトそのもの（値としては見えるようになる）。表示側の遅れ
- **負担**: 中。**NAudio の `WasapiCapture` では取れない**ので、`MMDevice.AudioClient → AudioCaptureClient` で自前のキャプチャループを書くことになる。ドライバがまともなタイムスタンプを返すことが条件
- **計測**: 現行の anchor 推定値と `qpcPosition` の差の分布、`TIMESTAMP_ERROR` / `DATA_DISCONTINUITY` の発生率

### P5. ロックとフライホイールの明確化

- **事例**: Ardour は「連続 2 フレームでロック」「**1 秒**のフライホイール、その間は**位置を動かさない**」「不連続は次フレーム予測との比較で検出」
- **現状との差**: 信号ロスは 250ms のタイムアウト、復帰は無音からなら有効 5 枚・保持からなら値が動いた 1 枚、と別体系（`LtcSignalLossPolicy`）。診断は `Normal/Duplicate/Jump/Reverse` の分類で、**ロック状態という概念が無い**
- **期待できる改善**: 状態遷移の見通し。現場で「追従しているのか、惰性で回っているのか」を UI に出せる
- **解決しないこと**: 定常精度そのもの
- **負担**: 小〜中。ただし既存の R 系・S 系のシナリオ判定に影響するので、テストの期待値を見直す必要がある

### ASIO について

Steinberg の資料でも、**ASIO の低遅延設定と外部クロック同期は別の設定項目**として扱われている。
このアプリのボトルネックは入力バッファの遅延そのものではなく（`age` で吸収している）、**速度の概念が無いこと（P1）と、表示までの遅れがループの外にあること（P2）**。
したがって **ASIO 対応の優先度は低い**。入力の揺れを減らしたいだけなら、WASAPI の共有モードで `IAudioClient3` の小さい周期を選ぶ方が負担が軽い。ただしこれも P1 の代わりにはならない。

**閾値も制御方式も、この計測の後に決める。**

| # | 測るもの | 方法 | 何が決まるか |
| --- | --- | --- | --- |
| M1 | **`age` の内訳**（サンプル終端 → 音声コールバック → Dispatcher キュー → UI 処理）の分布 | 既存のログ項目（`frameDelayMedianMs`、`anchorSpreadMs`）＋ Dispatcher 待ちの記録を 1 つ足す | 入力側の揺れのうち、どこが支配的か。P4 の価値 |
| M2 | **LTC の速度**（差分商）の分布と長時間ドリフト | 10 分と 60 分の連続追従で、LTC 値とサンプル時刻の対を記録して傾きを出す（**製品の制御は変えずに記録だけ**） | P1 の効果の見積もり。PC と LTC 源の時計差が ppm でいくつか |
| M3 | **定常誤差を 2 系統で同時に採る**（報告位置基準と表示 PTS 基準） | 既存の出力トレースに両方ある。同じ run で並べる | 固定遅延と変動遅延の分離。P2 の設計（測るだけか、ループに入れるか） |
| M4 | **重複・欠落の分布**（24fps 素材 × 60Hz 表示） | 出力トレースの publish と PTS を突き合わせる | P3 の効果と、増える遅延の見積もり |

いずれも **製品コードを変えずに記録だけで取れる**（M1 の Dispatcher 待ちだけ 1 行の追加が要る）。

## 6. 進める順序（計測の結果しだい）

1. **M1・M2 を先に取る**。M2 でドリフトが実測できたら P1 の設計に入る
2. **P1（速度の 3 つ組）を入れる。** Ardour に倣い、**フィルタを入れない**（差分商 + デッドゾーン）。制御則は今の比例制御のまま、外挿だけ速度を使う形から始める
3. **M3 を見て P2 を決める。** 固定遅延が支配的なら「測って `SyncOffsetMs` を提案する」で足りる。変動が大きいならループに入れる検討
4. **P4 は P1 の後**。速度推定の質を上げる補強として入れる（順序を逆にすると、何が効いたか分からなくなる）
5. **P3 と P5 は、上が落ち着いてから。** どちらも既存の不変条件とシナリオ判定に触れる

## 7. DAW の設計をそのまま持ち込めない点

- DAW は**音声を出す**。音声は連続量で、サンプル単位のリサンプリングで速度を変えられる。**映像は離散**で、1 フレームより細かくは合わせられない（実測 C の 60fps -13.2ms はこの下限に近い）
- Ardour の `speed` はトランスポート全体に掛かる。このアプリの `rate` は GStreamer の非フラッシュなレート変更で、**音声のピッチが変わる**（利用者の判断で許容済み、着地直後のみ ±20%）
- DAW は外部クロック（ワードクロック）を前提にできる。**このアプリは前提にできない**。だからこそ P1（速度の推定）の価値が相対的に高い
