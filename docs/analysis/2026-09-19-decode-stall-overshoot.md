# 復号が遅れている間に速度を上げ続けて行き過ぎる

作成: 2026-09-19 05:15、親。検証機の候補 7・M8 ×5（3 合格 / 2 失敗）から。
**利用者が以前から言っていた「デコードが間に合ってないのでは」に当たる現象。**

## 症状

M8（実素材、4K60 H.264、**中央 103 Mbps / ピーク 117 Mbps**）で、
**5 回中 2 回、同期のずれが 0.967 秒まで広がる。**

```
窓 10: 更新=0   位置前進=1.633  LTC前進=2.000  誤差 0.247   ← 遅れる
窓 11: 更新=85  位置前進=2.200  LTC前進=1.920  誤差 0.967   ← rate 1.20 で取り戻して行き過ぎ
窓 12: 更新=120 位置前進=2.117  LTC前進=2.080  誤差 0.070   ← 復帰
```

起点は**配信（復号）の一時的な落ち込み**。2 秒窓で **0.61 倍速**（74 枚 / 期待 119 枚）まで落ちる。

## 潰れた説明（検証機の実測）

| 仮説 | 結果 |
| --- | --- |
| GOP スキャンと重なった | **外れ**。重なった 1 回はむしろ最良（誤差 0.180・停滞 0・平均更新 119.93） |
| 素材の特定箇所 | **外れ**。4 回目は位置 30 秒、5 回目は 56 秒 |
| 素材のピークビットレート | **外れ**。**4 回目は 50 Mbps の最も軽い区間**、5 回目は 104 Mbps |
| 位置の交番 | **外れ**。符号反転 0 件、最悪 8 秒の PTS 比 1.0005〜1.0212 |
| 絵の停止 | **外れ**。`compose.publish` の最大ギャップ 132 ms |

**素材側では説明できない。** 残るのは「その時々の負荷」と、次の機構。

## 機構の仮説

**復号が間に合っていないときに再生速度を上げても、無い絵は出せない。**
それでも誤差は縮まらないので補正はさらに速度を上げ、**復号が戻った瞬間にその速度が効いて行き過ぎる。**

古典的な積分ワインドアップの形。ただし**まだ検定していない**
（レートを上げない対照が無い。検証機に Jump モードでの対照を依頼済み）。

### ±20% はどこから来るか

`SyncCorrectionController.LandingMaxRateDelta = 0.20`、窓は `LandingWindow = 1.0 秒`。
`NotifyLanding` は**粗い同期シークの発行**でも開く。つまり:

**復号の落ち込み → 誤差が育つ → シーク発行 → 着地窓が開く → 上限が ±20% → 行き過ぎ**

観測でも「rate=1.10000 → **rate=1.20000** → シーク 2 回」の順で出ている。

### 0.4.5 の回帰ではない（ただし頻度は変わりうる）

- **`LandingMaxRateDelta = 0.20`（T9）は v0.4.0 から**（`ea903cb`、2026-09-16。
  `git tag --contains` で v0.4.0〜v0.4.3 に含まれることを確認）
- **速度補正の既定 Smooth も v0.4.0 から**（`6307ec5`）

**機構は 0.4.5 より前から存在する。** ただし **D37-b で「追従中の実際のずれをシークではなく
速度で詰める」ようにした**ので、**この経路を通る頻度は 0.4.5 で増えている可能性がある。**
→ **公開済みの v0.4.3 で M8 ×5 を回して直接測る**（検証機に依頼済み）。

## 直し方の案: **実測レートを見る**

**アプリは既に「実際に進んでいる速度」を測っている。**
`PlaybackPositionFeedback` が、配信 PTS の前進から実測レートを EMA で持っている:

```csharp
double measured = dp / dt;            // 配信 PTS の前進 ÷ 実時間
_rate = _hasRate ? (_rate * RateKeep) + (measured * (1.0 - RateKeep)) : measured;
public double Rate => _rate;          // 既に公開されている
```

**指示した速度（1.10〜1.20）に対して実測が大きく下回っていれば、律速は復号であって時計ではない。**
そのとき速度をさらに上げても意味が無く、復号が戻ったときの行き過ぎだけが残る。

**案**: 指示レートと実測レートの差が続いている間は、**上限を上げない**（あるいは指示を保持する）。

- **既存の信号だけで判定できる**（新しい測定を足さない）
- しきい値は未定。**実測レートが指示レートを何割下回ったら「復号律速」と見なすか**は、
  M8 の落ち込み（0.61 倍速）と正常時（0.98 倍速）の間で決める
- **守りを足す形なので、平常時に発火しないことを数えること**
  （利用者の方針「安全対策のし過ぎで変に暴れても困る」）

## 未確定のまま残していること

- **「速度を上げたせいで行き過ぎた」は検定していない。** Jump モードの対照が要る
- **落ち込みの原因そのもの**（機械の負荷か、こちらの経路か）は分かっていない。
  CPU / GPU 使用率の記録は「計測が計測対象を乱す可能性」があるため保留
- **2/5 という頻度の確度**も低い（5 本）

## 公開時に使う文面（v0.4.3 でも落ちた＝回帰でなかった場合）

そのまま `docs/release-notes/v0.4.5.md` の「既知の制限」へ貼る。
**v0.4.3 で落ちなかった場合は貼らない**（回帰なので直してから公開する）。

> - **ビットレートの高い 4K60 素材で、まれに同期のずれが一時的に 1 秒近くまで広がることがある**
>   （実測: 中央 103 Mbps・ピーク 117 Mbps の実素材で、同じ条件の 5 回中 2 回。最大 0.967 秒。
>   いずれも数秒で復帰する）。復号が 2 秒ほど間に合わなくなって映像が遅れ、そのあと再生速度で
>   取り戻す際に行き過ぎるために起きる。**絵は途切れない**（表示の間隔は最大 132ms）
>   - **素材の重い場面で起きるわけではない。**実測では、いちばん軽い区間（50 Mbps）で起きた回もある
>   - **この版で新しく起きるようになったものではない**（同じ現象を v0.4.3 でも確認）
>   - 次の版で、**復号が間に合っていないことを検知して速度を上げすぎない**ようにする

数値の出どころ: 検証機の候補 7・M8 ×5（3 合格 / 2 失敗）。
ビットレートは ffprobe のパケット長から 1 秒ごとに算出したもの。
