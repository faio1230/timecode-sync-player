## 1. 再生位置の問い合わせは、シーク中に何を返しているか（コード読み）

`tcs_player_get_time_pos`（`native/gst-shim/src/tcs_gstreamer.cpp:3411-3452`）は 1 つの API で
**2 つの異なる時計**を返す。

| 状態 | 返す値 | 実装 |
| --- | --- | --- |
| 一時停止中（pump 完了、`latest_gen == generation`、PTS>0） | 最新配信フレームの stream-time PTS（= 表示済みの絵の位置） | 3425-3429 |
| それ以外（**再生中は常にこちら**） | `gst_element_query_position`（= パイプライン／セグメント位置） | 3430 |
| クエリ失敗時（再生中も） | **世代チェック無しで**最新配信 PTS にフォールバック | 3434-3437 |

シークはすべて flushing（`seek_prepare_locked:2493-2588`、`seek_send:2592-2622`。MP4/MOV は accurate、
TS は keyunit/snap-before）。`seek_prepare_locked` は `generation++`（2499）、未配信フレームの破棄、
配信ゲートの準備を行うだけで、再生中はパイプラインを PLAYING のままにする。

この組み合わせで、シーク中は次の 2 つの値が交互に現れる。

1. **フラッシュシークが処理された後**: 新しいセグメントは目標から始まるため、クエリは
   「目標 + 経過時間」を返す。**復号と表示が追いつく前でも位置だけ先に進む**（= これから表示される
   位置の先取り。`SingleModeSyncCoordinator.cs:32-33` の "time-pos can still be the synthetic
   requested target" と同じ現象）。
2. **処理前・クエリ失敗時**: 旧セグメントの位置、または**世代を見ないフォールバック**が
   直前フレームの PTS（= シーク前の古い位置）を返す。

>>> **2026-09-18 夜 訂正（実トレース 6 本・9,644 評価で確認）**: この §1 のモデルは誤り。
>>> 実際は「旧位置と新目標の**間で跳ぶ**」のではなく、**発行の瞬間に目標へ跳び、着地まで目標のまま固まる**。
>>> 詳細は文末の「§2 実測による §1 の訂正」を参照。以下の 2 段落は原文のまま残す。

つまり「報告位置」は表示済みフレームの位置ではなく、シーク中は **旧位置と新目標の間で跳ぶ**。
x1 の連鎖中に再生位置の残差が ±0.5〜0.8 秒（min -781 / max +567ms）で暴れたのは、この 2 つの時計の
切り替わりとして説明できる。LTC 側は 0.36ms で安定していた。

一方、表示済みフレームの PTS は shim 内に既にある（`latest_pts_ns`、配信コールバックで更新:
`tcs_gstreamer.cpp:1452-1453`。trace の `gst.position.ptsNs` / `gst.delivery` としても出る）。
**これをフィードバックに使っているのは一時停止経路だけ**で、再生中の同期判定はセグメント位置を見ている。

アプリ側には「着地を確認する」部品もある（`GstSeekingTracker.cs:64-88`。配信到着数の増加で
新位置フレームの到着を判定し、2 秒で時間切れ）。足りないのは「位置クエリの値に、それが
どの基準（パイプライン位置 / 配信フレーム PTS）で、どの世代かを付ける」ことと、それを
判定側で使い分けること。

### 案 1: 速度の推定
- **前提は崩れた。** ドリフトは実測で ppm 級（中央値 -0.0 / -0.8 ppm、p5〜p95 -0.8〜+1.6 ppm、103s）。
  10 分 run でも数 ms の水準で、フレーム量子化（25fps で 40ms）より小さい。
- 「誤差推定の安定化」として LTC 側に期待できる効果も無い。LTC 側は常時 σ 0.3ms で、振動の出どころではない。
- ただし**同じ概念を出力側に適用する価値**は今日の測定が示す（§3-3）。提案書の案 1 そのもの
  （LTC の速度推定）は 0.4.5 で実施しない。

### 案 2: 表示済みフレームの PTS を同期へ
- **前提は保たれ、むしろ測定で裏付けられた。** 制御ループが見ている「報告位置」と、現場が見ている
  「表示済みの絵」は別物で、差は固定 **-27〜-29ms** + 変動 σ **11〜12ms**（p95|差| 40〜46ms。M3）。
- ただし**ループに入れるのは危険**。表示 PTS をフィードバックにすると、復号・合成・表示の遅延ぶんの
  位相遅れが制御に入り、変動は 25fps の 1 フレーム（40ms）と同程度でフレーム量子化と区別できない。
- 提案どおり **「測って `SyncOffsetMs` の推奨値を出す」形**が安全。固定遅延 27〜29ms を消せる効果は
  現場の見え方に直結し、制御則は変えない。

### 案 3: 表示フレームの選択
- **前提は崩れた。** 24fps 素材 × 60Hz の重複は 2:50% / 3:49%（理想 2.5）で、定常区間の
  1〜3 フレーム欠落は 0（M4）。現状の「最新 1 枚」でも規則的に出ている。
- リング複数枚 + 遅延 1 枚ぶん + 不変条件への影響は、得られる改善（フレーム量子化）に見合わない。
- フレーム先頭基準の -27〜-29ms は案 2 の測定で扱える。0.4.5 では実施しない。

### 案 4: WASAPI の入力タイムスタンプ
- **精度面の前提は崩れた。** LTC 側は σ 0.3ms、アンカー段差（sampleTicks の進みが公称から 0.5ms 以上
  ずれるペア）は 25fps で 82/2240、24fps で 34/2145 で、実効値の跳びは中央値 0.5〜0.8ms
  （M2 と Q1 の追試）。
- 残る価値は「取りこぼし（`DATA_DISCONTINUITY`）とタイムスタンプ不定を知る」観測性で、精度改善ではない。
  必要になったときに計測用途で入れる。

### 案 5: ロックとフライホイールの明確化
- 精度への寄与は無い。シーク連鎖の実害は D37-a（ゲート）と D37-b（シーク中の位置を信用しない、
  不足は速度補正）で対処される。
- ただし「追従しているのか、惰性で回っているのか」を UI に出す価値は残る。0.4.5 の本筋ではなく、
  余力があればの項目。

## 3. 観点への回答

### 3-1. なぜシーク中に ±0.5〜0.8 秒暴れるのか
§1 のとおり。**同じ API が「新セグメントの目標位置」と「旧セグメントの位置（または世代無視の
フレーム PTS フォールバック）」を返し分け、どちらも表示済みフレームの位置ではない。** 目標への
跳びはシーク距離ぶん（x1 では 2.4〜11.2 秒の目標列）、戻りは旧位置ぶん。これが同期ループに
入ると「誤差が一瞬で消えてまた現れる」ように見え、補正シークの再発行（連鎖）を招く。
D37-a はこの入力をゲートで弾き、D37-b はシーク中の判定を止める。0.4.5 で残るのは
**フィードバックの基準を一貫させること**。

### 3-2. 案 2 の評価
§2 のとおり「測って提案」に限定するのが妥当。固定遅延 **-27〜-29ms**、変動 σ **11〜12ms**、
p95|差| **40〜46ms**（M3、25fps / 24fps の 2 run）。固定遅延を `SyncOffsetMs` に反映すれば
現場のずれは減る。ループに入れる判断は、10 分 run の変動（ドリフトではなく遅延の安定性）を
見てからでよい。

### 3-3. 案 1 を「誤差推定の安定化」として見たとき
- LTC 側には不要（σ 0.3ms）。
- しかし**出力側に (位置, 時刻, 速度) を持つ**価値はある。使うのは
  「最後に配信されたフレームの PTS + 経過時間 × 実測レート」で、シーク中でも
  **今画面に出ている位置**を連続に表現できる（絵が止まっていれば位置も止まる）。
  - 目標への跳びに汚染された誤差推定が無くなる。
  - D37-b の「着地が確認できるまで判定しない」を、「正しい入力で評価を続ける」に置き換えられる
    （実在の不足のときに速度補正へ回す判断も、この位置系列で行える）。
- これは D37-b と重なる部分が大きい。0.4.5 で実施するなら **「位置フィードバックの一貫化」**
  として 1 本にまとめるのがよい。LTC の速度推定そのものは実施しない。

## 追記（2026-09-18 夕、親）: シークと速度補正の分岐は「好み」ではなく収束条件だった

D37-b/b2 の実装を読み直して確認した。分岐のしきい値は固定値ではなく、
**素材ごとに学習したシーク 1 回の実測所要**（EMA、`TimecodeSyncSeekState.LearnedSeekDurationSeconds`。
未学習のみ 1.0 秒、異常値は 0.05〜10 秒の外で除外）。判定は `SyncDecisionEngine.Decide`:

```
誤差 <= シーク所要  →  シークを出さず速度補正
誤差 >  シーク所要  →  シーク
```

**これは利用者の好みで決める量ではない。** シーク中は位置が止まり LTC だけ進むので
**着地時の誤差 ≒ シーク所要**（実測 47 件で比 0.99）。したがって:

- 誤差がシーク所要より小さいときにシークすると、**直すより大きい誤差を新しく作る**
- シーク所要が許容（0.240 秒）を超える素材では、**シークは原理的に収束しない**（D37 の連鎖そのもの）

### 「学習値に上限を入れるべきか」— 入れてはいけない

一度は上限を検討したが、**逆効果**なので採らない。
シーク所要 2 秒の素材で 1.5 秒ずれている場合:

| 手段 | 結果 |
| --- | --- |
| 速度補正 | 約 15 秒で解消。絵は止まらない |
| シーク | 2 秒静止し、**着地時点で約 2 秒ずれ**（元より悪い）→ 許容超過 → **また発火・連鎖** |

上限を入れると、この連鎖を呼び戻すだけになる。**実装のままが正しい。**

### 残る本当の課題は素材側と可視化

- **解決は素材側**: GOP を短くする（既にリリースノートの推奨事項）。
  同じ 4K60 でも 1 秒 GOP なら所要は 184ms 級で、しきい値も下がりシークが正常に働く
- **0.4.5-C（利用者の要望で確定、2026-09-18）**: **素材を読んだ時点でロング GOP を警告する。**
  利用者の言葉: 「このような素材が来た場合、プレイリストやステータスバーなどどこかに
  不安定になる可能性がある警告を出した方がいいかもしれません」

  当初 親は「長い速度補正が続いている状態を見せる」（＝事後の状態表示）を考えていたが、
  **利用者案の方が良い**。事後では既に本番中であり、**読み込み時なら本番前に素材を差し替えられる**。
  指示書: `docs/prompts/2026-09-19-V045-C-long-gop-warning.md`

  判定方式の要点: デコーダに入る**符号化フレーム**側で `GST_BUFFER_FLAG_DELTA_UNIT` を見る
  （デコード後はフラグが当てにならない）。かつ**「2 つ目のキーフレームを待たず、一定時間
  キーフレームが現れなかった時点で警告」**にする。素直に間隔を測ると 10 秒 GOP では判明まで
  最大 20 秒かかるが、この方式なら**再生開始から約 3 秒**で出る。しきい値 3 秒

## §2 実測による §1 の訂正（2026-09-18 夜、実トレース 6 本・9,644 評価）

0.4.5-A 指示書 §2「実装前に 1 回だけ確認すること」の結果。**コード読みに基づく §1 のモデルは誤っていた。**

### 訂正: シーク中の報告位置は「跳ぶ」のではなく「目標で固まる」

| | §1 のモデル（コード読み） | 実測 |
| --- | --- | --- |
| シーク中の報告位置 | 旧位置と「目標 + 経過時間」の**間で跳ぶ** | **発行の瞬間に目標へ跳び、着地まで目標のまま固まる** |
| アプリから見た誤差 | ±0.5〜0.8 秒で暴れる | **シーク中はほぼ 0**（自分は目標に居ると見える）。LTC が進むぶん後半で符号が反転 |
| σ 445ms の正体 | 2 つの時計の交互出現 | **発行前の旧位置サンプルと発行後の目標サンプルの段差**（= シーク距離） |

**機構としてはこちらの方が悪質である。**
シークの最中、アプリは「自分は目標にぴったり居る」と思っているので**何も対処できない**。
その間 LTC だけが進み、**着地した瞬間に溜まったぶんがまとめて誤差として現れる**（= シーク所要）。
D37 で測った「着地時の誤差 ≒ シーク所要（47 件で比 0.99）」は、この構造の帰結だった。

### これは 0.4.5-A の根拠を強める

§3-2 の「着地未確認の間は配信 PTS + 外挿で評価する」方向は変わらない。**むしろ効果が大きい**。

- 配信 PTS 基準なら「**絵が止まっている間は位置も止まる**」が正しく効く
- **シーク中に誤差が育つのが見える**ようになり、着地時に待ち伏せされない
- 見えていれば、育っている不足に対して速度補正で応じる判断も、その場でできる

**§3 の設計に書く現状モデルは「目標 + 経過」ではなく「発行直後に目標で凍結」に直す。**

### クエリ失敗のフォールバック（`tcs_gstreamer.cpp:3434-3437`）— 痕跡 0、ただし留保付き

`sync.evaluate` の `playback=` を直前 20ms の `gst.position`（成功時のみ記録）と突き合わせた。

| trace | 評価数 | 成功クエリと一致 | 不一致（フォールバック痕跡） |
| --- | ---: | ---: | ---: |
| run1 / run2 / vp9c / vp9b | 1640 / 1640 / 1644 / 796 | 同数 | **0** |
| v3/d37a / v3/d37b2 | 1971 / 1953 | 同数 | **0** |

**留保（エージェントの自己申告。正しい留保なので採用する）**:
3434 のフォールバックは `gst.position` を記録せずに return するため、**既存トレースでは構造的に見えない**。
上の 0 は消去法（フォールバックなら古い PTS が返り、直前スナップショットと 0.5ms 以内では一致しない）であり、

### 補足: 定常状態では 2 つの時計はほぼ一致する（0.4.5-A の risk を下げる事実）

同じ §2 の解析で得られた数字。

| 状態 | `query_position` と配信 PTS の関係 |
| --- | --- |
| **通常再生** | **配信 PTS + 0.4〜7ms**（25fps の 1 フレーム 40ms の 1/6 以下） |
| シーク中 | 発行の約 4ms 後に目標へ跳び、着地まで目標で凍結（代表例: target 9.171 に対し 18/18 サンプルが 9.171〜9.172、その間 配信 PTS は 7.750 のまま） |
| 検証 | 「目標 + 経過時間」に一致したサンプル **0 件**、「旧位置」に一致したサンプル **0 件**（run1/run2/vp9c の連鎖 8 本ずつ） |

**したがって、基準を配信 PTS に切り替えても定常状態の挙動は実質変わらない。**
変わるのは**シーク中だけ**であり、そこは現状が壊れている区間である。
