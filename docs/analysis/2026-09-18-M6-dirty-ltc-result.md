# M6 の結果: ダーティーな LTC 信号に対する余裕（2026-09-18）

**利用者の問い**: 「いまは内部でタイムコードを生成したかなりクリーンな状態でテストを行なっていて、
現場だとダーティーな信号が来る可能性も考えられます」

**結論: 試した範囲では、ノイズ以外は壊れない。**

| 条件 | 試した範囲 | 最初に落ちた点 | 落ち方 | clean の実測 |
| --- | --- | --- | --- | --- |
| **A ノイズ** | SNR 40〜4dB | **SNR 4.5dB 付近** | **崖（急）** | 99.8% |
| B レベル | +3 〜 −60dBFS | **なし**（−60dBFS で 99.4〜100%） | — | 99.8% |
| C 欠落 | 10 / 50 / 200 / 600ms（5 秒毎） | なし（10ms で −2.1pt、幅に比例） | 緩 | 100.1 / 100.0% |
| **D サンプルレート不一致** | 44.1k→48k、96k→48k | **なし**（clean と同一） | — | 100.2 / 100.0% |
| **E 速度差** | ±50 / ±100 ppm | **なし**（clean と同一） | — | 100.0% |

- A は 2 run で完全に一致し、崖を再現。**SNR 4.5dB では受信フレームの値が完全に化け、ギャップ最大 6.1 秒**
- C は損失が幅に比例するだけ（600ms で −14pt）で、**届いたフレームの誤差は clean と同一**（p95 36〜43ms）。
  **600ms（外挿上限 0.5 秒超）でも復帰後に化けない**
- D は「壊れない」が結論。**アプリは不一致を検知しないままだが実害が無い**（`LtcAudioMonitor.cs:49`）
- B の +3dBFS は経路の正規化でクリップ条件を作れなかった（環境の性質として記載）

## 設計判断への波及

1. **D**: アプリがサンプルレート不一致を検知していないことを、**問題視しなくてよい**
2. **E**: 「比例制御が一定の速度差を吸収する（50 ppm で残差 50µs）」という計算が**実測で裏づけられた**。
   **0.4.5 で LTC の速度推定をやらない判断が、外部条件でも支えられる**
3. **C**: 外挿の現在の作りが妥当であることの傍証。**0.4.5-A フェーズ 2 で外挿を変えるとき、この性質を壊さないこと**

## 警告の材料: crest factor

**A は崖なので、デコード率では事前警告できない。**
ただし既存の peak/rms（2 秒毎ログ）から計算できる **crest factor が崖の手前で上がる**
（clean 1.0、SNR 6dB で約 1.67）。**0.4.5-C（ロング GOP 警告）と同種の警告が作れる可能性がある。**

## 限界（この測定で言えないこと）

- **崖は「ノイズ RMS ≒ 信号の 60%」の水準だが、現場の SNR 実測が無いので距離を定量できない**
- **試した範囲**: A 40〜4dB、B −60dBFS まで、C 600ms/5s まで、E ±100ppm まで

## M6-b（追加）: 利用者の回答で見つかった穴

**利用者の回答（2026-09-18）**: 「レコーダーからそのまま抜くこともある。**回線数が足りない場合は分配する
（その場合レベルが小さくなる可能性がある）**。**基本的にはアナログの回線**でつなぐ」

### 穴 1: レベル低下とノイズを別々にしか振っていない

**分配でレベルが下がると、そのぶん SNR の余裕が減る**（信号が小さくなってもアナログ経路のノイズは変わらない）。

**B の「−60dBFS まで問題なし」は、ノイズの無い経路での結果**であり、
**現場の「レベルが下がった信号 + アナログのノイズ」には、そのまま当てはめられない。**

→ **確認**: 「0dBFS に SNR 12dB」と「−20dBFS に SNR 12dB」で崖の位置が一致するか。
一致すれば支配する量は SNR ひとつ。一致しなければレベルにも独立した効きがある。

### 穴 2: ノイズの種類が現場と違う

M6 で使ったのは広帯域のノイズ。**アナログ回線で実際に乗るのはハム**（50/60Hz と倍音）。
**LTC は 1〜2kHz 帯の矩形波なので、スペクトルが違えば効き方も変わる。**

→ **確認**: 50Hz / 60Hz のハム（3 次・5 次まで）を、同じ SNR の広帯域ノイズと比べて崖の位置が違うか。
**親の予想: ゼロクロス判定に効くのは高域なので、低域のハムには耐性が高いのではないか**（当てにならない）。

### crest factor の設計は M6-b の後

**ハムは正弦波なので波高率が低く、広帯域ノイズとは crest factor の動きが違うはず。**
**ハムで上がらないなら、現場で効かない警告になる。** 順序を逆にすると作り直しになる。

## M6-b の結果（2026-09-18 23:25）: 支配する量は SNR ひとつ。ハムは広帯域より 3〜4dB 強い

### H1: レベル低下は、それ自体では危険を増やさない

**同じ SNR なら、レベルが −6dB でも −20dB でも −40dB でも結果は同じ。**

| レベル × SNR | decode% |
| --- | ---: |
| −6dB × SNR12 / −20dB × SNR12 | 100.0 / 100.0 |
| −6dB × SNR5 / −20dB × SNR5 / −40dB × SNR5 | 100.0 / 99.8 / 99.8 |
| −20dB × SNR4.5 / −40dB × SNR4.5 | **0.8 / 0.8（全滅）** |

**支配する量は SNR ひとつと確定。**

**利用者の現場条件（分配でレベルが下がる、アナログ回線）はこう整理できる。**

- **分配でレベルが下がること自体は問題ない**
- **危険なのは、レベルが下がったぶん相対的にノイズが大きくなること**（= SNR の低下）
- したがって**警告は SNR 相当の量だけを見ればよく、レベル単体の警告は不要**

### H2: ハムは広帯域ノイズより 3〜4dB 強い（親の予想どおり）

| | 崖の位置 |
| --- | --- |
| 広帯域ノイズ | SNR 5.0 → 4.5dB の間 |
| **50Hz ハム** | **SNR 2 → 1dB の間** |
| **60Hz ハム** | **SNR 2 → 1dB の間** |

**50Hz と 60Hz に差は無い。** LTC は 1〜2kHz 帯の矩形波でゼロクロス判定に効くのは高域なので、
低域のハムは効きにくい、という読みが当たった。**現場はアナログ回線なので、実際の余裕は M6 の値より 3〜4dB 大きい。**

### crest factor: ハムでは上がり方が浅く、飽和も早い

| SNR | 広帯域 | 50Hz | 60Hz |
| --- | ---: | ---: | ---: |
| clean | 1.000 | 1.000 | 1.000 |
| 12dB | 1.391 | 1.271 | 1.269 |
| 6dB | 1.663 | 1.442 | 1.442 |
| 3dB | ~1.70 | 1.518 | 1.523 |
| **崖** | **4.5dB で 1.73〜1.75** | **1dB で ~1.57** | **1dB で ~1.56** |

**同じしきい値では、警告のタイミングが両者でまるで違う。**

| しきい値 | 広帯域（崖まで） | ハム（崖まで） |
| --- | --- | --- |
| crest 1.5 | SNR 8〜9（**3〜4dB**） | SNR 3（**1〜2dB**） |
| **crest 1.4** | SNR 11（**6dB**） | SNR 6（**4〜5dB**） |

**現場はハムが主なので、ハム基準で置く。crest 1.4 なら崖まで 4〜5dB の余裕。**

### 誤検出のデータ

| 条件 | crest |
| --- | ---: |
| B（レベル）全レベル | 1.000 |
| D（サンプルレート不一致）最大 | 1.020 |
| E（±ppm）最大 | 1.027 |
| C（欠落）600ms の 1 窓のみ | 1.495 |
| **切替端の窓**（B で観測） | **4.7** |

**切替端の窓が大きく出る**ので、**peak が小さい窓の除外と、持続の判定が前提**になる。
単発の窓で警告を出してはいけない（0.4.5-C で踏んだのと同じ形の誤り）。

証跡: `TestResults/v3/m6-H1-level-snr-r1/r2-20260918-230211`、`m6-H2-hum50/hum60-*`、`m6-H2b-*-cliff-*`。
crest 抽出は `scripts/extract-capture-crest.py`。

## LTC 信号品質の警告は 0.4.6 以降の候補（2026-09-18 23:30、親の判断）

**設計は完了している**（`docs/analysis/` の M6 crest 設計、`agent-b`）。**実装は 0.4.5 に入れない。**

### 設計の要点（採用する形）

- **しきい値 crest 1.4**。**ハム基準**で置く（現場はアナログ回線＝ハムが主。崖まで 4〜5dB の余裕）。
  広帯域基準（1.5）だとハムでは崖まで 1〜2dB しかない
- **2 秒連続で超えたときだけ発報。** 単発では出さない
  （**切替端の窓は crest 4.7 まで跳ぶ**。単発判定だと素材を切り替えるたびに警告が出る）
- **peak が小さい窓は除外**（無音・信号断）
- **解除される**（GOP のラッチと違い、信号品質は現場で直せるので、直ったら消えないと確認できない）。
  **UI も GOP 警告と別フィールド**にする（ライフサイクルが違うため）
- crest の数字は **UI に出さずログに残す**（利用者になじみのない量）
- 文言案: 「LTC の信号品質が低下しています（ケーブル・レベル・接続を確認してください）」

### 見送る理由

1. **0.4.4 がまだ出ていない**（5 回目の候補に向かっている）
2. **0.4.5 のスコープは A と C で確定済み。** いま足すと「直したつもりが別の場所に出る」を繰り返す
   （同日 4 回発生している）
3. **実際の現場の信号で 1 度も試していない。** 未確認: アナログ実機、他音の混入、本物の SRC、低レベル＋ノイズフロア。
   **0.4.5-C（GOP 警告）は、まさにこの「実素材で試していない」状態で誤検出した**（生成素材では正しく動いた）

### 利用者に依頼した実測（2026-09-18）

**実際の現場の LTC 経路で crest factor を 1 度測る。**
**現状のビルドで既にアプリのログに peak/rms が出ている**ので、新しい機能は不要。ログを 1 つ受け取れば読める。

**分かること**:
- **現場の信号が崖からどれだけ離れているか**（いまは「ノイズ RMS ≒ 信号の 60%」という値しか無く、距離が測れない）
- **しきい値 1.4 が現場で誤検出しないか**（分配後や他音が混ざる状況で、平常時に 1.4 を超えないか）

**取れれば実測でしきい値を置ける。取れなければ保守的な値（誤検出しにくい方）で出す。**
