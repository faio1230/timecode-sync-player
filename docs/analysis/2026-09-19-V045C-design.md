# 0.4.5-C 設計: ロング GOP 素材の警告（表示のみ）

作成: 2026-09-19（同期担当、agent-a）。**この文書は設計のみで、製品・テストのコードは変更していない。**
実装は 0.4.4 の検証機結果待ち（実機も未使用）。0.4.5-A / B とは触る場所が重ならない。

出典:

## 0. 作るもの（要約）

- **再生中に、一定時間（既定 3 秒）キーフレームが現れない素材**を検出して警告する。
  警告は**素材の性質**（GOP が長い）の通知であり、**再生は止めない・同期の制御則は変えない**。
- 出す場所は 2 つ: **ステータス行**（いま鳴っている素材）と**プレイリストの該当行**（どのトラックか）。
- 文言: 「キーフレーム間隔が長いため同期が不安定になることがあります（推奨: 1〜2 秒）」
  + 間隔が確定したら「（実測 X.X 秒）」を追記。
- 判定は shim 内（デマルチプレクサ／パーサの src pad のパッドプローブ）。アプリは**ポーリング**で受け取り、
  **トラック単位で一度だけ**表示する（同一セッション中に点滅させない）。

## 1. 判定する場所（パッドプローブ）

### 1-1. 現在のパイプライン構成（コードで確認）

- コンテナは**拡張子で明示的に選ぶ**（`select_demux_for_path`、`tcs_gstreamer.cpp:2132-2149`）:
  qtdemux / matroskademux / tsdemux / mxfdemux / avidemux。未知の拡張子は decodebin。
- 映像チェーンは**デマルチプレクサの後に静的に構築**される（`build_video_chain_static`、`:1850-1956`）。
  並びは `queue → [parse] → decoder → convert … → appsink`（`vparse` の生成は `:1899`、
  `gst_element_link` の並びは `:1938-1949`）。parse は h264parse / h265parse / vp9parse / av1parse
  （`tcs_video_profiles.h:25-35`）。ProRes は parse 無し。
- デマルチプレクサの src pad は**動的**（`pad-added`）で、`on_demux_pad_added`（`:2156-2217`）→
  `on_video_pad`（`:2012-2053`）が映像 pad を `vhead`（= queue）へリンクする。
  decodebin がコンテナの場合は decodebin の src pad が**デコード済み raw video**。

### 1-2. プローブを付ける対象

| コンテナ / コーデック | 付けるパッド | 根拠 |
| --- | --- | --- |
| MP4/MOV + h264/h265/vp9/av1 | **`p->vparse` の src pad** | parser がビットストリームからキーフレームを確定する。コンテナの sync sample より一貫する |
| Matroska/WebM + h264/h265/vp9/av1 | 同上 | 同上（vp9parse / av1parse はフレームヘッダから判定） |
| MPEG-TS + h264/h265 | 同上 | **tsdemux の keyframe 情報は当てにならない**（`:2534-2541` のコメントどおり PES に IDR フラグが無い）ため parser が必須 |
| ProRes（mov/mxf） | **デマルチプレクサの映像 src pad**（`on_video_pad` に渡る `pad`） | parse が無い。コンテナの sync sample を見る（MXF は要確認） |
| decodebin フォールバック | **付けない**（`active=0` で報告） | decodebin の src pad はデコード後で `DELTA_UNIT` が無効。内部 pad の取り回しに見合う価値が無い |

キーフレームの判定は `GST_BUFFER_FLAG_DELTA_UNIT` が**立っていない**こと。プローブ種別は
`GST_PAD_PROBE_TYPE_BUFFER`、戻り値は常に `GST_PAD_PROBE_OK`（**バッファを変更・破棄しない**）。

### 1-3. 動的パッドとライフサイクルの取り回し

- parse がある構成: `build_video_chain_static` 内で `vparse` 生成直後に
  `gst_element_get_static_pad(vparse, "src")` へプローブを付ける（この時点で pad は静的）。
- parse が無い構成: `on_video_pad` でリンクするときに、渡されたデマルチプレクサ pad へ付ける。
  二重に付けないよう `gop_probe_installed` フラグをプレイヤーに持ち、チェーン構築時にリセットする。
- 全プロファイル試行は `build_pipeline` が `teardown_pipeline`（`:2673`）してから作り直すため、
  プローブは試行ごとの新しい要素に付く。
- **遅れて届くコールバック**: D34 のコメント（`:2717-2721`）どおり、teardown 後に旧パイプラインの
  スレッドが 1 回だけ触ることがある。プローブの user_data を
  `GopProbeContext { TcsPlayer* p; uint64_t epoch; }`（`GDestroyNotify` 付き）にし、
  ハンドラ先頭で `ctx->epoch != p->gop_epoch` なら `GST_PAD_PROBE_REMOVE` を返して状態に触らない。
  `gop_epoch` と計測状態は `build_pipeline` の先頭（試行ループの前）で +1 / リセットする。
- 映像トラックが複数ある場合は `on_video_pad:2014` と同じく**最初の 1 本だけ**を見る。

### 1-4. シーク時の再接続

`seek_prepare_locked`（`:2493-2588`、手動シーク・ステップ・ロード時シークが通る）で
`gop_reanchor = true` を立てる（`std::atomic<bool>`）。プローブはこれを見たら
**アンカーを無効化**して次のキーフレームを待つ。シークで PTS が大きく跳んでも、
「最後のキーフレームからの経過」が瞬間的に 3 秒を超えて誤警告しないため。
**警告ラッチと実測間隔はシークでは消さない**（トラック単位の状態。`:3-3` の指示）。

## 2. 判定ロジックとクロック

### 2-1. クロックはバッファ PTS（素材時間）で測る

**実時間（QPC / サンプル時計）ではなく、バッファの PTS 差で測る。** 根拠:

1. **GOP 長は素材の性質**であり、推奨値（1〜2 秒）も ffprobe の GOP とも同じ素材時間の話。
   実時間で測ると、Smooth 補正の ±10%・速度切替・シーク・一時停止で同じ素材が別の判定になる。
2. **機械の都合を素材の欠陥にしない**。デコードが詰まってバッファが来なければ実時間は進むが、
   PTS は進まない。**PTS 差なら「来ていない」ではなく「素材の間隔」だけを見る**
   （バッファが来ない限り `pending` が伸びないので、遅い PC で誤警告しない）。
3. PTS 差は qtdemux の D10 写像（segment の start/time ずれ）のような**定数オフセットが消える**。
   生 PTS ではなく demux/parser の出力 PTS（stream time）でよい。
4. `GST_BUFFER_PTS` が `GST_CLOCK_TIME_NONE` のバッファは無視する。
   PTS が逆行（TS の 33bit wrap 等）したら区間を破棄して**そのキーフレームでアンカーし直す**。
5. 再生レートが 4x なら素材の 3 秒は実時間 0.75 秒で来る（警告が早く出る）が、
   素材についての断定は変わらないので許容する。

補足: プローブは queue / decoder / appsink の backpressure を受ける位置にあるため、
デコード先読みは高々 1 秒未満。実時間 3〜4 秒で出るという目標は保てる。

### 2-2. 状態機械（純関数ヘッダ）

GStreamer に依存しない純関数として `include/tcs_gop_policy.h` を追加する
（既存の `tcs_delivery_policy.h` / `tcs_decode_policy.h` と同じ流儀。テストは `shim_test.cpp:286` の
`run_delivery_policy_tests` と同様に `run_gop_policy_tests()` を足す）。

```c
/* 0.4.5-C: long-GOP warning tracker. Pure logic, no GStreamer types. */
#define TCS_GOP_STATE_MEASURING 0   /* no gap >= threshold observed yet */
#define TCS_GOP_STATE_WARNING   1   /* a gap >= threshold was observed (latched) */

typedef struct TcsGopTracker {
  int32_t  state;              /* TCS_GOP_STATE_* */
  int32_t  anchor_valid;
  int64_t  anchor_pts_ns;      /* last keyframe PTS; 0 while waiting after a re-anchor */
  int64_t  max_interval_ns;    /* max keyframe-to-keyframe interval (0 = unconfirmed) */
  uint64_t keyframes;          /* keyframes observed since load */
  int64_t  threshold_ns;       /* default 3.0s, TCS_GOP_WARN_SECONDS override */
  uint64_t warning_qpc;        /* QPC when the warning latched */
} TcsGopTracker;

void tcs_gop_tracker_init(TcsGopTracker*, double threshold_sec);
void tcs_gop_tracker_reset(TcsGopTracker*);      /* load: state/keyframes/max も消す */
void tcs_gop_tracker_reanchor(TcsGopTracker*);   /* seek: anchor_valid=false のみ */
/* returns 1 when the warning latched on this observation, 0 otherwise */
int  tcs_gop_tracker_observe(TcsGopTracker*, int is_keyframe, int64_t pts_ns, uint64_t now_qpc);
```

`observe` の規則:

- `pts_ns < 0` は無視。アンカーが無効な間は**キーフレームが来るまで何もしない**（シーク直後の
  途中 GOP 開始を長 GOP と誤認しないため）。
- キーフレーム: `interval = pts − anchor` を計算して `max_interval_ns` を更新し、`anchor = pts`、
  `keyframes++`。`interval >= threshold` ならここでも警告をラッチする（非キーフレームが来ない
  素材の取りこぼし防止）。
- 非キーフレーム: `pending = pts − anchor`。`state != WARNING && pending >= threshold` で
  `state = WARNING`、`warning_qpc = now`、戻り値 1。
- 逆行（`pts < anchor`）: 区間を破棄してアンカーし直す（wrap / EOS 再開など）。

### 2-3. トラック切替・一時停止・EOS

- **トラック切替 = `tcs_player_load`**。`build_pipeline` の先頭で `gop_epoch++` + `tcs_gop_tracker_reset`。
- **一時停止**: PAUSED 中はバッファが進まない（preroll の 1 枚だけ）ので `pending` も伸びない。
  そのまま再生を続けた素材時間で判定される。追加の扱いは不要。
- **EOS 再開**など PTS が跳ぶ経路: 逆行・大跳びは `reanchor` と同じ扱いにする
  （`seek_prepare_locked` を通る経路は既に `gop_reanchor` が立つ）。
- **ギャップ凍結のヘルパロード**（`GapEnterCoordinator.LoadPrevious/NextTrack…`）は PAUSED ロードなので、
  警告は出ない。ロードのたびに shim 側はリセットされるが、アプリはトラックの印を保持するため
  点滅しない（§4-4）。

## 3. shim API（アプリへの伝え方 1/2）

`TcsStats`（`tcs_gstreamer.h:79-90`）は変更しない（ABI を触らない）。配信リング
（`TcsDeliveryEvent`）も使わない（出力トレース有効時しか実体が残らず、UI の供給源に不適）。

新しい**ポーリング用の getter** を追加する（`tcs_player_get_stats` `:3789-3806` と同じ流儀）:

```c
/* 0.4.5-C: long-GOP warning state. Safe to poll from the owner thread. */
typedef struct TcsGopStatus {
  int32_t  state;              /* TCS_GOP_STATE_* */
  int32_t  active;             /* 1 = a video chain with the GOP probe is built */
  uint64_t keyframes;          /* keyframes observed since load */
  double   max_interval_sec;   /* max keyframe interval (0 = unconfirmed) */
  double   pending_sec;        /* current buffer PTS − anchor PTS */
  double   threshold_sec;      /* effective threshold */
  uint64_t warning_qpc;        /* QPC when latched (0 = none) */
} TcsGopStatus;

TCS_GST_API int tcs_player_get_gop_status(TcsPlayer* player, TcsGopStatus* out);
```

- `TCS_OK` + ゼロ初期化（`active=0`）: パイプラインはあるがプローブ未設置（decodebin フォールバック等）。
- `TCS_ERR_NOT_LOADED`: パイプラインなし。`TCS_ERR_GENERIC`: 引数不正。
- `tcs_gop_tracker` の状態は `std::mutex gop_lock`（専用。frame_lock を増やさない）で保護する。
  プローブ（ストリーミングスレッド）と getter（UI スレッド）だけが触る。
- しきい値は `TCS_GOP_WARN_SECONDS`（既定 3.0、不正値は既定）で上書き可。
- ラッチ時に shim の `LOG` を 1 行だけ出す（`long-gop: warning latched anchor_ms=… pending_ms=…`）。

## 4. アプリ側（表示）

### 4-1. 受け取り方

- `Gst/GstNative.cs` に `TcsGopStatus` 構造体 + P/Invoke（`tcs_player_get_gop_status`）。
- `IGstNativeApi` / `GstNativeApi` に `TryGetGopStatus`、`GstPlaybackApi` に
  `TryGetGopStatus(out GopStatus)`（`TryGetTimePos` `GstPlaybackApi.cs:225-240` と同じ形）。
- **既存の 100ms UI タイマー `OnTick`（`MainWindow.xaml.cs:98, 1810-1855`）でポーリング**する。
  コールバックは追加しない（デリゲート寿命と UI スレッド marshaling を持ち込む必要がない。
  警告は 100ms 遅れても実害がない）。`_gstPlaybackApi` は MainWindow が具体型で保持済み（`:49`）。

### 4-2. 状態クラス（純ロジック）

`LongGopWarningMonitor` を新設する。入力は「現在のトラック ID」と `GopStatus?`、出力は遷移:

- トラック ID が変わったら**観測をリセット**（警告ラッチ・実測値）。トラック側に既に印があれば
  即座に「警告表示」状態から始める（再ロードで消えない）。
- `state == WARNING && active` で未ラッチなら **Latch**（ログ・トレース・プレイリスト印）。
- ラッチ後も `max_interval_sec` が増えたら **IntervalUpdated**（文言の「（実測 X.X 秒）」更新のみ）。
- ラッチは**単調**。シーク・一時停止・再ロードで消さない。同じトラックで二度ログ/トレースしない。

### 4-3. ステータス行

- `SyncViewModel`（`ViewModels/SyncViewModel.cs:191-200` のパターン）に `LongGopWarning`（string）を追加。
- XAML（`MainWindow.xaml:283-287`）の `SyncCorrectionStatusText` を `StackPanel` で包み、
  その下に `LongGopWarningText` を追加（`Foreground="#D7A24B"`、`FontSize="11"`、`TextWrapping="Wrap"`、
  `AutomationProperties.AutomationId="LongGopWarningText"`）。
  文言: 基本文 + 実測があれば「（実測 10.2 秒）」。警告なしは空文字（高さ 0）。
- 予備案: `GpuStatusText`（`:449-453`）の隣。**推奨は同期パネル**（同期の不安定さの通知なので）。

### 4-4. プレイリスト行

- `PlaylistTrack`（`PlaylistTrack.cs:3-14`）の末尾に `bool LongGopWarning = false` を追加し、
  `LongGopWarningText` / `LongGopWarningTooltip` を計算プロパティで足す。
  `ProjectSerializer` は明示フィールドだけを `TrackData` に写す（`ProjectSerializer.cs:55-68`）ため
  **プロジェクトファイルには保存されない**（セッション内の状態）。
- `PlaylistState.MarkLongGopWarning(Guid trackId)` を追加。`UpdateMediaDuration`（`:240-262`）と同じく
  `Tracks[index] = track with { LongGopWarning = true }` で置換する（`ObservableCollection` が
  行を再描画する。既に true なら no-op）。Timeline 再計算は不要。
- 行テンプレート（`MainWindow.xaml:530-586`）の先頭 `TextBlock` を `DockPanel` に変え、
  右端に警告 `TextBlock`（`Text="{Binding LongGopWarningText}"`、`ToolTip` は全文、
  `Foreground="#D7A24B"`、FontSize 10、`Margin="6,0,0,0"`）を置く。空文字なら幅 0。

### 4-5. ログとトレース

- ラッチ時: `Log.Information("Long GOP warning: track={Track} path={Path} maxIntervalMs={Max:F0} thresholdMs={Threshold:F0} keyframes={Keyframes}", …)`。
- 出力トレース有効時（`OutputTrace.Current.IsEnabled`）:
  `OutputTrace.Current.Record(new("gst.gop", "GST", Stopwatch.GetTimestamp(), Value: (long)Math.Round(maxIntervalSec * 1_000_000), Detail: "state=… keyframes=… pendingMs=… thresholdMs=… maxIntervalMs=…"))`。
  既存の µs 規約（`GstDeliveryTraceMapper` / `sync.evaluate`）に合わせ、`Value` は µs、実値は `Detail` に
  ms で明記する。ラッチ時と `max_interval_sec` 更新時に出す（素材の一覧が後から作れる粒度）。

### 4-6. アプリが守ること

- 警告は**表示だけ**。`SetPaused` / `SeekTo` / レート / 同期判定に一切触らない（プロンプト §4）。
- トラック切替で shim は自動リセットされる。アプリは**そのトラックの印を消さない**。
- `active=0`（decodebin フォールバック等）は「未計測」であり「異常なし」ではない。UI は何も出さない。

## 5. 再生せずに分かるか（読み込んだだけの判定）

**0.4.5-C ではやらない。** 検討した 2 経路:

1. **ffprobe（既存の任意依存）**: `MediaDurationReader`（`MediaDurationReader.cs:15-50`）は ffprobe が
   PATH にあるときだけ動く。`-select_streams v:0 -skip_frame nokey -show_entries frame=pts_time` で
   全キーフレーム PTS を取り最大間隔を出せる。ただし (a) ffprobe が無い環境では機能しない
   （警告の有無が環境で変わると現場が混乱する）、(b) 全編を走査するため長尺でコストが読めない。
2. **shim の demux 専用スキャン**: `filesrc ! demux ! fakesink` を別パイプラインで回し、同じ
   `tcs_gop_policy` に食わせる。3 秒ぶんの demux は実時間よりずっと速いが、**第 2 のパイプライン・
   スレッド・ライフサイクル**を shim に持ち込む（既存の「1 player = 1 pipeline」契約を崩す）。

どちらも「読み込み直後の一覧」を作れる可能性はあるが、**まず再生開始 3 秒（実測 3〜4 秒目標）で
十分**というのが指示書の判断であり、判定ロジックは §2-2 の純関数なので、後からどちらの経路にも
同じポリシーを再利用できる。**将来の追加候補**として `MediaDurationReader`（ffprobe がある場合のみ）を
自然なフックとして記録しておく。

## 6. 実装時のテスト

指示書 §5 の 4 項目は次の場所に置く:

| 指示書のテスト | 置き場 |
| --- | --- |
| キーフレームが 3 秒現れなければ警告状態になる | `tcs_gop_policy` の純テスト（`shim_test.cpp` の `run_gop_policy_tests`） |
| 1 秒間隔のキーフレームでは警告状態にならない | 同上 |
| トラック切替で状態がリセットされる | 同上（reset）+ C# `LongGopWarningMonitor`（trackId 変更） |
| 一度警告が出たトラックで点いたり消えたりしない | 同上（reanchor 後も WARNING のまま）+ C#（ラッチ単調） |

- shim 統合: 実素材/生成素材で `active=1` とプローブ設置、シークでラッチが消えないこと、
  ロードでリセットされること。
- C#: ステータス行・プレイリスト印の適用（`PlaylistState.MarkLongGopWarning` の冪等性、
  `ProjectSerializer` に保存されないこと）、既存の非E2E がすべて通ること。
- 実機は指示書 §6（10 秒 GOP 4K60 で警告までの秒数、1〜2 秒 GOP で出ないこと、ffprobe との一致）。

## 7. 触らないもの

- 同期の制御則（許容・Jump・Smooth・速度補正の分岐）。**表示だけ**。
- 再生の可否・バッファの流れ（プローブは読み取りのみ、`GST_PAD_PROBE_OK` 固定）。
- 既存 API / 構造体（`TcsStats`・`TcsDeliveryEvent`・`tcs_player_get_*` の既存分）。
- decodebin フォールバックの GOP 検出（§1-2。`active=0` で「未計測」と報告）。
