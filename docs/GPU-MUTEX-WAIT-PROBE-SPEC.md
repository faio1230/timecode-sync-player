# Spout送信mutexの取得待ち実証

2026-09-09。ユーザーの「次に進んでください」を受け、[初回実証](GPU-OUTPUT-PROBE-RESULTS-2026-09-09.md)で多数見つかったaccess mutex取得失敗を切り分ける。親が設計・評価、サブエージェントが独立試作の実装を担当する。

実装・比較は完了。[結果と次段階の判断](GPU-MUTEX-WAIT-PROBE-RESULTS-2026-09-09.md)を参照。0／1／2／4msを評価し、4msは両構成で再試験した。待ち指定の拡大だけでは安定60Hzに届かず、既定値0msを維持している。

## 比較する条件

`--mutex-wait-ms 0` と `--mutex-wait-ms 1` を、同じ新しい実行ファイルで比較する。既定は0を維持する。CLIは整数0〜4を受け付けるが、最初に評価するのは0と1だけとする。

GPU合成、送信用コピー、GPU完了確認、共有画像プール、Spout ABI、全画面のPresent設定、送信の位相は初回の条件を維持する。取得方式と送信位相を同時に変えない。

## 期限と所有権

各出力回には、スケジューラーが算出した次の予定時刻を期限として渡す。小数fpsでも別の丸め計算で期限を近似せず、同じスケジューラーの次回QPCを使う。

1. 送信用コピー完了・元画像の使用権返却後に、期限と停止要求を確認する。
2. WaitOneへ指定する待ち時間は、設定値と「期限までに残る整数ms（切り捨て）」の小さい方。待機呼び出しは1回とし、spinや再試行ループを追加しない。
3. 復帰後に停止要求と期限を再確認する。取得に成功していても、期限に達した／停止要求がある場合はmutexを返して送信を見送る。この場合、GPU仕事を発行していないので新しいGPU完了待ちは不要。
4. 期限前の取得成功なら従来どおりSendTextureを呼び、GPU完了確認後に外側mutexを返す。指定msを超過して復帰していても、次回期限前なら送信できる。指定msはOSへの要求であり、厳密な復帰時間保証ではない。
5. AbandonedMutexExceptionは所有権を得た状態として返却し、異常終了へ進める。取得失敗・期限超過・停止要求を成功公開として記録しない。

遅れた仕事を次の周期へ持ち越して追いかけない。次周期は従来の最新画像選択から再開する。待ち中に別の画像へ差し替える変更はこの比較に含めない。

Windowsの待機時間にはシステムクロック精度の影響があるため、実際の経過時間を記録する。[Microsoftの待機関数の説明](https://learn.microsoft.com/en-us/windows/win32/sync/wait-functions)。タイマー精度設定やグローバル設定をこの実証で変更しない。

## 記録と解析

- `send.acquire.start` / `send.acquire.end` を `(worker, scheduledQpc, imageId)` で照合する。開始QPCをtimeout計算の基準にも用い、WaitOne復帰直後に終了QPCを採取する。計測は小さなtimeout計算を含むCPU観測区間であり、カーネル待機だけの時間ではない。記録の追加は両時刻の採取後に行う。
- startのvalueは実際に指定した整数timeout ms。両イベントのdeadlineQpcは次回期限。endのdetailはacquired／busy／abandoned。
- 指定待ち時間、実効待ち時間の分布、取得の成否、実測時間の平均・p95・p99・最大、正の指定timeoutに対する実測超過時間、期限超過、取得後の期限超過を記録する。
- deadlineExpired／cancelledのスキップを分け、公開Hz・画像年齢・公開間隔・1秒区間最小件数・表示スキップも従来どおり評価する。
- 旧ログに取得イベントがないことは、それだけで無効にしない。新しい取得イベントでは不正な組・矛盾するmetadataを検出する。

## 実機試験

管理テスト・解析テスト・親レビュー後に、1080pで短い待ち1msの併用スモークを行う。正常終了とログを確認してから4Kキャンバスへ進む。

初回と同じDebug、GPU生成3840×2160、60Hz、32秒、解析窓 `[5,27)`、DISPLAY2の1920×1080表示、公式WinSpoutDXreceiverを使用する。common／splitそれぞれの併用で0msと1msを直列に比較する。改善した条件は再試験する。単独出力や送信位相への拡張は、この比較で必要性が生じた場合に別条件として判断する。

評価は平均Hzだけでなく、長い公開空白が減るか、全画面や生成周期を妨げないか、古い画像の送信や期限超過を増やさないかを見る。1msで改善しない場合は、実際にtimeoutしているのか、OS復帰が遅いのか、別のスキップ要因なのかを先に確認する。

0／1msの初回比較では、1msのcommon・splitとも60Hz生成・表示を維持したが、取得失敗がそれぞれ212／205回残った。取得区間の最大は2.55／1.98msで、期限超過はなかった。この証拠から、次に同じ実行ファイルで待ち指定だけを2msへ増やす。必要なら実装済み範囲内の4msまで比較し、それ以上へ無制限に待ちを伸ばさない。改善条件は再試験し、0ms条件の試行間変動も考慮する。

ログは新規の保存先へ出し、初回記録を保持する。実機は親のみ直列実行、自分で開始したプロセスだけを終了する。GPU異常があれば負荷や条件を増やす前に原因を確認する。通常設定・他アプリ・表示設定を保持し、WPR/UAC記録、GPUリセット、本体統合、hwdec変更、保留中のSpout無効化・OBS混在問題の修正は行わない。
