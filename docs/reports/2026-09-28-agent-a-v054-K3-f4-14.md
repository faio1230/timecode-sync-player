## 3. 前任の仮説の検証

### 3-1. 事実

1. **コピーとフェンスの順序（コード）**: `on_new_sample`（`tcs_gstreamer.cpp` 1615〜1618 行）は `frame_lock` の中で
   `copy_ring_locked` → `context4->Signal(ring_fence, latest_seq)` → `context->Flush()` をこの順で行い、その後で `frames` に積む。
   コピー元は復号済みのサンプルで、`GST_MAP_D3D11` で map したまま使い、同じデバイスであることを D16 の検査で確かめている（1356〜1407 行）
2. **アプリはフェンスの完了を待ってから描いている（ログ）**: f4-14 でも `holding the lease until the ring fence completes seq=683`（57.074）→
   `ring fence complete; drawing the held lease seq=683`（57.091）。`GStreamerSource.IsRingFenceComplete` は共有フェンスの値が seq に達したかを見る
3. **同じ型の 16 回中 15 回は正しい絵**（§2-3）。PAUSED を同じ ms に出したこと自体は f4-14 だけの特徴ではない
4. **修正前の 4 件は、目標フレームが 2 枚とも届いて描かれたのに同じ青い絵**（§2-2 の最終行）。
   2 枚目（dur 16.67）は PAUSED より前に publish され、別の slot（1）で acquire されている。コピーの途中で止まる状況が無くても、同じ症状が出ている
5. f4-14 の絵の左上の数字は 15 で、シーク前（PTS 15.883〜15.900）のフレームの内容

### 3-2. 判定

- 前任の仮説は **支持されない（否定寄り）**。同じ条件の回がほぼすべて正しく、条件の無い修正前の 4 件で同じ症状が出ているので、
  「ポンプの PAUSED の時機とコピーの途中」は症状の必要条件でも十分条件でもない
- 厳密には、f4-14 の slot 0 の中身（seq 683 のコピーが正しく入ったか）を直接読んだ証跡は無い。
  ただ、次の §4 の説明が正しければ、slot 0 の中身は画面に使われていない

## 4. 別の説明: Freeze の保存の門が照会位置で判定している

### 4-1. 事実（コード、`563b962`）

1. Freeze の間の描画（`GapRenderFramePolicy.Decide`）: 進入中（EnteringFreeze / WaitingForFrameStep）は `Hold`、確定後（FreezeComplete）は `GapFreeze`
2. `ComposeLayerPolicy.Decide`: `Hold` は **取得したフレームがあっても Held**（直前に合成したキャンバスの所有コピー）を描く。
   `GapFreeze` は保存済みの Freeze があればそれ、無ければ Held
3. `ComposeLayer.Compose`（`Output/ComposeLayer.cs` 138〜152 行）: Freeze を保存するのは、`gap == GapFreeze && frozen == null` の tick で、
   取得フレームか追跡中のソース画像の位置が `MatchesFreezeTarget(位置, freezeTargetSeconds)`（差 ≤ 0.05 秒）を満たすときだけ
4. `OutputEngine.ComposeTick`（1014〜1018 行）は `freezeTargetSeconds` に **`position`**（`TimelineOutputState.PositionSeconds`）を渡している
5. `PositionSeconds` は `MainWindow.SubmitOutputState` の `ReadPlaybackTimePos()` → `GstPlaybackApi.TryGetTimePos` →
   `PlaybackPositionContinuity.Observe` の値。continuity は同じ系列の中で後退 0.5 秒以内なら `_max` を返し続ける（`PlaybackPositionContinuity.cs` 79〜93 行）
6. shim の照会（`get_time_pos_locked`、3777〜3790 行）は、`paused && !pump_active` のときだけ配信した PTS を返し、ポンプ中はパイプラインの値を返す（D25-c）
7. f4-14 の最初の照会（57.053）はポンプが終わる前で 20.033。以後の照会（19.983）は continuity に 20.033 へ引き上げられる（`capture confirmed` の行でも `actual=20.033`）
8. 倍精度で `|19.983333333 − 20.033333333| = 0.05000000000000071`、`> 0.05`（`20.033333334` でも同じ。一致するのは 20.033333332 以下）
9. 修正前は UI 側の確定の門も照会位置で見ていて（§9-1）、`ForceFreezeComplete` の後も絵は青のまま 8 秒変わらなかった（§2-2）

### 4-2. 推論（f4-14 で起きたこと）

1. 57.044 のシークから Freeze の進入中は `Hold` で、画面は Held（シーク前に最後に合成したキャンバス = seq 681、PTS 15.883、数字 15）
2. 57.091 に seq 683 を描く tick が来るが、`Hold` なので画面は Held のまま。`TrackSourceFrame` は seq 683 を位置 19.983 で追跡する
3. 57.207 の確定で `GapFreeze` に変わる。追跡中の画像の位置 19.983 と比較相手 20.033 の差が 0.05 を僅かに超え、`SaveFreeze` が呼ばれない
4. `frozen == null` なので `GapFreeze` でも Held を描く。照会位置は continuity で 20.033 のまま（試験の位置の表示 20.017 = 20.0333… の切り捨て）で、以後も保存されない
5. 成功した回は照会位置が 19.983 で、差 0 で保存されている。2 枚目のフレームが来ない回（16 回）も同じ

この説明なら、次の 3 点がそろって説明できる: 絵がシーク前のもの（数字 15）であること、8 秒変わらないこと、修正前の 4 件（目標フレームは 2 枚とも届いていた）でも同じ絵だったこと。

### 4-3. 足りない証拠（推論の弱いところ）

- `ComposeLayer` は保存しなかったことをログに出していない。GapFreeze の tick の `LayerAction`（DrawHeld か DrawFrozen か）もログに無い
- 照会位置の値は小数 3 桁でしか残っていない。差が境界（0.05）ちょうどなので、値が `20.033333332` 以下なら一致して保存される。
  その場合は Freeze が slot 0 の中身から保存されたことになり、slot 0 の中身が古かった（前任の仮説の側）に戻る。
  ただし修正前の 4 件では 2 枚目のフレームが別の slot で描かれていて、2 つの slot がそろって古い中身になる必要があるので、こちらの可能性は低いと見る
- 20.033 が「尺 + 2 フレーム」になる理由（§9-1 の記述、D10 の qtdemux の 2 フレームのずれと同じ量）はコードで確かめていない。
  6 回とも同じ値なので、クロックで進む値ではなく決まった値（例 20033333333ns）だと推測している

直接確かめるには、`ComposeLayer` の GapFreeze の tick で「追跡中の画像があるのに目標と一致せず保存しなかった」ときに、位置・比較相手・差を Debug で 1 行出す計測（挙動は変えない）を入れて、F-4 を回すのが早い。
照会位置が 20.033 になるのは確定 336 回に 2 回（約 0.6%）なので、1 本の合格では何も言えない。
回数を数えるなら、「照会位置が目標から離れたまま確定した回」を分母にする。

## 5. 直し方の候補（実装はしない）

いずれも shim のロックの規則 I13 に触れない（案 C も照会だけで、状態変更・シークを増やさない）。

### 案 A（推奨）: 保存の比較相手を「Freeze の目標」にする（アプリだけ、定数を足さない）

- `TimelineOutputState` に Freeze の目標（`double?`）を足し、`SubmitOutputState` で `GapFreezeHandler` が EnteringFreeze / WaitingForFrameStep / FreezeComplete のときに
  その目標（C-4 の門と同じ値）を入れる。`ComposeTick` はこれを `freezeTargetSeconds` に渡す（無いときは今どおり `position`）
- 門の意味は D26 のまま（ジャンプ前の絵を凍結しない）: シーク前のフレームの PTS（15.9）は目標（19.983）から遠いので保存されない
- 既存の 0.05 秒はそのまま使い、新しい定数は無い。C-4 と同じ「配信 PTS と目標」の比較になり、2 つの門が同じものを見る
- テスト: D26-b の契約テスト（`a2e39bb`）の並びに、「照会位置 20.033・追跡中の画像の PTS 19.983・目標 19.983 → 保存する」を赤いテストで先に入れる
- ほかの経路への影響:
  - step（WaitingForFrameStep）: 同じ目標で判定するので、照会位置がずれたときに保存できるようになる。step の目標がハンドラに入っているかは実装時に確認
  - 読み込み（F-5 の次のトラックの先頭、目標 5.000）: 照会位置が目標どおりなら変わらない。ずれたときは今より保存しやすくなる（誤保存の心配は、目標 ±0.05 の外のフレームが弾かれるので増えない）
  - S-load（開始位置つきの一時停止のロード、`95e2074`）: 開始シークの目標が目標として渡るなら同上。ロードの間に `EnsureSourceGeneration` が Freeze を消す動きは変わらない
  - `CaptureCurrentFrameForGapFreeze`（現在のフレームを最終位置で保持）: 目標は「最終位置」。今は照会位置と比べているので、照会位置と目標が違うときの挙動が変わる。この経路の目標の値を実装時に確認する

### 案 B: 位置で比べず、UI が受け入れたフレームそのもの（世代・seq）を保存する（アプリだけ、定数を 1 つ減らせる）

- UI が `ui.frame accepted as the target frame` と判定したフレームの（世代, seq）を `TimelineOutputState` で GPU worker へ渡し、
  `ComposeLayer` は追跡中の画像のうち seq が一致するものだけを保存する。`FreezeTargetToleranceSeconds`（0.05）を消せる
- 門が UI 側の 1 つにまとまる（段 B の「着地の事象の一本化」の向き）
- 触る範囲は案 A より広い（`TrackSourceFrame` に seq を持たせる、`SourceFrameReady` の値の受け渡し）
- ほかの経路への影響: step・読み込み・S-load は同じ UI の判定（D21-b）を通るなら同じに動く。
  UI の判定を通らない `CaptureCurrentFrameForGapFreeze` は seq が無いので、別の扱い（現在のフレームの seq を使う）が要る

### 案 C: 根の側。ポンプ中の照会がパイプラインの値を返さないようにする（shim）

- D25-c を広げ、ポンプ中は現世代の配信 PTS を、まだ配信が無ければ「位置不明」（0.4.5-A の fallback と同じ `TCS_ERR_NOT_LOADED`）を返す。
  continuity が 20.033 を種にしないので、C-4 の門・保存の門・着地の門のどれも照会位置の 20.033 を見なくなる
- 定数は足さない。照会は既に `frame_lock` の中で行っていて、状態変更・シークは増えないので I13 に触れない
- ほかの経路への影響:
  - ポンプ中（実測 5〜192ms、§9-3）の位置が不明になる。同期の判断はその間保留になり、着地の判定が数 ms〜百数十 ms 遅れうる
  - step（`tcs_player_step_frame` もポンプを張る）: 1 フレーム送りの間、位置の表示が一瞬消える
  - 読み込み・S-load: 開始シークのポンプ中は位置が不明。ロードの成功判定や UI の時刻表示が位置に頼っていないかを確認する必要がある
- shim の変更なので Debug/Release のビルド、`scripts/check-shim-lock-rule.py`、`--policy-only`、重い素材の回帰を同じ統合に含める。
  案 A か B の代わりではなく、別の項目として検討するのがよい（照会位置の揺れは他の門にも効く）
