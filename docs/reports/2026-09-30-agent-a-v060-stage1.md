## shim が GstContext を配る経路（コードで確かめたこと、親の追加指示 2）

- 中身: `give_device_context`（`tcs_gstreamer.cpp`）が型 `GST_D3D11_DEVICE_HANDLE_CONTEXT_TYPE`（`gst.d3d11.device.handle`）、persistent の context を作り、`device` = `p->gst_dev`（shim の `ID3D11Device` を `gst_d3d11_device_new_wrapped` で包んだもの。デバイスは外部デバイスのアダプタの LUID で shim が作る）と、**固定値の `adapter` = 0u** を入れて `gst_element_set_context` する。
- prores-gpu の試行での順番:
  1. `set_decoder_adapter_luid` で dec の `adapter-luid` に shim の LUID を書く（要素の作成の確認の直後、bin に入れる前、状態は NULL）
  2. bin に入れた後、`give_device_context (p, p->vdec)` で **dec に直接 set_context**（ここで `via=set_context` の行）。LUID は 1 で書き済みなので、プラグインが LUID の一致で受け入れを決めるなら、この時点で一致の判定ができる
  3. 同じ関数の最後の `give_device_context (p, p->pipeline)` と、試行ループで demux を繋いだ後の `give_device_context (p, p->pipeline)`。GstBin の set_context は子へ配るので、dec は同じ context を合計 3 回受け取る
  4. その後でパイプラインのバスに `sync_bus_handler` を付け（`gst_bus_set_sync_handler`）、`set_state(PLAYING)`。要素が NEED_CONTEXT を出したら、同期ハンドラが同じ context を送り主へ set_context し、メッセージを捨てる（`GST_BUS_DROP`）。dec がここに来たら `via=sync-handler` の行
- つまり主経路は **要素への set_context**（NULL の状態で、LUID を書いた後）で、同期ハンドラは要素が自分から尋ねたときの受け口。`via=sync-handler` の行が出るのは、dec が set_context で受け取った context を使わずに尋ね直したとき（受け入れなかった兆候）。
- `adapter` = 0u は実際のアダプタの番号と関係なく 0 の固定値。プラグインが LUID でなく番号で照合する場合は、0 番以外のアダプタ（Optimus の RTX など）で一致しない可能性がある（親の情報では LUID の指定があれば LUID で照合するので、段 1 では変えていない）。
- 自作に落ちたかの見分け: `via=sync-handler` の行が出る、`adapter-luid ... read` が `set` と違う、`out-mem ... same=0`。3 つ目が判定の根拠。

## `.cso` が無いときの shim の試行の進み方（コードを読んだ結果、親の追加指示 3）

前提（親の情報）: 要素の作成は成功し、start()（READY→PAUSED）で RESOURCE/NOT_FOUND のエラーを出す。

- 要素は作れるので `build_video_chain_static` は通り（`chain-fail` にはならない）、`adapter-luid` も書ける。
- 試行ループは `gst_element_set_state (p->pipeline, GST_STATE_PLAYING)` を呼ぶ。GStreamer では NULL→READY→PAUSED の各段の子の状態変更が呼び出したスレッドで同期に走り、GstVideoDecoder は start() が FALSE なら READY→PAUSED を FAILURE で返し、bin も FAILURE を返す（GStreamer の一般の動き。この機で実行しての確認はしていない）。その場合 shim は `scr == GST_STATE_CHANGE_FAILURE` の分岐で `adapter-luid ... at=set-state-fail` → `load.attempt ... result=set-state-fail` → `teardown_pipeline` → `continue` で、**待ちに入らずに次の試行（prores-cpu）へ進む**。
- もし `set_state` が FAILURE を返さずにエラーだけがバスに出る場合（ASYNC のまま）: バスのスレッド（`bus_loop`、`set_state` の前に起動、2ms ごとに ERROR/EOS を取る）の `handle_bus_message` が frame_lock の下で `p->failed = true` と `last_bus_error` を立てる。preroll の待ち（100ms×30）は各 100ms の区切りで `p->failed` を見て抜け、最初のフレームの待ち（50ms×300）も `done = ... || p->failed` ですぐ抜ける。成否の門 `tcs_load_attempt_ok` は failed=1 で不合格、caps が決まっていないので `tcs_load_failure_is_caps_missing` が真になり `result=caps-missing` と記録して次へ進む。遅れは最大で preroll の 1 区切り（100ms）程度で、3 秒の満了は待たない。
- どちらの経路でも last-good は prores-gpu にならない（成功の門を通らないため）。バスのエラーの文言は `bus error: ...` の行に出て、全滅したときは `all video profiles failed ... (last: ...)` に入る。
- 実機でどちらの経路になるか（`result=set-state-fail` か `caps-missing` か）は親の確認で分かる。

## 気づいた点（コードとプラグインの introspection で分かった事実）

`gst-inspect-1.0 proresd3d11dec`（GStreamer 1.28.2、`GST_PLUGIN_PATH` に `native\gst-prores` を足して実行）:

- `adapter-luid`: **Integer64（gint64）**、範囲は符号つき 64 bit 全域、**既定 0**、`readable, writable, changeable only in NULL or READY state`。説明は「DXGI adapter LUID to use (0 = use the adapter index). Reads back the LUID of the device in use once the element has one」。
- `adapter`: Integer、既定 -1（「-1 selects default」）。shim は触っていない。
- `shader-directory`: String、既定 null（「Override directory containing prores_vld.cso and prores_idct_unorm.cso」）。既定のときにどこから読むか（Q7）は introspection では分からない。shim は触っていない。
- 要素の **Rank は none (0)**。decodebin の最終手段では自動で選ばれない（明示のプロファイル経由でだけ使われる）。
- sink: `video/x-prores`、variant は proxy / lt / standard / hq / 4444 / 4444xq、16〜8192、progressive / interleaved。
- src: `video/x-raw(memory:D3D11Memory)`、format は I422_10LE・Y444_10LE・I422_12LE・Y444_12LE・AYUV64。5 つとも `d3d11colorconvert` の pad template に含まれる（introspection の文字列の照合だけ。実際のネゴシエーションは未確認）。
- プラグインにはもう 1 つの要素 `proresd3d11rgb` がある（README）。shim では使っていない。
- 開発機の VC++ の `Runtimes\x64` は `v14.50.35719.00`。この機では `gst-inspect` でプラグインがロードできた。
- zip の README: MSVC 19.50 でビルド、「Microsoft Visual C++ Redistributable 2015-2026 x64, version 14.50 or later」、「Tested only on NVIDIA GeForce RTX 3070」、WARP / ソフトウェアのアダプタは断る。

コードから:

- ProRes の素材では、hardware の順で h264-gpu〜av1-gpu の 4 試行が先に来て、それぞれ D16・D16-b を通って連鎖を組み、pad の caps の不一致で次へ進む（これは今までの prores-cpu と同じ。prores-gpu は 5 番目の試行になる）。
- `on_new_sample` の D16 の守り（appsink に来たテクスチャのデバイスが shim のデバイスでなければ `failed`）は appsink の手前（`d3d11colorconvert` の後）で効く。デコーダの出力が別のデバイスでも、`d3d11colorconvert` が shim のデバイスへ移せばこの守りは通る。そのため「デコーダの出力のデバイス」は `out-mem` の行でしか分からない。
- 同梱でないときに `GST_PLUGIN_PATH` が変わると、GStreamer のレジストリ（既定の `%LOCALAPPDATA%` の下）がその回の起動で作り直される見込み（最初の起動が少し遅くなりうる）。
- 試験のプロジェクトの `bin` にも `gst-extra-plugins` が入るので、このブランチで E2E を回すと ProRes の素材は prores-gpu で開く（開けなければ prores-cpu）。

## 親が実機で確かめる手順（案）

前提: コンソールのセッション（RDP ではない）、出力先は RTX。ほかの担当が実機の試験を回していないこと。

1. このブランチで `powershell -File scripts\get-prores-plugin.ps1`、shim の Debug のビルドと `native\tcs_gstreamer.dll` への配置、`dotnet build`。`bin\Debug\net8.0-windows\gst-extra-plugins\` に 7 ファイルがあることを見る。
2. Debug のアプリを起動し、ProRes 4K60 の素材（開発機は `make-heavy-media.ps1` の ProRes 4K 59.94、検証機は M1）を 1 本ロードする。
3. `logs\tcs-gst-*.log` で次を見る:
   - `video-chain: prores-gpu elements=queue…,proresd3d11dec…,d3d11colorconvert…,capsfilter…,appsink…`
   - `prores-gpu: context given via=set_context (...)` が出て、`via=sync-handler` の行が**出ない**こと（出たら dec が context を受け入れずに尋ね直した）
   - `prores-gpu: adapter-luid set=<X> read=<Y> at=first-frame-wait frame=1`（X と Y が同じか。X が shim のデバイスのアダプタの LUID か）
   - `prores-gpu: out-mem d3d11=1 dev=… shim-dev=… same=1`（**`same=1` が段 1 の判定の根拠**。`d3d11=0` や `same=0` ならここで止めてプラグイン側へ＝Q4）
   - `decode.caps profile=prores-gpu dec-src=… sink=…`（colorimetry・range）
   - `load.attempt … profile=prores-gpu result=ok` と `load.summary … profile=prores-gpu`
   - 画面のメタデータ行が `V:proresd3d11dec`
4. 色の比較の材料: アプリを閉じ、`bin\Debug\net8.0-windows\gst-extra-plugins` を一時的に別の名前にして同じ素材をロードし（このとき prores-gpu は `chain-fail` になる見込み。その行も見る）、`decode.caps profile=prores-cpu dec-src=… sink=…` を 3 の行と並べる（段 2 の `TCS_PRORES_GPU=off` の代わり）。終わったらフォルダ名を戻す。
5. DLL あり・`.cso` なし: アプリを閉じ、`bin\Debug\net8.0-windows\gst-extra-plugins\` の `prores_*.cso` 6 個を一時的に別のフォルダへ移して（DLL は残す）同じ素材をロードする。見る行:
   - `video-chain: prores-gpu ...` と `prores-gpu: context given via=set_context`（要素は作れる）
   - `bus error: ...`（RESOURCE/NOT_FOUND の文言）
   - `prores-gpu: adapter-luid ... at=set-state-fail` と `load.attempt ... profile=prores-gpu result=set-state-fail`、または `result=caps-missing`（どちらの経路か）。その行の `total_ms` が 3000 に近くないこと（preroll の満了を待っていない）
   - 続く `load.attempt ... profile=prores-cpu result=ok` と `load.summary ... profile=prores-cpu`、メタデータ行 `V:avdec_prores`
   - 終わったら `.cso` を戻す
6. 失敗のときの見分け: `has no gint64 adapter-luid property -> chain-fail` や要素が作れない（`chain factory failed for profile prores-gpu`）はプラグインのロードの失敗（CRT の版・`GST_PLUGIN_PATH`）。`GST_DEBUG=GST_PLUGIN_LOADING:4` で理由が出る。`preroll-timeout`・`caps-missing` はネゴシエーションか復号の失敗で、その直後の `diag:` の `elem vdec … srccaps=…` の行が手がかり。
7. 最初の起動の時間（レジストリの作り直し）を 2 回目の起動と比べて記録しておく（設計書 8 節の「起動」の材料）。
