## 4. `CaptureCurrentFrameForGapFreeze` で変わり得た条件と、そのための変更

- この経路はシークしない。入口の判定は照会位置（`loadedPositionSeconds`）が目標の ±1 フレーム以内で、保存されるのは直前に取得した絵
- 目標と比べるようにすると、その絵の PTS と目標の差が 0.05 秒を超えるときに保存されなくなる。
  例: 25fps（1 フレーム 0.04 秒）で、入口の照会位置が目標の 1 フレーム手前、表示中の絵がさらに 1 フレーム手前（差 0.08）。
  以前はその絵の PTS と照会位置（一時停止後は配信した PTS）を比べていたので保存できていた
- 保存されないと表示は Held になる（同じ絵）。ただし Freeze が無い状態が続き、同じ目標への再進入で Freeze を使う場面の挙動が変わる
- そのため、この経路の間は目標を渡さない（照会位置で比べる）ことにした。この経路はシークしないので、f4-14 の原因（ポンプ中の照会がパイプライン値に固定される）は起きない
- テスト: `GapFreezeHandlerTests.OutputFreezeTarget_CurrentFramePath_KeepsQueriedPositionThroughConfirm`（捕捉中・確定後とも null、次のシークの進入では目標）

## 8. TSP-Fable の追加 1: 窓の境界（`3612c63`・`7d3f0ca`）

- 原因の読み: 位置はフレーム格子（ns）に乗った値なのに、秒の小数で閾値を切っていた。
  2 フレームちょうどの差でも倍精度では境界をわずかに超える（例 60fps で 16.716666667 − 16.683333333 は 2/60 を 6.7e-10 超える）
- 表し方: `GapFreezeFrameWindow.Contains(位置, 目標, フレーム時間)` = `|位置 − 目標| ≤ 2 × フレーム時間 + 1e-6`。
  2 フレームは D21-b の到着の判定の値で、既存の比較に散っていた `2.0` を `GapFreezeFrameWindow.Frames` の 1 か所にした。
  合成層の 0.05 秒（`FreezeTargetToleranceSeconds`）は消した。規則の定数は増えていない（余裕の 1e-6 は丸め誤差のための値）
- 0.05 が何フレームに当たるか: 消したコメントは「D21-b のフレーム到着判定（±2 フレーム）と同じ意図で、25〜60fps の 1〜3 フレームに収まる値」。
  意図が ±2 フレームなので 2 フレームにした。幅は fps で変わる:

| fps | 以前（0.05 秒） | 今（2 フレーム + 1µs） |
| --- | --- | --- |
| 60 | 0.05（3 フレーム） | 0.033334（狭くなった） |
| 59.94 | 0.05 | 0.033368（狭くなった） |
| 30 | 0.05（1.5 フレーム） | 0.066668（広くなった） |
| 25 | 0.05（1.25 フレーム） | 0.080001（広くなった） |
| 24 | 0.05（1.2 フレーム） | 0.083334（広くなった） |

- fps が不明なとき（コードで確認）:
  - 合成層: `MainWindow.SubmitOutputState` が `_fps` を `TimelineOutputState.VideoFps` で渡す。`GapFreezeFrameWindow.FrameSeconds` は 0 以下・非有限を `GapFreezeHandler.DefaultFallbackFps`（30）として扱う
  - UI の確定の門: `TryCompleteGapFreeze` が `_fps > 0 ? _fps : DefaultFallbackFps`、`GapFrameCaptureCoordinator.Decide` も fps が 0 以下なら 30。到着の判定（`OnSourceFrameReady`）と遅延確定（`IsLateConfirmFrame`）も同じ 30。
    合成層と UI が同じ 30 を使う
- そろえた比較（±2 フレームで目標と比べる 6 か所）: `ContinueModePlaybackPolicy.ShouldCaptureFreezeFrameAfterFrameStep`（C-4 の門）、`GapFreezeHandler.IsLateConfirmFrame`、
  `MainWindow.OnSourceFrameReady` の到着の判定とそのログの判定、`MainWindow.LogGapFreezeDecision`、`ComposeLayer.MatchesFreezeTarget`、シナリオ試験の写し（`GapFreezeEosRaceTests`）。
  ±1 フレームの進入の判定（`DecideGapEnter`）と同期の許容（`SyncDecisionEngine.ToleranceSeconds`）は別の窓なので触っていない
- テスト（`3612c63` で赤 3 件を確かめ、`7d3f0ca` で緑）:
  - `ContinueModePlaybackPolicyTests.ShouldCaptureFreezeFrameAfterFrameStep_AcceptsExactlyTwoFramesOnTheNanosecondGrid`（赤→緑）、`..._RejectsThreeFrames`（緑）
  - `GapFreezeHandlerTests.IsLateConfirmFrame_AcceptsExactlyTwoFramesOnTheNanosecondGrid`（赤→緑、3 フレームは外）
  - `ComposeLayerHeldTests.GapFreeze_SavesFrameExactlyTwoFramesFromTheTarget`（赤→緑。60fps の ns 格子、25fps、fps 不明 = 30fps の 3 通りで「差がちょうど境界 → 保存する」）、
    `GapFreeze_DoesNotSaveFrameThreeFramesFromTheTarget_WhenFpsIsUnknown`（緑）
- **自分で足したテストの書き換え（1 件）**: `610fdd1` の `GapFreeze_QueriedPositionStuckAtPipelineValue_IsOutsideTheTolerance` は fps を渡していなかった。
  窓が fps 依存になり、fps 不明（30fps、幅 0.0667）では差 0.05 が窓の中に入って期待と逆になる。60fps を明示し、「3 フレーム離れは窓の外」として読むよう書き直した。
  起きなくなったこと: なし（この試験が表す f4-14 の状況は 60fps の素材）。既存（このセッションより前）のテストは変えていない
- 狭くなった 60fps での影響（コードで読んだ範囲）: 以前 0.05 で通っていて 2 フレームを超える差は、UI の確定の門（もともと ±2 フレーム）を通らないので、確定の経路では変わらない。
  変わり得るのは、現在の絵をそのまま確定する経路（照会位置と表示中の PTS の差が 2〜3 フレーム）と、ギャップ外で追跡画像を上書きするかの判断（`TrackSourceFrame`）。
  前者は保存されず Held（同じ絵）になる。実機では確かめていない
