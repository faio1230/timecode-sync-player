## 2. 変更の要約

- 比較の窓 0.05 秒（`FreezeTargetToleranceSeconds`）はそのまま。新しい定数は無い
- `OutputFreezeTargetSeconds` の選び方（`OnSourceFrameReady` の目標の選び方と同じ）:
  - EnteringFreeze / WaitingForFrameStep: `PendingTargetSeconds`
  - FreezeComplete: `LateConfirmTargetSeconds`、無ければ `CachedTargetKnown` のとき `CachedTargetSeconds`、どちらも無ければ null
  - それ以外（Inactive・BlackFrameActive・ForceBlack）: null
  - 現在の絵をそのまま確定する進入（`EnterFreezeCaptureWithCurrentFrame`）の間は、状態によらず null。次の `EnterFreezeCapture`・`Reset`・遷移の取り消しで解除する
- null のとき合成層は今どおり照会位置で比べる
- `ComposeLayer.Compose` のシグネチャは変えていない（渡す値だけが変わる）
- Freeze の状態と目標は同じ `SubmitOutputState` の 1 件の中で渡るので、GapFreeze の tick に目標が遅れて届くことはない
- 増えた状態: `GapFreezeHandler._captureUsesCurrentFrame`（bool 1 つ）。§4 の理由による

## 4. `CaptureCurrentFrameForGapFreeze` で変わり得た条件と、そのための変更

- この経路はシークしない。入口の判定は照会位置（`loadedPositionSeconds`）が目標の ±1 フレーム以内で、保存されるのは直前に取得した絵
- 目標と比べるようにすると、その絵の PTS と目標の差が 0.05 秒を超えるときに保存されなくなる。
  例: 25fps（1 フレーム 0.04 秒）で、入口の照会位置が目標の 1 フレーム手前、表示中の絵がさらに 1 フレーム手前（差 0.08）。
  以前はその絵の PTS と照会位置（一時停止後は配信した PTS）を比べていたので保存できていた
- 保存されないと表示は Held になる（同じ絵）。ただし Freeze が無い状態が続き、同じ目標への再進入で Freeze を使う場面の挙動が変わる
- そのため、この経路の間は目標を渡さない（照会位置で比べる）ことにした。この経路はシークしないので、f4-14 の原因（ポンプ中の照会がパイプライン値に固定される）は起きない
- テスト: `GapFreezeHandlerTests.OutputFreezeTarget_CurrentFramePath_KeepsQueriedPositionThroughConfirm`（捕捉中・確定後とも null、次のシークの進入では目標）

## 7. 未解決の疑問

1. 実機の証拠はまだ無い。照会位置が 20.033 のまま確定した回は、修正後の確定 336 回に 2 回（約 0.6%）。
   次の F-4 では、`ui.decide capture confirmed ... actual=20.033` の回を分母にし、その回の絵と `layer.freeze Freeze not saved` の有無を見る必要がある
2. 時間切れの後（D32 の遅延確定の目標が残る間）に合成層が保存するようになった。これは修正前の A1 の 4 件の経路。
   遅延確定（UI 側）がまだ確定していないのに合成層の Freeze が先に保存されることになる。表示は目標のフレームになるが、UI の状態（Cached に入らない）とは食い違う
3. ロードの 2 経路では、`LoadPausedAt` から `EnterFreezeCaptureWithReload` までの間、目標は直前の状態のまま。
   直前が FreezeComplete（前のギャップの確定済み）で、ロードの世代切替で Freeze が消えた tick があると、前の目標で比べることになる。
   以前はこの間も照会位置で比べていた。UI スレッドの同じ呼び出しの中で状態が進むので、GPU worker がこの間の状態を受け取るかは確かめていない
4. 案 C（ポンプ中の照会がパイプライン値を返す）はこの版ではやっていない。照会位置 20.033 は、着地の門など他の照会位置の利用者には残る
