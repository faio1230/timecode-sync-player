## 項目ごとの変更

### 1. ベンダーの門

- `create_or_adopt_device` でデバイスを作った後、そのデバイスの `IDXGIDevice::GetAdapter` → `GetDesc` の `VendorId` を `TcsPlayer::adapter_vendor_id` に保存し、`device adapter vendor=0x%04x` を 1 行出す。外部デバイスの LUID で作る場合も、既定のアダプタで作る場合（外部なし）も、**実際に作ったデバイスのアダプタ**から読む。読めなければ 0。
- 新しいヘッダ `native/gst-shim/include/tcs_prores_gpu_policy.h`（純関数）:
  - `tcs_prores_gpu_allowed(mode, vendor_id)`: auto は 0x10DE だけ真、on は常に真、off は常に偽。範囲外の mode は偽。
  - `tcs_prores_gpu_skip_reason`: 門が閉じたときの理由（auto → `prores-gpu-vendor`、off → `prores-gpu-off`）。開いていれば NULL。
  - `tcs_prores_gpu_unverified`: on かつ vendor が 0x10DE 以外（0 を含む）。
  - `tcs_prores_gpu_mode_parse`（auto/on/off、ASCII の大文字小文字を区別しない、他は -1）、`tcs_prores_gpu_mode_name`、`tcs_prores_gpu_adapter_mismatch`（項目 3）。
- 試行ループ: `teardown_pipeline` の直後、D16 の前で、HAP でない `prores-gpu` の番なら門を見る。閉じていれば
  `load.skip path=… attempt=N profile=prores-gpu reason=prores-gpu-off|prores-gpu-vendor vendor=0x%04x` と `load.attempt … result=skipped-prores-gpu-off|skipped-prores-gpu-vendor` を出して次へ（D16 の skip と同じ形。result の値は既存の `skipped-adapter-unsupported` などに揃えた。C# 側で result の値を読む箇所は無い）。
  開いていて on かつ未検証のベンダーなら、その試行の前に `prores-gpu: mode=on on an unverified adapter vendor=0x%04x`。
- `--policy-only` の試験 `run_prores_gpu_policy_tests`: ABI の値（0/1/2）、vendor 5 種（NVIDIA・AMD・Intel・0x1414・0）× 3 モードの真理値表、unverified は on だけ、範囲外の mode、skip の理由、環境変数の値の解釈、mode の名前、不一致の規則。

### 2. モードの入口

- C ABI（`include/tcs_gstreamer.h`、`tcs_player_set_decode_mode` の隣）: 指示書のとおり `TCS_PRORES_GPU_AUTO 0` / `ON 1` / `OFF 2` と `tcs_player_set_prores_gpu(TcsPlayer*, int)`。ヘッダの既存の書き方に合わせてマクロは `TCS_GST_API`（指示書の `TCS_API` と同じもの）。形・値・戻り値は約束のまま: TCS_OK、ロード済み・範囲外・NULL は `TCS_ERR_GENERIC`（範囲外では値を変えない。`set_decode_mode` の範囲外は `TCS_ERR_INVALID_ARG` だが、約束に従い GENERIC にした）。
- `TcsPlayer` に setter の値（`prores_gpu_setting`、未呼び出しは -1）と環境変数の値（`prores_gpu_env`、未設定・不正は -1）を別々に持つ。有効な mode は env → setting → 既定 auto の順。setter は `set_decode_mode` と同じく `state_mutex` の下で `ever_loaded` を見る。env があって setter の値と違えば `prores-gpu: setting=<x> is overridden by TCS_PRORES_GPU=<y>` を 1 行。
- `TCS_PRORES_GPU` はプレイヤーの作成時（`tcs_player_create`）に 1 回読む。不正な値は `prores-gpu: TCS_PRORES_GPU=<値> is not auto|on|off; ignored` を 1 行出して無視。
- モードの行 `prores-gpu: mode=<auto|on|off> source=<setting|env|default> vendor=0x%04x -> <enabled|disabled>` はロードごとに 1 回。出す時点は 2 つのうち早い方:
  - demux が `video/x-prores` の pad を出した後の最初の `load.attempt` の行の直前（`on_video_pad` がストリーミングスレッドで原子的なフラグを立て、制御スレッドが `log_attempt` の先頭で読む）。hardware の順では最初の試行（h264-gpu の caps 不一致）の行の前に出る。software の順（prores-cpu が先）でも出る。
  - `prores-gpu` の番が来た時点（門の判定の直前）。
  - ProRes でない素材では、どちらの条件も満たさない限り出ない（全試行が失敗して prores-gpu の番まで来た場合だけは出る）。
- ロック規則の検査が「state_mutex を取る関数が増えた」で止まったので、`scripts/check-shim-lock-rule.py` の `STATE_MUTEX_HOLDERS` に `tcs_player_set_prores_gpu` を足し、`docs/OUTPUT-GPU-INVARIANTS.md` の I13 の注に 1 段落を足した（GStreamer の呼び出しなし、制御スレッド専用の scalar 書き込みとログ 1 行）。

### 3. 不一致を失敗にする

- 段 1 の `out-mem` のプローブ（デコーダの src pad、ストリーミングスレッド）が `same` を `TcsPlayer::prores_out_same`（`std::atomic<int>`、-1 = 未報告）に書く。試行ごとに `teardown_pipeline` の直後に -1 へ戻す。
- 最初のフレームの待ちと `adapter-luid` の読み返し（段 1 のログはそのまま）の直後、D34 のゲートの手前で、`prores-gpu` の試行なら判定する（ロックは持たない）:
  - `same == 0`、または（この試行の世代のフレームが来ていて）読み返しの LUID が shim の LUID と違う → 失敗。
  - `same == -1` でフレームも無い場合は判定せず D34 のゲート（caps-missing / preroll-timeout）に任せる。
  - 既存の試験用の切替 `TCS_FORCE_DECODER_LUID_MISMATCH`（D16-b 用）が立っていれば強制的に失敗（行の末尾に ` (forced)`）。
- 失敗の行: `load.attempt … profile=prores-gpu result=decoder-adapter-mismatch …` と `load.fail profile=prores-gpu reason=decoder-adapter-mismatch same=%d read=%016llx want=%016llx`。その後 `teardown_pipeline`（frame_lock の外）して次の試行（`prores-cpu`）へ。last-good は変わらない（成功の門を通らないため）。

### 5. 壊れたフレームの WARNING

- **既存の経路**: shim のバスのスレッド（`bus_loop`）は `gst_bus_timed_pop_filtered` で ERROR と EOS だけを取り出しており、この関数は型が合わないメッセージを**捨てる**。そのため WARNING は今まで**どのデコーダのものも黙って捨てられていた**（ログにも出ない）。同期ハンドラ（`sync_bus_handler`）は NEED_CONTEXT だけを扱い、他は PASS。GOP scan の別パイプラインも ERROR/EOS だけを見る。揃える先の既存の経路は無かったので、`bus_loop` に足した。
- 変更: 取り出す型に `GST_MESSAGE_WARNING` を足し、`handle_bus_message` で `GST_STREAM_ERROR` / `GST_STREAM_ERROR_DECODE` のもの（送り主の要素は問わない）だけを数える。それ以外の WARNING は今までどおり捨てる。
  - ロードごとに最初の 1 件だけ `decode.warning profile=<名前> src=<要素名> msg=<メッセージ> debug=<先頭 200 文字、改行は空白へ>`。
  - 件数はパイプラインごと。`teardown_pipeline` がバスのスレッドを join した直後に、1 以上なら `decode.warnings profile=<名前> count=N`（N は最初の 1 件を含む総数）を出して 0 に戻す。次のロード・`tcs_player_stop`・プレイヤーの破棄・次の試行で出る。
  - profile の名前は `load.attempt` と同じ名前（試行の開始時に `TcsPlayer::pipeline_profile` に保存。バスのスレッドの起動より前に書き、join の後に戻す）。
  - ロックは取らない（原子的な変数だけ）。画面・アプリへの通知・フォールバックはしない。`max-errors` は触っていない。

### 6. GLib・GStreamer の致命的なメッセージをログへ

- `gst_init` を 2 か所（`tcs_player_create` と `tcs_scan_gop`）の `call_once` から `gst_init_once()` 1 つにまとめ、`gst_init` の直後に 1 回だけ登録する（Debug・Release 共通、条件コンパイルなし）。登録の行: `log hooks: glib default handler (warning+), gst debug ERROR (GST_DEBUG unset|set, default threshold N)`。
- GLib: `g_log_set_default_handler` で差し替え、WARNING・CRITICAL・ERROR を `glib.<レベル> domain=… fatal=0|1 msg=…` として `LOG`（ファイルへは 1 行ごとに fflush 済みの既存の経路）に出した後、**元の既定のハンドラ（戻り値。NULL なら `g_log_default_handler`）へ必ず渡す**。致命的なものの abort は GLib の `g_logv` が既定のハンドラの後に行うので、挙動は変わらない。`G_DEBUG` は触っていない。
  - 届かない経路（コードと GLib の仕様からの読み。実行しての確認はしていない）: `g_log_set_handler` でドメイン専用のハンドラを持つドメイン、構造化ログ（`G_LOG_USE_STRUCTURED` でビルドされたコードの `g_warning` など）、`g_assert` の失敗（GLib の版によっては `g_log` を通らずに表示して abort する）。
- GStreamer: `gst_debug_add_log_function` で ERROR 以下の番号（ERROR のみ）だけを `gst.ERROR cat=… obj=… at=file:line:function msg=…` として出す。量の上限として 1 秒あたり 20 行、超えた分は数えて次に通った行の後に `gst.ERROR suppressed=N (rate limit 20/s)`。
- **既定の状態（`GST_DEBUG` 未設定）で ERROR が出るか**: 出ない。GStreamer 1.28.2 の SDK の `gst/gstinfo.h` で `GST_LEVEL_DEFAULT` は `GST_LEVEL_NONE`（「so nothing get printed」）で、しきい値が NONE のままでは ERROR のメッセージもログ関数へ届かない。そのため **`GST_DEBUG` が未設定で既定のしきい値が ERROR 未満のときだけ、`gst_debug_set_default_threshold(GST_LEVEL_ERROR)` にした**。`GST_DEBUG` が設定されていればそのしきい値に触らない（その場合、ERROR 以外のレベルは shim のログには出さない）。
  - 副作用: GStreamer の既定のログ関数（stderr）にも ERROR の行が出るようになる。アプリの stderr はどこにも残らない（`tests/.../Helpers/AppStreamCapture.cs` のコメント）。ERROR の行は通常の再生では少ない見込みだが、プロファイルの試行の失敗（caps 不一致・`.cso` 欠落など）で数行出る可能性はある（実機で数を見てほしい。下の手順 5）。
  - しきい値を上げたくない場合は、この 1 行を外せば、GStreamer 側のフックは `GST_DEBUG` を設定したときだけ働く形になる（判断は親に委ねる）。

## 7. 解体の読み（`set-state-fail` の後の `teardown_pipeline`）

コードを読んだ結果。実行しての確認はしていない。

- 順番: `bus_running=false` → バスのスレッドを join（ロックを持たずに待つ。バスのスレッドが `handle_bus_message` で frame_lock を持っていても、それを放してから抜ける）→ frame_lock の下で `frames`・lease・seek の状態を片付け → gop_lock の下で GOP の計測を片付け（frame_lock とは入れ子にしない）→ **frame_lock の外で** `set_state(NULL)` → `gst_object_unref(pipeline)` → 要素の欄（`vdec` ほか）を NULL に。ロック規則に沿っている（検査も PASS）。
- `set_state(PLAYING)` が FAILURE で返った直後は、bin の状態が要素ごとにまちまち（シンク側は PAUSED まで上がり、失敗した要素より上流は READY 以下のことがある）だが、`set_state(NULL)` はどの状態からも下ろせる。ストリーミングスレッドは NULL への遷移の中で pad の非活性化によって止まる。要素の欄を NULL にするのは unref の後で、その間に要素の欄を読むのは制御スレッドだけ（ストリーミングスレッドのコールバックは引数の要素か、プレイヤーの生存期間の欄＝`device`・`gst_dev` だけを使う）。**frame_lock・共有リング・プレイヤーの欄を壊す経路は見つからなかった。** 共有リングは `teardown_pipeline` では触らない（プレイヤーの破棄の `destroy_ring` だけ）。
- `set_state(NULL)` の最中に古いパイプラインの `on_new_sample` が frame_lock を取ってフレームを積む可能性は既知（D34 のコメント。世代で弾く）。`set-state-fail` の試行ではフレームが出ないので当たらない。
- **見つけた欠陥（段 1 のコード、直していない）**: `install_first_frame_probes` の `out-mem` のプローブの文脈（`FirstFrameProbeContext`）は、プローブを付けた pad そのもの（デコーダの src pad）への参照を持つ。プローブが 1 回も発火しない試行（`set-state-fail`、`.cso` 欠落、フレームが出ない試行）では、プローブが外れないので「pad → プローブ → 文脈 → pad の参照」の循環になり、**その pad と文脈が解放されない（小さなリーク。試行 1 回あたり pad 1 つ）**。壊れる経路ではない（外れた pad にバッファは来ないので、文脈の `player` を使うことも無い）。直し方の案: `out-mem` の文脈は `dec_src` を使っていないので、参照を持たせない（`nullptr` を渡す）。赤いテストが GPU と素材なしには作れないため、指示書の「根拠を添える」を満たせず、この段では直していない。

## 8. GOP scan の読み

### (a) 走るか・何で開くか（事実）

- アプリの `SetLoadedTrack`（`MainWindow.xaml.cs`）が `BeginGopScan` を呼び、`Task.Run` のスレッド（スレッドの優先度は Lowest に下げる）で `GstPlaybackApi.ScanGop` → shim の `tcs_scan_gop` を呼ぶ。**素材の種類・コーデックで分けていない**ので ProRes でも走る（止めるのは `TCS_GOP_SCAN=off` だけ）。同じパスは 1 回だけ（`GopScanCache`）。`LoadCurrentPlaylistTrack` は `SetLoadedTrack` の後にロードを呼ぶので、**スキャンは再生のロードと並行して走る**。
- `tcs_scan_gop` は再生と別のパイプライン `filesrc ! parsebin`、parsebin が出す pad ごとに `fakesink`。映像の pad にだけ DELTA_UNIT を見るプローブ。HAP だけは pad が出た時点で読み切りを打ち切る。ProRes は最後まで読む（予算は C# から 0 が渡り、shim の既定 10 分）。
- **`GOP scan:` の行はスキャンが終わった後に出る**: `ScanGop` は `tcs_scan_gop` が戻ってからその行を書き、`tcs_scan_gop` は戻る前に `set_state(NULL)` と `gst_object_unref(pipeline)` を済ませる。したがって 13:46:05.750 の行の時点で、スキャンのパイプラインは既に解体されている。
- 復号はしない（読み）: parsebin は GStreamer の仕様でデマルチプレクサ・パーサなどだけを繋ぎ、デコーダは繋がない。ProRes にはパーサが無いので、qtdemux の `video/x-prores` の pad がそのまま出る見込み。`proresd3d11dec`（rank none）も `avdec_prores` も繋がれないはず。実行しての確認はしていない。

### (b) scan の結果を使う箇所と ProRes での値（事実）

ProRes は全フレームがキーフレームなので、scan は全サンプルをキーフレームと数え、`maxGap` ≒ 1 フレームの間隔（59.94fps で約 17ms）になる見込み。

| 使う箇所 | 挙動 | ProRes での結果 |
| --- | --- | --- |
| `GopScanVerdict.Judge`（`GopScanCache.Quality`） | maxGap > 10 秒で Error、> 5 秒で Warning、キーフレーム 2 未満は Unknown | Ok（警告なし） |
| ステータス行 `LongGopWarning`（`UpdateGopScanWarning`） | Warning/Error のときだけ文言 | 空 |
| プレイリストの印 `MarkLongGopWarning` と `Long GOP warning` のログ | Warning/Error のときだけ | 出ない |
| シーク所要の見積もり `SetSeekCostHintSeconds` | maxGap × 0.42（上限 5 秒）。**既定は 0 を渡す**（`TCS_SEEK_COST_HINT=on` のときだけ値を渡す） | 既定で 0。on でも約 7ms |

- 他に scan の結果を読む箇所は無い（`_gopScanCache`・`GopScanResult` の参照は上の 3 ファイルだけ）。再生のパイプラインの中の長い GOP の検出（`install_gop_probe`、ProRes はパーサが無いので demux の pad に付く）は scan とは別の仕組み。
- まとめ: ProRes では scan の結果は挙動を何も変えない。「イントラのみのコーデックは scan を飛ばす」にしても、失うのは「ProRes のファイル全体の読み（再生と同じディスクを並行で読む I/O）」と `GOP scan:` のログの行だけ。直すなら HAP と同じ場所（`gop_scan_pad_added` で caps の名前を見て打ち切る）に `video/x-prores` を足す形が既存の型に合う（直すのは親の判断の後）。

### (c) 致命的な型に当たりうる箇所（事実と読み）

- scan の経路のコードは `g_error`・`g_assert` を使っていない。`gst_pad_link` の失敗は無視、caps が NULL のときも分岐で避けている。

## 親が実機で確かめる手順（案）

前提: コンソールのセッション、出力先は RTX、他の担当が実機を回していない。このブランチで `powershell -File scripts\get-prores-plugin.ps1`（キャッシュがあれば照合だけ）、shim の Debug のビルドと配置（済み）、`dotnet build`。`bin\Debug\net8.0-windows\gst-extra-plugins\gstproresd3d11.dll` が 132,608 バイト（v0.2.1）であることを見る（このツリーでは確認済み）。

1. **起動時の行**: `device adapter vendor=0x10de` と `log hooks: glib default handler (warning+), gst debug ERROR (GST_DEBUG unset, default threshold 1)`。
2. **門の 3 モード × ProRes 4K60**（アプリを毎回起動し直す。環境変数はアプリの起動前に設定）:
   - 未設定（auto）: `prores-gpu: mode=auto source=default vendor=0x10de -> enabled`、`load.attempt … profile=prores-gpu result=ok`、`V:proresd3d11dec`。
   - `TCS_PRORES_GPU=off`: `mode=off source=env … -> disabled`、`load.skip … profile=prores-gpu reason=prores-gpu-off vendor=0x10de`、`load.summary … profile=prores-cpu`、`V:avdec_prores`。色の比較の材料（`decode.caps profile=prores-cpu …`）もここで取れる。
   - `TCS_PRORES_GPU=on`: `mode=on source=env … -> enabled`、RTX では unverified の行が**出ない**こと。
   - `TCS_PRORES_GPU=bogus`: `TCS_PRORES_GPU=bogus is not auto|on|off; ignored` と `source=default`。
   - H.264 の素材 1 本: `prores-gpu: mode=` の行が**出ない**こと。
   - vendor の門（auto で NVIDIA 以外）は検証機の内蔵 AMD（出力先なし）で `reason=prores-gpu-vendor vendor=0x1002` と `prores-cpu`。`on` にすると `mode=on on an unverified adapter vendor=0x1002` の後に prores-gpu を試す（合否に入れない）。
3. **不一致の失敗を人工的に起こす**: `TCS_FORCE_DECODER_LUID_MISMATCH=1` で ProRes をロード → `load.attempt … profile=prores-gpu result=decoder-adapter-mismatch` と `load.fail profile=prores-gpu reason=decoder-adapter-mismatch same=1 read=… want=… (forced)` → `profile=prores-cpu result=ok`。この切替は他の GPU プロファイル（h264-gpu など）も D16-b で飛ばすので、ProRes の素材だけで使う。本物の不一致（same=0 や LUID の違い）を起こす手段は開発機には無い（Optimus の検証機で出力先を内蔵 GPU と RTX で入れ替えても、shim はどちらでも出力先のアダプタにデバイスを作り、プラグインにはその LUID を書くので、一致する側になる見込み）。
4. **壊れたフレーム**: 開発機の ProRes 20 秒の素材を複製し、`mdat` の中ほど（ファイルの 30%・50%・70% の位置など、先頭の moov を避ける）で 16〜64 バイトずつを 0xFF などで上書きした素材を作る（Python で数行。ffmpeg の `-bsf:v noise` でもよいが、版で書式が違うので要確認）。`prores-gpu` でロードして再生し、止まらないこと、`decode.warning profile=prores-gpu src=… msg=…` が 1 行、次のロードかアプリの終了の時に `decode.warnings profile=prores-gpu count=N`。同じ素材を `TCS_PRORES_GPU=off` で開くと、`avdec_prores` の WARNING の出方（出るか、同じ STREAM/DECODE か）も比べられる。
5. **ERROR の量**: 2 の各回と `.cso` を外した回（段 1 の手順 5）で、`gst.ERROR` の行が何行出るか、`suppressed` が出るかを数える。平常の再生（ロードの後）で `gst.ERROR` が出続けないこと。
6. **GLib の行**: 平常の運用で `glib.WARNING` / `glib.CRITICAL` が出るかを数える（出るなら既存の警告で、今まで見えていなかったもの）。
