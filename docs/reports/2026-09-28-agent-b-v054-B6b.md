#### D37-c/e: 1.8 秒のずれを速度で詰めると元の欠陥（追従開始で遅れたまま走る）が再発するか

- 経路（Single、Smooth、学習値 2.0）: Engine は `rate catch-up preferred` を返してシークせず、補正は
  `rate = 1 + clamp(e / 1.0 秒, ±0.10)`（`SyncCorrectionController.RateFor`、`TimeConstantSeconds = 1.0`、`MaxRateDelta = 0.10`）。
  速度補正からシークへ切り替える仕組み（エスカレーション）は無い（`EndRateCatchUp(escalated: true)` は閾値を超えたときだけ）。
- 計算: |e| が 0.1 秒になるまでは上限 0.10 で 1 秒に 0.1 秒ずつ詰まり、1.8 → 0.1 に約 17 秒、その後は時定数 1 秒の指数で
  1 フレーム（0.04 秒）の不感帯まで約 0.9 秒。**合計約 18 秒。tol（0.24 秒）を超えている時間は約 15.6 秒**。
  ずれが縮まり続けるので「効かない」判定（2 秒で 10ms 未満の改善）は開かない。
- ハーネスは速度で位置を動かさない（`HeldLtcStopAndRunThroughTests` のコメント）ため、上は式からの計算で、実測ではない。
- 結論として書ける事実: 学習値 2.0 の素材では、追従開始で 1.8 秒遅れた状態が約 15 秒続く（元の D37-c の型が再発する）。
  Jump 補正モードでは 0.08 秒超でシークするのでこの型は起きない。

| 通常の再生中（Single・Continue 同じトラック） | M(t) = 同期に使う LTC の実効値（T2 のサンプル時計の経過と T3 のオフセットを含む）をクリップの範囲に収めた値。D7-a の先行補償（`TCS_SEEK_LATENCY_COMPENSATION`、既定は無効、上限 0.4 秒）が有効なときだけそれを足す | `SyncDecisionEngine.Decide` |
| 追従開始（同期の有効化・監視の開始） | 上と同じ（追従開始の特別扱いは無い） | 同上 |
| 着地待ち中の遠い新要求の置き換え（門 8） | その時点の要求の目標（M(t)） | `TimecodeSyncService.ReplacementSeekDecision` |
| ギャップの出口（同じトラック） | 写像した素材位置（M(t)）へ `SeekTo` を直接発行し、すぐ再開する | `ContinueOnTrackCoordinator.HandleFrame` |
| トラック切替（読み込み） | 写像した素材位置 + D7-a の補償（既定 0） | 同上 |
| 停止モードの保持の着地・ランスルーの保持の入口 | 保持値（LTC は止まっている） | `ReapplyHeldValueOnPause`・`AlignOnRunThroughHoldEntry` |

学習値 2.0 は目標には使われず、relocate の閾値 max(tol, 2.0) にだけ効く。

### (3) 先行量が無いとき、再生中の relocate は鎖になるか

**台本**: Continue、1 トラック、同期して 5 秒走った後に LTC が 3 秒前へ飛び、そのまま 30 秒進む。飛んだ後のシークの所要を c にした。Smooth。

| c（秒） | シーク | 学習値 | 飛んでから tol 以内に入るまで | 30 秒後の誤差 |
| --- | --- | --- | --- | --- |
| 0.1 | 1 | 0.120 | 着地時点で tol 以内 | −2ms |
| 0.2 | 1 | 0.200 | 着地時点で tol 以内 | −2ms |
| 0.3 | **84（鎖）** | 0.320 | 入らない | −360ms |
| 0.5 | 2 | 0.520 | 約 3.9 秒 | −2ms |
| 1.0 | 4 | 1.000 | 約 11.5 秒 | −2ms |
| 2.0 | 5 回発行して **一度も着地しない** | なし | 入らない | −6962ms（4 秒の台本） |

**着地後の遅れは c と同じ**: ログでは着地のたびに `delta=0.320`（c = 0.3 のとき）。c の間に位置は止まり、LTC は c 進むため。

**c = 0.3 の鎖**:
- 着地後の |e| は 0.320 で、閾値 max(tol 0.24, 学習値 0.320) とちょうど同じ値になる。
- 約 0.36 秒ごとに relocate が続いた（`rate catch-up preferred deltaMs=320.0 limitMs=320.0` の直後に `escalated to seek` が出る回もある）。
- 学習値は観測した着地の遅れ（40ms の刻み）で、着地後の遅れも同じ量になる。つまり |e| と閾値は作りとして同じ大きさで、どちらに倒れるかは刻みと丸めで決まる。
- c = 0.5 は 2 本で閾値の内側に倒れて速度補正へ移り、c = 1.0 は 4 本で移った。どれも同じ境界の上にある。

**c = 2.0 は一度も着地しない**:
- 着地待ちの間も LTC が進み、要求の目標が着地待ちの目標から 4×tol（0.96 秒）を超える。
- すると門 8 の置き換えが働いて、約 1 秒ごとに新しいシークに入れ替わる（`sync.gate pending-replace` の連続）。
- 所要がおよそ 4×tol を超える素材では、再生中の relocate は着地する前に置き換わり続ける。

**元の記録**: D37-e の導入時（`ae4b1ee` のコミットの文書）の M3 の分析は「シーク所要と詰めたい誤差が同じ大きさなので、シークが自分の所要ぶんの誤差を作り直す（原理的に前進しない）」で、同じ型。

**一時停止中のシーク（ギャップの出口）**:
- 台本: A[0,5)・B[8,…)、Black のギャップを経て LTC が A の中（2.0）へ戻る。
- ギャップの出口は `SeekTo` の直後に `CompleteGapExit` が再開する（着地を待たずに再開する）。
- ハーネスでは着地まで位置が止まり、着地後の遅れは c と同じだった（c = 0.3 で −316ms、c = 0.5 で −520ms）。
  その後は閾値（学習値）以内として速度補正で詰めた（0.5 のとき 1 秒で約 0.1 秒）。
- 出口の `SeekTo` は `ReportSeekSent` を通らないので着地待ちに入らない。直後の同期評価が再生位置（まだ着地前）を見て、2 本目の同期シークを出した（seeks = 2.00, 2.08）。
- 「着地の後に LTC 側へ再開する」経路（再開を着地まで待つ経路）は、今のコードのギャップの出口には無い。
- 実機の GStreamer で、一時停止中のシーク → 再開のときに遅れが c になるか（再開の基準時刻がいつ決まるか）は、この調査では確かめていない。
- 遅れないのは、LTC が止まっている場面（停止モードの保持の着地、ランスルーの保持の入口）だけ。

### (4) D37-e の「先行しない」の期待が守っている欠陥

- `ContinueOnTrackCoordinatorTests.GapExitLanding_WithLearnedSeekCost_DoesNotLookAhead` と
  `TimecodeSyncServiceTests.EvaluateDecision_GapExitLanding_DoesNotUseLookahead`（削除済み）の主張は、「ギャップ明け・切替には広げない（所要が短く過剰打ちになる）」。
- `ae4b1ee` の文書の根拠は「定常の補正シーク・ギャップ明け・トラック切替は所要が短く、先行補償が過剰打ちになる」。
  実機で起きた欠陥の番号は付いておらず、適用範囲を追従開始に限る設計の固定だった。
- 先行量を追従開始の外へ漏らしたときに実機で起きた欠陥は D37-g（`0833d37`）。
  - 境界ホールドの解除・LTC の Jump の後のシークに学習値（0.655 秒）が乗り、10.060 に対して 10.714 へ着地した。
  - その場面は LTC が止まっていたので同期評価が走らず、行き過ぎたまま前へ流れた（E2E S-3）。
- まとめると、「先行しない」が守っていたのは「LTC が進んでいない（または所要が短い）場面で先行量ぶん行き過ぎる」こと。
  - 先行量が要るのは LTC が進んでいる間の relocate。
  - 害になるのは LTC が止まっている間の relocate。
