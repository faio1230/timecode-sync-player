### #7 の修正（`5cbe146`）

1. `SingleModeSyncCoordinator`・`ContinueOnTrackCoordinator`: 位置のサンプル（`read.Sample`。秒と同じ照会の結果で、追加の照会は無い）を、
   出力トレースと関係なく常に `EvaluateDecision` に渡す。`traceEnabled` の変数と使われなくなった `using` を削除した。
2. `PlaybackPositionFeedback.Observe`: 着地済み（配信の世代 ≥ 現在の世代）の評価位置を、照会位置（`Seconds`）ではなく配信 PTS
   （`DeliveredSeconds`、基準 `Delivered`）にした。
   - 理由: shim は再生中の照会位置をパイプライン位置（基準 Pipeline）で返し、配信 PTS は別の欄（`tcs_gstreamer.cpp` の `get_time_pos_locked`）。
     旧の実装は、トレースありでも着地済みの間は照会位置で判定していた。このため赤いテストの「照会 20.483・配信 19.983」の場面は、トレースを有効にしても赤だった
     （トレースの有無だけを直しても緑にならない）。
   - 配信の有無は世代だけで決める（`DeliveredGeneration > 0`。旧は `DeliveredSeconds > 0` も条件で、PTS 0.0 の先頭フレームは未配信扱いだった）。
     B4b の補正の誤差（`TryReadDeliveredSeconds`）と同じ条件。
3. `TimecodeSyncService.EvaluateDecision`: 位置のサンプルがあり、評価位置の基準が配信 PTS でない（配信の世代 0 など）間は、relocate の粗い判定をしない。
   - `PositionUntrusted` の決定で保留し、次の評価で判定する。計数用に `sync.gate no-delivered-defer` を出す。
   - エンジンの未信頼の口は、門 12 の `untrusted-defer` の計数に混ざるので使っていない。
   - 位置のサンプルが無い呼び出しは、従来どおり照会位置で判定する（下の未解決 1）。
   - 着地待ちの枝と `TCS_SYNC_POSITION_FEEDBACK` のフラグの条件は変えていない。
   - shadow の記録（`RecordShadow`・trace の行）は、今どおりトレースが有効なときだけ。
4. 新しい定数・門は無い。shim は触っていない。

### 停止中の relocate の残差（`c58c2dd`、計測のみ）

- `held-landing`（停止モードの保持の着地）と `hold-entry`（ランスルーの保持の入口）の着地は、着地の時点で残差を 1 行出す。
  - 残差 = 着地した配信フレームの PTS − 着地先（保持値）。
  - `outside` は tol と比べる（規則 4 の入口と同じ判定）。
  - 連続 relocate の判定（`afterOutsideLanding`・`chained`）もこの残差で決まる。
- ほかの発生元は、今どおり着地の後の最初の判定で M(now) と比べる。
- 赤から緑: `B6bPredictiveLocateTests.Metrics_HeldLandingResidual_IsMeasuredAgainstTheHeldValue`。
  - 場面: 停止モード、25.0 へ飛んで保持し、40.0 で再開。
  - 旧は `errorMs=-15080.0 outside=True reason=held-landing`（再開後の M(now) と比べていた）。
  - 新は保持値と比べ、|errorMs| < 100。

## 洗い出しの表

設計書 `docs/design/v0.5.4-gate-unification.md` の §10-0 の下「10-0-1. 試験の道具で製品の判断・状態が変わる箇所の洗い出し」に、次の 3 つの表を置いた。
- A: トレースの有無で分かれる箇所
- B: 挙動を切り替える環境変数
- C: 試験用の口・試験の構成

要点:
- 出力トレースの有無で判断に効いていたのは #7 の 2 か所（Single・Continue の位置のサンプル）だけで、`5cbe146` で直した。
  そのほかの `OutputTrace.Current.IsEnabled`・`traceEnabled` の分岐は、どれも記録だけだった。
  `SeekingProbe` はトレースありで Information 行が増える。精度トレースは GPU の読み戻しの負荷が増える。
  shim の `position_trace` は `frame_lock` の中で記録を積む。
- `TCS_SYNC_POSITION_FEEDBACK` の着地待ちの枝は、旧はフラグ on かつトレースありのときだけ効いていた。
  #7 の後はトレースとは関係なくフラグだけで決まる（既定 off、負債として残す）。
- `TimecodeSyncService.RecordPositionShadow` は呼び出し元が無い（記録だけの口で、判断に効かない）。
- LTC シナリオ・E2E・精度の実行が設定する環境変数のうち、製品が読むのは次の 3 つ。いずれも挙動の切り替え（表 B）ではない。
  - `TIMECODE_SYNC_PLAYER_OUTPUT_TRACE`
  - `TIMECODE_ACCURACY_TRACE`（精度の実行だけ）
  - Spout の送信名

## 未解決の疑問

1. **位置のサンプルが無い呼び出し**は、今も照会位置で判定する。
   - 製品でこの経路に入るのは、`GstPlaybackApi.TryGetPositionSample` が例外で失敗し、`TryGetTimePos` だけが成功したときに限られる。
   - 単体テストの多く（Recorder が位置だけを返す `ContinueOnTrackCoordinatorTests` など）はこの経路で判定しており、本番の経路（配信 PTS）とは違う。
   - サンプルが無いときも「判定しない」に揃えるかは、判断が要る（揃えると、その単体テストの配置の書き換えが要る）。
2. **旧 DLL（`_ex` なし）**のフォールバックは配信の世代 0 のサンプルになるので、#7 の後は relocate も判定しない（B4b で補正は既に止まっている）。
   同梱の DLL には `_ex` がある。
3. **配信の有無を世代だけで決めた**ため、shim が配信の PTS 0 を返す間（`latest_pts_ns` が 0 の先頭フレーム）も配信済みとして扱う。
   shim の側は `latest_pts_ns > 0` を「配信あり」の条件にしている箇所がある（照会のフォールバックなど）。実機で先頭の 0.0 の着地の扱いが変わるかは確かめていない。
4. **ハーネスの偽の再生 API**は、照会位置の基準を常に `Pipeline`、着地済みの照会位置を配信と同じ値で返す。
   再生中の照会位置と配信 PTS の差（実機のパイプライン位置の先行・後退）は、`SetPositionWithoutDelivery` で作ったときだけ出る。
