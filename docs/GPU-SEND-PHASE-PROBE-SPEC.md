# Spout送信位相と画像選択の実証

2026-09-09。ユーザーの「次に進んでください」により、[短時間待ち実証](GPU-MUTEX-WAIT-PROBE-RESULTS-2026-09-09.md)の次段階を進める。親が設計・レビュー・評価、サブエージェントが独立試作と解析器を実装する。

実装と7回の直列実機試験は完了。[結果](GPU-SEND-PHASE-PROBE-RESULTS-2026-09-09.md)を参照。位相4msで画像年齢の改善は再現したが、Spoutの安定60Hzは未達。splitの位相0ms再試験では表示準備未完了も多発しており、スレッド分離だけの保証にはしない。

## 根拠と目的

前段階のsplit 5試行を既存ログで結合すると、解析窓のcopy.start 1,318〜1,320件中、当該送信回と同じ予定時刻の合成画像を使ったのは各0〜1件だった。残りは1周期前の合成画像。合成公開は予定時刻からp99約0.70〜0.95ms、最大約0.95〜2.16ms後だった。

両ワーカーが同じ予定時刻に動き始めるため、新画像の合成完了前に旧画像を選んでいる可能性が高い。ただし既存ログのcopy.startは選択そのものの時刻ではない。画像選択前後の計測を追加し、送信位相だけをずらして画像年齢と出力周期の両方を評価する。

## 変更するもの

`--send-phase-ms`（double、既定0）を追加する。有限かつ `0 <= phase < 1000 / fps`。0以外はsplitかつSpout出力を持つ条件のみ許可する。

合成・表示側のスケジューラーは従来の共通原点を維持する。送信側の原点のみ `共通原点 + round(phaseMs * QPC周波数 / 1000)` とし、同じfpsのTickScheduleを使う。次回期限はずらしたスケジューラー自身のDueQpc。終了時刻は両ワーカーとも共通原点＋指定秒数のまま。古い回の追いつき送信はしない。

画像を選ぶ処理順序、コピー、同一画像の再送、GPU完了確認、プールと所有権、mutex取得方式、全画面のPresent設定は変更しない。位相は独立試作用の設定であり、本体設定や既定出力遅延の採用ではない。

## 計測

- 既存compose.publishはプール公開直前。pool.Publish復帰直後にcompose.visibleを追加し、公開の前後を区間として記録する。
- AcquireLatest直前／直後のQPCを取得してからsend.select.start/endを記録する。両イベントは実際に選ばれた画像のstampを持ち、画像なしなら0。end detailはlatest（送信用保持画像と異なる）、retained（同じ）、none。
- 選択区間内に合成の公開区間が重なる場合、プール内部の厳密な前後関係は断定しない。選択開始前のvisibleは確実に利用可能な候補、選択終了までのpublishは利用可能だった可能性のある候補として区別する。
- 選択画像の年齢、元画像の合成予定時刻と送信予定時刻の差、公開から選択までの時間、選択時の画像番号差を集計する。コピー失敗で保持画像を送信する場合は、選択画像と実際の送信画像を混同しない。
- 公開頻度、公開間隔、1秒区間最小件数、公開時の画像年齢、mutex取得失敗、表示見送り、期限超過は従来と同じ。新イベントの対応・stamp等は解析窓外も含めて検証する。旧ログとの互換性を維持する。

## 比較手順と判定

管理テスト・解析器テスト・親レビュー後、1080p・split・位相2msの短いスモーク。正常終了を確認して4Kキャンバスの比較へ進む。

4K比較はsplit／both、GPU生成3840×2160、60Hz、32秒、warmup5秒、解析窓 `[5,27)`、同じ1920×1080表示先、公式WinSpoutDXreceiver。mutex待ち指定は4msで固定し、同じ新実行ファイルで位相0／1／2／4msを比較する。結果から有望な位相と0msを再試験する。異常時には条件を増やさず、まず原因を確認する。

目的は公開成功時の画像年齢を下げつつ全画面の周期とSpoutの公開頻度・空白を悪化させないこと。平均年齢だけ改善しても、長い公開空白や多数の見送りが増えれば採用根拠にしない。実行ごとに受信周期との相対位相が変わり得るため、単一試行の最高Hzで結論を出さない。GPU生成試作の結果はmpv再生性能や実受信・物理4K60表示を保証しない。

実機は親のみ直列実行。新規ログへ記録し、既存ログ・通常設定・他アプリ・表示設定を保持。所有プロセスだけを終了する。WPR/UAC記録、GPUリセット、hwdec変更、mainでの作業、本体統合、GPUプレビュー、保留中のSpout問題の修正へ範囲を広げない。
