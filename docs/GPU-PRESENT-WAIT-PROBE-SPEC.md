# 全画面の準備待ち0／1ms実証

## 目的と固定条件

前段の [mutex待ち8ms実証](GPU-MUTEX-8MS-PROBE-RESULTS-2026-09-09.md) を受け、split・送信位相4ms・Spout mutex要求8ms・公式WinSpoutDXreceiverを固定する。全画面のframe latency waitable objectを即時確認する現行0msと、最大1msを要求する候補を比較する。表示準備未完了の見送りを減らせるか、合成とSpoutの周期・画像年齢を悪化させないかが判断対象。

親が受信機対照試験B1（`20260909T125122043Z-split-both-4af6402d2bca4b2384159a3a213882ee`）の既存ログを照合したところ、解析窓の準備未完了301回では合成完了が予定から平均0.297ms／最大0.838ms、表示成功1,019回では平均0.295ms／最大0.909msだった。合成完了のCPU観測時刻だけでは見送りの差を説明できない。これはGPU内部原因の確定ではなく、準備確認を比較する根拠とする。

独立GPU試作のみ変更する。本体統合、mpv、hwdec、GPUプレビュー、受信機の変更は含めない。DXGI buffer count 2、MaximumFrameLatency 1、Presentの同期間隔1、共有3枚、送信側専用コピーとGPU完了確認を維持する。CLI `--present-wait-ms` は整数0〜1、既定0。非ゼロは全画面出力を含む場合だけ許可する。

## 準備確認と寿命

最新画像のleaseと共有sourceのkeyed mutexを取得した後、現在と同じ場所で準備を確認する。1周期の期限は次の予定時刻と共通試験終了時刻の小さい方。開始前に停止・期限を確認し、native waitは一度だけ、要求は `min(設定値, floor(残時間ms))` とする。要求1msは実際の復帰時刻の保証ではなく、再試行はしない。

wait後とGPU描画開始前にも期限・停止を確認する。成功した準備通知は、実際にPresentを試行するまで管理側に保持する。成功直後に期限に達した場合は画像を返し、次周期で最新画像を選び直して保持済みの準備状態を使う。古い画像のキューは作らない。成功通知後に見送って通知を失う事態を防ぐための管理状態であり、実際の物理表示完了を示すものではない。

GPU処理を発行したら期限・停止に関係なく完了または既存の安全なdrainを待ち、leaseとkeyed mutexを返す。draw完了後に期限・停止ならPresentを見送り、準備状態は保持する。Present中に共有sourceのkeyed mutexを保持しない。次周期でbackbufferを上書きできるのは既存GPU完了確認後だけ。native errorは既存の停止経路へ渡し、リセットや記録採取を追加しない。

## 記録と評価

`present.ready.start/end` に予定時刻・画像ID・期限・実効要求・結果・準備状態保持の有無を記録する。待ち前後のQPCを採ってからログへ投入する。準備済みで即座に戻った時間も含むので、待ち時間だけで「0msなら見送った画像を救った」とは数えない。保持済み状態を再利用した回とnative waitを分ける。

全ログでペア・期限・要求範囲・準備状態の遷移・Present前の準備確認を検証する。時間窓では準備未完了数、期限見送り、準備確認時間、合成／全画面／Spout公開頻度、各公開間隔、公開画像年齢、コピー見送りを比較する。CPUテストで期限直前・期限後・停止・成功通知の保持と再利用を検証する。

親がDebugビルドと管理テストを確認後、まず1080p・windowed・1msを12秒（warmup 2秒）実行。その正常終了を確認して、4K生成キャンバスで0→1→1→0msの順に各32秒（warmup 5秒、解析窓[5,27)秒）を一回ずつ直列実行する。全条件を同じ新しいバイナリで測り、各回終了と記録を確認してから次へ進む。monitor index 1の実描画寸法は1080pで、表示設定は変更しない。

0msで問題が再現しなければ有効性は未確定とする。1msで全画面だけ改善しても合成やSpoutに悪化があれば単純採用しない。短時間で全て60Hzでも常時60Hz、異なる画像の実受信、物理4K60を保証しない。最大待ちの追加拡大やswap設定の変更は別の判断項目。

既存ログ・通常設定・他アプリを保持し、終了するのは所有確認済みの起動プロセスだけ。WPR/UACのGPU記録、GPUリセットは行わない。
