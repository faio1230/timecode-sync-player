## 責務の境界

```text
再生ヘッダ・タイムライン状態 ＋ 利用可能なソース画像
                          ↓
              ポスト処理（目標60Hzで評価）
              ・現在位置に対応する画像の選択
              ・固定キャンバスへの拡大縮小・配置
              ・将来のエフェクト
                          ↓
                  通常映像のレイヤー
                          ＋
                テストカードの上位レイヤー
                          ↓
                 最新の合成済み出力画像
                  ├─ 全画面（目標60Hz）
                  ├─ Spout（目標60Hz）
                  └─ プレビュー（既存の縮小・上限）
```

クリップ、シーク、Freeze、Black、将来のフェードを解釈する責務はポスト処理側に置く。各出力は画像の意味を解釈せず、確定済み画像の画素または描画資源、寸法、公開番号、寿命を扱う。タイムラインの制御状態を出力側へ重複実装しない。

初期の「同じフレームを両出力へ渡し、両方の完了後に次の組へ進む」案は採用しない。出力ごとに独立して最新画像を使うベストエフォート方式とする。

## 画像が間に合わない場合

- 再生ヘッダの現在位置に対して、利用可能な最適な画像を選択する。
- AからBへ切り替わる時刻を過ぎてもBの画像が用意できない場合、通常映像の最後の確定画像であるAを保持する。準備待ちを理由に黒を挿入しない。
- 保持するAは、素材上の最終フレームとは限らず、最後に確定できた画像である。
- Bの準備中にヘッダがCへ進んだ場合、後から届いたBは採用しない。Aを保持し、Cの利用可能な画像へ切り替える。Bが一度も表示されないことを許容する。
- 準備待ちが長引く場合や読み込み失敗でも保持を続ける。状況は操作画面に表示し、出力へエラー表示や黒を自動挿入しない。
- 明示的なタイムラインのBlack／Freezeなどの状態は、ポスト処理が既存の意味に従って解釈する。
- 保持できる確定画像がまだ一枚もない場合、設定されたキャンバスサイズの不透明な黒を初期画像とする。

テストカードを通常映像の保持画像へ取り込まない。通常映像の確定画像と、カード合成後の確定画像は別に管理する。

## 周期と時計

- 全画面とSpoutは、素材のfpsとは独立した目標60Hzで開始する。後から設定で変更できるよう、周期を一か所から渡す。
- 全画面表示ではティアリングを避ける。表示が間に合わない回はスキップし、次の機会に最新の確定画像を使用する。ディスプレイの実際の更新周期と目標60Hzを同一とみなさず、Spoutの目標周期を表示先の更新周期へ暗黙に従属させない。具体的なPresent設定と表示準備の確認方法は実証設計で決める。
- ポスト処理も目標60Hzで再生ヘッダと利用可能な画像を評価する。新しい画像の到着だけに評価契機を限定しない。
- 再生ヘッダを進める時計の選択は既存仕様を維持する。LTCを使わない通常再生は再生エンジンの再生時計に従う。出力周期のための独立した再生時計は導入しない。
- 遅れた評価・出力回数をまとめて取り戻さない。その時点の最新状態を扱い、次の予定時刻へ進む。
- 新しい画像がないときも、各出力は保持画像で周期動作を継続する。特にSpoutは同じ画像でも送信を継続する。
- 同じ画素の再生成やコピーの省略と、周期出力の継続は別に判断する。
- 一方の出力が遅れても他方は待たない。出力間の画像番号差・公開時刻差を許容して測定する。
- 開始済みのネイティブ送信は取消済みと扱わない。実行中の画像を保持し、次の処理開始時に最新の確定画像を取得する。
- プレビューは現在の最大960×540、通常30Hz／全画面中10Hzという負荷制限を維持する。テストカードもその経路で表示する。

目標周期は実際の公開・受信・物理表示周期の保証ではない。予定時刻、処理開始／完了時刻、使用した画像番号を別々に記録し、同じ画像の再送と画像更新を区別する。

## プロジェクトの固定キャンバス

| 項目 | 合意内容 |
| --- | --- |
| 新規プロジェクト | キャンバス初期サイズ1920×1080。幅・高さをプロジェクト設定で変更可能 |
| サイズの所有 | 素材から独立したプロジェクトの設定。素材切替で自動変更しない |
| 配置方式 | 縦横比を維持した高さ合わせ／幅合わせ |
| 方式の所属 | プロジェクト既定値を持ち、クリップごとに上書き可能 |
| 初期方式 | 高さ合わせ |
| はみ出し | 指定した辺への合わせ方を優先し、キャンバス外を切り落とす |
| 配置位置 | 初期実装は中央揃え固定 |
| 余白 | 不透明な黒 |
| 将来の追加 | 配置方式の識別子と計算処理を分離し、別のフィット方式を追加できる構造 |
| 既存プロジェクト | キャンバス情報がない場合、初回にサイズを選択する。次に保存した際に記録する |
| サイズ変更 | タイムラインの再生・LTC追従を止めた状態だけで可能。Freeze／準備待ちで画が静止している状態は含めない |
| 設定の反映 | 編集途中のサイズを逐次出力せず、変更後の画像が確定したところで反映する |

### データモデルの実装案

保存形式は現在の `ProjectData`／`TrackData` を起点に拡張する。次の役割を分離し、具体的な型名やマイグレーションは実装設計で決める。

- プロジェクトの映像設定：キャンバス幅・高さ、既定の配置方式。
- クリップの配置設定：個別の方式指定。未指定はプロジェクト既定値を継承する。
- 配置の計算：素材の寸法とキャンバス設定から描画領域・切り落とし領域を決める。描画APIに依存させない。
- 将来の効果設定：配置設定と分ける。今回フェードや汎用の効果編集機能は実装しない。
- 実行時のフレーム：画像の所有権やGPU資源は保存データへ入れない。

## テストカード

- 通常映像の上に被さる独立したレイヤーとして合成する。全画面・Spout・プレビューを一括で切り替える。
- プロジェクトのキャンバスサイズで生成し、通常と同じ出力経路を通す。クリップ用の配置方式やフェードはカードへ適用しない。
- カードON/OFFで再生・LTC同期の状態を変更しない。再生中なら進行を続け、停止中なら停止を維持する。解除時はその時点の通常映像レイヤーを表示する。
- ON/OFFはプロジェクトに保存しない。アプリ起動時OFF。同じ起動中のプロジェクト切替では操作者の選択を維持する。
- 操作はタブ内の補助機能として配置する。具体的なタブへの配置は既存UIを確認して決める。
- 初期カードの候補は外周枠・中央十字・グリッド・カラーバー・解像度／目標Hz・動く目印／更新番号。具体的な図柄は未確定。

## アプリの終了

×ボタンを押した段階で、終了方法を選ぶ確認画面を表示する。その段階では再生・出力を継続する。

- キャンセル：そのまま継続。初期選択もキャンセルとし、Enterの誤入力で強制終了しない。
- 通常終了：新規処理の受け入れ停止、実行中処理の完了、所有する資源の解放を行う。待機中もUIを応答可能にし、待っている処理を表示する。
- 強制終了：確認画面から最初から選べる。一定時間の経過を待つ条件を付けない。利用者が選んだら追加確認を挟まず、送信等の完了を待たずにこのアプリを終了する。

通常終了の待機中にも強制終了を選択できるようにする。資源使用中に別スレッドから強引にDisposeして通常終了扱いにすることと、明示的なアプリ強制終了を混同しない。強制終了はWindows全体や他アプリの終了ではない。

## GPU異常時の復旧

本体の新しいGPU描画基盤について、デバイスや描画資源が無効になった場合は操作画面に通知し、自動復旧を一度だけ試す。成功時は、その時点の再生位置に対応する映像へ復帰する。復旧失敗や再発時は自動再試行を繰り返さず、操作者が手動で再試行できるようにする。

これは通常の処理遅延や素材の準備待ちとは分けて扱う。GPU資源自体が無効な場合、直前画像の継続表示は保証できない。単なる処理時間超過を、使用中資源を破棄してよい根拠にしない。終了時の通常終了／明示的な強制終了の方針も維持する。既存のSpout単発無効化問題の修正へ範囲を広げるものではない。

## GPU処理の検討

固定キャンバスへの拡大縮小・合成、将来の独自シェーダーにはGPU処理を検討する。HLSLを使用してよいという合意があり、Direct3D 11＋HLSLを最初の実証候補とする。GPU方式の採用と全面移行はまだ確定していない。

`hwdec=no`とGPUポスト処理は別の選択である。デコード設定は維持し、CPUの元画像をGPUへ渡す小さな実証から判断できる。現行のCPU配列用 `OutputFrame` をGPUテクスチャへ単純置換すれば済むとは扱わない。

最初のGPU実証について追加で合意した条件:

- 合成・全画面表示・Spout送信と受信は同じGPUを使用する。複数GPU間の転送は最初の実証に含めない。
- 操作画面はWPFを維持し、全画面の映像部分はDirect3D 11で表示する。現行のWPF `Image`／`WriteableBitmap` 経由を置き換える実証とする。本番経路への全面移行を意味しない。
- 複数の全画面は、基本的に同じ合成済みキャンバスを表示する用途とする。各画面ではキャンバス全体を縦横比を維持して中央に表示し、余白を黒にする。クリップのキャンバス内配置とは別の処理とする。
- 合成以降、全画面とSpoutへはGPU上の画像を渡す。CPUへの読み戻しと再アップロードを必要としない経路を評価する。Spout内部などのGPU内コピーまでゼロとみなさない。
- 最初の実証には、合成・全画面群・Spout送信を共通GPUスレッドで処理する比較用の基準構成を含める。Spout送信を分離する構成との比較から最終的なスレッド構成を判断する。共有スレッドで生じる他出力への待ちの影響も測定する。
- 実証は指定作業ツリー内の独立した検証用アプリで行う。最初はGPU上で生成する動く目印・画像番号付きテスト画像を使い、その後にCPU画像のアップロード、mpvの実動画を接続する。GPU生成画像だけの結果を動画再生全体の4K60達成とは扱わない。
- 初回は全画面1面とSpout1系統の単独・併用を直列で比較し、その後に全画面3面へ広げる。
- Spout分離版では、最新の合成済みGPU画像を送信専用のGPU画像へコピーしてからSendTextureへ渡す方式を実証する。GPU内コピーの完了後に合成画像の使用権を返し、その後の送信待ちから合成画像の保持期間を分離する。同じ画像を再送する場合は専用画像を再利用する。コピーの完了確認と資源再利用の同期方法は具体化が必要。追加コピーなしでも複数領域で合成を続けることは可能であり、コピーによる性能改善を前提にしない。
- 拡大縮小・合成・全画面・プレビューの映像表示を、共通のDirect3D基盤へまとめる方向で検証する。通常の映像表示経路では、アップロード後のCPU読み戻しを避ける。操作UIはWPFを維持し、プレビューの映像領域はHwndHost等でDirect3D表示を埋め込む候補とする。先に全画面とSpoutを比較し、その後にGPUプレビューを加える。既存プレビューの解像度・更新頻度上限は初期評価条件として維持する。描画基盤の共通化と、すべての処理を単一スレッドに置く判断は別とする。

映像のGPU処理への統一は実証の設計方針であり、本体全体を直ちに移行する合意ではない。CPUからGPUへのアップロード、mpv側の処理、GPU負荷、Present、Spout送信・同期は残るため、全体のボトルネック解消を事前に保証しない。GPU生成画像、CPU画像入力、mpv実動画の段階ごとに測定する。

2026-09-09の事前調査では、手元の `native/SpoutDX.dll` のPEエクスポート表を読み取り、`?SendTexture@spoutDX@@QEAA_NPEAUID3D11Texture2D@@@Z` とデバイス指定の `OpenDirectX11` の存在を確認した。この事前調査時点ではDLLのロード・GPU起動は行わず、その後の独立実証で実動作を確認した（下記の初回実証結果を参照）。DLLのSHA-256は `BBCEE6F0031F6BD1A6461585C53F3F8F3CECBF006B486661BCDE6413E2ADDEF5`。Debug出力先のDLLも同一だった。エクスポートの存在は、呼び出しの実動作や資源の寿命管理の検証を代替しない。

全画面ごとの専用スレッド／専用D3D11デバイス案は未採用。合成画像プールの5枚（全画面1面）／7枚（3面）という会話中の見積もりは、各出力が独立してGPU使用完了まで1枚ずつ保持する案に対するものだった。固定枚数の合意とは扱わず、共通スレッド案を含む最終的な所有権から算定し直す。各画面のスワップチェーン等の領域は合成画像プールと別に計上する。領域数を古い画像の待ち行列の長さと混同しない。

### OBSとSpoutプラグインの調査

OBS本体は確認時の開発コミット `012c6c23c73283ee5591ae00d08af14d9eeb8279` を参照。共通のグラフィックススレッドで合成と各displayの描画を実行する。プログラムプロジェクターは合成済みメインテクスチャを各表示先へ描く。D3D11経路では表示待ちハンドルがある場合に待ち時間ゼロで準備を確認し、準備未完了の表示先はその回の描画を飛ばす。Presentやドライバー内部の待ちが完全にないという保証ではない。

参照: [描画ループ](https://github.com/obsproject/obs-studio/blob/012c6c23c73283ee5591ae00d08af14d9eeb8279/libobs/obs-video.c)、[プロジェクター](https://github.com/obsproject/obs-studio/blob/012c6c23c73283ee5591ae00d08af14d9eeb8279/frontend/widgets/OBSProjector.cpp)、[D3D11表示処理](https://github.com/obsproject/obs-studio/blob/012c6c23c73283ee5591ae00d08af14d9eeb8279/libobs-d3d11/d3d11-subsystem.cpp#L2232)。

Off World Live製Spoutプラグインは `1.12.0`（`b7327b8bdb107a256dac4b45c2b5112298844a14`）を参照。全体出力はOBSのraw_videoコールバックでCPUのBGRA画素を受け取り、独自のD3D11デバイスを用いるSendImageへ渡す。フィルター出力はOBSのD3D11デバイスを共用し、描画コールバック内でSendTextureを呼ぶ。フィルターは中間描画領域と今回／前回の領域を持ち、前回分を送信してから今回／前回を交換する。この固定的な前回分送信を本アプリへそのまま採用する合意はない。

参照: [全体出力](https://github.com/Off-World-Live/obs-spout2-plugin/blob/1.12.0/source/win-spout-output.cpp)、[フィルター出力](https://github.com/Off-World-Live/obs-spout2-plugin/blob/1.12.0/source/win-spout-filter.cpp)。

技術調査・実証で決める事項:

1. 全画面表示とSpoutへGPU合成結果を渡す具体的なAPI経路、現行DLLの実動作、CPUへ読み戻さずに表示するGPUプレビューの埋め込み方法。
2. GPUデバイス／コンテキストの所有スレッド、合成と各出力が読む資源の分離、GPU完了確認と寿命。
3. 出力が読む画像を上書きせず、遅い出力が合成や他出力を止めない有限個の資源管理。
4. UIが持つタイムライン状態を、ポスト処理へ一貫した状態として渡す方法。出力側へクリップ判断を戻さない。
5. 実際の元画像と素材・シーク世代・時間位置の対応を、現行mpv経路でどこまで確認できるか。`time-pos`の単独読み取りを画像の厳密な時刻証明にしない。
6. カード表示を含む合成後画像と、保持対象となる通常映像の画像を分ける方法。

参考一次資料: [HLSL](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx-graphics-hlsl)、[WPFとDirect3D9の相互運用](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/wpf-and-direct3d9-interoperation)、[Spoutの対応テクスチャ](https://leadedge.github.io/)。これらは現行コード・DLLとの適合確認を代替しない。

## 実装と評価の進め方

親エージェントが設計・評価、サブエージェントが実装を担当する。具体的な変更範囲と依存関係を技術面から固め、小さな実証の結果でGPU・スレッド構成を判断する。今回の合意を理由に、GPU描画への全面変更を自動的に始めない。

### 実証実装の前に親エージェントが具体化する事項

- 共通スレッド版とSpout分離版の資源所有表。各D3D11デバイス、コンテキスト、合成画像、送信用画像、スワップチェーンの作成・使用・解放担当を決める。
- GPU画像の状態遷移と同期API。命令の発行、GPU処理の完了、出力APIの復帰を区別し、公開可能時点・コピー元の返却可能時点・領域の再利用可能時点を定義する。その所有関係から有限個の領域数を算定する。
- 60Hzの予定時刻、表示準備確認、最新画像の取得、スキップ、同一画像の再送の処理順序。ティアリングを避けるPresent設定を具体化する。
- 検証用アプリのプロジェクト構成、Direct3Dの呼び出し方法、画素形式と色の扱い、終了時の待機と資源解放。必要なABI確認を含める。
- 測定区間と比較表。共通スレッド版と分離版の単独・併用条件で、平均頻度だけでなく公開間隔の分布・最長停止・画像の生成から出力開始までの時間・画像番号差・スキップ数を記録する。各構成で異なるコピーや同期の負荷を明示し、結果の差をスレッド数だけの効果と決めつけない。

タイムライン状態の受け渡し、mpv画像の世代・時間位置の対応、GPU復旧後の通常映像再構築は、本体へ接続する前に具体化する。GPU生成画像だけの初回実証へ、タイムラインや全プロジェクトモデルの改修を同時に持ち込まない。

検証は、データモデル・配置計算・画像の採否・周期スケジューラー・寿命・終了処理の管理テストと、実際の描画・送信経路の実機試験を分ける。画像準備の時刻、合成確定時刻、出力予定／開始／完了時刻、画像番号、スキップ数を測定し、公開頻度だけで新画像が届いていると判断しない。

実機試験は直列実行し、公式WinSpoutDXreceiverを使う。既存ログ・通常設定・他アプリを保持し、自分が起動したプロセスだけを終了する。WPR/UACを伴うGPU記録採取は自動実行しない。Spoutの単発無効化・OBS画像混在問題の修正へ範囲を広げない。

### 共有source保持区間とコピー再取得の比較結果（2026-09-10）

### 共有フェンス同期と表示通知駆動の比較結果（2026-09-10）

アーキテクチャレビューで挙げた「読者同士の排他」と「表示の時計」を [フェンス・vsync実証](GPU-FENCE-VSYNC-RESULTS-2026-09-10.md) で切り分けた。共有 source を keyed mutex なしの NT ハンドル共有＋D3D11.4 共有フェンスにすると、全画面描画と Spout コピーの衝突は構造的に0になり、負荷条件で Spout 年齢最大が 89／122ms から 23／22ms、合成開始遅れが 0.08ms から 0.007ms、CPU も低下した。後続の比較基準は `--source-sync fence`（keyed＋再取得は代替案として保持）。

表示通知駆動（`--display-pacing vsync`）は表示未準備の見送りをなくし 60Hz を維持したが、60Hz 表示では tick との表示遅延の優劣を現在の計測点（Present 呼出し時刻）では判定できない。既定 tick を維持し、走査時刻の計測（DXGI フレーム統計）と 60Hz 以外の表示先での比較を次の判断材料にする。本体側の契約候補は「フェンスで書き終わり順序を保証し、読者同士は排他しない」「読者→書き手は lease で防ぐ」。

### 走査時刻の計測結果（2026-09-10）

### vblank 位相基準の表示の比較結果（2026-09-10）
