## 2. 事前の確かめ

始める前に全部を確かめ、1 つでも満たさなければ進めない。無効な回を数分で止めるための確かめで、満たさないまま流した結果は合否に使わない。

| 項目 | 期待 | 確かめ方 |
|---|---|---|
| ディスクの空き | 4 GB 以上 | ドライブの空きの値を記録 |
| UAC と前面の窓 | consent.exe が 0 個。試験の窓より前に他の窓が無い | プロセスの一覧、前面の窓の題 |
| 画面のセッション | console のセッションで動いている（リモートデスクトップではない） | query session の出力 |
| 主ディスプレイ | 1920×1080、60Hz | ディスプレイの一覧の出力 |
| GPU | 外付けの GPU の adapterLuid で起動する（内蔵の GPU ではない）。AMD 内蔵の回は除く（その回は内蔵の adapterLuid を期待） | アプリのログの adapterLuid の行を、GPU の一覧の LUID と突き合わせる |
| GStreamer の環境変数 | GSTREAMER_1_0_ROOT_MSVC_X86_64 が付いていない（両方のアカウントで） | 環境変数の一覧 |
| アカウント | 回ごとに、ログオン中の利用者が 0.1 の表のアカウントである。フォルダを消す前と、検証用のアカウントの各回の前にも確かめる | ログオン中の利用者の名前を記録（文書には書かない） |
| 旧の名前の環境変数 | プロセス・利用者・機体の環境変数と、リポジトリの外のキットのスクリプトに、`TCS_` か `TIMECODE_SYNC_PLAYER_` で始まる名前が残っていない。残ってよいのは TCS_FFMPEG と TCS_FFPROBE だけで、それも新しい名前に直すのが望ましい | 名前の一覧（3 つの範囲とキットのスクリプトの検索の結果） |
| 試験した exe（各回） | 試験した exe が、その回の配布物を置いた場所（zip を広げた先か、インストール先）のもの | ランナーの出力の `app=` の行。その場所の logs\erytheia-YYYYMMDD.log の Information の行「=== ERYTHEIA v{Version} 起動 === ログ: {Path}」の場所 |
| skip の数（各回） | SUMMARY の skipped の数が期待の数と同じ | SUMMARY の行と、2.2 の期待の数の表 |

GStreamer の場所は、環境変数 GSTREAMER_1_0_ROOT_MSVC_X86_64 → 同梱 → Program Files の順で決まる。変数が付いていると同梱のものを使わないので、3.2 の 6 の確かめができない。

試験の側の環境変数（ERYTHEIA_E2E_APP_PATH、L1・L2・L3 の値、プロジェクトの場所など）は、旧の名前を読まない。旧の名前を読むのは ffmpeg と ffprobe の 2 つだけ（TcsFfmpeg.psm1 と tests\Helpers\FfmpegTool.cs）。検証機の手元の呼び出しが旧の名前のままだと、警告なしで無視される。

- ERYTHEIA_E2E_APP_PATH が効かないと、試験は試験の出力フォルダの横の ERYTHEIA.exe を使う（E2EAppRunner.cs:388-395）。その回の配布物の exe を試験しないまま合格になるので、試験した exe の場所を各回で確かめる。
- プロジェクトの場所の変数が効かないと、筋書きが skip になり、failed は 0 のままになる。このため skipped の数を期待の数と比べる。

### 2.1 shim の SHA の分け方

| どこで | 確かめること |
|---|---|
| 開発機（送る前） | erytheia_gstreamer.dll の SHA が、build-release と bin\Release の 2 か所で同じ。DLL のビルドの時刻が、shim のソース（native/gst-shim）の最後のコミットより後。結果を SHA の一覧に書く。setup の中の shim は開発機では取り出していない（innoextract 1.9 が Inno Setup 6.7.3 の setup を読めなかったため）。その分は検証機で、入れた後に照合する |
| 検証機 | 上書きの回と新しく入れる回の両方で、シナリオを回す前に、入れた後の erytheia_gstreamer.dll と ERYTHEIA.exe の SHA を送った一覧と照合する。合わなければ止める。zip の中の DLL も同じ一覧と照合する |

## 3. 上書きの回（v0.6.6 → v0.6.7）

検証用のアカウントで行う。

### 3.1 上書きの前に確かめること・置くもの

| 項目 | 期待 | 確かめ方 |
|---|---|---|
| 新しい設定の場所 | %LOCALAPPDATA%\ERYTHEIA\settings.json が無い（フォルダとキャッシュはあってよい） | settings.json の有無。フォルダの有無と中身の一覧も記録する |
| 入っている版 | v0.6.6 が入っている | 窓の題「Timecode Sync Player v0.6.6」の PNG、インストール先の exe の一覧 |
| 旧のログ | 下の写しを置いた後の一覧 | インストール先の logs のファイルの一覧（最終書き込みの日時つき） |

新しい設定の場所の確かめは settings.json のファイルで見る。同梱の GStreamer で起動すると、設定の場所の指定と関係なく、新しい場所にキャッシュのフォルダができる。引き継ぎは settings.json のファイルの有無だけで決まる（AppSettings.cs の MigrateLegacySettings）ので、フォルダがあっても引き継ぎは壊れない。言い方がフォルダのままだと、順やアカウントが変わったときに偽の不合格になる。

順は次のとおり。v0.6.6 は起動のたびに、最終書き込みが 7 日より古い tcs-gst-*.log を消すので、写しを置いた後は v0.6.6 を起動しない。

1. v0.6.6 の起動が要る作業を全部済ませる。
   - 設定: オフセット、LTC の機器、fps の固定、全画面の出力先の 4 項目を既定でない値にする。値を記録する。
   - .tsp のプロジェクト 1 本を作る。
   - 窓の題「Timecode Sync Player v0.6.6」の PNG を撮る。
2. v0.6.6 を閉じる。
3. 旧のログの写しを置く（下）。
4. 上書きの前の一覧（logs のファイルの一覧と、上の表の残り）を取る。
5. その後、v0.6.6 は起動しない。そのまま上書きの回へ進む。

**旧のログの写しを置く。** ログはインストール先の logs にある（設定の場所ではない）。検証用のアカウントの最後のログオンは 10-08 なので、その日のログは回の日には 31 日を超えていて、消えるのが期待になる。日数の違う回を作るため、既存のログの写しを、名前の日付と最終書き込みを付け替えて logs に置く。日数は回の日から数え、境目（7 日・31 日）から 1 日以上離す。

| 置く写し | 名前 | 最終書き込み | 上書きの後の期待 |
|---|---|---|---|
| 旧のアプリのログ | timecodesyncplayer-YYYYMMDD.log（日付は最終書き込みに合わせる） | 9 日前、20 日前、29 日前 | 残る（8〜30 日前） |
| 旧のアプリのログ | 同上 | 33 日前、40 日前 | 消える（32 日以上前） |
| 旧の shim のログ | tcs-gst-YYYYMMDD.log（同上） | 9 日前、20 日前 | 消える（8 日以上前） |
| 旧のアプリのログと shim のログ | 各 1 本 | 5 日前 | 残る（6 日以内） |

## 7. 合否の一式

設計書の 5 節の順の 6（候補）の検証機の分:

- 固定の一式（標準 3、L-1 6、A の切替、RTX）
- 落ちの自動の集計: 新しいランナーで固定の一式を回す中で 1 回確かめる。run-result に crashes の項目（count と各件）と launches が出て、判定に crashes が効くこと（試験基盤の束の 2）
- AMD 内蔵の GPU でテストカードと再生を 1 回
- 検証用のアカウントの上書き（3 節）・アンインストール（4 節）・新規（5 節）
- shim の SHA の照合（2.1 の検証機の分）

実素材を使う回は M1〜M7 で呼ぶ。実素材と、そこから切り出したフレームは検証機から出さない。数値だけを返す。
