## 0. 要約

- 既存の `SyncScenarioHarness` は本番の同期の骨格を本物で動かしている（`SyncScenarioHarness.cs:24-30, 50-221`）。足りないのは「時間」と「再生の進み方」で、いまはテストが両方を手で動かしている（`D38SeekGatesTests.cs:57-64`）。
- 足すのは 4 つ: ①`TimeProvider`・QPC・単調ミリ秒を 1 つの時計から進める `ScenarioClock`、②`IPlaybackApi` の形をした時間つきの偽プレイヤー、③Normal／Duplicate／Jump／無音を時刻で並べる LTC 台本、④時刻つきの観測（hold-landing・jump-black・hold-pause・門の発火）。
- 実機 22 シナリオのうち、位置・シーク・一時停止・ギャップ状態・ラベルはこの層で同じ定義にできる。**画素（黒判定・参照一致）と実時間（fps 更新、UIA の読み、復号・ロード所要）はできない**。jump-black は「状態が黒だった」の代理判定に留める（§3）。
- D39 の型 (2)（オフセットの復元）はプレイリスト層だけで決定的に再現できる。型 (1)（WPF の選択外れ）は ListBox の性質なので、この層では「選択中の行を差し替えない」不変条件までを固定し、外れそのものは E2E に残す（§4）。
- 実装は 5 コミット。①②③で既存テストを緑のまま土台を差し替え、④で観測と門の基準表、⑤で D39 の赤いテスト（§5）。諮る点は §6。

## 1. いまの土台の棚卸し

### 1-1. 本物で動かしているもの

- 同期の中心: `TimecodeSyncService`（信頼・保留・ロードゲート、`TimecodeSyncService.cs:70-88, 210-230, 282-304`）、`LtcSyncController`（フレーム処理と分岐、`LtcSyncController.cs:91-112, 538-545, 1055`）。
- コーディネーター一式: `ContinueOnTrackCoordinator`、`SingleModeSyncCoordinator`、`GapEnterCoordinator`、`AudioControlCoordinator`（`SyncScenarioHarness.cs:50-220`）。`SyncRules` の持ち主の判定（`:144-151, 212-215`）と `PlaylistCurrentTrackLabelFormatter`（`:537-549`）も本物。
- モデル: `PlaylistState`（`:236, 305-315`）、`GapFreezeHandler`、`LtcFrameProcessor` / `TimecodeFpsSelector` / `TimecodeFrameDiagnostics`（`:157-160`）。
- 入力の検査: `TimecodeSyncSeekState`（保留・着地・タイムアウト）、`PlaybackPositionTrust`、`SeekDecisionGate`、`SyncDecisionEngine`（テストから `SeekState` / `SyncService` で触れる、`:231-234`）。

### 1-2. 偽物・手動に置き換えているもの

- 再生: `_playbackSeconds` / `_durationSeconds` / `_videoFps` / `_renderedFrames` のフィールド（`:35-37`）。`AdvancePlayback` が位置を直接置き、時間では進まない（`:435-439`）。`Seek` は即時に位置を書き換える（`:513-519`）。`LoadFile` も即時で、ロードの所要が無い（`:466-479`）。`IsSeeking` / `NativeSeeking` / `PlaybackPositionUnstable` はテストが手で立てる（`:246, 292, 282`）。
- LTC 入力: 解読済みの `LtcFrameProcessingResult` を直接注入する（`:317-331, 337-345`）。オーディオデバイス、LTC デコーダ、サンプル時計の配信の時間は無い（QPC は `getQpc` で注入可能、`:219`）。
- ギャップ: `ArrangeGapStateForModel` と `CompleteFreezeCapture` で状態だけを作る（`:441-449`）。描画面は `GapState` からの導出（`:298-303`）で、フリーズ画像の中身は無い。
- 速度補正: `ApplyRateInstant` はレートを記録するだけ（`:197-206`）で、位置はレートで動かない。`AppliedRates` / `RateAttempts` / `CorrectionStatus` が観測点（`:277-284`）。
- UI/出力: 境界の記録だけ（`Operations` / `DisplayStates` / `CurrentTrackLabels` / `PlaybackPropertyWrites`、`:237-243`）。WPF、GPU、Spout、プレビューの読み戻しは無い。

### 1-3. 扱えないもの（足す理由）

- **時計が 2 つある**: 単調ミリ秒は `_monotonicMilliseconds = 10_000` を `Tick100Milliseconds` で進める（`:32, 347-357`）。`TimeProvider`（`ManualTimeProvider.cs:3-22`）は別で、既存テストは 2 つを手で同時に進める（`D38SeekGatesTests.cs:57-64`）。D37 系は QPC も UTC から手で作る（`D37eFollowStartLookaheadTests.cs:124-128`）。門の待ち（250ms・500ms・2 秒・5 秒）とゲートの窓（0.25 秒）を同じ軸で測れない。
- **進み方が無い**: 位置が時間で動かないので、保持中に進むランスルー（R-3）、着地までの経過（1-3 秒）、pending のタイムアウト（2 秒）を、テストが 100ms 刻みで手書きする必要がある。
- **着地・ロード・尺の遅れが無い**: シークの着地の遅れ・通り過ぎ（D38 §8 の 0.22〜0.29 秒）、ロードの所要、`TryGetDuration` の到着遅れ（D39 の 0.6〜1.0 秒、`release-0.5-plan.md:198`）を表現できない。
- **観測に時刻が無い**: `ScenarioPlaybackOperation` は名前と値だけで時刻を持たない（`:6`）。hold-landing の latency や門の発火時刻を仮想時間で取り出せない。D38 の再現テストは Serilog の実時刻に頼っている（`D38SeekGatesTests.cs:19-43`）。

## 2. 足すものの設計

### 2-1. ScenarioClock（仮想時計）

- 1 つのクラスが 3 つの時間を持つ。基準は `MonotonicMs = 10_000`（現行と同じ）、`UtcNow = 2026-09-26T00:00:00Z`、`Qpc = 基準 + MonotonicMs * Stopwatch.Frequency / 1000`。`Advance(TimeSpan)` だけで 3 つが 1:1 で進む。`TimeProvider` を継承（`ManualTimeProvider` の発展）し、`UtcNow` を返す。
- `Advance` は決まった順で処理する: ①LTC 台本・偽プレイヤー・尺の到着などの予約コールバック、②`Controller.Tick(MonotonicMs)`（`LtcSyncController.cs:1055`）、③イベントの記録。テストは `Advance` を呼ぶだけで、日時・QPC・単調ミリ秒・再生位置が同じだけ進む。
- harness の配線: `TimeProvider: clock`、`getUtcNow: () => clock.UtcNow.UtcDateTime`、`getQpc: () => clock.Qpc`（`LtcSyncController.cs:109-112`）、`ReceiveFrame` / `ReceiveProcessedFrame` / `Tick` には `clock.MonotonicMs` を渡す。
- 互換: 旧 ctor（`ManualTimeProvider` と `getQpc`）と `Tick100Milliseconds()` は残し、内部で `ScenarioClock` に写す。既存の 84 箇所（`new SyncScenarioHarness` の検索結果）は移行なしで緑のまま。移行は機械的で、D38 以降のテストから順に `h.Advance(...)` に寄せる。
- 実時間は使わない。同じ入力なら同じ結果になることが目的なので、`Thread.Sleep` は層に置かない。

### 2-2. ScenarioPlayback（偽の再生 API）

- `IPlaybackApi` を実装する（`Contracts/IPlaybackApi.cs:8-55`）。状態は path / paused / rate / position / duration / fps / size / codec / seeking / 世代と連番。`PlaybackResult` は操作ごとに注入できる（`FakePlaybackApi.cs:16-31` と同じ形）。
- `Advance` で動く: 再生中なら `position += Δ × rate`。ロード中は `IsSeeking() == true` で位置は進まない。シークは「発行〜着地」の間、位置は旧値のまま（または `TryGetPositionSample` を false）で、着地時刻に目標（+ `OvershootSeconds`）へ飛び、必要なら戻る。
- 設定できる値: `SeekLandingDelay`、`SeekOvershoot`、`LoadDuration`、`DurationArrivalDelay`、`SeekFails` / `LoadFails`、`PositionGoesBackward`（D37-b の不信を作る）、`RateApplySucceeds`（T5 Smooth の失敗）。プレイリストの尺は `FakeMediaDurationReader : IMediaDurationReader` が同じ時計で遅れて返す（D39・ロード尺の遅れ用）。
- 既定値はすべて 0（即時着地・即ロード・尺は即返す）にし、既存テストの意味を変えない。`Operations` の `seek` / `loadfile` / `pause` の記録は harness 側に残し、既存のアサートを壊さない。
- `TryGetPositionSample` は `PlaybackPositionBasis` と世代を `GstPlaybackApi.cs:274-323` に合わせて返す（D37-b の信頼、D25 の交番、D37-a のゲートを同じ入力で動かす）。`TryGetDuration` / `TryGetFps` は到着前は false。
- harness の `_playbackSeconds` ほか（`:35-37`）は `ScenarioPlayback` のアダプターに置き換える。二重の真実を残さない（§6-3）。

### 2-3. LTC 入力の台本

- `LtcScript` は時刻つきの区間の列: `Normal(from, duration)`、`Duplicate(seconds, duration)`、`Jump(toSeconds, count=1)`、`Silence(duration)`、`Raw(status, seconds, count, applySync)`。
- `Advance` のたびに、LTC のグリッド（既定 25fps）で区間のフレームを `Controller.ReceiveProcessedFrame(...)`（`LtcSyncController.cs:545`）へ流す。`receivedAt` は `clock.MonotonicMs`。Normal は 1/fps ずつ進め、Duplicate は値固定（`SyncScenarioHarness.cs:324-331`）、Jump は 1 枚（`HeldLandingAfterJumpReproTests.cs:41-47`）を既定にする。
- 無音はフレームを出さない。250ms の確定は時計が進むだけで発火する（`LtcSignalLossPolicy.cs:224`、E2E の 0.25 は `LtcScenarioE2ETests.cs:812`）。復帰の N 枚も台本で与える。
- 既存の `SupplyLtc` / `SupplyHeldLtc` / `SupplyLtcFrame` は残し、台本はその上に載せる。タイムコードの丸めは既存と同じ（`SyncScenarioHarness.cs:337-345`）。

### 2-4. 観測（時刻つきイベントと指標）

- `ScenarioEvent(AtMs, Kind, Detail, Value)` を harness に足し、`Operations` と併記する。既存の `Operations` の名前は変えない。
- 実機 E2E と同じ定義の指標を出す:
  - **hold-landing**: Jump の到着時刻（台本の `AtMs`）から、その後の最初のシーク発行（`ReportSeekSent` / `seek`）まで。距離 > 4×tolerance かつ 1.0 秒超で over budget（`LtcScenarioE2ETests.cs:2213-2220` と同じ。tolerance は映像と LTC の大きい方の 1 フレーム、同 `:2216`）。
  - **jump-black**: Jump から着地までの tick で `RenderSurface == Black`（`SyncScenarioHarness.cs:298-303`）だった回数。Jump 直前が黒なら数えない（`JumpBlackPolicy`、`ScenarioCapturePolicies.cs:26`）。画素の判定ではなく**状態の代理**（実機は `LtcScenarioE2ETests.cs:2255-2300`）。
  - **hold-pause**: 台本の保持開始（値に届いた最初の Duplicate / Jump）から `signal-loss-pause` または `pause yes` の効果まで。実機 R-1 の定義（`:823-839`）と同じで、UIA の読みを含まないぶん厳密。
  - **follow**: 各 tick の `(ltc, position)` をサンプルし、`LtcFollowSeries.MaxErrorSeconds` / `IsFollowing`（`Helpers/LtcFollowSeries.cs:8`）で S-1 と同じ ±0.3 判定。
  - **門の発火**: 各ステップの後で観測可能な状態の変化を記録する。`SeekState.HasPendingSeek`、`SyncService.IsPlaybackPositionUsable`、`IsLoadingFile` / `HasPendingFileLoadRelease`（`TimecodeSyncService.cs:227-230, 282-304`）、`Single.IsBoundaryHeld`、`GapState`、`IsSeeking` / `NativeSeeking`、`AppliedRates` / `CorrectionStatus`。門 3・7・13（`JumpAppliedOnce` の捨て、pending のタイムアウト、ゲート）は公開状態に無いので、Serilog の sink で現在の仮想時刻を刻むか、テスト専用の trace の口を製品に足す（§6-2）。
- 出力は E2E の `harness.jsonl` と同じ形の `scenario.jsonl`。D38 文書 §7 / §9 の前後比較表（着地時間の中央値、`TimedOut` 回数、シーク本数、jump-black、hold-pause 超過）を in-process から作れるようにする。

- 置き場所: `tests/TimecodeSyncPlayer.Tests/Integration/Scenario/`（`ScenarioClock.cs`、`ScenarioPlayback.cs`、`LtcScript.cs`、`ScenarioJournal.cs`）。harness 本体は現行の場所のまま。
- 指標の計算は E2E と共有する（`HoldLandingExpectation.cs:9-26`、`ScenarioCapturePolicies.cs:18-27`、`LtcFollowSeries.cs:8`）。定義の食い違いが版の比較を壊すため。

## 4. D39 の再現（例）

### 4-1. 仕組み（コードの根拠）

- 一覧は `ObservableCollection` で、行は record の差し替えで更新される（`PlaylistState.cs:8, 225-230, 257-259`）。`UpdateMediaDuration` は `Tracks[index] = updated` の後に `RecalculateTimelineFrom(index)` を呼ぶ（`PlaylistState.cs:259-261`）。
- オフセットの編集は `Tracks[index] = updated` の後に `RecalculateTimelineFrom(index + 1)`（`PlaylistTimelineOffsetEditor.cs:61-65`、呼び出しは `MainWindow.xaml.cs:1487`）。
- 尺は追加後に 1 本ずつ遅れて届く（`PlaylistViewModel.cs:95-111`、`release-0.5-plan.md:198` の 0.6〜1.0 秒）。WPF の `ListBox` は `ItemsSource = _playlist.Tracks`（`MainWindow.xaml.cs:585`）で、選択は `SelectedIndex` と VM の相互写像（`:1195-1197`）。行の差し替えで選択が外れるのが型 (1)。
- E2E は「2 本追加 → B を選ぶ → 上へ → 行 0 のオフセットを 10 秒に → 保存 → 読み直し」（`SystemScenarioE2ETests.cs:27-66`）。

### 4-2. この層での再現（同じ時計で）

1. `t=0`: 2 本追加（`AddFiles(autoOffset: true)`）。`FakeMediaDurationReader` は A=20 秒を t=600ms、B=30 秒を t=700ms に返す予約にする。
2. `t=100`: 2 行目を選ぶ（`PlaylistState.Select(1)`）。選択の Id を控える。
3. `t=200`: 1 行目のオフセットを `00:00:10:00` に編集（`PlaylistTimelineOffsetEditor.Apply(..., autoOffset: true, fps: 25)`）。
4. `t=600/700`: `UpdateMediaDuration` が届く（`Advance` の予約コールバックとして正確な順序で走らせる）。
5. 期待: 編集した行の `TimelineOffset` が 10 秒のまま、選択は B の Id のまま。**現行コードでは赤**（A の尺の到着で `RecalculateTimelineFrom(0)` が走り、先頭からの自動配置が編集した行のオフセットを `00:00:00` に戻す。`PlaylistState.cs:217-233, 259-261`）。

- 型 (1) はこの層では「選択中の行（Id）のインスタンスが差し替わったか」までを記録する。WPF が選択を外す挙動そのものは再現できないので、修正の不変条件（行を差し替えない、または差し替え後に Id で選択を戻す）をここで固定し、実際の外れは E2E の `SystemScenarioE2ETests` に残す。
- **同じ時計で動く**: プレイリスト層は `IMediaDurationReader` の完了と `UpdateMediaDuration` 呼び出しの順序だけが問題で、WPF に依存しない。型 (2) は `ScenarioClock` の予約キューで完全に決定的にできる。型 (1) の WPF 部分だけが層の外。

## 6. 利用者に諮ること

1. **D39 の赤いテストを修正前にツリーへ置いてよいか。** 親がコミットするため、C5 を赤のまま入れるか、修正コミットと同じタイミングにするか、`Skip` + trait で置くかを指定してほしい（CI を赤くしない運用なら後者）。
2. **門の発火の時刻の取り方。** 公開状態で見える門（着地・信頼・ロード・ギャップ・持ち主）は観測だけで足りるが、門 3・7・13（`JumpAppliedOnce` の捨て、pending のタイムアウト、ゲート）はログにしかない。Serilog の sink に現在の仮想時刻を刻む（製品コード無変更）か、テスト専用の trace の口を製品に足すか。後者は振る舞いを変えないが製品に触れる。
3. **harness の再生フィールドを偽 API に一本化してよいか。** `_playbackSeconds` ほか（`SyncScenarioHarness.cs:35-37`）と `Seek` / `LoadFile` を `ScenarioPlayback` に置き換える。二重の真実を消せるが差分が大きい。既定挙動を現行と同一にしてから置換する案を推す。
4. **層の置き場所と共有の範囲。** `Integration/Scenario/` に置き、E2E の `Helpers`（`HoldLandingExpectation`・`JumpBlackPolicy`・`LtcFollowSeries`）を共有する案。定義の一致を保証できる。
5. **S-2 への jump-black の追加**（`release-0.5-plan.md:220`）を、この層の状態代理で先にやるか、E2E の画素判定のまま待つか。前者は早いが、停止モードの絵の乱れの判定は画素にしか無い（D38 文書 §9）。

## 7. 親の判断（2026-09-26、TSP-Opus）

§6 の 5 件は利用者に諮るものではなく、親が決める技術上の判断として扱う。

1. **赤いテストは修正と同じコミットに入れる**（D38 と同じ）。担当は修正の前に赤になることを確かめ、その結果を報告に書く。ブランチを赤のままにしない。Skip で置くのは、直す版が別のとき（例: §6 の 15 のように決定待ちのもの）だけ
2. **門の発火は、仮想時刻を刻む Serilog の sink で取る**（製品コードは変えない）。観測の口は、段 0 で担当 p3 が足す `sync.gate <名前> …` の Debug 行（`docs/prompts/2026-09-26-v054-stage0-gate-baseline.md`）。足りない門が残れば、p3 の段 0 の側で 1 行足す
3. **再生のフィールドは `ScenarioPlayback` に一本化する**。既定の振る舞いを現行と同じにしてから置き換える案で進める
4. **置き場所と共有は案のとおり**（`Integration/Scenario/`、E2E の Helpers を共有）
5. **S-2 の jump-black は両方やる**: この層では状態の代理で先に入れ、E2E の画素の判定も v0.5.4 で足す（`release-0.5-plan.md` の v0.5.4 節）

進め方: C1 → C2 → C3 を先に入れる（非 E2E だけで判定）。C4 は p3 の段 0（`sync.gate` の行）が v0.5.4 に入った後。C5 は D39 の修正（潰す一覧の K1・K2）と同じコミット。
