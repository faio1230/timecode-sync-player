## 1. 【本命】切替の直後の位置合わせ 3 本の連鎖

### 1-1. 事実

- 検証機（3 版とも同じ形、M3 → M4 の切替 20 回の毎回）: 切替のロードの着地の後に relocate が 3 本、+0.475 → −0.330 → −0.252。target は ltc の 0.364 → 0.364 → 0.284 先。公開不足は 0.000〜0.016 秒（材料 5 節、検証機の報告）
- **目標の式**（親が確認）: `target = clamp(ltc + SeekTargetLookaheadSeconds)`（`SyncDecisionEngine.cs:203-204`）。中身は `RelocateLookaheadSeconds = IsMasterMoving ? LearnedSeekDurationSeconds ?? _seekCostHintSeconds : 0`（`TimecodeSyncService.cs:214-215`）。ヒントは環境変数 `TCS_SEEK_COST_HINT=on` のときだけ（担当の報告、既定は無効）
- **c の学習**（親が確認、`TimecodeSyncSeekState.cs`）: 着地ごとに `c ← 0.7c + 0.3x`（`:384-388`）。`x < 0.05` 秒と `x > 10` 秒は捨てる（`:36-37`）。ロード（`BeginFileLoad`）で学習を捨て（`TimecodeSyncService.cs:472`）、**直後の `BeginLoadWait`（`:437`）が `_sentAt` を立てる**ので、ロードの着地（目標なし、`:274-305`）でも `LearnSeekDuration` が走る（`:304-305`）。リセット直後の 1 件目はそのまま c になる
- **つまり切替の直後の c はロードの遅れ**（LoadFile の発行 → 新しい世代の最初の配信）。開発機のログ（10-01）で、50ms 以上のロードの着地の後、次の FileLoad までに出た relocate の lookaheadMs は **695/695 件でそのロードの着地の delayMs と一致**（担当の報告、親は未照合）
- **0.05 秒の下限は c を上へ偏らせる**: 開発機のログでシークの着地 3,698 件のうち 3,635 件が 0.05 秒未満で学習から捨てられている（担当の報告）。学習に残るのは遅かった着地だけ
- 1 本目は「切替の入口の合わせ」ではなく、ロードの着地の後の通常の relocate（Continue の切替はロード 1 回だけ、`ContinueOnTrackCoordinator.cs:61-95`、担当の報告）。後ろ向きに c を足すのは規則 3 の文言どおり（「経路では分けない」）
- **規則 3 の文言**: 「c はシークの所要の学習値、学習前は 0」（`v0.5.4-gate-unification.md` 10-1）。**ロードの遅れを c に入れるのは文言と食い違う**。`TimecodeSyncSeekState.cs:17-20` のコメントも「ロード直後は学習値なし」で、v0.5.4 段 B3（ロードも着地の事象に通した）の副作用と読む（担当の報告、親は B3 の経緯と矛盾しないことを確認）

### 1-2. 連鎖の読み（推定）

c₀ = 0.364（M4 のロードの遅れ）で 1 本目が +0.33 行き過ぎ → 1 本目の着地は 0.05 秒未満で学習されず c は 0.364 のまま → 2 本目も 0.364 先へ（後ろ向きなのに行き過ぎ）→ 2 本目の着地 約 0.097 秒が学習され c = 0.7×0.364 + 0.3×0.097 = 0.284 → 3 本目の行き過ぎ 約 0.18 < 許容 0.24 で止まり、残りは varispeed が拾う。間隔 0.27・0.25 秒は門 14（250ms）の間隔（2 節）

**確かめること（実装の前、検証機の既存のログで）**: 実際に発行したシークの時刻と目標は `Continue mode: sync seek ltc= … target=` の行で取り直す（`decision action=` の行は判定が変わったときだけ、デバウンスの前に出るので発行の正ではない）。各着地の delayMs は配布ビルドでは出ない（Debug）ので、1 周だけ Debug ビルドで `new-landing target=NaN delayMs=` と `sync.gate relocate … lookaheadMs=` を取るか、1-4 の要約の行で取る

## 4. 一時停止中のシークの +1 フレームの食い違い（材料 6 節）

### 4-1. 事実（担当の報告。行は担当が再確認）

- harness の `Position()` は UIA の `TimeLabel` の「/」の前を、メタ表示の fps（F3）でフレームから秒に戻す（`LtcScenarioE2ETests.cs:2112-2116`）。ラベルの元は `TryGetTimePos`（`GstPlaybackApi.cs:254-264`）で、shim は一時停止中（ポンプ終了後）は**最後に配信したフレームの PTS** を返す（`tcs_gstreamer.cpp:4290-4300`、親が確認）
- 候補 2-2（担当が見つけた、**試験側**）: harness の `Seek()` はシークバーの比 `target / duration` を入れる（`:1860-1890`、親が確認）。この duration は**ラベルの「/」の後をフレーム切り捨てのまま読んだ値**（`PlaybackDuration()`、`:2034-2038`、親が確認）。アプリは `比 × 本当の尺`（`SeekBarInteractionController.cs:45-52`、親が確認）で目標を作るので、尺に近い目標（tail = `MediaOut − OneFrame`）ではアプリに届く目標が harness の目標より最大約 1 フレーム先になる。shim の「最初のフレーム − 目標 = 0〜+1」と足して最大 +2
- 候補 2-1（**製品側**）: 一時停止中のシークのポンプ（`pump_preroll_tick`、`:2847-2920`）は新しい世代のフレームが 1 枚あれば `pump_active=false`（`:2873`、親が確認）にしてから非同期で PAUSED を出す。その間に 2 枚目が配信されると、2 枚目の PTS が報告される（画面も 2 枚目なので報告と絵は一致する見込み）

### 4-2. 設計

- **まず検証機の既存のログで 2-2 を確かめる**（追加の実機の試験なし）: reference-stale の kind 別の内訳（tail だけか head にも出るか）と、アプリの `Seek command sent … target=`（`MainWindow.xaml.cs:2942-2944`）と journal の target の差（フレーム数）。v0.6.2 の一式の ProRes の回（refStale 60）の生ログで足りる

## 6. instant-rate の CRITICAL（`gst_segment_do_seek: assertion`）の整理

- 事実: v0.6.2 の一式で shim のログに 147 行（v0.6.1 は 172 行）。速度の食い違いは開発機で 180 回再現せず、診断の行だけ（v0.6.1 のノート）。経路は「flush シークの直後に同期で 1.0 を送る」（`LtcSyncController.OnSeekIssued` → `TryRestoreRateToUnity()`、規則 3「relocate は発行した時点で 1.0」）
- 候補: (a) アプリで 1.0 の戻しを新しい世代の最初のフレームの後へ遅らせる（規則 3 の文言が「発行した時点」から「着地の時点」に変わる）、(b) shim で flush シークの直後の instant-rate を segment が届くまで保留する、(c) shim のログの中継（`glib_log_to_shim`）でこの assertion だけ数えて落とし、要約の行に件数を出す
- **親の推し: (b)**。規則 3 の文言を変えず、assertion の原因（segment の前に instant-rate を出す順序）を消す。flush シーク中は速度が絵に効かないので、保留しても挙動は同じはず。I13（frame_lock 中に状態変更・シークを呼ばない）を守る形にする。(c) は情報を隠すので入れない。**(a)・(b) のどちらにするかは TSP-Fable の判断**

## 7. 【利用者に諮る材料】RunThrough の保持の入口の合わせの要否（材料 7 節）

- 数字: v0.6.2 の一式の A-2 の 1 回目で、試験の音声経路の LTC の乱れ（約 0.9 秒の Reverse/Duplicate）に対し、規則 4 の入口の合わせ（後ろ向き 0.24 秒）＋復帰の確定 Jump ＋ 0.90 の追い付きで、映像の止まり 0.517 秒。同じ一式の他の回・やり直しでは 0 回。利用者の運用「頭だけ LTC で合わせて走らせる」（`v0.6.1-jump-confirm.md` 3-5）では入口の合わせの害は小さいとしていた
- 選択肢: (i) 今のまま（規則 4 どおり、乱れのたびに 0.2〜0.5 秒止まりうる）、(ii) RunThrough では停止の値への合わせをしない（止まった LTC から離れて走り続ける。復帰の Jump で 1 回合わせる）、(iii) 合わせの閾値を許容でなく大きいずれ（例: 1 秒）だけにする（定数が増えるので推さない）
- S-4 の直し（入口の合わせがクリップの端へ clamp したシークを Single で記録する、`v0.6.0-prores-gpu.md` 8-2）がこの経路に乗っている。(ii) を選ぶなら Single の境界ホールドの経路を壊さないことを赤いテストで固定する

- **キーフレームの効きの前後比較（2026-10-02 10:53〜11:04、MediaInOffset 3.3・SegmentSeconds 15、M3,M2,M1 の 5 分、前 = v06 の v0.6.2 相当・後 = v053 の `d7435ab`、測定の担当）**: 目標を逆の位置に置くと結果も逆になった。4K GOP 2 への切替 6 回で、**後（(a)）は 1 本 6/6**（lookahead 0・cSource=none、目標はキーフレーム 4.004 の 0.09〜0.14 秒後で着地 3〜4ms、残差 +4〜+20ms、syncSettle 405〜529ms）、**前は 2 本（+・−）6/6**（lookahead 400〜422 = ロードの着地、目標はキーフレームの 0.53〜0.58 秒後で着地 111〜123ms、syncSettle 801〜957ms）。1080p は前後とも relocate 0。公開不足は前 0.025 / 後 0.081 秒、許容超え 0

## 7b. 【利用者に諮る材料】4K の長い GOP のシークの所要（2026-10-02、TSP-Fable の指示で 7 節の隣に置く）

- 事実（開発機、H.264 4K59.94 GOP 2 秒、Debug、先行量 0 のシーク）: 着地の所要は**目標の手前のキーフレームからの距離**で決まる。距離 0.1 秒 → 3ms、0.5 秒 → 0.12 秒、1.7 秒 → 0.42 秒（13 節）。予測の式が距離にほぼ比例（4K の復号の速さ 約 4 倍速）することの根拠
- 影響: スカラの先行量 c では、目標の位置しだいで行き過ぎ（c が大きい）か追いかけ（c=0 のシークが遅れる）になり、4K GOP 2 の切替のたびに relocate が 1〜3 本出る。公開不足は 0.000〜0.016 秒（検証機）で見た目の害は小さい。推奨素材の範囲の上限（GOP 2 秒）
- 直すには c を「目標ごとのシークの所要の予測」（キーフレームからの距離 × 復号の速さ、GOP の走査の結果を使う）にする新しい仕組みが要る。利用者の「長 GOP のための仕組みを同期の中心に足さない」に触れるので、v0.6.3 では入れず、利用者に諮る（TSP-Fable）
