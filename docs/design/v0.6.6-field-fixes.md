# ERYTHEIA v0.6.6: 現場の報告の直し（設計書）

作成: 2026-10-07（TSP-Opus）。材料は[現場からの報告 2026-10-06](field-feedback-2026-10-06.md)。利用者の方針は「基本的に直していく」。束の中身と順は利用者が決めた（3節）。

## 0. 原則

- 同期の規則・ゲート・定数・目標の定義には触れない。F-7は同期が使う入力（クリップの長さ）を正しくするもので、規則は変えない。スクラブ（R-3）と1フレーム送り（R-4）は、今の手動のシークと同じ経路（同期の保留を取り消し、手動のシークとして知らせる）に乗せ、新しい経路を足さない。
- 現場で起きたことを、開発機と検証機でも起こせる形の試験にしてから直す（F-7は「PATHにffprobeが無い」条件を試験に足す）。
- 1つの版には、性格の近いものをまとめる。

## 1. 項目ごとの設計の要点

### F-7 ffprobeが無いとクリップの長さが0のまま（最初）

- 規則に触らない根拠: 同期が使う入力（クリップの長さ）を正しくするだけで、規則・ゲート・定数・目標の定義は変えない。長さを使う判定（Continueのクリップの選び方、クリップの端）は今のコードのまま
- 今の作り: クリップは長さ0で追加され、長さは `MediaDurationReader`（ffprobe）でだけ入る（プレイリストへの追加 `PlaylistViewModel.cs:95-111`、開く・プロジェクトの読み込み `PlaylistDurationBackfillService.cs:14-33`）。ffprobeが無いとnullで、長さは0のまま（`MediaDurationReader.cs:41・61`）。shimの長さは `TryGetDuration`（読み込んだ1本だけ）と、GOPの走査の `DurationSec`（`GstPlaybackApi.ScanGop(path)`、任意のパスで呼べる、`GopScanCache`に保存）があるが、プレイリストへ書き戻していない
- 波及: タイムラインの幅とスクロール（`TimelineLayoutCalculator.cs:80-101`、`TimelinePanel.xaml.cs:97-107`）、追加時の自動オフセット（`PlaylistState.RecalculateTimelineFrom`）、Continueの「今どのクリップの時間か」（`PlaylistState.FindTrackAtTimelinePosition:176-186`、長さ0だとそのクリップに一度も当たらない）、`GapFreezeHandler`・`ContinueOnTrackCoordinator`の端の判定
- 直し方の案（TSP-Fableのレビューで改めた）: **shimを正にして、ffprobeは長さに使わない。** 「ffprobe → 無ければshim」の順にすると、開発機・検証機（ffprobeあり）と利用者の機体（なし）で経路が分かれたままになり、F-7を隠した罠がそのまま残る（試験の構成は本番と同じに）。取れた長さは今と同じ `PlaylistState.UpdateMediaDuration` でUIスレッドから書き戻す（後ろのクリップの自動オフセットの置き直しも今と同じ）。ffprobeを配布物に入れる案は採らない
- 費用: GOPの走査（`ScanGop`）は全フレームを数えるので重い（ログでProRes 1080p 29.97が1.9秒、3840×768が4.5秒）。プレイリストに10本足して数十秒待たせるのは不可。追加時は容器の長さだけを取る安い呼び出しをshimに足す案（PAUSEDまで上げてdurationを問い合わせる、またはdiscoverer）と比べ、形式ごと（H.264・H.265・ProRes 422/4444・HAP・AV1）の所要と長さを測って決める。読み込み時のGOPの走査は今どおりで、`GopScanCache`で二重の走査を避ける
- 確かめること: 安い呼び出しの長さ・`ScanGop`の長さ・ffprobeの長さを、形式ごとに並べる（開発機、切り替えの根拠）。差が1フレームを超える形式があれば、その形式の扱いを決める。所要は1本あたりの中央値と最大
- 試験: 単体（長さが入り、自動オフセットが置き直される）。E2E（**アプリのプロセスの環境だけ**PATHからffmpegを外し、プレイリストに3本足してタイムラインの幅と自動オフセットとContinueの判定が正しい）。ランナー自体はffmpegを使う（LTCのwav、素材）ので、外すのはランナーがアプリを起動するときのPATHだけ。検証機の回も同じ。あわせて、アプリの起動時のログにffprobeの有無を1行出す（現場のログで分かるように）
- 直ったら: F-1（タイムラインの幅とスクロール）とF-4（自動オフセット）を、追加の変更なしで直るかを確かめる（TSP-Fableの読み: `UpdateScrollBarRanges`の最大値が長さ0で0になるのが原因）

### F-7の決定（2026-10-07、TSP-Fable、下調べの表を受けて）

- **長さの正は、shimに足す軽い関数（容器の長さだけを問い合わせる）。** filesrc ! (typefindで選んだdemux) ! fakesinkをPAUSEDまで上げてdurationを問い合わせ、デコーダは作らない（下調べのA2）。プレイリストへの追加のときと、開く・プロジェクトの読み込みのとき（Backfillの経路）の両方でこれを使う。`ScanGop`の`DurationSec`は長さに使わない（HAPで0を返す）。ffprobeは長さに使わない
- 縛り:
  1. ffprobeとの一致より一貫性を優先する。同期が使う再生時の長さ（`TryGetDuration`、qtdemuxの値）と、プレイリストの長さ（軽い関数）が同じ出所であることを単体で固める（同じ素材で両者が一致）。ffprobeとの「1.5フレーム以内」は記録の試験として残す。mvhdと映像のトラックの長さの差（下の表の60秒のmp4、+1.32フレーム）は記録だけで、ヘッダを読む別の手は足さない
  2. 軽い関数で取れなかった（0か失敗）とき: 読み込んだときに`TryGetDuration`で書き戻す → それも無ければ0のまま（今と同じ）。UIの長さの欄は「--:--」のように不明と分かる表示にし、黙って0を長さとして使わない
  3. 呼び出しは今と同じくUIスレッドの外（追加は`PlaylistViewModel`の非同期、開く・プロジェクトはBackfillの経路）。書き戻しは今の`UpdateMediaDuration`でUIスレッドから。順と自動オフセットの置き直しは今のまま
  4. 起動時のログにffprobeの有無を1行出す（現場のログで分かるように）。「ffprobe is not available, cannot read duration」の警告は、長さに使わなくなるので消す。`scripts/inspect-gop.ps1`のffprobeはそのまま
  5. 試験: 単体（軽い関数の長さ、取れないときの順、不明の表示）。E2E（アプリのプロセスだけPATHからffmpegを外し、3本足してタイムラインの幅・自動オフセット・Continueの判定が正しい。HAPを1本含める）。下の表の形式を試験の素材の一覧にする
- 下調べの表（開発機、RTX 3070、GStreamer 1.28.2、ffprobe 4.2.3。A1＝discoverer、A2＝軽い関数の試し、B＝`ScanGop`、C＝ffprobe。所要はキャッシュ無しの1回目のms）:

### F-3・R-3 シークバーのスクラブ（つかんだまま動かすと再生位置が動く）

- 規則に触らない根拠: スクラブのシークは今の手動のシークと同じ経路（同期の保留の取り消し、手動のシークの知らせ）に乗せ、`IsSeeking`の扱い（つかんでいる間は同期の補正を止める）も今のまま。シークの所要の学習値（c）には触らない
- 今の作り: メインのシークバーは押したときに `IsSeeking` を立て、離したときにだけシークを送る（`MainWindow.xaml.cs:2088-2102`、`CommitSeekBarSeek :2969-2988`）。動かしている間は時刻の表示だけ動く
- 直し方の案（TSP-Fableのレビューで改めた）: 動かしている間も、シークを送る。間引きは固定の間隔ではなく「**前のシークが着地するまで次を送らない**（飛行中は1本だけ、最後の位置は必ず送る）」にする。長GOPのH.264や4K60のProResでは正確なシークが100msを超えるので、固定の間隔だと詰まる。着地はUIの側で着地の通知を待つ。同期の側のシークの所要の学習値（c）には触らない。一時停止中は1枚だけ出すポンプ（v0.6.3の段5）がそのまま使える。同期との関係: `IsSeeking`はすでに同期の状態の入力で、つかんでいる間は同期の補正を止めている。スクラブ中のシークは今の離したときのシークと同じ経路（`CancelPendingSync`・手動のシークの知らせ）に乗せ、同期の規則には触れない
- c の学習のサンプルは離したときの 1 本だけ（今と同じ）。途中のシークは `CancelPendingSync` と `SeekTo` だけ
- つまみの外を押したとき、変更前は Slider（`IsMoveToPointEnabled`）が押下を処理済みにして `Seek_MouseDown` が呼ばれていなかった。`handledEventsToo` で受けるようにし、"Seek MouseDown" と `CancelPendingSync("seekbar-down")` が新たに出る。クリック 1 回のシークは 2 本のまま
- 確かめること: Sync ONで再生中にスクラブしたとき、離した後に同期が今どおり戻ること（規則4の入口の合わせなど、手動のシークの後の挙動が変わらない）。4K60のProResでの間引きの間隔
- 試験: 単体（スクラブ中のシークの間引き、離したときの最後の1本）。E2E（つかんで動かす間に位置が動く、離した位置で止まる、Sync ONで離した後に同期が戻る）
- GPUでの計測（2026-10-07、開発機 RTX 3070、v0.6.6 7d19a70のDebug、親が実行）: 4K59.94のProRes 422 HQ（合成の素材、`proresd3d11dec`で確認）を、`ScrubE2ETests.ScrubMeasurement_WithGivenMedia`で約1.4秒ずつ2回つかんで動かした。送った本数は81・84本（1秒あたり58.9・60.7本、ほぼ描画の更新ごと）、飛行の所要は中央4.0・3.2ms、最大8.5・6.0ms。2回の間のUIのheartbeatの遅れは60回で中央9.4ms、最大14.3ms（しきい値100msの内）。担当の回の4K ProResの数字はCPUデコード（`avdec_prores`、worktreeに`native\gst-prores`が無かった）なので使わない
- 記録だけ: shimのSeekの呼び出しはUIスレッドで同期に待つ（担当の回のCPUデコードで16〜31ms）。GPUではheartbeatの遅れが100msを超えなかったので、「着地の後、少なくとも映像1フレーム後に次を送る」案は入れない（TSP-Fable 10-07の基準）

### R-9 オフセットの数値入力（必須）

- 規則に触らない根拠: 同期が読む値（`SyncOffsetMs`）と範囲は今のまま。入力の口を足すだけ
- 今の作り: つまみ（-1000〜1000ms、1ms刻み）と表示の文字だけ（`MainWindow.xaml:319-328`）。設定は `SyncOffsetMs`
- 直し方の案: 表示の文字の横に数値の入力欄を足し、`Sync.SyncOffsetMs`に同じくバインドする（範囲の外は今の `SyncOffsetPolicy` で丸める）。Enterか入力欄を離れたときに反映。単位はmsのまま（利用者の方針）。同期の側は今と同じ値を読むだけ
- 試験: 単体（入力の解釈、範囲の外、数字以外）。UIのE2E（入力して反映、設定に保存）
- 入力の規則（実装で固定）: 受けるのはmsの整数だけ。前後の空白と先頭の+・-は許し、全角の数字・符号・空白は半角に直して読む。小数（12.5）・指数・桁区切り・単位付き・空は数字以外と同じに扱い、反映せず前の値に戻す。範囲の外は `SyncOffsetPolicy` で丸め、入力欄にも丸めた値を戻す。Escは反映せず前の値に戻す。入力欄はつまみと同じ `SyncOffsetMs` を通るので、設定の保存は今の経路のまま
- 全角の数字・符号・空白は半角に直してから読む
- 桁あふれ（例 400 桁）は範囲の外として丸める（そのままだと 0 になるため）

### R-4 1フレーム送り・戻し

- 規則に触らない根拠: 今の10秒送りと同じ手動のシークの経路に乗せる
- 今の作り: ◀◀ ▶▶は10秒送り（`PlayerViewModel.cs:22-23`、`MainWindow.xaml.cs:1706-1721`）。shimに `tcs_player_step_frame` がある（前方向だけ、現在位置に1/fpsを足したシーク）が、`IPlaybackApi`には出ておらず使われていない
- 直し方: **1フレーム送り・戻しのボタンを別に足し、◀◀ ▶▶の10秒送りも残す**（利用者の決定）。中身は「今の表示のフレームの位置 ± 1/fps」への正確なシークで、shimの `step_frame` は使わない（前方向だけで、一時停止中の1枚のポンプとの組み合わせが未検証のため）。経路は今の `SeekRelative` と同じ（同期の保留を取り消し、手動のシークとして知らせる）。fpsは素材のメタの値
- 確かめること: 格子の線ちょうどの位置での丸め（v0.6.4で踏んだ型、棚卸し#9・#28）。目標を「今のフレームの頭 ± 1フレーム + 半フレーム」のように、フレームの中に置く
- 試験: 単体（目標の計算、29.97・59.94・60・25で格子の線ちょうど）。E2E（10回送って10フレーム進む、戻して元に戻る）
- Sync ONのときは、今の「利用者の一時停止＋手動のシーク」と同じ扱いになり、新しい分岐は足さない
- 実装（v0.6.6）: ◀◀と再生の間に「-1F」（1 フレーム戻す）、再生と▶▶の間に「+1F」（1 フレーム送る）。今のフレームは最後に届いた配信フレームの PTS（スクラブの着地と同じ照会）で、配信がまだ無いときは何もしない（"FrameStep ignored reason=NoDelivery"）。飛行中は1本だけで、押した数は積み上げ、着地（配信の世代がシークの世代に追いつく）の後に1本送る。先頭と末尾で止める。再生中は再生/一時停止ボタンと同じ経路で止めてから動かす。ログは "Seek command sent source=FrameStep" と "FrameStep landed"
- 実機で見た事実（開発機、H.264 720p の29.97と59.94）: 正確なシークの後の配信 PTS は目標（フレームの頭 + 半フレーム）に切り詰められて出る（例 29.97 の49フレーム目で 1.651650）。フレームの番号は合う

### R-13 LTCの入力のメーター

- 規則に触らない根拠: 監視がすでに計算している値をUIへ出すだけで、LTCのデコードと同期には触らない
- 今の作り: ピークとRMSはすでに2秒ごとに計算してログに出している（`LtcAudioSampleProcessor.cs:41・75`、`LtcAudioMonitor.cs:125-153`）が、UIへ出す口が無い
- 直し方の案: 監視からUIへレベルを知らせるイベントを足し（例 100msごと、UIスレッドへはBackgroundで）、LTCの欄に横長のメーター（ピーク）を出す。あわせて「LTCを受け取れているか」を、デコードできたLTCのフレームの数で表示する（音は入っているのにLTCが読めない、という現場の状況を本人が気づけるように）。波形の表示は要望の「できれば」なので、まずメーターと受信の表示だけ
- 試験: 単体（レベルの計算と間引き）。E2E（LTCを流すとメーターが動き、受信の表示が付く。雑音だけのときは受信の表示が付かない）
