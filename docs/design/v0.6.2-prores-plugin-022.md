## 0. 版の変更（2026-10-02 02:4x、利用者の指示、TSP-Fable 経由）

- **v0.2.2 の代わりに v0.2.3 を同梱する**（`8037733`、zip `5e3926f6…`、DLL `1ded64c4…`、.cso 6 個は同じ）。v0.2.3 の変更は v0.2.2 の不備の修正だけ: デコーダの qos=false を毎フレーム確かめ、false なら事前破棄をしない（GstVideoDecoder の finish_frame と同じ）。既定（qos=true）の動作と性能は v0.2.2 と同じ。TSP はデコーダに qos を設定せず、appsink が QoS を出さないので、TSP の経路では v0.2.2 と同じく働かない
- v0.2.2 で作った候補（`5ee2081`）の検証機の一式で、ProRes RTX の S-2 の参照の採取が 1 件落ちた（一時停止中のシークの位置が 2 フレーム先）。v0.2.1 / v0.2.2 の交互の比較（各 3 回、QoS の破棄の行と reference-stale の率）で、v0.2.x と関係があるかを決める。既定の設定での判定は v0.2.3 も v0.2.2 と同じなので、比較の結論は v0.2.3 に当てはまる
- 「無関係」なら v0.2.3 で候補を作り直し、検証機の固定の一式をやり直す（DLL が変わるので省略しない）。「原因」なら止めて Gst-ProRes と原因を見る
- 切り分けの追加の手（記録）: v0.2.3 では proresd3d11dec に qos=false を付ければ、デコーダの側だけで事前破棄を止められる

## 1. 取り込む版

- **v0.2.2 の正式版**（Gst-ProRes の回答 2026-10-01）。いま候補 v0.2.2-rc.2 が Pre-release で、検証機の再測定の後に同じコードで正式版を公開し、zip と DLL の SHA-256 が届く。**固定するのは正式版の値**（rc の zip `0e11bf34…` は使わない）
- 変更は 1 点だけ: QoS で締切を 1 フレーム以上過ぎたフレームを parser にも GPU にも渡さず捨てる（以前は GPU で復号してから捨てた）
- 変わらないもの（Gst-ProRes の回答）: 要素名・プロパティ・.cso（バイト同一）・caps と colorimetry・DLL 名・CRT の下限・max-errors・プロファイル・adapter-luid の扱い。README の説明の修正（ハイブリッド GPU での D3D11 要素のアダプタの揃え方）は TSP に当たらない

## 2. TSP の再生経路では v0.2.2 の変更は働かない（事実）

- shim の appsink: `create_appsink_tail`（`native/gst-shim/src/tcs_gstreamer.cpp`）で `"sync", sync_pacing`（`TRUE` 固定）、`"drop", FALSE`、`"max-buffers"`。**`qos` は設定していない**
- GStreamer 1.28.2 の `gst-inspect-1.0 appsink`: **qos の既定は false**（sync の既定 true、max-lateness の既定 -1）。appsink は上流へ QoS イベントを出さない
- 実測（親、2026-10-01 22:2x）: 試験用の ProRes 4K59.94 を shim の試験プログラムで GPU の経路（`profile=prores-gpu result=ok`、`decoder=proresd3d11dec`）で再生し、flush シークと速度の即時変更を 12 回。`GST_DEBUG=GST_QOS:6,GST_EVENT:5` の出力 1901 行（seek・segment の行は出ている）に **"qos" を含む行は 0**
- したがって、v0.2.2 の「GPU の処理が追いつかないときに遅れたフレームを復号の前に捨てる」は、TSP では働かず、害も無い。**利用者に見える変化は無し**（プラグインの版の更新のみ）

## 4. 検証

- 開発機: ProRes の回 2 本（GPU 142・CPU 0・不一致 0）、非E2E 全件
- 色の比較: **省略する**。理由: .cso（シェーダー）と caps・colorimetry が v0.2.1 とバイト同一・同じで、復号の絵を作る経路が変わらない（変わったのは QoS で捨てるかどうかだけで、TSP では働かない）
- 候補を検証機へ: 固定の一式 1 回（標準 3 通り・本番構成 1、L-1 6、A 2、ProRes 2 通り（RTX／内蔵 AMD）、PR1〜PR4 のロード）

## 5. 起票（v0.6.x の候補、利用者に諮る事項、優先度低）

- **appsink に `qos=TRUE` を付けるか**: 付けると、GPU の処理が追いつかないとき（重い素材・多数同時）に「ほぼ止まる（0.7〜3 fps）」→「処理能力 ÷ 本数でコマ落ちしながら続く」（Gst-ProRes の実測、4K HQ 60p 4 本で 1.15 → 42.6 fps）。同期と出力の挙動の変更なので v0.6.2 には入れない。本番では「止まる」より「コマ落ちで続く」方が合うかを利用者に諮る。推奨素材の範囲内（1 本〜2 デッキ）では GPU が追いつかない状況は観測していない
