# v0.5.3 段 3g-1: ギャップの読み込み 2 経路の「別の口」の設計案

作成: 2026-09-26。対象はブランチ `agent-a-v053-3a` の `c1b63b7`（`480502c` 以降、v0.5.3 と同じ先頭）。
**コードは変えていない**（この md だけ）。行番号は `c1b63b7` 時点。ファイル名は `src/TimecodeSyncPlayer/` からの相対。

背景: 段 3a の表 `docs/design/v0.5.3-load-paths.md` §2 の #3（ギャップの `LoadPausedAt`。
`GapEnterCoordinator.cs:199`・`:242`）と #4（Freeze の取り込みの読み直し。`MainWindow.xaml.cs:2376` →
`GapFreezePathGuard.cs:48`）。そのまま `BeginFileLoad`（`TimecodeSyncService.cs:293-307`）に通すと、
一時停止のままロード解除が最大 5 秒遅れ（その間すべてのシーク抑止）、着地窓がギャップ明けと重なり、
Freeze の取り込みが壊れる（3a の所見 3・4）。利用者の決定（2026-09-26）:
**「ロード中の印を立てずに、必要なものだけを切る別の口」を作って v0.5.3 で直す。**

判断の基準（この案のすべての行に適用する）:

1. Freeze の取り込みとギャップ明けの処理が、今と同じに動くこと
2. 前のファイルの状態を次へ持ち越さないこと

## 1. 提案する口

`TimecodeSyncService` に internal の口を 1 つ足す（仮の名前）:

```csharp
internal void BeginGapFreezeLoad(string source)
```

する（`BeginFileLoad` と同じ順序を保つ）:

1. `SyncLifecycle.Record(SyncLifecycleEvent.GapFreezeLoad, source)`（§4 のイベントを足す場合）
2. `_fileLoadEpoch++`（前のファイルの端へのシークの記録 `boundarySeekTarget` を無効にする。v0.5.1 と同じ機構）
3. `_fileLoad.ClearReleasePending()`（前のファイルの解除の回収待ちを下ろす）
4. `_seekState.Clear()`（前のファイルの保留シークを捨てる）
5. `_seekState.ForgetLastSettled()`（前のファイルの着地の記録を忘れる。3f と同じ）
6. `LifecycleRaised?.Invoke(SyncLifecycleEvent.GapFreezeLoad)`（コントローラ側の `jumpAppliedOnce`・
   `heldReapplyDone`・`smoothUnavailable` を下ろす。3e のイベントを使う）

しない（`BeginFileLoad` との差がこの口の本体）:

- `_fileLoad.Begin`（`loadingFile` を立てない。全シーク抑止と最大 5 秒の解除を起こさない）
- `NotifyLanding`（着地窓を開かない。ギャップ明けの `NotifyLanding` に任せる）
- `_lastSyncSeekAt = now`（デバウンスを更新しない。ギャップ明け 250ms のシーク抑止を作らない）
- `_positionTrust.Reset()`（位置の信頼を触らない。§2 の判断）
- `_engine.ResetSeekGate()`（ゲート履歴を切らない。§3 の保留）
- `_seekState.ResetLearning()` / `_publishedSeekCostSeconds`（§3 の保留）
- `_latencyCompensator.MarkLoadSent`（同期主導のロードではない）

呼ぶ場所（3 か所。すべて UI スレッド）:

| # | 呼び出し元 | 条件 | source |
| --- | --- | --- | --- |
| 3a | `GapEnterCoordinator.LoadNextTrackFirstFrameForGapFreeze`（`GapEnterCoordinator.cs:213` の `LoadPausedAt` の後） | `commandResult.Load.Success` | `load-paused-at` |
| 3b | `GapEnterCoordinator.LoadPreviousTrackFinalFrameForGapFreeze`（`:256` の後） | 同上 | `load-paused-at` |
| 4 | `MainWindow.IsCurrentPathExpectedForGapFreeze`（`MainWindow.xaml.cs:2389` の `result.ReloadIssued` の中） | `result.Load?.Success == true` | `path-guard` |

渡し方: `GapEnterEffects`（`GapEnterCoordinator.cs:364-382`）に `Action<string>? BeginGapFreezeLoad = null` を
**既定値つきで**足し、`MainWindow.CreateGapEnterCoordinator`（`MainWindow.xaml.cs:1124` の近く）で
`_syncService.BeginGapFreezeLoad` を渡す（既定値つきなので既存のテストの組み立てはそのままコンパイルできる）。
#4 は `MainWindow` から直接呼ぶ（`GapFreezePathGuard.Check` は静的で、読み込みはガードの中で起きるため、
呼び出し元で `result.Load?.Success` を見て呼ぶ）。

1 秒ごとに繰り返し呼ばれても害がないか（#4）:

- 口は冪等（消えているものを消し、番号を進め、イベントを 1 行出すだけ）。`boundarySeekTarget` 以外に読み込み番号を
  読むものは無く、番号が進んでもギャップの捕獲は読まない。
- ログだけは読み直しのたびに 1 行出る（最大 1 秒に 1 行。デバウンス `LoadfileReloadDebounceMs` で上限）。
  既存の `Continue mode: ignored stale gap freeze frame ... reissued load ...` 警告と同じ頻度なので許容（§4）。
- `_seekState.Clear()` を 1 秒ごとに呼ぶのは、ギャップ中は同期評価が走らないため実害が無い（次に読むのはギャップ明け）。

## 2. ラッチごとの判断（3a の 9 行 + 4 つ = 13 行）

| # | ラッチ | 判断 | 理由 |
| --- | --- | --- | --- |
| 1 | `jumpAppliedOnce` | 消す | 前のファイルの「Jump を 1 回適用済み」を持ち越すと、ギャップ明けの最初の Jump が Normal フレームまで抑えられる。捕獲は読まない。 |
| 2 | `heldReapplyDone` | 消す | 同上（保持値の 1 回適用）。ギャップ中に保持（Duplicate）が続くと Normal フレームで消えないため、口で消す。 |
| 3 | `smoothUnavailable` | 消す | 前の素材で拒否された Smooth を持ち越さない（§6 の 6 の意図）。捕獲は読まない。差はギャップ明けの補正が Smooth をもう一度試すことだけ（1 回拒否されれば再び立つ）。 |
| 4 | `fileLoadReleasePending` | 消す | 前のファイルの解除をギャップ中の保持フレームが `PollFileLoadRelease` で回収し、古い値へ再適用しない。 |
| 5 | `positionUntrusted` | **残す** | 3a 所見 3。消すとギャップ明けの `EvaluateDecision` が着地前に位置を使い、`NotifyLanding` の前提が変わる（捕獲・解除が壊れる）。新しいファイルの位置も未信頼が正しい。 |
| 6 | `clipBoundaryHeld` | **残す** | Single 専用のラッチ。ギャップは Continue にしか無く、3c のモード切替で Single→Continue の時点で消えている。口から Single の状態に触れない。 |
| 7 | `boundarySeekTarget` | **読み込み番号で無効（実質消える）** | `_fileLoadEpoch++` で記録の番号が変わる（v0.5.1 と同じ）。明示クリアは要らない。 |
| 8 | `pendingSeek` | 消す | 前のファイルの保留目標が、新しいファイルの最初のシークを抑止・置換しない。 |
| 9 | `lastSettledRecent` | 消す | 3f と同じ。前のファイルの着地目標で 0.5 秒抑止しない。 |
| 10 | `loadingFile` | **立てない** | 口の目的そのもの。立てると `ShouldSuppressSeek` が全シークを止め、一時停止のまま解除が最大 5 秒遅れる。 |
| 11 | `seekLandingActive` | **立てない（開かない）** | ギャップ明けの `NotifyLanding` に任せる。先に開くと着地窓がギャップと重なる。既に開いている窓は、ギャップ中は評価が走らないため残してよい（ギャップ明けが開き直す）。 |
| 12 | `followStartLanding` | **立てない（開かない）** | 同上。`NotifyLanding(FollowStart)` を呼ばない。追従開始はギャップ明けの最初の有効フレームが消費する。 |
| 13 | `rateRestorePending` | **残す** | ファイル単位の状態ではない。倍率の復帰は次の補正評価（ギャップ明け）が行う。捕獲は読まない。口で `ResetCorrection` を呼ぶと今と違う。 |

## 4. できごととログ

- `SyncLifecycleEvent` に `GapFreezeLoad` を足す案（`SyncLifecycleEvent.cs:16` の `FileLoad` の隣）。source は
  `load-paused-at`（#3 の 2 か所）と `path-guard`（#4）。ログは `Sync lifecycle: GapFreezeLoad source=...` の 1 行。
- 1 秒ごとの読み直しで 1 行/回出るが、デバウンスで上限が付き、既存の Warning と同じ頻度なので**出してよい**。
  止めたい場合は (path, target) の重複を N 秒抑える案があるが、解析スクリプトが「読み直しの回数」を数えられなく
  なるため採らない。
- `FileLoad` の列は汚さない（ギャップの読み込みは同期のロードゲートを通らない、という事実を別のできごとで残す）。
- このイベントは 3e の `LifecycleRaised`（`TimecodeSyncService.cs:68`）でコントローラにも届き、
  `jumpAppliedOnce`・`heldReapplyDone`・`smoothUnavailable` を下ろす入口を兼ねる（イベントを足さない場合は、
  同じ用途の internal イベントを別に足す必要がある）。

## 所見

1. 口の判断は「消す 6・番号で無効 1・残す 3・立てない 3」。捕獲が読む状態（`FrameSeenSinceCapture`・目標フレーム一致）

2. `positionUntrusted` を残すのが 3a 所見 3 への答え。消す案は着地窓をセットで開く必要があり、「着地窓は開かない」と
   両立しない。
3. ログは `GapFreezeLoad` を足し、1 秒ごとの読み直しでも 1 行/回（既存 Warning と同じ頻度）。
4. ハーネスの `LoadCurrentFile` をこの口へ更新すると、段 0 の表は 7 行が Keeps→Clears になり、
   `SyncLifecycleLogTests` 1 件が変わる。
5. 影響は Freeze 系（F-1〜F-5・RealProjectGap）に限られ、Black 系（G-*）は無影響。

## 親の承認と変更（2026-09-26）

案を承認する。ただし次の 1 点を変える。

- **コントローラの 3 ラッチ（#1 `jumpAppliedOnce`・#2 `heldReapplyDone`・#3 `smoothUnavailable`）はこの口では下ろさない。`LifecycleRaised` も上げない。**
  ギャップの読み込みは、Jump を適用する処理の途中（同じフレームの `ApplySync` → ギャップの分岐 → `LoadPausedAt`）で起きる。
  そこで「Jump を 1 回適用した」ラッチを下ろすと、続く同じ Jump のフレームを再び適用しうる（D20-b (i) の目的を壊す）。
  段 0 の表のこの 3 行は「v0.5.3 では直さない」として理由つきで記録する（段 3c の読み込みの行と同じ扱い）
- §7 の保留 3 点（学習・ゲート・未確認の Jump と同期の保留）は**今のまま触らない**（v0.5.3 で振る舞いを変える範囲を小さくする）

したがって口がするのは: できごとの記録（`GapFreezeLoad`）、読み込み番号を進める、解除の回収待ちを下ろす、シークの保留を捨てる、直前の着地の記録を忘れる、の 5 つ。
段 0 の表で Keeps→Clears になるのは `fileLoadReleasePending`・`pendingSeek`・`lastSettledRecent`・`boundarySeekTarget` の 4 行。
