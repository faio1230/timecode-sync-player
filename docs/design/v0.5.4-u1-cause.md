# v0.5.4 K7（U-1）: 「配信が約 5 秒止まる」の原因測定

作業: w5:p3、2026-09-26。ブランチ `agent-a-v054`（段 0 の後）。指示は
`docs/prompts/2026-09-26-v054-u1-measure.md`。製品の振る舞いは変えていない。計測用の一時計装は
`artifacts/analysis-data/v054-u1/instrumentation.diff` に分けて保存し、作業ツリーからは戻した。

## 0. 結論

1. **U-1 が数える「配信が約 5 秒止まる区間」は、テストプロジェクトの 5 秒ギャップ（トラック間）である。**
   U-1 を回している重い素材の周回（`run-ltc-scenarios.ps1 -MediaDir … -Media M1,M3,M4 -MediaInOffsetSeconds 5`）は
   `-GapSeconds` の既定 5（`scripts/run-ltc-scenarios.ps1:42`）で .tsp を作る。M1(5–20)・M3(25–40)・M4(45–60) の
   間に 5 秒のギャップがあり、U-1 は LTC 6→49 を流すので 2 つのギャップを跨ぐ。停止区間は `gap.enter mode=pause` →
   5 秒 → `load.issue detail=start` と完全に一致し、その間 **合成は 60Hz で publish し続け**（`compose.publish` 301 tick、
   最大間隔 17.8ms）、**UI スレッドも生きている**（`preview.shown` 115、`gst.position` 171）。
2. **UIA は原因ではない。** ギャップ有りのプロジェクトでは UIA の読みを **1 回だけ**にしても同じ 2 つの 5 秒停止で
   失敗する（下の表の gap5-noread。Held≥250ms 3 件・最長 9167ms、配信の空き 2 件・最長 5154ms）。
   ギャップ無しのプロジェクト（U-1 の本来の前提。`tests/…/LtcScenarioE2ETests.cs:266-269` の
   「実素材（ギャップ無しの Continue）のプロジェクトでだけ回す」）では、**50ms の高頻度 UIA でも配信は止まらず合格**する
   （起動直後を除く配信の空きは最大 138ms = トラック切替のロード。Held≥250ms は 0）。
3. 配信（GPU worker の合成・publish）と UI スレッドの間に、秒単位で待たせる結びつきは無い。UI→GPU は
   最新 1 件の mailbox（`Output/TimelineOutputState.cs:26-44`、`Output/OutputEngine.cs:931-936`）で待ち合わせなし、
   GPU→UI は `Dispatcher.BeginInvoke` の投げっぱなし。フレーム通知（`RenderSession` → Background）の UI 側の
   待ちは、計装で **中央 0ms・p95 13ms・p99 111ms・最大 524ms（起動時）** だった（§2）。
4. **UIA の読み 1 回は重いが、配信には効かない。** 読み 3 回（LTC→位置→LTC）の中央 239ms・p95 658ms・最大 1119ms
   （1 読みあたり中央 28〜105ms）。これは WPF UIA のプロセス間往復と UI スレッドの応答待ちで、アプリ側の
   バインド getter は保存済み文字列を返すだけ（§1）。読みの間隔を 50/200/1000/ほぼ 0 に変えても最悪値は
   135〜428ms で変わらない（読みの速さは UI の空きで決まり、読みが UI を詰まらせている形跡は無い）。
5. 直しの第一候補は **U-1 をギャップ無しプロジェクトで回すこと**（製品コードを触らない）。合成・配信の経路に
   触れずに済む。TSP-Fable の「表示値をキャッシュして UIA の読みを軽くする」は、getter が既にキャッシュ済みの
   文字列返しであること、配信が UI と独立であることから、**この不具合には効かない**（§6-3）。

## 1. 測ったこと 1: UIA の読み 1 回あたりの UI スレッドの占有

### どのプロパティが UI スレッドへ渡るか

U-1 の読み（`LtcScenarioE2ETests.U1_Continue_HighRateUiaAudit_KeepsSyncAndOutput`）:

- `scenario.LtcSeconds()` → `Text("LtcTimecodeText")`（`LtcScenarioE2ETests.cs:1961`）
- `scenario.Position()` → `Text("TimeLabel")`（`:1955-1959`）
- 起動時の `MediaFps()` → `Text("MetaLineText")`（`:1990-1995`）
- `E2EAppRunner.Text` は UIA の TextPattern `DocumentRange.GetText(-1)`（空なら `Name`）（`Helpers/E2EAppRunner.cs:298-312`）。

UIA の要求は WPF の自動化ピア経由でアプリの UI スレッドが処理する。アプリ側のバインド getter は**文字列を返すだけ**:

- `ViewModels/SyncViewModel.cs:266-270`（`LtcTimecodeText`）
- `ViewModels/PlayerViewModel.cs:38-42`（`TimeLabel`）、`:44-48`（`MetaLine`）
- `ViewModels/PlaylistViewModel.cs:89-93`（`CurrentTrackLabel`）

値を作るのは UI スレッド（`MainWindow.xaml.cs:2461` の `UpdatePerFrameUI`、`:294-298` の `ApplyFrameText`）。
getter の中で shim・GPU・DB を触る箇所は無い。

### 実測（一時計装、ギャップ無し・50ms、run `v054-u1-gap0-50-instr2`）

読み 1 回 = LTC → 位置 → LTC の 3 呼び出し。126 回分:

| 指標 | LTC 1 回目 | 位置 | LTC 2 回目 | 3 呼び出し合計 |
| --- | ---: | ---: | ---: | ---: |
| 中央 | 104.7ms | 27.9ms | 75.8ms | **239.3ms** |
| p95 | — | — | — | **658.2ms** |
| 最大 | — | — | — | **1119ms** |

最悪の読みは 23:18:31.9 の 1119ms。**最小の 3 呼び出しでも約 100ms**かかる。読みの間隔を変えた素の U-1 の
`worstReadMs` は 50ms=405ms、200ms=428ms、1000ms=385ms、1 回のみ=135ms で、**読みの頻度を 1/20 にしても
最悪値は下がらない**。読みの遅さは「UI スレッドがその瞬間に空いていないこと」と UIA の往復そのもので決まり、
読みが UI を占有して詰まらせる形跡は無い。

## 2. 測ったこと 2: 止まった区間の UI スレッドの処理内容

止まった区間の代表（gap5-noread、+25.41→+30.43 の 5024ms、一時計装なし）:

| 区間内の事象 | 値 |
| --- | ---: |
| `gap.enter mode=pause` | +25.45s |
| `compose.publish`（GPU worker） | 301 件（最大間隔 17.8ms = 60Hz 継続） |
| `source.acquire detail=Ended` | 299 件（トラック M1 の EOF） |
| `preview.shown`（UI） | 115 件 |
| `gst.position`（UI → shim の位置照会） | 171 件 |
| `gst.delivery` | 2 件（区間の両端） |
| `load.issue detail=start` | +30.42s（ギャップ出口のロード） |

つまり「配信が止まった」のは**再生側のフレームが無い（EOF + ギャップの一時停止）**ためで、合成は止まっておらず、
UI スレッドもフレーム通知・位置照会を処理し続けている。フレーム通知が Background キューで待たされている形跡は無い。

UI 側の待ち時間（一時計装。`RenderSession` の `Dispatcher.BeginInvoke(Background)` を包んで計測。
`ui.renderUpdate` lag）:

| 指標 | 値（ギャップ無し・50ms、instr2） |
| --- | ---: |
| 件数 | 2212 |
| 中央 | 0ms |
| p95 | 13ms |
| p99 | 111ms |
| 最大 | 524ms（+1.1s の起動直後。ほかは +25.9s の切替 507ms など） |
| `preview.shown` の最大間隔 | 517ms（p95 57ms） |

秒単位の待ちはどこにも無い。ギャップ区間の 5 秒は、UI・合成・フレーム通知のいずれの詰まりでもない。

## 3. 測ったこと 3: 配信の経路が UI スレッドに依存しているか（コード）

- 合成と publish は GPU worker の中で完結する（`Output/OutputEngine.cs:943-982` lease→合成、`:1061` `compose.publish`、
  `:1101` preview readback）。UI を待つコードは無い。
- UI → GPU は最新 1 件の mailbox。`SubmitOutputState`（`MainWindow.xaml.cs:612-629`）が `TimelineOutputState` に
  上書きし、GPU worker は `ComposeTick` で取れるときだけ `Take()`（`Output/OutputEngine.cs:931-936`）。待ち合わせなし。
- GPU → UI は `Dispatcher.BeginInvoke` の投げっぱなし（プレビュー: `MainWindow.xaml.cs:637-668`、状態・再生成依頼:
  `:702-730`、`:763-792`）。GPU worker から `Dispatcher.Invoke`（同期）は無い。
- フレーム通知は shim のコールバック → `RenderSession` のレンダースレッド → `RenderUpdateScheduler`（合流）→
  UI へ Background（`RenderSession.cs:58-103`、`:112-144`、`RenderUpdateScheduler.cs:23-57`、`MainWindow.xaml.cs:244-247`）。
  UI が混むと通知は合流して遅れるが、**レンダースレッドと GPU worker は止まらない**。
- UI と配信が共有するのは shim の `frame_lock` だけ（UI の `tcs_player_get_time_pos` は
  `native/gst-shim/src/tcs_gstreamer.cpp:3831-3849` でロック保持のまま `gst_element_query_position`。
  GPU worker の `Acquire`/`Drain` は `:3921-3925`/`:4222-4235`、streaming thread の `on_new_sample` は `:1490-1494`）。
  ただし今回の 5 秒停止は `source.acquire=Ended`（EOF）とギャップ一時停止が原因で、ロック待ちの形跡
  （`compose.ringWait` の多発・`compose.fencePending` の滞留）は無い。

## 4. 測ったこと 4: UIA の間隔を変えたときの配信の止まり

## 5. 補足の観測

- 一時計装の 1 回目（run `v054-u1-gap0-50-instr1`）は、ギャップ無しでも失敗した。原因は UIA ではなく、
  **LTC 入力の約 3.3 秒の途切れ**（アプリの音声統計は `callbacks=40` のまま `decodedFrames=0` が 2 区間続き、
  復帰時に LTC が 8.32 秒ジャンプ）。たまたま動画 M1 の EOF と重なり、次のトラックへの切替が LTC 復帰まで
  3.8 秒遅れた（アプリは最終フレームを保持し、復帰で正しく切替。既定は RunThrough なので一時停止しない）。
  読みログをメモリ集約に変えた 2 回目（instr2）は合格し、読みの間隔も正常だった。原因は計装の
  読みごとのジャーナル I/O か、テスト側の信号生成の一時的な詰まりと見られる（製品側の配信経路ではない）。
- クリーンな周回の `signal-loss-confirm`（段 0 の Debug ログ）は 1 周あたり 1 回（起動直後の 250〜344ms）。
  U-1 の信号は通常は安定している。
- 一時計装は `artifacts/analysis-data/v054-u1/instrumentation.diff` に保存した（アプリ: フレーム通知の
  Background 待ちを `ui.renderUpdate` として出力トレースへ記録 / テスト: 読みごとの内訳をメモリに集約して
  `u1-read-stats` に記録）。作業ツリーは元に戻してある。

## 6. 直し方の候補

### 6-1. U-1 をギャップ無しプロジェクトで回す（推奨。製品コードを触らない）

- **a. 実行側**: U-1 用に `-GapSeconds 0` の周を分ける（runner が U-1 用の .tsp を別に作る、でも可）。
  触る範囲: 実行手順・ドキュメントのみ。危険: なし。見積もり: 30 分（実行 1 回で確認）。
- **b. テスト側の自己ガード**: `scenario.Tracks` の隣接（前トラックの End と次の Start）を検査し、
  ギャップがあれば `scenario.Invalid(...)`（または Skip）にする。触る範囲: `LtcScenarioE2ETests.cs` のみ（約 10 行）。
  危険: なし（前提をテスト自身が守る）。見積もり: 0.5 日（ビルド + U-1 1 回で確認）。
- 効果: 重い素材の周回でも U-1 が本来の意図（高頻度 UIA で配信が乱れないこと）を判定できる。
  既知の制限・リリースノートの「UI を 50ms ごとに読むと配信が数秒止まる」は、実測では
  「テストプロジェクトの 5 秒ギャップを監査が数えていた」なので、条件の書き直しが必要（親の判断）。

### 6-2. 監査をギャップ対応にする（ギャップ付きプロジェクトで U-1 を回し続ける場合のみ）

- `OutputContinuityAudit` が `gap.enter` / `source.acquire detail=Ended` / `load.issue` を読み、ギャップ・EOF・
  切替に重なる Held と perf の欠落を除外する。触る範囲: `tests/Helpers/OutputContinuityAudit.cs` と U-1。
  危険: 監査が緩くなり、合成側の本物の停滞を除外しうる（除外条件の設計が要る）。見積もり: 0.5〜1 日。

### 6-3. 表示値のキャッシュ（TSP-Fable の見立て）は採用しない

- 測定結果: 読まれる getter は既に保存済み文字列のフィールド返し（`SyncViewModel.cs:266-270` ほか）。
  読みの時間は WPF UIA のプロセス間往復と UI スレッドの空きで決まり（3 読みの中央 239ms、最小でも約 100ms）、
  キャッシュで削れる余地はほぼ無い。配信経路は UI と独立で、50ms の UIA でも止まらない（§4）。
- 触る範囲: なし（採用しない）。危険: 効果のない変更で回帰リスクだけ増える。見積もり: —。
- もし外部ツールの読みの応答そのものを良くしたいなら、別件として WPF の自動化ピア・毎フレームの
  TextBlock 更新の設計を見直す候補がある（U-1 の失敗とは無関係。v0.5.4 の既知のエラーには当たらない）。
