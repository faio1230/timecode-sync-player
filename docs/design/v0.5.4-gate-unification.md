## 0. 目標と合否

- 目標（利用者の決定 2026-09-26）: 「着地の判定は 1 つ、Jump の雑音の除去は 1 つ、シークしてよいかの門は 1 つ、一時停止の持ち主は 1 つの集合」
- 合否（GOAL 1 節）: 固定の一式 2 回＋重い素材 3 本立て＋検証機。加えて**平常時の遅延の前後比較**で悪化 0、門の数と遅延の減少を示す。
  比べる指標は段 0 と同じ（`scripts/analyze-v054-gates.py` の出力: 門ごとの発火回数と遅延、着地の遅れ、pending の時間切れ、シーク本数、通り過ぎの戻し、同じ目標への 3 本目以降、黒フレーム、一時停止の遅れ）
- **再発を押さえるテスト（2 節の右列）が全部緑**であること。前後比較の表だけでは、守っていた型が測定に現れないまま消えうる（TSP-Fable のレビュー）
- やり方: 1 門（または 1 つの畳み）1 コミット。守っていた欠陥の再発を、決定的なシナリオ層（`docs/design/v0.5.4-scenario-layer.md`）の単体で先に押さえてから触る

## 3. 測定で決めること

- 14（デバウンス）を消した後、13 だけで連続シークが増えないか。段 0 の「同じ目標への 3 本目以降」（発振）が 0 のままであること、同期シークの本数が増えないことを、標準 2 周と重い素材で確かめる。増えたら 14 は残し、表に理由を書く
- 10・12・5 の一本化の前後で、S-2・C-1 の着地の遅れと、未信頼の間に出たシーク（0 であること）を比べる

## 4. §8 の改善候補（停止モードの Jump 直後の即時停止）

- D38 文書 §8: 停止モードで Jump の直後に Duplicate が続いたら、250ms を待たずに一時停止する。戻しのシークが 1 フレーム以内に収まり、門 19 で消える
- これは**振る舞いの変更**（停止が最大 250ms 早くなる）なので、GOAL 3 節の「挙動を変える判断」に当たる。**利用者に諮る**（下の 5 節）

## 5. 利用者に諮ること

1. §8 の改善を入れてよいか（停止モードで、LTC が飛んでから止まったときに、映像がすぐ止まる。いまは約 0.25 秒進んでから戻る）
2. 14（デバウンス）を消したときに、LTC の信号が乱れた現場で同期のシークの回数が増える危険。測定で増えなければ消す、増えたら残す、という決め方でよいか

### 決定（2026-09-26、利用者の回答）

1. **§8 の改善を入れる**（停止モードで、Jump の直後に Duplicate が続いたら待たずに一時停止する）
2. **14（デバウンス）は測定で決める**（消して、標準 2 周・重い素材でシークの本数と発振が増えなければそのまま、増えたら残す）
3. **13 を B へ移す変更も測定で決める**（2026-09-27、利用者の回答）: 確認済みの Jump は 13 を通さずにシークする。着地の遅れの中央が下がり、シークの本数と発振が増えなければ入れる

## 6. 段取り

### 9-1. 着地の事象（shim は変えない案を第一にする）

- **定義**: シーク（または開始位置つきのロード）で進んだ世代の、最初のフレームが配信されたとき。
  shim はシーク・ロードのたびに世代を進め（`tcs_player_seek` が新しい世代を返す）、`acquire(gen)` は古い世代のフレームを返さない（D25）。
  アプリは位置のサンプルごとに `PlaybackPositionSample.DeliveredGeneration` と `CurrentGeneration` を受け取っている（`Contracts/PlaybackPositionSample.cs`、`Gst/GstPlaybackApi.cs:322`）。
  したがって **着地 = `DeliveredGeneration >= シークの世代`** で、位置の窓（門 6 の target−tol〜target+2tol）や 200ms の cooldown に頼らずに判定できる
- **着地せず**: シークから安全の時間切れ（1 つの定数）までに着地の事象が来なければ「着地せず」。EOS（K3 で配線した Ended）で目標のフレームが来ない型もここに入る
- **shim を変えるのは後段**: 上の判定で足りない型（一時停止中のシークでフレームが配信されない、EOS でフレームが来ない）が再現テストで残るときだけ、
  shim に「世代の最初のフレームを配信した」通知を足す。その場合は実機ロード 1 本、`scripts/check-shim-lock-rule.py`、D34 のロード成功ゲートの単体（`--policy-only`）を統合に含める

### 9-8. 着地の定義の修正（段 B の準備の結果、2026-09-27）

`docs/design/v0.5.4-stageB-prep.md` の確認で、(a) 一時停止中のシークと (b) 開始位置つきのロードは世代で着地を取れるが、(c) 連続したシークでは
shim のセグメントの畳み込み・5 秒の安全弁・ポンプの期限切れで、前の世代のフレームが新しい世代の最初のフレームとして配信され得る、と分かった。
そこで **着地 = `DeliveredGeneration >= シークの世代` かつ 配信されたフレームの位置（`DeliveredSeconds`、PTS）が目標の近く（target−tol〜target+2tol）** にする。
照会した位置ではなく配信したフレームの位置を見るので、今の門 6（照会した位置の窓と 200ms の cooldown）より確か。shim は変えない。
開始位置つきのロードの基準は「ロードの API を呼んだ後の世代」（ロードの中で世代が 2 回進むため）。
9-1 の後段（shim の通知）は、この定義でも閉じられない型が再現テストで残るときだけにする。
- B1 に足す指標（TSP-Fable、§9-8 の承認つき）: (1) シークの後に最初に届いた新しい世代のフレームの PTS が窓の外だった回数（(c) 型の実測。0 でなければ shim の通知を検討）、

### 10-1. 規則

1. **マスター時計**: LTC のフレームの終端時刻（サンプル時計）で `M(t) = 最後に受理した値 + (t − 終端時刻)`。フレームが途切れたら freewheel（250ms）の間は外挿を続け、超えたら「マスター停止（無音）」。
   同じ値のフレーム（Duplicate）が 2 枚続いたら即「マスター停止（保持）」（U8）
2. **誤差**: `e = 再生位置 − (M(t) − トラックの写像のオフセット)`。再生位置は配信したフレームの PTS（着地の判定と同じ源）
3. **2 段の追従**: `|e| > 閾値`（= max(tol, r_max × c)）→ シーク（relocate）1 回。着地の状態（世代と PTS）で確定するまで判定を止める。着地せず（時間切れ）なら再開。
   **relocate の目標 = M(now) + c**（マスターが動いている間。c はシークの所要の学習値、学習前は 0。経路では分けない。マスター停止中は停止した値で先行量を付けない）。
   すべての relocate（ギャップの出口を含む）を着地の状態に通す（2026-09-28、TSP-Fable の判定）。
   **relocate は varispeed を持ち越さない**: どの経路の relocate でも、発行した時点で倍率を 1.0 に戻し、位置の不安定による補正の停止を下ろす（2026-09-28）。
   **着地待ちの間の「遠い新要求」（門 8）の比較**: 前方の許容を、シークの発行からの経過時間ぶん広げる（着地を待つ間にマスターは実時間より速くは進まないので、
   動き続けるマスターを離れた新要求と取り違えない）。後方は広げない。上限は着地の時間切れ（3 秒）で自然に付く（2026-09-28、TSP-Fable の判定）。
   `|e| ≤ 閾値` → varispeed: `rate = 1 − k·e` を ±上限で制限（今の補正器）。**relocate の直後の 1 サンプルは varispeed しない**
4. **マスター停止中**: マスター停止に入るとき、停止した値へ 1 回合わせる（規則 3 と同じ判定）。以後は varispeed も relocate もしない。停止モードは一時停止、RunThrough は 1.0 で走る。
   **入口は Duplicate 2 枚（両モード、Jump の有無を問わない）**（2026-09-28、U8 から「適用した Jump の後に」を外した）
   **マスター停止の定義は 2 つある（2026-09-28、TSP-Fable の判定）**:
   (a) 先行量を 0 にする判定は「直近のフレームが Duplicate（1 枚）か信号断」（安全側。止まりかけた LTC の先へ先行量ぶん行き過ぎるのを避ける。D37-g の型）。
   (b) 規則 4 の入口の合わせは「Duplicate が 2 枚続いたら」（誤検出を避ける側。発生器の合わせ直しで同値が 1 枚挟まるだけで停止の合わせをしない）。
   （2026-09-28 に TSP-Fable の判定で書き直し。B3 で見つかった保持中の補正はこの規則の違反）。復帰（新しい値かフレームの再開）で 2〜3 に戻り、値が飛んでいれば 3 の relocate

モデルの外側（「誰が制御しているか」と「M(t) をどのトラックの何秒に写すか」）: 単発の壊れたフレームを弾く Jump の確認（4、1 フレーム）、手動操作（22）、一時停止の持ち主の集合（D）、
Continue のトラックの写像・ギャップ・境界ホールド。これらは chase の内側に条件を持ち込まない。

### B3 の速度の変更の増加の原因（p6 の調査、2026-09-27）と親の判断

- R-3（ランスルー）: 確定した Jump の適用の直後に rate 0.964 が入り、保持の 4 秒間はそのまま走り続けた（規則 4 の違反。ランスルーは 1.0）。R-1・R-4 の増加は保持中ではなく、準備のシークの後の収束
- S-1 ほかの増加: 着地が早く確定し、その時点の 10〜60ms のずれ（照会した位置と配信した位置の差）を Smooth が 2〜4 秒かけて小さな段で詰める（1 回のずれで 40〜100 行）。旧は 200ms の cooldown の間に不感帯の中まで縮んでいた
- 判断: (1) 規則 4 を B4 として実装する（D の集合か直近の Duplicate の間は補正を評価しない、ランスルーの保持に入る時に rate を 1.0 に戻す。赤いテスト 3 場面）。
