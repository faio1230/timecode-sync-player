# v0.5.4 K3: ギャップの Freeze で、最終フレームへのシークが EOS と重なると直前の絵が残る（A1 型）

- 作成: 2026-09-27、担当 w5:p3、ブランチ `agent-a-v054`（v0.5.4）。作業ツリーは `timecode-sync-player-v053`
- 範囲: 決定的な再現と直し方の候補まで。**製品コードは直していない**（git への書き込みもしない）
- 根拠: `docs/prompts/2026-09-27-v054-k3-a1.md`、`docs/release-0.5-plan.md` の「既知の間欠」と「潰す一覧」K3、
  `docs/analysis/2026-09-17-A1-gap-freeze-frame-not-updated.md`（以下 A1 解析）、`docs/design/v0.5.2-sync-state.md` §11-3
- 行番号はこの作業ツリーの v0.5.4 時点。`native/` は `native/gst-shim/src/tcs_gstreamer.cpp` の行

## 0. 要約

- **再現できた。** シナリオ層（`ScenarioClock` + `ScenarioPlayback` + `GapFreezeHandler` + 取り込みの門）で、
  「最終フレームへのシークの着地」と「EOS」の前後を固定した 4 件を足した。EOS がシークの後を追い越す順序の
  1 件だけが赤（非E2E 2,800 件: 合格 2,799・失敗 1・スキップ 0。trx は `TestResults/v054-k3-a1/non-e2e.trx`）
- **機序**: EOS と重なると、シークで作った新世代のフレームが 1 枚も配信されない。アプリの確定門は D21 で
  「進入後に届いたフレーム」を要求する（`GapFrameCaptureCoordinator.cs:32-33`）ため、位置が目標の ±2 フレームに
  入っていても確定できず、3 秒（`GapFreezeHandler.cs:54`）で打ち切って Held（直前の絵）が残る。
  D32 の遅延確定（`GapFreezeHandler.cs:221-241`）は「フレームが遅れてでも届けば」効くが、この順序では
  フレームが 1 枚も来ないので発火しない
- **位置の数値**: 検証機の失敗は 尺 20.000 / 30fps で 目標 19.967・位置 20.033。差 0.0667 はちょうど 2 フレームで、
  アプリの位置許容（±2 フレーム、`ContinueModePlaybackPolicy.cs:72`）には入る。落ちているのは位置ではなく
  「進入後に届いたフレーム」の有無。なお `ComposeLayer` の Freeze 保存は許容 0.05 秒（`ComposeLayer.cs:64`）なので、
  EOS 側の位置のフレームが来ても保存されない（±2 フレームと 0.05 秒のずれ。§1-6）
- **直し方**: 第一候補は C# 側の復帰（Ended をギャップ捕獲へ配線し、EOS を観測したら最終フレームのシークを
  やり直す。次に、効かなければ目標位置での再ロード）。根治は shim 側の配信（EOS と重なった最終フレームを
  捨てない）。時間切れの定数の調整だけでは直らない（§3）
- **この文書は設計判断まで。** 触る範囲・危険・見積もりを出して止まる（利用者に諮るのは親）

## 1. いまのコードでの順序

### 1-1. ギャップ進入（pause → 待ち開始 → seek）

`SeekToFinalFrame` の実行は `GapEnterCoordinator.StartGapFreezeCaptureCore`（`GapEnterCoordinator.cs:77-115`）:

1. `ResetEndAdvanceTriggered`（:79）
2. `ApplyGapPause`（:80）→ `PauseForGap` = `SetPaused(true)`（`GapPlaybackCommandExecutor.cs:19`）。
   **シークより先に一時停止**（A1 解析 §3 の F-1 の順序と同じ）
3. `EnterFreezeCapture`（:102）→ `_frameSeenSinceCapture = false`・`StartedAt = now`（`GapFreezeHandler.cs:140-151`）
4. `SeekTo(target)`（:103）→ `PlaybackOperationsCoordinator.SeekTo`（`PlaybackOperationsCoordinator.cs:122-161`）→
   `IPlaybackApi.Seek` → shim `tcs_player_seek`

### 1-2. shim の seek と EOS

`tcs_player_seek`（`tcs_gstreamer.cpp:3566-3598`）:

- `seek_prepare_locked`（:2783-2881）: `generation++`（:2788）・**`p->frames` を全消し**（:2808-2811）・
  期待境界 `seek_boundary_expect = seen + 1`（:2803-2807）・`p->eos` を消す（:2819-2823。paused 中は
  PLAYING 復帰を予約しない）
- 送信は `seek_send`（:2887-2918）。MP4 は accurate（:2837-2840）
- `was_paused` なら `pump_arm`（:3595-3596）。pump は paused のときだけ有効（:2512）で、
  PLAYING へ上げて新世代のフレームを待つ。期限は既定 4000ms（:243、`TCS_PUMP_BUDGET_MS` で変更可）
- バススレッドは EOS を待ち、観測すると `p->eos = true`（:2659-2664）
- `pump_preroll_tick`（:2537-2613）: `pump_generation` のフレームが `p->frames` に来るまで待ち、
  期限到達なら PAUSED へ戻し `last_error` を記録、`seek_boundary_expect` を 0 にする（:2572-2584）

### 1-3. EOS と重なったときに起きること（フレームが 1 枚も来ない）

順序が問題になるのは、**seek の準備（`p->eos` を消した後）を EOS メッセージが追い越す**場合:

- `p->eos = true` はフレームの配信を直接止めない。しかし seek 後に新世代のフレームが `p->frames` に
  入らないと、`tcs_player_acquire` は「フレーム無し + eos」で `TCS_ERR_ENDED` を返す（:3985-3992）。
  アプリ側は `GStreamerSource.TryAcquire` がこれを `SourceStatus.Ended` にし、`onEnded` を呼んで
  `GstSeekingTracker.NotifyEnded` だけを通す（`GStreamerSource.cs:159-164`、`MainWindow.xaml.cs:783-784`）
- 位置クエリは、現世代の配信フレームが無いので pipeline の値へ落ちる（`get_time_pos_locked` :3765-3810）。
  これが 20.033（尺 + 1 フレーム）として観測される
- **D25 の前シークフィルタ**（:1306-1331、:1333-1354）: 新しい seek の SEGMENT が appsink に届かないまま
  バッファが来ると、そのバッファは「シーク前」とタグされ落とされる（`on_new_sample`）。落とし続けは
  期限（pump 4000ms）まで続く。EOS と重なったときに、目標フレームがここで落ちている可能性がある（§1-7）
- pump が期限で諦めるときも、フレームは 1 枚も配信されていない

### 1-4. アプリ側の取り込み門と 3 秒

- 100ms タイマー（`MainWindow.xaml.cs:2097-2107`）と描画コールバック（:2210-2248）が
  `TryCompleteGapFreeze` を呼ぶ。門は `GapFrameCaptureCoordinator.Decide`（`GapFrameCaptureCoordinator.cs:23-41`）で、
  「状態が EnteringFreeze/Waiting・expected path・ネイティブシーク中でない・**進入後にフレームが届いた**・
  位置が目標 ±2 フレーム」のすべてを要求する
- フレーム到着は `OnSourceFrameReady`（`MainWindow.xaml.cs:2255-2285`）がソースフレームの PTS で判定する。
  Ended では `SourceFrameReady` が呼ばれない（`OutputEngine.cs:955-969` は `Ready` のときだけ通知。Ended は
  :978-979 で skip）ので、`_frameSeenSinceCapture` は false のまま
- 時間切れは **3.0 秒**（`GapFreezeHandler.cs:54`、判定 :250-253）。これは shim の pump 予算
  **4000ms より先に切れる**（A1 解析 §1.2）。タイマーは `ForceFreezeComplete` で打ち切り（:2109-2113）、
  `CachedTargetKnown = false`（`GapFreezeHandler.cs:199-215`）→ 合成は GapFreeze でも `frozen == null` なので
  Held（直前の絵）を描き続ける（`ComposeLayer.cs:14-20`、:140-152）

### 1-5. D32 の遅延確定が発火しない理由

- D32 は、打ち切り後も同じギャップに居る間、目標一致フレームの到着で捕捉を開き直す
  （`GapFreezeHandler.cs:96-103`、:221-241、`MainWindow.xaml.cs:2261-2268`、:2304-2315）
- 発火の入口は `OnSourceFrameReady` なので、**フレームが 1 枚でも遅れて届けば**確定できる。
  この順序の失敗は「新世代のフレームが 1 枚も配信されない」ことが本体で、D32 の入口に到達しない
- A1 解析のあとに入った D32 3 件（`93ac50e`・`8468056`・`badf947`、2026-09-17）と v0.5.1 の
  状態遷移化（`b52867c`）のあとでも残る、という v0.5.2 §11-3 の観測と整合する

### 1-6. 数字の確認（19.967 / 20.033、30fps）

- 標準素材（`artifacts/media/ltc_a/b/c.mp4`）は 30fps・尺 20.000。目標 = 尺 − 1 フレーム = 19.9667。
  EOS 側の位置 = 尺 + 1 フレーム = 20.0333
- 差 0.0667 = 2/30。`ShouldCaptureFreezeFrameAfterFrameStep` は `<= 2 フレーム`（`ContinueModePlaybackPolicy.cs:72`）
  なので**位置だけならちょうど許容に入る**。落ちているのは `frameSeenSinceCapture` だけ
- ただし `ComposeLayer` の Freeze 保存の許容は 0.05 秒（`ComposeLayer.cs:64`、:216-218）。EOS 側の位置の絵は
  目標とみなされない。位置許容を広げる案は、この 2 つの数字が食い違うため単独では効かない

### 1-7. 仮説（shim のどこで落ちるか）と確かめ方

どれもログで切り分けられる。A1 解析 §4.4 の記録に加え、次の行を同時に取る:

| 仮説 | 見える証拠 |
| --- | --- |
| S-a: seek の SEGMENT が appsink に届かず、目標フレームが D25 で落ちた | `D25: dropped pre-seek sample pts_ms=...`（`tcs_gstreamer.cpp:1344-1354`）、`lease: acquire none ... rc=-6`（:3989） |
| S-b: pause したまま pump が期限まで待って諦めた（フレーム自体が出ない） | `paused-seek: pump deadline ...`（:2598-2604）、`GapSeeking?` ではなくアプリの `gap freeze final-frame capture timed out`（`MainWindow.xaml.cs:2111`） |
| S-c: EOS が seek の後を追い越した | `bus EOS`（:2662）の時刻が `seek: send end`（:2904）の後。`p->eos` は消えない |

**確かめ方（実装はしていない）**: native の smoke test に `--eos-final-seek <file>` を足し、
「終端の直前から PLAYING → 一時停止 → `duration − 1/fps` へ paused seek」を回す。EOS を seek に
重ねる順序は `TCS_TEST_HOLD_SEEK_LOCK_MS`（:2824-2825。seek の準備中 `frame_lock` を保持する）で
固定できる（バススレッドは同じロックで待つため、EOS の処理が seek の準備の後へ入る）。
既存の `--paused-seek-pixels`（`shim_test.cpp:1397-1570`、tail の既定が 19.967）は「少し再生 → 一時停止 →
tail へ seek」までで、EOS を重ねる順序を持たない。
**このツリーではビルドしなかった**: native のビルドは `vendor/Spout2` を要求し（`CMakeLists.txt:15`）、
この作業ツリーには無い（`native/gst-shim/get-spout.ps1` が取ってくる。ネットワークと大きな副作用）。

### 2-2. 4 件と赤

| テスト | 順序 | 今日 |
| --- | --- | --- |
| `EosLandsBeforeTheSeek_TheSeekClearsTheEosState_AndTheFrameConfirms` | EOS → seek の着地 → フレーム到着 | 緑（shim の契約どおり） |
| `FrameArrivesAfterTheSeek_ConfirmsTheFreeze` | seek → 進入後にフレーム到着（通常、D21-b） | 緑 |

必要メッセージは「EOS と重なった最終フレームのシークでも、フリーズは最終フレームで確定できること（A1 型）」。
この赤は「フレームが 1 枚も配信されない」ことを固定する再現で、直し方（C# の復帰 / shim の配信）が
決まったら、直し方に合わせて赤のテストを緑にしてコミットに含める（`docs/design/v0.5.4-scenario-layer.md` §7-1 の規則）。

### 2-4. shim の単体で再現できるか（調査）

- **できる見込み（未実施）**。§1-7 の `--eos-final-seek` を足せば、順序を仮想時間ではなく
  `TCS_TEST_HOLD_SEEK_LOCK_MS` で固定して、「目標フレームが配信されるか」だけを見られる。
  EOS の再現に実時間の運は要らない（一時停止 → EOS 処理を seek の後ろに置く）
- 実施しなかった理由: native ビルドに `vendor/Spout2` が要る（このツリーに無い）。また、K3 の再現は
  C# 側で足りる（上記）。shim 側を直すと決まったら、このモードを追加して native で赤 → 緑にするのが筋

### 2-5. 実機 F-4（回していない）

E2E は VB-CABLE 等の実機が要るため回していない。回数と時間切れの数（v0.5.2 §11-3 の 2/151）は
親の固定の一式の記録を使う。この再現の目的は、率の低い実機の失敗を机上で 1 件に固定すること。

## 3. 直し方の候補（直さない）

`推奨素材（H.264）で起きる型なので既知の制限にはしない` が前提。候補は「C# 側でフレームを
取り直す」と「shim 側で配信を取りこぼさない」の 2 系統。

| # | 候補 | 触る範囲 | 仕組み | 危険 | 見積もり |
| --- | --- | --- | --- | --- | --- |
| C-1 | **EOS を捕獲へ配線し、最終フレームのシークをやり直す**（第一候補） | C# のみ | `onEnded`（`MainWindow.xaml.cs:783-784`）に、GPU worker から UI への通知を足す。`EnteringFreeze` で `TryBeginSeekRetry`（`GapFreezeHandler.cs:170-178`、上限 2 回）→ `SeekTo(target)`（:2332-2358 の再シークと同型）。shim は seek で EOS 状態を消して pump を張り直す（:2819-2823）ので、2 回目は EOS の追い越しが起きない | Ended は acquire のたびに来るので、連打の抑制（1 件だけ予約。既存 `_gapFreezeStaleFrameRetryPosted` と同型）が要る。再シークで shim 世代が進む（リース返却・`ClearSourceFrame` の経路は既存と同じ）。EOS が真に post-seek の場合は 2 回目も失敗し得る（その場合は C-2 へ） | 半日〜1 日 + E2E 再確認 |
| C-2 | **EOS で目標位置の一時停止ロードに切り替える**（C-1 の後段） | C# のみ | C-1 の再シークでフレームが来ないとき、直前トラックを `LoadPausedAt(path, target)` で読み直す（`GapEnterCoordinator.cs:245-301` の経路と同じ。新しいパイプラインは EOS 状態を持たない） | 4K・長 GOP ではロード + プリロールが 3 秒を超え得る（D22 の F-5 証跡は 開始位置つき一時停止ロードが 3 秒に届かない）。推奨素材（H.264）なら 0.1〜0.5 秒程度で収まる見込み。ギャップ中の読み直しは既存の `BeginGapFreezeLoad` の口を通す | 半日 + 検証 |
| S-1 | **shim で、EOS と重なった最終フレームを捨てない／配信する**（根治） | shim | 候補は 3 つ: (a) `seek_prepare_locked` のフレーム全消し（:2808-2811）で、EOS 済みかつ最新サンプルの PTS が目標 ±1 フレームなら新世代へ付け替えて残す、(b) `pump_preroll_tick` の期限時に、EOS 済みで目標一致の最新サンプルがあれば配信して seek 成功として扱う、(c) `on_new_sample` の D25 前シークフィルタで、EOS 後に届いた目標一致のサンプルだけ通す | D25 の「シーク前の絵を新世代として配信しない」不変条件を壊さないこと（PTS の一致と EOS を条件に限定）。shim Release の再ビルドと全形式（H.264 / ProRes / VP9 / AV1 / HAP）の回帰、検証機での確認。**どの候補が正しいかは §1-7 のログで先に切り分ける** | 切り分け半日 + 実装/native 半日〜1 日 + 回帰 1〜2 日 |
| S-2 | **時間切れの定数の整合**（単独では直らない） | C# + 設定 | アプリ 3.0 秒 < shim pump 4.0 秒（`GapFreezeHandler.cs:54`、`tcs_gstreamer.cpp:243`）。アプリ側を pump より長くする（例 4.5 秒） | フリーズの打ち切りが一律に遅れ、遅い素材で Held の期間が延びる。フレームが 1 枚も来ない型には効かない。D32 があるので遅延フレームは元々拾える | 半日 + 全 E2E |

**推奨（親への案）**: C-1 → C-2 の順でアプリ側を先に試し、F-4 の再測定で残るなら S-1 の切り分けと
実装に入る。理由: (1) v0.5.4 は安定版で shim の再ビルドは回帰の広さが最も大きい、(2) C-1 は既存の
再シーク機構（D21-b）と EOS の配線だけで、shim の契約（seek で EOS を消す）をそのまま使える、
(3) C-1 が効かない場合の C-2 も既存の読み込み経路の再利用で、新しい状態を持たない。
S-1 は根治で、native の再現とログの切り分けが出てから設計する。

## 4. 未確定点・申し送り

- **赤テストの扱い**: C-1 の実装で緑になった（§5）。修正と同じ作業ツリーに置いてある
  （git へ書き込み禁止のためコミットはしていない）。リポジトリの規則
  （`docs/design/v0.5.4-scenario-layer.md` §7-1）どおり、修正と同じコミットに入れる
- **shim の実際の落ち所は未確定**（§1-7 の S-a / S-b / S-c）。C-1 が実機で効かない場合に S-1 を選ぶなら、
  先に `--eos-final-seek` とログで切り分ける。この文書の再現は C# の確定門の側から見た形で、
  shim の内部順序は推定
- **位置の許容の食い違い**（±2 フレーム = 0.0667 と Freeze 保存の 0.05 秒）は K3 の直接の原因ではないが、
  EOS 側の位置のフレームを使う案を出すときに必ず引っかかる。触るなら別項目として起票する

### 6-2. shim の中で何が起きたか（コードに照合した読み）

1. ポンプの出口はコード上 2 つだけ（`pump_preroll_tick`、`tcs_gstreamer.cpp:2537-2613`）:

   arm + 4000ms）で `timed_out`。**期限の行は (ii) のとき必ず出る**（:2587-2605）。今回この行が
   無いので、ログが欠けていなければ **(i) 新しい世代のフレームが shim のキューに publish された**、
   が読み。ポンプは期限 51.05 より前に終わっている（`pump_arm` は 47.05 の直後）
2. `bus EOS` の行が run の最後まで無い（:2659-2664）。seek の準備は `p->eos` を消す
   （:2819-2823）ので、**シークの後に EOS はアプリへ届き得ない**。`tcs_player_acquire` が
   `TCS_ERR_ENDED` を返すのは「フレーム無し + `p->eos`」のときだけ（:3985-3992）なので、

3. D25 の落としの行（:1347-1351）も無い。ただしこの行はプレイヤー通算の初回（または 120 回
   ごと）しか出ない（:1346-1348）。**この run の前に 1 枚でも落ちていれば、このシークの落としは
   無音**なので、「落としが無かった」の証拠にはならない（I-1 で見る）
4. セグメントの畳み込み（:2793-2807）。このシークの期待境界は `seen+1` で、直前に rate.instant が

### 6-3. なぜフレームも Ended もアプリに届かなかったか

- **Ended**: 6-2-2 のとおり。シーク後に EOS が来ないため、Ended は仕様どおり来ない
- **フレーム**: shim はキューに 1 枚 publish した（6-2-1）のに、app は `SourceStatus.Ready` を
  一度も得ていない（絵が変わらない、`OnSourceFrameReady` の再シーク警告も出ない、位置も目標
  19.983 を示さない）。**欠落は shim の配信そのものではなく、キュー → 合成の受け渡しにある
  可能性が高い**。無音で止まり得る箇所:
  - app のリース門: `GStreamerSource.TryAcquire` は `active`（app が持つ 1 本のリース）が旧世代の
    まま残っていると、shim を呼ばずに NotReady を返す（`GStreamerSource.cs:151-157`）。計数は
    出力トレースにしか出ない
  - shim のリース保持: `tcs_player_acquire` は `p->leased` があると無音で 0 を返す
    （:3969-3977。`TCS_LEASE_LOG` が off）
  - publish はされたが使えない: PTS が 20.017（目標 +2 フレームちょうど、`v0.5.4-gate-unification.md`
    §9-8 の (c) 型）、リング外（slot<0。app は run 内で初回だけ警告するが、このログに無い）、
    フェンス未完（D25-b が保持し、3 秒で Fault の行が出るはずだが無い）
- **時間定数の逆転**: app の時間切れ 3.0s（`GapFreezeHandler.cs:54`）は shim のポンプ期限 4.0s
  より先に切れる。今回、シーク 47.048 → 打ち切り 50.132 で、ポンプの期限は 51.05 だった。
  **ポンプが期限直前に配信しても、フリーズは 50.13 に打ち切られ、D32 は 1 枚届かなければ発火しない**
- 18:06:11.647 のもう 1 件は、app ログでは「次のトラックの先頭（target=5.000）のロード」の
  時間切れ（18:06:08.587 進入 → 11.647 打ち切り）で、最終フレームの型とは別。同じ原因として
  一般化しない（その回の shim ログを先に取る）

### 7-3. shim ログに時刻が無いときの突き合わせ（時刻を入れる変更が入るまでの手順）

shim の行は 1 プロセスの間は順序が保たれ、run フォルダの app ログにはミリ秒つきの時刻がある。
時刻を推定するときは、次の**同一性で結合する**（時間の近さより強い）:

1. **リース**: app `source ... infoGenSeqSlotPts=G/S/slot/P` ↔ shim `lease: acquire gen=G seq=S slot=...`
2. **配信**: app `ui.frame ... gen=G seq=S position=P` ↔ shim `frame: ... pts_ms=<P*1000> seq=S`
3. **シーク**: app `SeekTo target=T` ↔ shim `seek: send begin (accurate) ... target_ns=<T*1e9>`。
   その直後の `pump_arm`→`pump_tick` がポンプの範囲。`paused-seek: pump deadline ... elapsed_ms=` の有無で
   6-2-1 の読み（フレームが publish されたか）を確定する
4. **ロード**: app `Gst loadfile path=... start=...` ↔ shim `load.attempt path=... paused=...`
5. **リング**: app `GStreamerSource: 共有リングを開き... epoch=E` ↔ shim `ring: created/recreated ... epoch=E`

2 つの run フォルダ（app ログは `<ReportDir>\app-logs\` にコピーされる）を行き来するときは、
上の 1〜5 のどれかで対応する行を見つけ、その間の shim 行を app の時刻で挟んで読む。
