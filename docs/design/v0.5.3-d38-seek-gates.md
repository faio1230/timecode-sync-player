# v0.5.3 D38: ランスルーで保持後のジャンプの着地が約 2 秒遅れる（シーク経路の時間ベースの門の棚卸し）

作業: w5:p3、2026-09-26。製品コードは変えない（この文書と E2E の記録のみ）。
背景: `docs/release-0.5-plan.md` の D38、`docs/prompts/2026-09-26-v053-d38-investigation.md`、段 3j-0 の `latencyOverBudget`。

## 0. 結論

- **再現**: 開発機の E2E C-1（ランスルー、同一トラック内の往復）で、距離 12 秒の 19 ジャンプすべてが
  着地シークまで **約 1.5〜2.0 秒**（段 3j-0 の `latencyOverBudget` が全回 true）。
- **二分探索**: `947796d`（D37-b「シーク中は位置を信頼せず」2026-09-18）の前後で確定。
  前 = 0.05〜0.21 秒（19 回）、後 = 1.56〜1.91 秒（19 回）。**D37-b が原因**。
- **仮説（TSP-Fable）はほぼそのとおり**。加えて、保持の直後の Jump が 250ms より遅いと
  `ObserveJumpFrame` が復帰に数えず、**`JumpAppliedOnce` が残ったまま Jump がログなしで捨てられる**
  門も効いている（§2-8）。新しい値は後続 Duplicate の「保持値の変化」で適用されるため、遅れがさらに乗る。
- 直す範囲は親が決める（§4 は候補の評価まで）。

## 2. 仮説の確認（コードとログ）

1. **着地シークの発行で位置の信頼を落とす**: `ReportSeekSent` が
   `_positionTrust.InvalidateForPendingSeek()` を呼ぶ（`TimecodeSyncService.cs:265-280`、
   `PlaybackPositionTrust.cs:43-48`）。
2. **信頼が戻るのは Settled を見たときだけ**: `ShouldSuppressSeek` の中の
   `TrackSeekStatusTransition`（`TimecodeSyncService.cs:227-257`、`:503-518`）。Settled は
   `HasReachedSeekTarget`（target−tol〜target+2×tol）を 200ms の cooldown の後
   （`TimecodeSyncSeekState.cs:88-107`、`:154-161`）。時間切れなら `RequireReacquire`（:512-513）。
3. **Settled を判定するのは同期を適用するフレームだけ**: `ShouldSuppressSeek` の呼び出しは
   Continue の `HandleFrame`（`ContinueOnTrackCoordinator.cs:134-154`）と Single の `Apply`
   （`SingleModeSyncCoordinator.cs:73`）だけ。どちらも `ApplySync`（`LtcSyncController.cs:1214`）から。
4. **保持中はその機会が無い**: ランスルーで LTC が保持されている間は Duplicate で、`ApplySync` は走らない。
   着地シークが実際に着地しても Settled を観測できず、pending は未着地のまま残る。
5. **次の Jump では位置が窓の外**: 保持中も再生は進むため、次の Jump の時点で `HasReachedSeekTarget` は
   成立しない。信頼が無いので `EvaluateDecision` は `WhilePositionUntrusted`（`SyncDecisionEngine.cs:78`、
   `TimecodeSyncService.cs:109-115`）を返し、シークを出さない。
6. **置き換えの規則が効かない**: 到達不能な pending を新しい要求で置き換える
   `IsNewRequestFarFromPending`（`TimecodeSyncSeekState.cs:109-118`、`:135-142`）は要求の target を見るが、
   未信頼の決定は Seek ではないため `requestedTarget` は NaN（`ContinueOnTrackCoordinator.cs:136`）で常に false。
7. **時間切れ → 再取得 → ゲート**: 2 秒の pending タイムアウト（`TimecodeSyncSeekState.cs:120-125`、
   既定 `TimeSpan.FromSeconds(2)`）→ `RequireReacquire` → 3 安定サンプル（±20%、
   `PlaybackPositionTrust.cs:59-104`）→ D37-a のゲート（0.25 秒窓・3 サンプル・中央値 > tol、
   `SeekDecisionGate.cs:42-46`、`:77-129`）→ シーク。実ログ（現在のコード、C-1）:
   `07:56:07.763 applying the first Jump frame once ltc=8.000` → `sync.apply Deferred` ×16 →
   `08.795 pending "TimedOut"`（直前 06.762 のシークから 2.0 秒）→ `09.344 seek gated` →
   `09.562 Continue mode: sync seek ... success=true`（**1.799 秒**）。
8. **もう 1 つの門（親の依頼で追加）**: 保持の直後の Jump が timeout（250ms）より遅いと、
   `ObserveJumpFrame` は「保持の直後」と見なさず復帰しない（`LtcSignalLossPolicy.cs:190-201`、`:267`）。
   損失の印は残り、理由は SignalLoss に下がる。このとき `JumpAppliedOnce` が下りていなければ
   （保持中は Normal フレームが来ないので下りない）、Jump は `TryReapplyAfterFileLoadRelease` の
   経路で**ログを出さずに捨てられる**（`LtcSyncController.cs:641-650`）。新しい値は後続の Duplicate の
   「保持値の変化」で適用され、その要求も未信頼とゲートを通るため、遅れがさらに乗る
   （二分探索の 1.56〜1.91 秒はこの込みの値）。

## 4. 統合の案（TSP-Fable の候補の評価）

方針（利用者、2026-09-26）: 門を 1 つ足すのではなく棚卸しして統合する（「守りすぎも欠陥」）。
「着地の判定は 1 つ、ジャンプの雑音の除去は 1 つ、シークしてよいかの門は 1 つ」にまとめる案。

- **(a) 保留の着地判定を毎フレーム（保持の Duplicate でも）行う**
  - 効き方: 3・4 の「Settled を観測する機会が無い」を直接消す。着地シークが実際に着地していれば、
    保持中でも Settled → `MarkLanded` で信頼が戻り、次の Jump は未信頼とタイムアウトを通らない。
  - 実装の形: フレーム処理の先頭で、pending があれば `ShouldSuppressSeek(playback, tol)` を呼ぶ
    （Sync を適用しないフレームでも）。判定は `HasReachedSeekTarget` の既存窓のまま。
  - 危険: 保持中は再生が進むため、窓を「通過」した後は成立しない。着地の瞬間に窓へ入ったことを
    見るには、保持中の位置サンプルを毎回見る必要がある（D37-b が避けた「飛んだ位置での判定」では
    ない。判定は着地の確認だけに使う）。
  - ほかのシナリオ: **S-2（停止）** は位置が動かないので、目標付近なら現状どおり Settled（変化小）。
    **C-2（別トラック）** はロード中の抑止（17・18）が先に効く。**D37 の着地窓** は速度補正優先の
    判定に使う信頼が早く戻るだけで、窓の開閉条件は変えない。**D30 の確認** は無関係。
- **(b) 距離が 4×tol を超える新しい要求は、位置が未信頼でも置き換える**
  - 効き方: 8 が NaN で効かない問題を消し、2 秒のタイムアウトを待たずに pending を捨てる。
    ただし置き換えは「シークを出す」ではなく「pending を外す」なので、その後の信頼回復（11）と
    ゲート（13）は残る。短縮は約 1〜1.5 秒（タイムアウトぶん）。
  - 実装の形: `WhilePositionUntrusted` の決定でも要求 target（クランプ済み）を返す、または
    `ShouldSuppressSeek` へ渡す `requestedTarget` を未信頼でも作る。
  - 危険: 未信頼中の要求で pending を捨てると、直前のシークの着地を確認しないまま次の要求へ移る。
    置き換えの距離条件（4×tol）を満たす大きな移動だけなので、D20-b(ii) の意図（到達不能 pending の
    解消）と同じ。S-2 は停止中に新しい要求が来ないため不変。C-2 は別トラックへの Jump が確認窓（4）
    を通った後に効く。D37 は着地窓中のシーク優先（16）と両立する。
- **(c) ランスルー保持中は動く窓で判定する**
  - 効き方: 6 の窓の上限を「目標 + 保持開始からの経過」で動かし、通過後の位置でも着地と見なす。
  - 危険: 「着地した」と「通過した」の区別が消え、D7-a が抑止した通過後の再シークを呼び戻す。
    保持中は目標が固定なので、窓を動かすより「一度入ったらラッチ」の方が安全。
  - ほかのシナリオ: S-2（停止）は不変。C-2 は目標が変わるので動く窓の基準が曖昧。D37 の着地窓の
    前進ガードと役割が重なる。
- **案**: (a) + (b) が筋（着地の観測機会を戻し、タイムアウト依存を外す）。(c) は単独では使わない。
  ただし 2・3・4 の「Jump の雑音の除去」と 5〜14 の「シークしてよいかの門」をどう 1 つにまとめるかは、
  表を見て親が決める。直す範囲はこの文書では決めない。

## 6. 直す範囲（親の判断、2026-09-26）

- **(a) と (b) を入れる。(c) は入れない。** 二分探索の前（`947796d^`）は 0.05〜0.21 秒で、D37-b が足した
  「未信頼の間は Settled を見る機会が無い」と「未信頼の要求は置き換えに使えない」の 2 点だけが差。
  どちらも新しい門ではなく、既存の門（6 と 8）が本来の質問に答えられるようにする直し方なので、門の数は増えない。
  - (a) 着地の判定（門 6）は、同期を適用しないフレーム（保持の Duplicate）でも pending があれば行う。
    窓は既存の `HasReachedSeekTarget` のまま。判定は信頼の回復（門 10）にだけ効き、シークは出さない
  - (b) 置き換え（門 8）は、未信頼の決定でも要求の目標（クランプ済み）を渡して判定する。
    置き換えた後の再確認（11）とゲート（13）は残す
- **門 3（`JumpAppliedOnce` でログなしに捨てる）は、この修正では振る舞いを変えず、捨てたときにログを 1 行出す。**
  C-1 と重い素材の周回で回数を数え、(a)(b) の後も遅れの原因に残るなら次の手で扱う。
- 「守りすぎも欠陥」の確認: (a)(b) で平常時（S-1〜S-4、C-2）のシークの回数と `pending "TimedOut"` の回数が
  増えないこと、D7-a が抑止した通過後の再シーク（着地から 500ms 以内の同じ目標への再シーク）が増えないことを数える。

## 7. 修正の結果（2026-09-26、w5:p3）

直した範囲は §6 のとおり（(a) と (b)、(c) は入れない。門 3 はログのみ）。

- (a) `LtcSyncController` の保持の Duplicate の分岐で `TimecodeSyncService.ObservePendingSeekLanding` を
  呼び、pending があれば既存の着地判定（`ShouldSuppressSeek`）を行って信頼を戻す（シークは出さない）。
- (b) 未信頼の決定でも、要求の目標（クランプ済み、`SyncDecision.RequestedTargetSeconds`）で
  `TimecodeSyncSeekState.DiscardIfUnreachable` を判定し、到達不能な pending を**捨てる**（re-pend しない。
  re-pend は自分の要求を 2 秒抑止するため）。捨てた後は再確認（11）とゲート（13）を通る。
  2 つの条件を足した: いま着地の窓に入っている pending は捨てない（着地判定を優先）、
  現在位置の近くの要求では捨てない（既存の「pending の着地を待つ」テストを壊さない）。
- 門 3: 捨てた箇所に `sync: Jump dropped (JumpAppliedOnce) ltc=… reason=…` を 1 行（振る舞いは変えない）。
- E2E: `hold-landing` の `latencyOverBudget` を失敗の条件に切り替え。
