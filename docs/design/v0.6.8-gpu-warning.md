下書き（2026-11-16）。基点は main b1e64a7。製品のコードはまだ書かない。

TSP-Fable のレビュー（2026-11-16）で方向は通った。指摘された点（判定の時点、判定の失敗の扱い、再生が無効の起動のログ、3.4 の書き方、文面、ログの行の頭、用語）を直し、TSP-Fable の判定で決めた項目と合わせてこの版に入れた。利用者に聞くのはインストーラーの 1 点だけ（9 節）。

## 1. 出所と依頼

### 1.1 依頼の出所

- 利用者の言葉（趣旨）: 「GPU の設定が適切でない場合は警告が画面に出るように修正してほしい」。検証機の担当の中継で、親と TSP-Fable は利用者から直接は聞いていない。
- 次の 6 項目は検証機の担当の案で、利用者が 6 項目を求めたのではない。
  1. GPU のベンダーと名前をログに 1 行
  2. GPU の名前を画面に常時表示
  3. 独立の GPU があるのに内蔵で動いているとき、起動時に操作を止めない警告で指定の方法を示す
  4. 「Decode behind」などが続くときの常駐の警告に、内蔵かどうかを併記
  5. インストーラーが GpuPreference=2 を登録するか、旧の指定を引き継ぎ、アンインストールで外す
  6. 内蔵 GPU で起動したときに警告が出る試験

### 1.2 背景（事実）

出所は検証機の担当の報告で、親と TSP-Fable は確かめていない（v0.6.7 の設計書 7.11 と同じ出所）。

- v0.6.7 で exe の名前が TimecodeSyncPlayer.exe から ERYTHEIA.exe に変わった。Windows のアプリごとの GPU の指定（HKCU の `Software\Microsoft\DirectX\UserGpuPreferences`。exe のパスを値の名前にして覚える。`GpuPreference=2` が高パフォーマンス）は、旧の exe のパスにしか無かった。
- 11-14 の本番では、外付けの RTX と AMD の内蔵 GPU を積んだノート PC で、インストール版 v0.6.7 が 5 回の起動すべてで AMD の内蔵 GPU（shim の `device adapter vendor=0x1002`）で動いた。
- 素材は 4K60 の h264 で、「Decode behind」が 2423 行、「playback clock is slower than realtime」が 23 行出て、カクつきがあった。
  - RTX で動かした 11-16 の回でも、Decode behind は同じ桁で出た（10.1）。「内蔵だったから Decode behind が出た」とは読まない。
- 画面にもログにも「内蔵 GPU で動いている」という警告は無かった。ログにあるのは、OutputEngine の `adapterLuid=` の数値と shim の vendor だけ。
- その後、利用者の依頼で、検証機の担当が検証機のインストール版の ERYTHEIA.exe に `GpuPreference=2` を登録した（ほかは変えていない）。以後のその機体のログは RTX で動く前提で読む。ただし、全画面の出力先が保存されていると指定より出力先が優先される（3.1）ので、前提は新しいログの行（6 節）で確かめる。
- 本番の機体では、v0.6.7 が設定を旧の場所から引き継ぐので、全画面の出力先は v0.6.6 のときの名前が残っていたはず（TSP-Fable の読み）。当日、その出力先がどのアダプターの下で見つかったか（見つからなかったか）は分かっていない（10 節）。
- 11-14 の本番の 5 回の起動のログ（検証機の担当の報告。ログを読むだけ。親と TSP-Fable は未確認）:
  - 5 回とも shim は vendor=0x1002。adapterLuid は 70793、70827、71760、71164、71164。
  - 全画面を開いたのは 3 回目・4 回目・5 回目で、5 回目は 2 度開いた。開いた 4 つは、全部 `\\.\DISPLAY2`。
  - 「出力先が見つからなかった」の行は無い。
  - 4 回目は、全画面の大きさが 3840x2160 → 6420x2180 → 1280x720 と変わった。
- Windows の起動と停止の記録（検証機の担当の報告。親と TSP-Fable は未確認）:
  - 1 回目と 2 回目の間に再起動（08:30、利用者の操作）。2 回目と 3 回目の間に再起動（08:52、利用者の操作）。
  - 3 回目と 4 回目の間に、Windows の予期しない停止が 2 回（イベント 6008、Kernel-Power 41）。起動は 10:14:17 と 10:20:31。原因の記録なし（束の外）。アプリが動いていない間か 4 回目の前なので、v0.6.7 の良し悪しの判断には使わない。
  - 4 回目と 5 回目の間には再起動なし（adapterLuid は同じ値）。11:07 にスリープと復帰、11:09 にモダン スタンバイ。
  - adapterLuid の値が変わった 3 つの間は、どれも再起動か予期しない停止をまたいでいた。4 回目 → 5 回目は同じ値で、間に再起動なし。
  - 終了の行が無い起動が 2 回: 2 回目は利用者の操作の再起動で終わった。4 回目は、間に再起動が無いのに終了の行が無い（原因の記録なし。束の外）。
  - 保存された出力先から LUID を解決したことを示す行は、ログに 0 行（v0.6.7 には、その行が無い）。
- 読み（未確定）:
  - 1・2 回目は全画面を開いていないのに AMD。「保存された出力先が AMD の下で見つかった」か「出力先が無く、既定が AMD」かは、解決の行が v0.6.7 に無いので分からない。v0.6.8 の 6 節の行（`origin=`）が入れば、次からは分かる。
  - 警告の側から見ると、本番の日の状態（使われたのが AMD、独立の GPU がある）は規則 6 が狙う場合そのもの。ただし、検証機で 2 つの並びの先頭が実際に分かれるかは未確認（7.3 の検証機の回で確かめる）。

## 2. 範囲

範囲は先に固定する（TSP-Fable の判定）。後で広げない。

| 項目 | 扱い | 理由 |
|---|---|---|
| 中心 | GPU の設定が適切でないときに、画面に警告を出す | 利用者の言葉 |
| 3 起動時の警告 | **入れる** | 中心そのもの |
| 1 ログの 1 行 | **入れる**（Information の段） | 警告の判断の材料を後から読めるように。E2E とランナーは Information 以上の行だけで確かめる決まり |
| 6 試験 | **入れる** | 判定は純粋な関数にして単体で試す（7 節） |
| 2 GPU の名前の常時表示 | **入れる**（判定は 5.4） | 小さい。警告が出ない平常の機体でも、どの GPU で動いているかを画面で確かめられる |
| 4 遅れの警告に内蔵かを併記 | **入れない** | 下に理由 |
| 5 インストーラー | **既定はア（何もしない）で進める**。イ（旧の指定を写す）を望むかだけを利用者に聞く | 事実は 8 節。答えを待たずに進める |

4 を入れない理由:

- 「Decode behind」と画面の「デコードが追いついていません」は、UI へ渡した回数を数えたもので、デコードの指標ではない（v0.6.7 の設計書 3 節の棚卸しの「デコードの遅れの警告の数え方」の行。`DecodeHealthMonitor.Evaluate` の入力は UI の処理回数）。数え方を直す件は、別の候補として残っている。
- 別の警告に条件を足すと、同期や表示の判断の近くを触る。v0.6.8 の束は起動時の判定と表示だけに留める。
- 内蔵で動いていることは 3 の警告が起動時から出し続けるので、遅れの警告に重ねて書かなくても操作者には見える。
- 入れるなら、遅れの警告と内蔵の組が現場で何回出たかの数を先に出してからにする。

v0.6.7 の設計書 7.10 に並べたほかの候補（LTC の乱れの後の速度の揺れ、切替の合否の数え方）は入れない。7.10 の「アプリが、出力先の無いときに高性能の GPU を選ぶ」も入れない。使う GPU の選び方は変えず、知らせるだけにする。

## 3. 今の作り（コードの事実）

この節の事実は TSP-Fable も確かめた（`MainWindow.xaml.cs` の `FindAdapterLuid` の呼び出し、`DisplayCombo_SelectionChanged` で出力先の名前が保存されること、shim が合成の LUID でアダプターを探して vendor を出すこと、プローブが既定のアダプターを使うこと、復旧の逃げ先が既定のアダプターであること）。

### 3.1 合成のデバイス（OutputEngine）

- `MainWindow`（起動の部品の組み立て）が `OutputEngineSettings.AdapterLuid` に `OutputDisplays.FindAdapterLuid(設定の FullscreenDisplayDeviceName)` を渡す。
- 設定の `FullscreenDisplayDeviceName` は出力先の選択（`MainWindow.DisplayCombo_SelectionChanged`）で保存される。
- `OutputDisplays.FindAdapterLuid`（`Output/OutputEngine.cs`）: `IDXGIFactory1.EnumAdapters1` で全アダプターを回り、各アダプターの `EnumOutputs` の `DeviceName` が保存された全画面の出力先の名前と一致したアダプターの LUID を返す。名前が空、見つからない、例外のときは null。
- `GpuDevice` のコンストラクター（`Output/GpuDevice.cs`）:
  - LUID が有れば `Displays.FindAdapter` でそのアダプターを取り、`D3D11CreateDevice(アダプター, DriverType.Unknown)` で作る。作ったデバイスの LUID が違えば例外。
  - LUID が null なら `D3D11CreateDevice(null, DriverType.Hardware)`。アダプターは DXGI の既定（`EnumAdapters1` の 0 番）になる。
  - どちらでも、実際の LUID を `IDXGIDevice.GetAdapter` で読んで `GpuDevice.Luid` に持つ。
- `OutputEngine.InitializeGpuResources` が `OutputEngine: 初期化完了 canvas=… adapterLuid=…` を Information で出す。名前とベンダーは出していない。
- デバイスの消失からの復旧（`OutputEngine.CreateGpuDeviceForRecovery`）: 同じ LUID で作れないときは Warning を出して既定のアダプター（null）で作り直す。復旧の後に GPU が変わることがある。
- 復旧の順は `GpuRecoveryPlan`。全部の手順が通ると、`OutputEngine.AttemptRecovery` が `GpuStatusChanged(Recovered)` を通知する。`MainWindow.OnGpuStatusChanged` は、これを Dispatcher で UI のスレッドへ渡す。共有リングを開き直せないときは `GStreamerRebindRequested` で shim の player を作り直し、shim は新しい合成のデバイスの LUID で自分のデバイスを作る。
- 起動の前の `D3D11CapabilityProbe.Detect`（D3D11.4 の有無）は、いつも既定のアダプター（null、Hardware）で調べる。出力先の設定は見ない。

つまり、使う GPU は次のとおり。マニュアル（USER-MANUAL.md の 6 節「既知の制限」）の記述とも合う。

| 全画面の出力先 | 使う GPU |
|---|---|
| 保存されていて、見つかった | その出力先を列挙したアダプター。指定はアダプターの選び方には直接効かない。ただし、指定で出力を並べるアダプターが変わると、使う GPU も変わる（3.4 の 1 回の観測） |
| 保存されていない（Spout だけで使う）、または見つからない | DXGI の既定のアダプター。アプリごとの指定はここに効く（3.4 の未確定を参照） |

### 3.2 shim のデバイス

- `create_or_adopt_device`（`native/gst-shim/src/tcs_gstreamer.cpp`）: アプリから渡された合成のデバイスの LUID を読み、`find_adapter_by_luid` で同じアダプターを探して、その上に自分のデバイスを作る。見つからなければロードを失敗にする（合成のデバイスは使わない。ステージ 6b）。
- 作った直後に `device adapter vendor=0x%04x` を shim のログ（`erytheia-gst-*.log`）に出す。値は `DXGI_ADAPTER_DESC.VendorId`。名前は出していない。
- したがって、合成と shim のデバイスは作りの上で同じアダプターに乗る。11-14 の本番で shim が AMD だったのは、合成のデバイスが AMD だったため。
- 「adapterMismatch」と呼んでいる数は、デコーダの要素のアダプター（`adapter-luid`）が shim のデバイスと違う件の数（D16-b の `decoder_matches_shim_adapter` と ProRes の `tcs_prores_gpu_adapter_mismatch`）。違うときは、その GPU のプロファイルを飛ばして CPU のデコードへ移る。合成と shim が違うアダプターになる件ではない。
- shim の LUID と vendor は、アプリ（C#）へは渡っていない（`IGstNativeApi` に該当する関数は無い）。

### 3.3 名前とベンダーの取り方

- `DXGI_ADAPTER_DESC1`（Vortice の `IDXGIAdapter1.Description1`）に `Description`（名前の文字列）、`VendorId`、`DeviceId`、`Luid`、`DedicatedVideoMemory`、`Flags`（`DXGI_ADAPTER_FLAG_SOFTWARE` を含む）がある。アプリの側で、合成のデバイスの LUID から名前とベンダーを取れる。新しい shim の関数は要らない。
- `IDXGIFactory6.EnumAdapterByGpuPreference` で、Windows の分類による順を取れる。Microsoft のリファレンスの記述:
  - `DXGI_GPU_PREFERENCE_HIGH_PERFORMANCE`: 外付けの箱の GPU（xGPU）→ 独立の GPU（dGPU）→ 内蔵の GPU（iGPU）の順
  - `DXGI_GPU_PREFERENCE_MINIMUM_POWER`: iGPU → dGPU → xGPU の順
  - `DXGI_GPU_PREFERENCE_UNSPECIFIED`: `EnumAdapters1` と同じ
  - 対応は Windows 10 1803 から
- D3D11 の `D3D11_FEATURE_DATA_D3D11_OPTIONS2.UnifiedMemoryArchitecture`（`CheckFeatureSupport`）で、デバイスが主メモリを共有する作り（内蔵の GPU に多い）かを取れる。

### 3.4 Windows の指定と DXGI の関係（未確定を含む）

- アプリごとの指定（高パフォーマンス・省電力）は、`EnumAdapters1` の並び（0 番）を変え、既定のアダプターで作るデバイスの行き先を変える。と見ているが、Microsoft の文書で確かめたのではない。検証機の過去の回（旧の exe に指定があった v0.6.6 で NVIDIA）と、11-14 の本番（新しい exe に指定が無く AMD）は、この見方と矛盾しない。
- 指定が `EnumAdapterByGpuPreference` の高性能の並びと省電力の並びまで変えるかは、リファレンスに書いてない。判定（4 節）への響きは次のとおり。
  - 並びが指定で変わらない作りなら、判定は Windows の分類どおりに働く。
  - 指定が省電力で、並びまで変わる作りだった場合は、両方の並びの先頭が同じ（内蔵）になり、規則 5 で `Ok` になる。この場合は見落とす。
  - つまり、どちらの作りでも誤って出す側には倒れないが、見落としはありうる。
  - 検証機の回（7.3）で、指定を変えたときの両方の並びを記録して確かめる。→ 高性能・省電力の並びの先頭は、指定で変わった（検証機 1 台、各 1 回。12.15）。`EnumAdapters1` の 0 番は、今日の行には出ていない。使われた GPU が指定に従った、までが事実。
- 内蔵と独立の GPU を積むノート PC で、DXGI が各ディスプレイの出力（`EnumOutputs`）をどのアダプターの下に並べるかは、機体と指定で変わりうる（10 節）。保存された出力先を AMD の側で見つけると、指定を高パフォーマンスにしても AMD で動く。
- **1 回の観測がある**（検証機の担当の報告。親と TSP-Fable は未確認）:
  - 事実: 利用者の起動 1 回（11-16 12:43:07）。shim は vendor=0x10de、adapterLuid=73851。全画面の出力先の名前（`\\.\DISPLAY2`）が保存されていて、全画面がそこで開いた。指定（GpuPreference=2）は、その前に利用者の依頼で登録したもの。
  - 読み: 指定で、`\\.\DISPLAY2` を並べるアダプターが変わった。ただし、指定の前の同じつなぎ方での並びの記録が無いので、前後の比べは成立していない。本番の日（1.2）は DISPLAY2 が AMD の下で、指定の後（11-16）は同じ名前が NVIDIA の下で見つかった。この読みと合うが、つなぎ方が同じだった記録は無い（4 回目の 6420x2180 は表示の構成が違った印）。
  - 内蔵と独立の両方に端子があるデスクトップでは、指定で出力の並びは動かないはず、というのは未確認の読み。このためツールチップの端子の案内（12.7）は残す。
  - 検証機の回（7.3）で、指定を無し・省電力・高パフォーマンスにして並びを記録して確かめる、は残す。→ 高性能・省電力の並びの先頭は、指定で変わった（検証機 1 台、各 1 回。12.15）。`EnumAdapters1` の 0 番は、今日の行には出ていない。使われた GPU が指定に従った、までが事実。 → 出力をどのアダプターの下に並べるかの確かめは、未実施で閉じた（12.15）。未確定のまま。

## 4. 「適切でない」の定義と場合の表

### 4.1 軸の案

| 案 | 中身 | 評価 |
|---|---|---|
| A | いま使っているアダプター（合成のデバイスの LUID）が、高性能の並びの先頭と違えば警告 | 単純。ただし独立の GPU が 2 つの機体で、出力先のある 2 つ目を使うと警告になる。高性能の並びで同じ種類の GPU の中の順は文書に無い |
| **B（採る）** | A に加えて、いま使っているアダプターが省電力の並びの先頭（Windows が iGPU と分類したもの）で、かつ高性能の先頭と省電力の先頭が違うときだけ警告 | 「独立の GPU があるのに内蔵で動いている」を、Windows の分類だけで言える。ベンダーの名前を使わない。独立の GPU が 2 つで内蔵が無い機体では、同じ種類の中の順が 2 つの並びで同じなら発火しない。順が違うと発火しうる（文書に無い） |
| C | D3D11 の UnifiedMemoryArchitecture が真なら内蔵とみなす | ドライバーの申告しだい。単独の軸にはしない。B の補強（両方が真のときだけ警告）にするかは、検証機の値を見てから決める（10 節） |
| D | ベンダー ID（0x1002・0x8086 を内蔵とみなす） | **使わない**。AMD・Intel の独立の GPU を内蔵と取り違える |
| E | 専用のビデオメモリの量のしきい値 | **使わない**。しきい値の根拠が無い |

**判定は B（TSP-Fable の判定）**。C（UnifiedMemoryArchitecture）は記録だけで始め、判定の入力に載せてログに出す。必須の条件に足すか（B かつ C）は、検証機の値を見てから決める。内蔵 AMD が真・RTX が偽と分かれば足す。こうすると、独立の GPU が 2 つの機体での誤発火の恐れ（同じ種類の中の順が並びで違う場合）も消える。分かれなければ B だけにして、その恐れを既知の制限として残す。

開発機は RTX 3070 が 1 つだけ（TSP-Fable が確かめた）なので、開発機では規則 4 しか通らない。規則 5〜7 は単体の試験と検証機で確かめる。

### 4.2 判定の入力と出力

判定は純粋な関数にする（名前は仮に `GpuPlacementPolicy.Evaluate`）。

入力:

- アダプターの一覧: LUID、名前、VendorId、ソフトウェアのアダプターか（`DXGI_ADAPTER_FLAG_SOFTWARE`）
- 高性能の並びの先頭の LUID、省電力の並びの先頭の LUID（`IDXGIFactory6` が無ければ null）
- いま使っている LUID（`GpuDevice.Luid`）
- 選ばれ方: 保存された出力先から、または既定のアダプター
- リモートのセッションか（`GetSystemMetrics(SM_REMOTESESSION)`）
- （記録だけ）UnifiedMemoryArchitecture
- 判定の時点（`startup` か `recovery`）
- 再生が有効か（`OutputBackendState.PlaybackAvailable`）

出力（判定の結果）:

| 結果 | 意味 | 画面 |
|---|---|---|
| `Ok` | 適切 | 出さない |
| `IntegratedInUse` | 独立の GPU があるのに、Windows が iGPU と分類した GPU で動いている | 警告を出す |
| `NotJudged` | 判定しない（理由を持つ: 再生が無効、材料の取得の失敗、リモート、ソフトウェア、一覧が取れない、など） | 出さない（ログだけ） |

判定の規則（B 案）:

0. 再生が無効（D3D11.4 なし、`ERYTHEIA_FORCE_GPU_UNAVAILABLE`）→ `NotJudged`（理由 `playback-unavailable`）。デバイスの準備が時間切れのときも同じ扱いで、理由は `device-timeout`
1. 一覧が取れない、または `IDXGIFactory6` が無い → `NotJudged`（理由 `no-preference-order`）
2. リモートのセッション → `NotJudged`（理由 `remote-session`）
3. いま使っているアダプターがソフトウェアのアダプター → `NotJudged`（理由 `software-adapter`）
4. ソフトウェアのアダプターを除いたハードウェアのアダプターが 1 つ以下 → `Ok`
5. 高性能の先頭と省電力の先頭が同じ → `Ok`（Windows の分類で差が無い）
6. いま使っているアダプターが省電力の先頭で、高性能の先頭と違う → `IntegratedInUse`
7. それ以外 → `Ok`

材料の取得（アダプターの一覧、`IDXGIFactory6` の並び、`CheckFeatureSupport`）で例外が出たときは、`NotJudged`（理由 `error`）にする（4.4）。

### 4.4 判定の時点と、失敗の扱い

判定の時点:

- OutputEngine のデバイスができるたびに、同じ純粋な関数で判定し直し、名前の表示と警告を更新する。時点は 2 つある。
  - 起動: `MainWindow` が `OutputEngine.WaitForDevice` を待った後（UI のスレッド）
  - 復旧の完了の後: `MainWindow.OnGpuStatusChanged` が `Recovered` を受けた後（UI のスレッド）
- 復旧で別のアダプターへ移ると、判定し直さなければ常時表示の名前が古いまま残り、嘘になる。このため、レビューの前の「判定は起動で 1 回」は取り下げた。
- 復旧そのものの動きは変えない。OutputEngine に足すのは、今のデバイスの LUID と選ばれ方（保存された出力先、既定、復旧の逃げ先の既定）を読むための読み取りだけ。`CreateGpuDeviceForRecovery` の分岐と `GpuRecoveryPlan` の順は触らない。
- 復旧が失敗した（`Failed`）ときは判定し直さない。名前の表示と警告は最後の判定のまま残す。GPU の状態の行（`GpuStatusText`）に「GPU 出力停止」が出る。

失敗の扱い（判定は起動を壊さない）:

- 材料の取得と判定のどこで例外が出ても、`NotJudged`（理由 `error`）にして、Warning の 1 行を出す。起動と再生は続ける。画面の警告は出さず、名前の行は取れた範囲で出す（名前も取れなければ隠す）。
- 判定は GPU worker の合成の周期の中では呼ばない。呼ぶのは上の 2 つの時点の、UI のスレッドの 1 回だけ。DXGI の Factory を毎回作る費用が合成の周期に入らない。

再生が無効の起動:

- D3D11.4 が無い起動と `ERYTHEIA_FORCE_GPU_UNAVAILABLE` の起動でも、6 節の Information の行を 1 行出す（`verdict=NotJudged reason=playback-unavailable`）。「`at=startup` の行の数 ＝ 起動の数」という数え方（7.2）を崩さないため。

## 5. 出し方と文面の案

### 5.1 出し方

- 操作を止めない。モーダルの画面を出さない。フォーカスを奪わない。
- 全画面の出力と Spout の絵には載せない（主窓の操作の領域にだけ出す）。
- 置き場: 主窓の右の欄の「出力」の欄（`CanvasGroup`）。いまの `GpuStatusText`（GPU の消失と復旧の状態）のすぐ上に、新しい TextBlock を 1 つ置く（仮の AutomationId は `GpuPlacementWarningText`）。
- 見た目はいまの警告の行（`LongGopWarningText`・`CodecWarningText`・`DecodeHealthWarningText`・`GpuStatusText`）に揃える。`StatusNote` の型、文字 11、折り返し、色は橙（`#D7A24B`。`GpuStatusText` と同じ）。先頭に「⚠」（`DecodeHealthMonitor.StatusText` と同じ）。
- 出すとき、Warning の段で 1 行をログに出す（6 節の行とは別。E2E はこれを数える）。
- 警告が見えている間は、常時表示の名前の行（5.4）を隠す。警告の 1 文目に同じ名前が入っているので、名前が 2 回並ばない。「×」で警告を消したら、名前の行を出す。

### 5.2 文面の案

**実装では、関数は選ばれ方（origin）を受け取り、`default` と `saved-display` は同じ文（Windows の「高パフォーマンス」）、`recovery-default` は別の文にした（12.7。TSP-Fable の判定 2026-11-16）。一度出した「saved-display なら指定は効かない」という理由は、検証機の 1 回の観測（3.4）で取り下げた。下の 2 文の案は経緯として残す。**

本番の 5 回がどの場合だったかは分かっていない（出力先が保存されていたか、どのアダプターで見つかったか）。仮の文面は、どちらの場合でも嘘にならない次の 2 文にする（TSP-Fable の判定）。最終の文面は、検証機で出力先を入れ替える回（7.3）の結果で決める。

> ⚠ 内蔵 GPU（{いま使っている GPU の名前}）で動いています。高性能の GPU（{高性能の先頭の名前}）があります。4K60 の素材はカクつくことがあります。
> Windows の「設定 → システム → ディスプレイ → グラフィック」で ERYTHEIA.exe を「高パフォーマンス」にして、アプリを再起動してください。全画面の出力先が内蔵 GPU の側のディスプレイのときは、出力先も見直してください。

- 1 文目は判定の材料（Windows の分類と、いま使っている LUID）だけで言える事実。
- 「出力先も見直して」は、保存された出力先が内蔵の側で見つかった場合に、指定だけでは直らないため。出力先が保存されていない場合にも嘘にはならない。
- 選ばれ方が `saved-display` のときは、「高パフォーマンスにして再起動」は効かない案内になりうる（3.1）。今は分けられない。ノート PC で DXGI が出力をどのアダプターの下に並べるかが確かめられていない（3.4）ため。
- このため、文面は 1 か所の文字列（選ばれ方を引数に取る 1 つの関数）にまとめ、検証機の回の後に差し替えやすくする。差し替えは文字列と、その単体の試験の期待だけで済むようにする。
- 名前は `DXGI_ADAPTER_DESC1.Description` をそのまま出す。空なら「名前不明」と VendorId の 16 進。

### 5.3 消し方と、次の起動

**案 a に決めた（TSP-Fable の判定）**。v0.6.6 の全画面の警告の利用者の決定（毎回出す）に揃うので、方針の中と見た。

| 案 | 中身 |
|---|---|
| **a（採る）** | 起動の間ずっと出す。行の右の小さな「×」で、その起動の間だけ消せる。次の起動でまた判定し、当たればまた出す。「今後表示しない」は付けない |
| b | 消す手段は無い。起動の間ずっと出す |
| c | 一定の時間（例 30 秒）で消える |

- a は v0.6.6 の全画面の警告の「毎回出す、『今後表示しない』は付けない」（利用者の決定）に揃えた。v0.6.6 の全画面の警告は確認の画面（`FullscreenConfirmDialog`）で操作を止めるが、今回は操作を止めないので、揃えるのは「毎回出す」の扱いだけ。
- 本番中に出っぱなしで邪魔かどうか: 置き場は出力の欄の 2 行で、全画面と Spout には出ない。b でも絵には響かない。それでも、操作者が分かったうえで内蔵 GPU で続けるときに消せるよう、a の「×」を付ける。
- c は採らない。気づかないまま消えると、11-14 と同じになる。
- 復旧の後の判定し直し（4.4）で `IntegratedInUse` になったときは、その起動で「×」を押していても、また出す。GPU が変わったことを知らせるため。

### 5.4 GPU の名前の常時表示（項目 2）の判定

**実装で、置き場を「出力」の見出しの行の右に変えた（12.8）。下の「GpuStatusText の上の 1 行」は経緯として残す。**

- **入れる**。「出力」の欄の `GpuStatusText` の上に、灰色（`#888888`、文字 11）の 1 行「GPU: {いま使っている GPU の名前}」を出す（仮の AutomationId は `GpuAdapterNameText`）。
- 理由: 警告が出ない平常の機体でも、操作者と試験がどの GPU で動いているかを画面で確かめられる。E2E は Information の行で確かめるので、画面の文字は E2E の判定には使わない（PNG で確かめるときにだけ使う）。
- 警告が見えている間は隠す（5.1）。復旧の後の判定し直しで名前を更新する（4.4）。
- 大きさ: 部品は TextBlock 1 つと、判定の結果を表示へ渡す 1 か所。
- 見せ方に触れるので、入れた後に、それより前に入れた項目の UI の E2E と、v0.6.7 の UI の受け入れの E2E を回し直す（CLAUDE.md の「1 版に複数の項目を入れるときの E2E」）。行が 1〜2 行増えるので、右の欄のプレイリストの見える行数（v0.6.7 の #45）を PNG で前後比べる。

## 6. ログの 1 行

- 段は Information。アプリのログ（`erytheia-*.log`）に、判定のたびに 1 行出す（4.4 の 2 つの時点）。再生が無効の起動でも、起動で 1 行出す。
- 行の頭はほかの行と紛れない `GPU placement:` にする。実装の前に、開発機と検証機の既存のログで `GPU placement` が 0 件なのを数える。リポジトリのコードとスクリプトでは 0 件（2026-11-16、`git grep`）。
- 形（案）:

```
GPU placement: at={startup|recovery} used="{名前}" vendor=0x{VendorId} luid={LUID} origin={saved-display|default|recovery-default} highPerformance="{名前}" minimumPower="{名前}" hardwareAdapters={数} uma={0|1|?} remote={0|1} verdict={Ok|IntegratedInUse|NotJudged} reason={…}
```

- `origin` は選ばれ方。`saved-display` は保存された出力先のアダプターを使ったとき、`default` は既定のアダプター、`recovery-default` は復旧で同じアダプターに作れず既定へ移ったとき。
- 取れなかった値は `?` にする（再生が無効の起動では `used` 以下の多くが `?`）。
- 警告を出すときは、別に Warning の段で `GPU placement warning shown: …` の 1 行を出す（5.1）。E2E はこの Warning の行の数を数える。
- 材料の取得で例外が出たときは、Warning の段で `GPU placement failed: …`（例外の型と文）を出す。Information の行も `verdict=NotJudged reason=error` で出す。
- ソフトウェアのアダプターで動いているときは、Warning で 1 行足す（4.3）。
- 既存の `OutputEngine: 初期化完了 … adapterLuid=` と shim の `device adapter vendor=` は変えない（ランナーと過去のログの読みが使っている）。

## 7. 試験

### 7.1 単体

- `GpuPlacementPolicy.Evaluate` の試験は 4.3 の場合の表を 1 行ずつそのまま試験の表にする（xUnit の `Theory`）。アダプターの一覧と並びは注入する。
- 足す行:
  - 独立の GPU が 2 つで、高性能の並びと省電力の並びの中の順が違う場合（両方の順）
  - Basic Render Driver が一覧にある GPU 1 つの機体（`Ok`）
  - 名前が空のアダプター（文面に VendorId が出る）
  - 材料の取得のどこか（一覧、`IDXGIFactory6`、`CheckFeatureSupport`）が例外を投げる場合（`NotJudged`・`error`、警告なし、例外が外へ出ない）。取得は注入できる口にして、試験で例外を投げる
  - 再生が無効の場合（`NotJudged`・`playback-unavailable`、ログの行は出る）
  - 復旧で別のアダプターへ移った場合（`at=recovery`・`origin=recovery-default`。名前が新しいアダプターの名前に変わり、警告の有無が新しい判定に従う。消していた警告も、`IntegratedInUse` ならまた出る）
- 文面の組み立て（名前の差し込み、空の名前）と、ログの行の組み立ても単体で試す。
- 判定を呼ぶ口が 2 つの時点（起動の待ちの後と `Recovered` の後）だけであることを、状態の通知の並び（`Recovering`→`Recovered`、`Recovering`→`Failed`）を流す試験で確かめる。`Failed` では判定し直さない。

### 7.2 発火 0 を数える

- 開発機（GPU は実質 1 つ）の E2E 一式（Release の exe、フィルターは `Category=E2E&FullyQualifiedName!~LtcScenarioE2ETests`）で、`GPU placement warning shown` の Warning の行が 0 回、`GPU placement: at=startup` の Information の行が起動の回数と同じであること。`GPU placement failed` も 0 回。
- 検証機の固定の一式（RTX）でも同じく数える。0 でなければ候補にしない。

### 7.3 警告が出ることを確かめる試験

- 開発機では内蔵 GPU で動く条件を作れない。警告の表示の E2E は試験のためだけの切り替えで判定の結果を `IntegratedInUse` に固定して確かめる（案: 環境変数 `ERYTHEIA_FORCE_GPU_WARNING=1`）。
  - E2E で確かめること: `GPU placement warning shown` の行が 1 回、`GpuPlacementWarningText` が見える、操作が止まらない（再生のボタンが押せる）、フォーカスが主窓のまま、「×」で消える。
- 本番で誤って効かないこと:
  - 先例の `ERYTHEIA_FORCE_GPU_UNAVAILABLE`（`OutputBackendState`）と同じ作りにする。プロセスの環境変数だけを読み、設定ファイルにもインストーラーにも出さない。
  - 効いたときは、起動のたびに Warning で「検証用の注入: ERYTHEIA_FORCE_GPU_WARNING により…」を出し、6 節の行の `reason` にも `forced` と出す。
  - 画面の文面は変えない（試験で本物の文面を確かめるため）。ログで見分けられる。
  - 単体の試験で、変数が無い・空・`0` のとき判定が変わらないことを確かめる。
- 検証機の実機の回（内蔵 GPU で動く本物の条件）:
  - 検証機の回は、利用者が機体を空けたと言ってから。
  - 内蔵で動かすには、ERYTHEIA.exe の指定を一時的に省電力にするか消す必要がある。利用者の依頼で `GpuPreference=2` を登録した経緯があるので、変える前に利用者の許可を取り、終わったら `GpuPreference=2` に戻して値を確かめる。
  - 確かめること: 指定を省電力にしたとき警告が出る（→ 外れた。省電力では出ない。12.15）。`GpuPreference=2` に戻して再起動したとき警告が出ない。どちらも 6 節の行の `used` と shim の `vendor` が合う。
  - 合わせて、出力先を内蔵の側・RTX の側のディスプレイにしたときの `origin` と `used` を記録する（3.4 と 10 節の未確定を確かめる）。最終の文面（5.2）はこの結果で決める。
  - 指定の後に保存された出力先（`\\.\DISPLAY2`）が NVIDIA の下で見つかった 1 回の観測がある（3.4）。前後の比べは成立していないので、この回で指定を変えたときの並びを記録して確かめる。
  - 指定を省電力・高パフォーマンス・無しにしたそれぞれで、高性能と省電力の両方の並びを記録する（3.4。並びが指定で変わるか）。記録には 6 節の行の `highPerformance` と `minimumPower` を使う。

### 7.4 公開の前に足す 1 回

- インストール版を、GPU を明示せずに（環境変数も試験の切り替えも無しで、ショートカットから）普通に起動して、使われた GPU を 6 節の行と shim の vendor で見る。検証機で行う。
- 結果（`used`・`origin`・`verdict`）を記録に残す。

## 8. インストーラーの件の事実

インストーラーは Inno Setup（`scripts/installer.iss`）。`PrivilegesRequired=lowest` で、`PrivilegesRequiredOverridesAllowed` は無い。今は `UserGpuPreferences` に何も書かない。

### 8.1 昇格して動くとき、書き先の HKCU は実際に使う人のものになるか

- Inno Setup の文書（PrivilegesRequired の項）: `lowest` では、管理者の組の人が起動しても管理者の権限を求めず、いつも「管理者でないインストールのモード」で動く。このモードでは HKA は HKEY_CURRENT_USER を指す。
- 同じく（非管理者モードの項）: 管理者の権限がたまたまある（昇格して起動された）ときは、Setup や [Code] がそれを使うことがある。
- 同じく（[Run] の項）: 利用者が setup.exe を右クリックして「管理者として実行」したときや、昇格済みのプロセスから起動したときは、Setup は元の利用者の資格で何かを動かす機会が無い（`runasoriginaluser` が効かない）。
- 今の installer.iss では Setup 自身は昇格しない。VC++ の再頒布パッケージだけが `shellexec` で別に起動され、そこで UAC が出る。普通にダブルクリックで入れる限り、Setup の [Registry] や [Code] が書く HKCU は、入れた人のもの。
- 書き先が別の人になりうるのは、「管理者として実行」したときで、とくに標準の利用者が別の管理者の資格で昇格した（肩越しの昇格）とき。このときの HKCU は管理者の資格の側になる、と見ている。これは Windows のトークンの一般の振る舞いで、Inno Setup の文書には書いてない。検証機では確かめていない（10 節）。
- アプリを使う人とインストールした人が違う機体（共用の機体）では、どの方法でも、インストーラーが書く指定はインストールした人にしか効かない。`UserGpuPreferences` が HKCU にあるため。

### 8.2 アンインストールで外すとき、利用者が自分で付けた指定と区別できるか

- 値の名前は exe のパスそのもので、Windows の設定の画面から付けたものと、インストーラーが付けたものは、同じ名前・同じ形になる。値そのものからは区別できない。
- Inno Setup の [Registry] の `uninsdeletevalue` は、値の中身を見ずに消す。使うと、利用者が自分で付けた指定（同じパス）も消える。
- 区別したいときの作り（案）: インストーラーが書いたときに、書いた値と「書いた」という印をアプリの側の場所（例: アンインストールの情報の近く）に残し、アンインストールでは今の値が書いた値と同じときだけ消す。ただし、利用者が後で同じ値を自分で付け直した場合は、やはり区別できない。
- 値の文字列には `GpuPreference=` のほかの項目が並ぶことがある（Windows 11 の設定の画面が別の項目を同じ文字列に足す）、と見ている。確かめていない（10 節）。並ぶなら、値を丸ごと消すと、ほかの項目も消える。
- 更新のときは、インストール先が旧のフォルダ（`Programs\TimecodeSyncPlayer`）のまま残る（`UsePreviousAppDir`）。旧の指定を引き継ぐなら、旧のフォルダの `TimecodeSyncPlayer.exe` の値を、同じフォルダの `ERYTHEIA.exe` の値へ写すことになる。

## 12. 実装で足した決まり（TSP-Fable のレビュー、2026-11-16）

### 12.1 UI のスレッドから合成の D3D11 デバイスに触らない

- 復旧の最中に合成のデバイスは捨てられる。UI から `CheckFeatureSupport` などを呼ぶと寿命の競合になる。
- LUID・選ばれ方・名前・VendorId・UMA は、デバイスを作った場所（GPU worker の `InitializeGpuResources` と、復旧の `CreateGpuDeviceForRecovery` の作り直しの直後。どちらも合成の周期の外）で 1 回だけ読み、変更できない 1 つの値（`GpuDeviceIdentity`）にまとめる。UI は `OutputEngine.DeviceIdentity` を読むだけ。
- 読み（`GpuDeviceIdentityReader.Read`）は例外を外へ出さない。名前・UMA の読みが失敗したら、その値を null（ログでは `?`）にして Warning を 1 行出し、デバイス作りは続ける。
- アダプターの一覧と 2 つの並びは、UI の側で別の DXGI の Factory を作って取る（`DxgiGpuAdapterOrderSource`）。
- 起動では、`DeviceIdentity` を `deviceReady.Set()` より前に書く。`WaitForDevice` が真を返した後に UI が読めば、値は必ず入っている。

### 12.2 復旧の道に足すのは「作った後の読み取りと値の差し替え」だけ

- `CreateGpuDeviceForRecovery` の差分は、`gpu = device;` の次の 1 行（`PublishDeviceIdentity(...)`）だけ。try と catch（同じアダプターで作れないときに既定へ移る分岐）と `GpuRecoveryPlan` の順には差分を出さない。
- このため、選ばれ方は作った後の LUID と求めた LUID を比べて決める（`GpuPlacementPolicy.RecoveryOrigin`）。求めた LUID が無ければ `default`、同じなら `saved-display`、違えば `recovery-default`。既定へ移った先が、たまたま求めたアダプターと同じだったときは `saved-display` と出る。使う GPU は同じなので、判定は変わらない。
- デバイスの消失の模擬（`ERYTHEIA_SIMULATE_DEVICE_LOSS`）の既存の E2E を、表示を入れた後に回し直す。

### 12.3 壊れた側の数え（起動の所要）

- 判定は起動の `WaitForDevice` の後（`waitForDeviceEndMs` の後、`windowLoadedMs` の前）に UI のスレッドで 1 回走る。DXGI の Factory を作って一覧と並びを読む分だけ、起動が延びうる。
- 判定を入れる前と後の Release の exe を、開発機で交互に起動して `Startup timing:` の行を比べる（結果は 12.4）。

### 12.4 起動の所要（壊れた側の数え）

- 開発機（RTX 3070）で、変更前（3981c10）と今（f49aabc）の Release の exe を交互に 6 回ずつ起動し、`Startup timing:` の行を比べた（設定は一時の場所、素材なし、2026-11-16 13:12〜13:17）。

### 12.5 判定は呼び出し口でも囲む（TSP-Fable のレビュー）

- `GpuPlacementJudge.Run` の try は、材料の取得から行・名前・文面の組み立てまでを囲む。どこで例外が出ても `NotJudged`（`error`）で返す。
