## 4. instant-rate の CRITICAL の整理

- shim: `tcs_player_seek`（`tcs_gstreamer.cpp:4100-4133`）は flush シークを出して segment を待たずに戻る。`tcs_player_set_rate_instant`（`:4209-4256`）は `GST_SEEK_FLAG_INSTANT_RATE_CHANGE` の seek を送り、成功なら `player->rate` に書く。直前の flush の segment が届いたかは見ていない。segment を数える既存のプローブ `on_appsink_flush_probe`（`:1427-1452`、appsink の pad）
- アプリ: シークを出すと `ReportSeekSent` → `SeekIssued` → `LtcSyncController.OnSeekIssued`（`:407-418`）→ 倍率が 1.0 でなければ `TryRestoreRateToUnity()` → `ApplyRateInstant(1.0)`。**flush シークの直後に同期で 1.0 を送る**経路（規則 3「relocate は varispeed を持ち越さない、発行した時点で 1.0」）。Jump 補正（`:1239`）は SeekTo の前に 1.0 を送る（順序が逆）
- v0.6.1 の確認: 速度の食い違いは再現せず（108＋72 回）、CRITICAL は診断の行だけ。検証機の一式では 0 回
- 「出ない順序」の候補: (a) アプリで 1.0 の戻しを新しい世代の最初のフレームの後に遅らせる（規則 3 の文言が変わる）、(b) shim で flush シークの segment に rate=1.0 を入れる、または instant-rate を segment の後まで保留。「行を抑える」案: `glib_log_to_shim`（`:117-131`）でこの assertion だけ数えて落とす

## 5. 【優先度高】トラック切替の直後の同期シーク 3 本の連鎖（2026-10-02 起票、TSP-Fable）

- 事実（検証機の報告、v0.6.2 の候補 `5ee2081` の A-1、親は未確認）: M3 → M4 の切替のたびに同期シークが 3 本続く（+0.45 → −0.34 → −0.26、1 周 3 分、一式で 60 本）。**v0.6.1 の A-1 でも同じ数**で、v0.6.2 の新しいものではない。A-1 は合格（合否には効いていない）
- 優先度高の理由（TSP-Fable）: 推奨素材（H.264）のトラック切替は本番の基本操作で、切替ごとに 3 本のシークが出るのは着地の揺れ（前向きに行き過ぎて 2 回戻る）そのもの。Latest の運用に関わる
- 集める事実（検証機に依頼済み）: (1) 3 本の間隔と各着地の位置、(2) その窓の公開不足（0.5 秒以内か）、(3) 1 本目の +0.45 が切替の入口の合わせか規則 3 の relocate か（reason）、(4) v0.6.1・v0.5.4 の候補 4 の A でも同じ 3 本だったか
- 原因の読みの候補（v0.6.3 で確かめる）: 規則 3 の目標 M + c の c（先行量）の見積もりが切替の直後に大きすぎる型か、切替のロードの後の着地の順序か
