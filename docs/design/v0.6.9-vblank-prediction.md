# v0.6.9 の最初の項目（全画面の vblank の予測）— 設計の下書き

下書き（2026-11-18）。基点は main 289410a。製品のコードはまだ書かない。数は、断りが無いものは v0.6.8 の設計書 12.17・12.18 から引いた（出所は検証機の担当と v068-impl の報告で、親と TSP-Fable は生の記録を未読）。この設計では、どれも測り直していない。

---

## 1. 出所と依頼

- 検証機（ノート PC。RTX で合成し、外付けの 4K の画面は内蔵 GPU の側につながる）で、4K の全画面への出力が約 20 分の巡りのうち約 7 分、約 30 fps に落ちた（2 回のうち 2 回。v0.6.8 の設計書 12.17）。合成は 60 fps のままだった。
- 開発機（GPU が 1 つで、画面はその GPU につながる）では、予測は実際の画面に合っていた（1 回、6 分。12.18）。
- 利用者の言葉（趣旨）: 「ノート PC で運用できるようにしたいから、この構成はあり得る」。この構成は想定の内として扱う。
- 依頼: 全画面の vblank の予測を、SyncRefreshCount が進まない機体でも実際の画面に付いていかせる。

## 3. 今の作り（コードの事実）

- 全画面の swapchain は `MaximumFrameLatency` が 1 で、`Present(1)`（`Output/SwapchainTarget.cs`）。
- `OutputEngine` は gate を `new VblankDisplayGate(PresentMarginMs, 0, Stopwatch.Frequency)` で作る。refreshHz が 0 なので、周期の初期値は 60 Hz の値（16,667 µs 相当）。作るのは 3 か所で、全画面の接続（`AttachFullscreen`）、大きさの変更（`ResizeFullscreen`）、デバイスの復旧の後の作り直し（`RecreateFullscreenForRecovery`）。gate の状態は作り直しのたびに捨てられる。
- `OutputEngine.ObserveScanout` は `GetFrameStatistics` を読み、`ScanoutTracker.Observe` に渡す。`ScanoutTracker` は PresentCount が前より進んだ観測だけを返す（同じ統計の読み直しは、ここで落ちる）。返った観測は `present.scanout` としてトレースに記録し、`vblank.ObserveScanout(SyncQpcTime, SyncRefreshCount)` に渡し、続けて `AlignCompose()` を呼ぶ。
- `VblankDisplayGate.ObserveScanout`:
  - 最初の 1 件は無条件に受ける（`lastSyncQpc`、`lastSyncRefresh` を置き、`HasScanout` を立てる）。
  - 2 件目からは、`syncRefresh <= lastSyncRefresh || syncQpc <= lastSyncQpc` なら捨てる。受けたときは、`(syncQpc − lastSyncQpc) / (syncRefresh − lastSyncRefresh)` を直近 8 件（`PeriodSamples`）に入れ、その中央を周期にする。位相は受けた観測の時刻そのもの（`lastSyncQpc` を置き換える）。
  - SyncRefreshCount が 0 のままだと、受けるのは最初の 1 件だけになる。周期は初期値のまま、位相は最初の観測のままで、予測は「最初の scanout の時刻 ＋ k × 16.6667 ms」で自走する。
- `Predict(now)`: `lastSyncQpc + k × PeriodTicks − LeadTicks > now` を満たす最小の k の vblank を返し、狙いは vblank の `marginTicks` 前。`ComposeAlignGate.Decide` も同じ `Predict` を使う（合成の位相も、この予測に揃う）。
- Present の前に、前のフレームが列から出た合図を「予測した vblank の 1 ms 前」まで待つ（最大 4 ms。`OutputEngine.HoldVblankReadiness`）。来なければその回は Present せず、`display.vblank.notReady` を記録して予測を捨てる（`Defer`）。
- この判断のコードは v0.4.0 から同じ（12.17、TSP-Fable がタグで確かめた）。
- 試験: `VblankDisplayGateTests` は、回数が進む観測だけを扱っている。回数が 0 のままの観測の試験は無い（12.17 の試験基盤の候補）。
- 標準の同期のランナーの台本（`scripts\` の .ps1）には、全画面を開く処理が見当たらない（grep。`GpuOutputProbe` の道具を除く）。標準の 1 本はこの項目の道をほぼ通らない見込み。

## 4. 観測の事実

### 4.1 検証機（12.17 の 2 回目。RTX で合成、4K の外付けは内蔵の側）

- `present.scanout` 59,863 件すべてで、SyncRefreshCount が 0、PresentRefreshCount も 0。
- SyncQPCTime は進んでいた。+180〜+840 s で、PresentCount が 1 だけ進んだ続きの組のうち、差が 15〜18 ms の 39,517 組の平均が 16.666456 ms（中央 16.665800 ms）。予測の周期（16.666700 ms）より 14.6 ppm 短い。15〜18 ms の外の組が 39 あり、平均には入れていない。この 39 組の中身（差の値、前後の組）は見ていない。
- この平均は下の「Present から scanout まで」と同じ記録の別の見方で、独立の裏付けではない（12.17）。
- `display.vblank.predict` の周期は 16.666700 ms の 1 種類。`compose.align` の補正は全窓で中央 0.0 µs。`display.attach` は 1 本。
- present.start から、その画の SyncQpcTime まで（以下 L と書く）の 60 秒ごとの中央:
  - +0〜+70 s: 19.13 → 18.28 ms。この区間は約 30 fps。
  - +70〜+180 s: 16.47〜16.49 ms。60 fps。
  - +180 s から、60 秒に約 0.82 ms ずつ減り、+840 s で 7.43 ms。ここまで 60 fps。
  - +850〜+870 s で 23.0 ms 前後へ跳び、以後約 30 fps。
- 予測した vblank − present.start の中央は、ほぼ全区間で 2.4〜2.5 ms（+70 s で 0.88 ms に跳び、約 110 秒で戻る）。
- 1 回目（20:19〜20:40）も、開いた直後の約 70 秒が約 30 fps だった。細かい数は残っていない。

### 4.2 開発機（12.18。GPU 1 つ、画面はその GPU）

- SyncRefreshCount は進み、0 は 0 本。PresentRefreshCount も同じ値で進む。
- L の 60 秒ごとの中央は 2.39〜2.44 ms で動かない（最初の 1 件だけ 18.98 ms）。
- 30 秒ごとの present.return は 1793〜1800、notReady は 0〜2。

### 4.3 読み（TSP-Fable の 12.17 の読みに、この設計で足した分）

確定ではない。合否（8 節）の回で確かめる。

- 12.17 の読み: L が約 18.2 ms（1 周期 ＋ 1.5 ms。次の回の合図の待ちの期限）より長いと次の回が必ず飛び、約 30 fps になる。予測と実際の画面が約 14 ppm ずれるので L が縮み、7.3 ms ほどを割ると次の vblank に間に合わず、1 周期遅れて約 30 fps に入る。
- この設計で足した読み: **開いた直後の約 70 秒は、予測の位相が実際の画面とほぼ一致していた区間**。予測は最初の scanout の時刻から始まるので、開いた直後は予測の格子と実際の格子がほぼ重なる。そのとき L は 19.13 ms（Present の約 2.5 ms 前 ＋ 1 周期）で、約 30 fps だった。つまり、この機体では Present から画面に出るまでに 2.5 ms より長くかかり、狙った vblank の次に出る。
- ここから言えること: SyncQPCTime で位相を実際の画面に合わせ直すだけ（狙いを今どおり vblank の 3 ms 前に置く）だと、この機体では、開いた直後の約 70 秒の状態（約 30 fps）が続く見込み。今の作り（約 13 分は 60 fps）より悪くなる。5.4 で扱う。
- 60 fps だった区間の L は 7.43〜16.49 ms（60 秒ごとの中央）。この範囲の端の外で 60 fps が続くかは、観測が無い。

## 5. 設計（案）

### 5.1 考え方

- 回数が進む機体では、今と同じ道を通す（5.2）。
- 回数が 0 のままの機体では、SyncQPCTime だけで実際の画面の格子（位相と周期）を取り直し続ける（5.3）。
- 回数が 0 のままの道だけ、狙う位相を実際の格子から半周期ずらす（5.4）。
- 時刻も進まないときは、今と同じ自走（5.5）。

### 5.2 回数が進む機体（今の道）

- gate を作ってから受けた観測の SyncRefreshCount が一度でも 0 でなければ、その gate では今のコードと同じ計算をする（受ける条件、8 件の中央、位相の置き換え、`PredictedRefresh` の数え方）。
- 最初の 1 件の SyncRefreshCount が 0 でなければ、5.3 の道には入らない。開発機（12.18 では最初から 147971992）は、この道だけを通る。
- 0 が続いた後で 0 でない値が来た場合も、そこからは今のコードの計算に渡す。この移り方は観測が無く、今のコードの振る舞い（`lastSyncRefresh` が 0 のままの差で割る）も変えない。

### 5.3 回数が 0 のままの道（時刻だけで合わせる）

gate を作ってから受けた観測の SyncRefreshCount がすべて 0 の間だけ、この道を通る。

- 観測の受け取り:
  - `syncQpc <= 前に受けた観測の時刻` は捨てる（逆行・止まり）。
  - `syncQpc > 観測した時刻`（`OutputEngine` が `GetFrameStatistics` の直後に読む QPC。今も `observedQpc` として読んでいる）は捨てる。まだ来ていない vblank の時刻はあり得ない。
  - 上の 2 つの捨ては、5.3 の「外れ」の連続の数に入れない（時刻の値そのものが使えないので、格子の作り直しの手がかりにならない）。
- 格子への当てはめ:
  - 今の格子（基準の時刻 A と周期 P）に対し、n = round((syncQpc − A) / P)、ずれ r = syncQpc − (A + n × P)。
  - |r| が許容幅（5.7 の 1）より大きければ「外れ」として捨て、位相も周期も動かさない。
  - 外れが 8 回続いたら（5.7 の 2）、格子を作り直す（その観測を基準にし、周期を初期値に戻し、溜めた値を捨てる）。画面のモードが接続の作り直し無しに変わった場合と、長い空白で周期の誤差が許容幅を超えた場合を拾う。
- 位相（1 回の値で動かさない）:
  - 受けた観測の時刻を直近 8 件溜める。
  - 最新の受けた観測を仮の基準にして、8 件それぞれのずれを測り、その中央だけ仮の基準を動かしたものを A にする。
  - 外れ値が 1 件混じっても、中央はほかの 7 件の範囲から出ない。12.17 の外れの率（39 / 39,556）なら、8 件に 2 件以上が混じることはまれ。
- 周期:
  - 続けて受けた 2 件で n が 1 のときだけ、その差を今の 8 件の中央（`PeriodSamples`）に入れる。n が 2 以上の差は、周期には使わない（30 fps の区間の差や、空白の後の差で、周期の取り違えを入れないため）。
  - 周期の推定は今の回数の道と同じ形（8 件の中央）にした。名目のまま位相だけ合わせても、位相は 1 フレームごとに取り直すので、14.6 ppm の差は 1 フレームで約 0.24 ns にしかならない。推定を入れる理由は、59.94 Hz の画面（名目との差が 1 フレームに約 17 µs）で 8 件のずれを比べるときに偏りが乗らないようにするため。
- `PredictedRefresh`（トレースだけに出る）は受けた観測の n を足していく数にする。

### 5.4 狙う位相を半周期ずらす（回数が 0 のままの道だけ）

- 5.3 で求めた格子の基準 A に、半周期（P / 2）を足したものを予測の基準にする。`Predict` が返す「vblank」は、この道では実際の vblank ではなく、Present の狙いの基準になる。
- 理由（4.3 の読みに頼る。確定ではない）:
  - ずらさない（実際の vblank の 3 ms 前に Present する）と、この機体では開いた直後の約 70 秒の状態（L が約 19.1 ms、約 30 fps）が続く見込み。
  - 半周期ずらすと、Present は実際の vblank の約 8.3 ＋ 2.5 ＝ 10.8 ms 前になる（予測 − present.start の中央 2.4〜2.5 ms は 12.17 の値）。L は約 10.8 ms で、60 fps が観測された範囲 7.43〜16.49 ms の内に入る。下の端まで約 3.4 ms、上の端まで約 5.7 ms。
  - 半周期は周期から決まる値で、合わせ込む数ではない。範囲の真ん中（約 12 ms）に寄せる数を別に足すことはしない。
- 代わりに払うもの: 回数が 0 のままで、しかも Present から画面に出るのが速い機体があれば、画面に出るのが今より約 8.3 ms 遅くなる（60 fps は保つ）。そういう機体は観測が無い。
- 合成の位相（`ComposeAlignGate`）は同じ `Predict` を使うので、合成も同じだけずれる。式は変えない。
- 回数が進む機体（5.2）は、ずらさない。

### 5.5 回数も時刻も進まない

- SyncRefreshCount が 0 で、SyncQPCTime も前と同じか戻るなら、5.3 の最初の条件で捨て続ける。予測は最初の観測からの自走のままで、今と同じ。半周期のずらしは、最初の観測の時点で回数が 0 なので入る。今と位相が半周期違うだけで、自走であることは変わらない。
- SyncQPCTime が 0 のまま来る場合も同じ（最初の観測の時刻 0 から自走。今と同じ）。
- 決めきれなかった点: この場合に半周期のずらしを入れるか（9 節）。

### 5.6 60 Hz 以外の画面で回数が 0 のまま

- 周期の初期値は 60 Hz なので、50 Hz の画面（20 ms）では、ずれが約 3.3 ms になって許容幅で捨て続け、8 回ごとに作り直す。作り直しの後も同じで、予測は今と同じく実際の画面に合わない。
- 範囲の外（2 節）。今より悪くしないこと（落ちない、例外を出さない）だけを単体テストで確かめる。

### 5.7 足す定数と根拠

| 番号 | 定数 | 値 | 新しいか | 根拠 |
|---|---|---|---|---|
| 1 | 格子からのずれの許容幅 | 1 ms | 新しい | n を取り違えない上限（半周期 8.3 ms）より十分小さい。gate が表示に残す余裕（`LeadMs` の 1 ms）より大きいずれを位相に入れない。検証機の 15〜18 ms の内の組のずれの分布は見ていない（平均と中央だけ）。合否の回で外れの数を記録する（8.1） |
| 2 | 作り直しまでの外れの連続 | 8 回 | 今の `PeriodSamples` を使う | 周期と位相の中央と同じ窓（60 Hz で約 133 ms）。1 回の外れでは作り直さない |
| 3 | 位相の中央の件数 | 8 件 | 今の `PeriodSamples` を使う | 周期の中央と同じ窓 |
| 4 | 半周期のずらし | P / 2 | 周期から決まる | 5.4 |

新しく値を決める定数は 1 つ（許容幅）。

### 5.8 トレースとログ

- トレースに足す（gate の判断には使わない）:
  - 回数が 0 のままの道に入ったとき 1 件（`display.vblank.timeOnly`）。
  - 外れで捨てたとき 1 件ずつ（ずれの µs を値に）、作り直しのとき 1 件。逆行・未来の時刻で捨てたときも 1 件ずつ（種類を分ける）。平常の受け取りでは記録しない。
- アプリのログ（Information）: 回数が 0 のままの道に入ったとき、全画面の接続ごとに 1 行。現場のログで、この道を通ったかを後から読めるようにする。行の文は実装で決める。2 節の「ログの 1 行」の件（表示の数が合成の数を下回った窓）とは別。

### 5.9 採らない案

- **DwmFlush を足す**: 採らない。GPU worker を止める呼び出しで、止まる長さを測っていない。背景として、Microsoft の `IDXGISwapChain::GetFrameStatistics` の Remarks には「Hardware Flip Queue の機体では、統計が更新される前に DwmFlush が要るかもしれない」「複数のモニターの場面の多くでは、統計は信頼できない」とある。検証機の SyncRefreshCount が 0 なのが、この記述の場面に当たるかは確かめていない。
- **位相だけ合わせ直し、狙いは今どおり（ずらさない）**: 4.3 のとおり、検証機では約 30 fps が続く見込み。
- **着地の遅れ（L が 1 周期を超えた回）を見てから、ずらしの量を決める**: しきい値と回数の定数が増える。半周期で 60 fps の観測範囲に入るので、先に足さない。
- **回数が進む機体でも、この道に寄せる**: 開発機で合っている道を変える理由が無い。

## 6. 単体テスト

`VblankDisplayGateTests` に足す。時計は今の試験と同じ 1 µs 刻み（Frequency 1,000,000）。今ある試験は期待を変えない。

1. **回数 0・時刻だけ進む**: 名目より 14.6 ppm 短い周期（16,666.4 µs 前後）の vblank の時刻を、毎周期 1 件、25 分ぶん（約 90,000 件）、SyncRefreshCount 0 で流す。
   - 期待: 全期間で、予測の基準と「実際の格子 ＋ 半周期」の差が 50 µs 以内。
   - 2 回に 1 回だけ観測が来る入力（30 fps の区間の形）でも同じ。
   - 今のコードではこの試験が落ちること（差が 25 分で約 21.9 ms まで広がる）を、実装の前に確かめる。
2. **回数が進む**: 今ある試験を変えずに通す。加えて、回数が進み、時刻に揺れ（±20 µs）がある入力で、予測が今のコードの式（最新の観測 ＋ k × 8 件の中央）と全件一致すること。半周期のずらしが入らないこと。5.8 のトレースの件数が 0 であること。
3. **回数も時刻も進まない**: 同じ SyncQPCTime を 1,000 件流す。予測は最初の観測からの自走で、例外を出さない。SyncQPCTime が 0 のままの場合も同じ。
4. **逆行と跳び**:
   - 時刻が戻る観測、観測した時刻より先の時刻の観測を 1 件混ぜる。捨てて、位相も周期も動かない。
   - 格子から外れた観測を 7 回続ける。作り直さない。8 回目で作り直し、その後の予測が新しい格子に付く。
   - 5 秒の空白の後の観測（格子の上）を受け、位相が保たれる。
   - 50 Hz の時刻を回数 0 で流し、例外を出さない（5.6）。
   - 作り直し（接続・大きさの変更・復旧）は、`OutputEngine` が gate を作り直すので、gate の試験では「新しい gate は前の状態を持たない」ことだけを確かめる。
5. **外れ値の混入**: 1 の入力に、+0.9 ms（許容幅の内）と +5 ms（外）の外れ値を、1,000 件に 1 件の割合で混ぜる。予測の基準の差は 50 µs 以内のまま。+5 ms の側は外れとして数えられ、作り直しは起きない。

## 8. 合否（回す前に固定）

先に決めた数で読み、後から窓やしきい値を変えない。落ちたら、定数を合わせ込まずに設計へ戻る。

### 8.1 検証機の 4K の全画面（この項目の合否の中心）

条件:

- 12.17 の 2 回目と同じ構成。RTX で合成（検証のコピーの exe に高パフォーマンスの指定を付け、最初の起動の `GPU placement:` の行が NVIDIA なのを見てから続ける。終わったら外して前後を比べる）。外付けの 4K の画面（3840x2160@60）は内蔵 GPU の側。キャンバス 3840x2160。LTC なし。切替は 3 分ごと。
- 全画面を開いてから 25 分以上（1,500 s 以上）。トレース付き。
- 静かな状態（利用者がほかの作業を止めた状態）で回すかは 9 節。

回が有効である条件（満たさなければ無効で、合格にも不合格にもしない）:

- トレースが outcome=completed、droppedEvents=0。
- `display.attach` が 1 本。
- `present.scanout` の SyncRefreshCount が全件 0（0 でない値があれば、この回は 5.3 の道を試していない）。
- `display.vblank.timeOnly` が 1 件。

読む範囲: 全画面を開いてから 30 s 後から、閉じるまで。最初の 30 s は記録するが、合否に使わない（開いた直後は gate の観測がまだ溜まっていない）。

合格の条件（全部）:

1. 30 秒ごとの present.return が、どの窓も 1,780 以上（60 fps で 1,800。12.17 の 60 fps の区間は 1786〜1800、約 30 fps の区間は 900 前後）。
2. 10 秒ごとの `display.vblank.notReady` が、どの窓も 10 以下（12.17 の約 30 fps の区間は 10 秒あたり 286〜299、落ち始めは 44）。「続く区間」は、これを超えた窓が 1 つでもあることとする。
3. L（present.start からその画の SyncQpcTime まで）の 60 秒ごとの中央が、全窓で幅 1.0 ms の内に収まる。あわせて、最初の 5 分と最後の 5 分の中央の差が 0.5 ms 以内。今の作りのずれ（60 秒に約 0.82 ms）なら、2 分ほどで 1 は外れる。

記録だけ（合否に使わない）:

- L の中央の値（4.3 の読みでは約 10.8 ms。外れても、上の 3 つを満たせば合格）。
- 外れ・逆行・未来・作り直しの件数（5.8）。
- `compose.publish` の 30 秒ごとの本数。
- `display.vblank.predict` の 1 フレームあたりの本数（12.17 は約 100、12.18 は約 1.2。2 節の「待ちが 0 で回る」件の副作用の確かめ）。
- 表示の数が合成の数を下回った窓の数（2 節の「ログの 1 行」の件の副作用の確かめ）。

### 8.2 開発機（壊れた側として数える）

条件: 12.18 の 2 回目と同じ。GPU 1 つ、出力先は RTX につながる 4K（3840x2160@60）、素材は 1080p60 の H.264、再生から 20 秒で全画面、6 分、トレース付き。設定は一時の場所。

有効の条件: トレースが completed・dropped 0。SyncRefreshCount が進む（0 は 0 本）。

合格の条件（全部。前の晩の数から悪くなっていないこと）:

1. `display.vblank.timeOnly` が 0 件（今の道だけを通った）。
2. L の 60 秒ごとの中央が、全窓で 2.2〜2.7 ms（前の晩は 2.39〜2.44）。最初の 1 件は除く。
3. 30 秒ごとの present.return が、全窓で 1,790 以上（前の晩は 1793〜1800）。最初の窓は除く。
4. 30 秒ごとの notReady が、全窓で 5 以下（前の晩は 0〜2）。

### 8.3 標準の同期の 1 本（検証機、RTX）

- 静かな状態で回す。最初の起動の `GPU placement:` の行が NVIDIA なのを見てから続ける。
- 判定は今の合否の一式の決まりどおり（標準の表。relocate と boundary は範囲の内、落ち 0）。
- hold と 3 つの和は、12.17 で範囲の下に外れ、説明は未了のまま。この回の数を、範囲の作り直しの材料にする。作り直しの手順（どの回の数から、どう範囲を作るか）は、回す前に決める（9 節）。この回の数を見てから手順を決めない。
- 3 節のとおり、ランナーは全画面を開かない見込みなので、この回は vblank の直しの合否ではなく、同期の側が壊れていないことの確かめとして読む。

### 8.4 ほか

- 非E2E 全部が合格。UI の E2E は、既知の落ち（v0.6.8 の設計書 12.17 の GStreamerBackend_SurvivesRepeatedTrackSwitches）だけ。

## 9. 未確定・決めきれなかった点

- **半周期のずらし（5.4）は、4.3 の読みに頼っている**。「開いた直後の約 70 秒は、予測が実際の画面とほぼ一致していた」は、予測が最初の scanout から始まる作りと、L が 19.13 ms だったことからの推定で、その区間の予測と実際の格子の差を直接測ったものではない。8.1 の回で 1 が満たされなければ、ずらしの量を合わせ込まずに設計へ戻る。
- **7.3 ms（これより遅く出すと次の vblank に間に合わない）の出どころは未確認**（12.17 から持ち越し）。半周期のずらしの下の余裕（約 3.4 ms）は、この値に頼る。4K の素材や負荷で変わるかは分からない。
- **回数も時刻も進まない場合（5.5）に、半周期のずらしを入れるか**。入れても入れなくても自走で、今の作りでも位相は偶然で決まる。どちらにするかは TSP-Fable の判断。
- **許容幅 1 ms の根拠は弱い**。検証機のずれの分布を見ていない。8.1 の回で外れの件数を記録する。
- **8.1 を静かな状態で回すか**。12.17 は別の開発が動いたままの回だった。比べるなら同じ条件、合否としては静かな方が読みやすい。
- **hold の範囲の作り直しの手順（8.3）**。
- 検証機で SyncRefreshCount が 0 になる理由（GPU をまたぐ構成か、内蔵 GPU の側の画面か）は分けていない（12.18）。この設計はどちらでも同じ道を通るが、内蔵 GPU で合成して内蔵の側の画面へ出す構成で 5.3 の道に入るかは分からない。
- 15〜18 ms の外の 39 組が何だったか（2 周期ぶんの差か、時刻の乱れか）は見ていない。
