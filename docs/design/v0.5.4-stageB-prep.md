## 0. 要約

- **世代の意味**（§1）: (a) 一時停止中のシークは、ポンプが配信した最初のフレームで `DeliveredGeneration` が
  シーク世代へ進む（成立）。(b) 開始位置つきロードは世代が進み、最初のフレームで追いつく（成立。ロードの
  内部で世代が 2 回進む点に注意）。(c) 連続シーク（g → g+1）は、通常は D25 が g のフレームを落とすが、
  **セグメントの畳み込み・5 秒の安全弁・ポンプ期限では g のフレームが g+1 の「最初のフレーム」として
  配信され得る**。着地 = `DeliveredGeneration >= シーク世代` だけでは (c) を閉じられない
- **偽の再生 API の着地の事象の口**（§2）: `ScenarioPlayback` がシーク・ロードで世代を進め、着地の遅れの後に
  最初のフレームを配信する（`Landed` イベント・`LandingCount`・`DeliveredSeconds/Generation`）。既定は
  これまでと同じ時系列（遅延 0 は即時）で、位置の動きは変えない
- **再発テスト**（§3）: 段 B で畳む門の対応表と、U6 で赤になった 4 本の一覧。新規テストは 5 件
- 非E2E 全件: **2,801 合格・失敗 0・スキップ 0**

## 1. 世代の意味を 3 つの場面で確かめる

### 1-1. 共通の仕組み（コードの行）

### 1-2. (a) 一時停止中のシーク（ポンプが最初のフレームを配信して `DeliveredGeneration` が進むか）

順序（コードの行）:

1. `tcs_player_seek`（:3566-3598）: `seek_prepare_locked`（:2783-2881）が `generation++`（:2788）と
   期待境界の設定（:2803-2807。`seen + 1`）を行い、`p->eos` を消す（:2819-2823）。送信は `seek_send`（:2887-2918）
2. 一時停止中（`was_paused`）なら `pump_arm`（:3595-3596 → :2505-2534）: `p->paused` のときだけ有効（:2512）、
   期限（:2518）、**PLAYING へ上げる**（:2530）。理由は構造体のコメント（:440-446）:
   「PAUSED のままのフラッシュシークは目標のサンプルを preroll に残し、`sync=true` の appsink は
   クロックが動くまで `new_sample` を出さない」
3. `pump_preroll_tick`（:2537-2613）が `pump_generation` のフレームを待つ（:2554-2558）。届けば pump を閉じ、
   必要なら PAUSED へ戻す（:2607-2611）
4. `on_new_sample` が `latest_gen = p->generation`（:1568）と `latest_pts_ns`（:1569）を更新し、
   その世代をフレームに付ける（:1622）
5. 照会は `delivered_generation = latest_gen`（:3816）と `current_generation = p->generation`（:3755）を返す

**結論: 成立する。** ポンプが最初のフレームを配信した時点で `DeliveredGeneration == CurrentGeneration`
（シーク世代）になる。**成立しない型も同じ行から読める**: ポンプ期限（既定 4000ms、:243）までフレームが来なければ
`seek_boundary_expect` を 0 にして（:2583）PAUSED へ戻るので、`latest_gen` はシーク前のまま
（`DeliveredGeneration < CurrentGeneration` = 着地せず）。K3 の EOS 型（新しいフレームが来ない）も同じ形。
段 B の安全の時間切れは、このポンプ予算（4 秒）との関係を設計に書く必要がある（§9-7-2）。

### 1-3. (b) 開始位置つきのロード（世代が進み、最初のフレームで追いつくか）

順序（コードの行）:

1. `build_pipeline` が `attempt_gen = ++p->generation`（:3020-3022）
2. 最初のフレームを取るために **PLAYING へ上げる**（:3092。コメント :3100-3105
   「d3d11 デコーダ + コンバータは PLAYING でしか出さない」）。最初のフレームの門は
   `frames_decoded > 0 && latest_gen == attempt_gen`（:3134）
3. `start_sec > 0` なら**内部でもう一度シーク**する（:3218-3228）。ここで `seek_prepare_locked` が呼ばれ、
   世代がさらに 1 回進む
4. 一時停止のロードは音声の最初のバッファを待って PAUSED へ落とす（:3244-3272）

**結論: 成立する。** 最初に配信されたフレームが `latest_gen` をその時点の世代へ進め、その後の照会の
`DeliveredGeneration` が追いつく。**注意**: ロードは内部で世代を 2 回進める（:3022 と :3225）ため、段 B の
着地の状態は「ロード要求の前に取った世代」と比べない方がよい。ロード API が返った後の世代（または
`DeliveredGeneration == CurrentGeneration`）を着地の条件にするのが素直（§9-1 の実装で決める）。
**未確定**: 位置つきロードの最初のフレームが PLAYING 中に配信されるか、PAUSED へ落ちた後の preroll に
残るかは、素材とタイミングに依る（直後に明示シークする経路はポンプで拾えるが、D22 の
「次トラックの冒頭フレームを一時停止ロードするだけ」の経路はこのフレームに頼る）。§1-5 の実機ログで確かめる。

### 1-4. (c) 連続したシーク（g の後に g+1。g のフレームが遅れて届いても着地にしないか）

順序（コードの行）:

1. シーク g: `generation` が g、期待境界は `flush_boundary + 1`（:2803-2807）。appsink のパッドプローブが
   SEGMENT で `flush_boundary` を進め（:1288-1289）、バッファにその時点の境界を付ける（:1293-1297）
2. シーク g+1: 再び `generation++`、期待境界は「そのときの `flush_boundary` + 1」。**意図的に積まない**
   （:2793-2802 のコメント）。同じコメントが最悪の場合を明記している:
   「2 つのフラッシュシークが 1 つの SEGMENT に畳まれると、2 本目の SEGMENT は appsink に届かない。
   `seen+1` では、**前のシークのフレームが新しい世代の最初のフレームとして配信され得る**
   （owner の着地のゲートが弾いて再シークする。D21-b）」
3. 通常は、g のバッファは境界タグが期待より古いので `sample_is_pre_seek` が落とす（:1330、:1344-1354）
4. **5 秒の安全弁**（:1312-1319）: 期待が実現しないまま 5 秒経つと期待を捨て、以後のサンプルを通す
5. **ポンプ期限**（:2583）: 期限切れでも期待を捨てる（D24 の診断。フレームを永久に落とさないため）

**結論: 「ない」とは言えない。** (i) セグメントの畳み込み（:2793-2802 が明記）、(ii) 5 秒の安全弁
（:1312-1319）、(iii) ポンプ期限（:2583）の 3 経路で、前の世代のフレームが現在の世代として
`latest_gen` に載り得る。`p->latest_gen = p->generation`（:1568）は**到着時に現在の世代を付ける**ので、
フレームの中身の世代とは一致しない。したがって **着地 = `DeliveredGeneration >= シーク世代` だけでは
(c) を閉じられない**。いまのコードは位置の窓（門 6）で、目標から離れた遅延フレームを弾いて再シークする
（D21-b）。段 B は (1) 位置や内容の確認を着地の条件に残す、または (2) §9-1 後段の shim の通知
（世代の最初のフレームを配信した、を明示する）を足す、のどちらかが要る（設計の判断材料）。

### 1-5. 実機のログで確かめる手順（親が回す）

アプリのログ（`<exe>\logs\timecodesyncplayer-*.log`）:

- `Timecode sync decision ... playback=... deliveredGen=N currentGen=M`（`SyncDecisionEngine.cs:271`）。
  **シーク・ロードの直後の行で `deliveredGen` と `currentGen` を比べる**。同じなら着地の事象が来ている。
  `deliveredGen < currentGen` が続くなら着地待ちのまま
- `sync.gate seek-settled target=... elapsedMs=...`（`TimecodeSyncSeekState.cs:219`。着地の確定）、
  `sync.gate pending-timeout`（:244 付近。2 秒の時間切れ）、`sync.gate pending-replace`（:233。遠い要求の置き換え）
- `Seek command sent source=... value=...` と `Gst loadfile ... paused=...`（発行とロードの時刻）

shim のログ（`TCS_LOG_FILE`。既定は exe の隣の `tcs-gst-*.log`）:

- `seek: send end (accurate) ... ok=1`（:2904）と `pump_arm: set_state(PLAYING)`（:2529）
- `paused-seek: pump deadline ...`（:2598-2604。出たら (a) の不成立）、`pump_tick: set_state(PAUSED)`（:2608/2610）
- `lease: acquire gen=N seq=M ...`（:4041。配信された世代と連番）、`frame: ... pts_ms=...`（:1644-1649）
- `D25: dropped pre-seek sample pts_ms=...`（:1347-1351。落とした数。(c) の確認）、
  `load.attempt ... first_frame_ms=...`（:2967-2976。(b) の最初のフレームの時刻）
- 位置トレース（`TIMECODE_SYNC_PLAYER_OUTPUT_TRACE` 有効時の delivery 追記）: 位置と配信 PTS、
  フォールバックが拒否された印（`kDeliveryFlagPositionFallbackRejected`。:3793-3796）

手順の対応:

| 場面 | 見る行 | 判定 |
| --- | --- | --- |
| (a) | `pump_arm` → `lease: acquire gen=g` → 最初の `sync decision` の `deliveredGen==currentGen` | ポンプ予算内なら着地。`pump deadline` があれば着地せず |
| (b) | `load.attempt ... result=... first_frame_ms=...` → `sync decision` の `deliveredGen==currentGen` | 最初のフレームの配信で追いつく |
| (c) | 2 本の `seek: send` の間に `D25: dropped pre-seek sample` が出るか、`sync decision` の `deliveredGen` が g のままか | 落ちていれば安全。落ちずに現在世代になったら「畳み込み」の疑い（位置が目標から離れていれば D21-b の再シークが出る） |

### 1-6. 段 B への含意（まとめ）

- (a)(b) は `DeliveredGeneration == CurrentGeneration` を着地の事象の材料にできる
- (b) のロードは世代が内部で 2 回進む。比較の基準は「ロード API の後」の世代にする
- (c) は世代だけでは閉じない。位置/内容の確認を残すか、9-1 後段の shim 通知を足す。**これは段 B の設計判断**
- 安全の時間切れはポンプ予算 4000ms との関係を書く（§9-7-2）

## 2. シナリオ層の偽の再生 API の着地の事象（`ScenarioPlayback`）

足したもの（`tests/TimecodeSyncPlayer.Tests/Integration/Scenario/ScenarioPlayback.cs`）:

- `CurrentGeneration`: シーク・ロードで進む世代（shim の `p->generation`）
- `DeliveredSeconds` / `DeliveredGeneration`: 最後に配信されたフレーム（無ければ 0。shim の
  `latest_pts_ns` / `latest_gen`）
- `Landed`（`Action<ulong>`）と `LandingCount`: 着地の事象（シーク・ロードの世代の最初のフレームの配信）
- 世代の進み方: `Seek` / `Load` の**発行時**に進める（遅延の有無に依らない。`seek_prepare_locked` と同じ）。
  `ApplyPendingSeek` / `ApplyPendingLoad` では進めない（完了で二重に進めない）
- 配信: 着地の遅れ（`SeekLandingDelaySeconds` / `LoadDurationSeconds`）が 0 なら発行と同時、遅れがあれば
  完了時に「最初のフレーム」を配信して `DeliveredGeneration` を進め、`Landed` を 1 回出す。連続シークでは
  後のシークが前の着地待ちを置き換え、**最後の世代の 1 回だけ**が着地になる
- 再生中の進み（`AdvanceTime`）と `SetPosition` は世代を進めず（`SetPosition` は従来どおり進める）、
  配信位置だけを更新する（`latest_gen = p->generation` と同じ）
- **既定は今までと同じ時系列**: 遅延 0 のシーク・ロードは即時に位置が変わり、テストの位置・時刻は変わらない
  （変わるのは位置サンプルの `Delivered*` が 0 ではなく実際の配信を表すことだけ）
