# v0.5.2 設計: 同期の状態を見える形にする

作成: 2026-09-24。レビューを受けて改訂（§8）。**承認済み（§7）。**

## 1. なぜやるか

同期には、不具合のたびに足してきた一時状態（ラッチ）が約 40 個あり、5 つのクラスに散らばっている。
それぞれ「いつ消えるか」が、コメントとコードで食い違っているものがある。

- D33×D35 で S-3 が回帰した
- v0.5.0 の S-4 は、端へのシークの記録（`_boundarySeekTarget`）がファイルの読み込みをまたいで残ったのが原因だった
- どちらも「そのラッチをどのできごとで消すか」が、1 か所で決まっていないことから起きている

棚卸し（§6）では、S-4 と同じ型の候補がほかに 10 件見つかった。

## 2. いまの形（棚卸しの要約）

状態は、独立した 4 つの軸の組み合わせで決まっている。

| 軸 | 取りうる値 | いま表しているもの |
| --- | --- | --- |
| **入力（LTC）** | 未監視 / 検出待ち / 追従 / Jump 確認待ち / Jump 適用済み / 保持 / 損失（停止）/ 損失（ランスルー） | `LtcSyncController` の `_pendingJump*`・`_jumpAppliedOnce`・`_lastHeld*`・`_heldLossLandingSeconds`・`_heldReapplyDone`・`_followStartPending`、`LtcSignalLossPolicy` の `_isLost`・`_pausedByPolicy`・`_reason` |
| **位置の持ち主** | 通常 / ロード中 / 解除回収待ち / ギャップ / 境界ホールド | `TimecodeSyncService` の `_isLoadingFile`・`_fileLoadReleasePending`、`GapFreezeHandler.CurrentState`、`SingleModeSyncCoordinator` の `_clipBoundaryHeld`・`_boundarySeek*` |
| **シーク** | なし / 保留 / 着地窓（FollowStart / その他） | `TimecodeSyncSeekState`、`_seekLanding*`・`_landingOrigin`、`_positionTrust` |
| **速度補正** | 1.0 / 補正中 / 位置不安定で停止 / 1.0 への戻し待ち | `_correction`（内部状態）、`_lastAppliedRate`・`_rateRestorePending`・`_smoothAvailable`・`_correctionPausedForPosition` |

さらに**一時停止の持ち主が 5 つ**あり、互いを見ていない。

- 信号断のポリシー（`_pausedByPolicy`）
- 境界ホールド（`SetEndHold`）
- ギャップ（`_pauseOwnedByGap`）
- プロジェクト復元
- 利用者の操作

## 3. 作り直しの方針

**振る舞いを変えない版（v0.5.2）と、変える版（v0.5.3）を分ける。** 二つの変更を同じ候補に混ぜない（D33×D35 と同じ構図を避ける）。

### 段 0: 寿命の表をテストにする（v0.5.2、最初の仕事）

既存の単体テストは、ラッチの寿命をほとんど試験していない（§6 末尾）。そのため「振る舞いを変えない」を既存テストだけでは示せない。

- §2 の各ラッチについて、「どのできごとで消える／消えない」を**表そのものをテストデータにした特性テスト**（table-driven）で書く
- 表の各行は `ラッチ × できごと → 現状（消える／消えない）` と `意図（消えるべき／残るべき／未定）` の 2 列を持つ。§6 の候補一覧は、この表のうち「現状」と「意図」が食い違う行そのものにする（別の表を持たない）
- **現状のコードで全行が緑になること**を確かめてから、段 1 へ進む
- 表は、書いた者とは別に親がコードと突き合わせて 1 行ずつ承認する（書いた者の自己確認にしない）。承認済みの表だけを、段 1 の配線の入力にする

### 段 1: できごとを 1 か所に集める（v0.5.2、振る舞いは変えない）

ラッチを消すきっかけになる「できごと」を列挙した型（`SyncLifecycleEvent`）を作る。

- 対象のできごと: ファイル読み込み、モード切替、同期の有効／無効、監視の開始／停止、手動シーク、停止、ギャップの出入り、信号の復帰、fps モード変更、補正モード変更、信号断モード変更
- 各クラスは 1 つの入口（`OnLifecycle(evt)`）で受け、段 0 の表の「現状」の列どおりに消す
- できごとは、**いまラッチを消している呼び出しと同じ場所・同じ条件でだけ出す**。`BeginFileLoad` を通らない読み込み 4 経路から「ファイル読み込み」を出すと、いま消えていないラッチが消えるようになり振る舞いが変わる。そのため段 1 では出さず、v0.5.3 の最初の件（§6 の 2）で扱う
- できごとはログにも 1 行ずつ出す（`Sync lifecycle: <できごと>`）。v0.5.1 と候補で同じシナリオのできごとの列を突き合わせ、変えていないことを直接示す材料にする
- 段 0 の特性テストが緑のまま通ることが、この段の判定

### 段 2: 軸ごとに状態をまとめ、軸をまたぐ規則を 1 か所に集める（v0.5.2、振る舞いは変えない）

§2 の表の 4 軸を、それぞれ 1 つの型にまとめる（例: `LtcInputState` は enum の段階と、その段階でだけ意味を持つデータ）。

- ばらばらの bool と nullable の組み合わせを、「今どの段階か」＋「その段階のデータ」に置き換える
- 段階の外で意味のない値は、型の上で持てないようにする
- 遷移は各型のメソッドに集め、ログの文言も今と同じにする（E2E とログ解析のスクリプトがログを見ているため）

軸ごとの型だけでは、D33×D35 のような**軸の間の干渉**（境界ホールド × 保持着地）は防げない。そこで**軸をまたぐ規則の表**を 1 枚作り、いま散っている条件を 1 か所の判定関数（純関数）に集めて単体で回す。

- 例: 境界ホールド中は保持着地を出さない（D35-b）、ロード中はシークを保留する、位置が不安定な間は速度補正を止める（0.4.8）、ギャップ中は信号断の復帰を出さない
- 表と関数の入力は 4 軸の状態、出力は「この操作をしてよいか」。規則ごとに単体テストを持つ
- 段 2 では規則の中身を変えない（今の条件を写すだけ）

### 一時停止の持ち主の集合（v0.5.2、小さな変更）

§6 の 12（境界ホールドの解除が、ほかの持ち主が止めていても再生を再開する）だけを個別のラッチで直すと、6 つ目のラッチになる。そこで:

- 一時停止の持ち主を**集合（flags）**で 1 つ持つ（信号断・境界ホールド・ギャップ・プロジェクト復元・利用者）
- 各持ち主は自分のフラグを立てる／下ろすだけにし、**集合が空になったときだけ再開する**
- 持ち主ごとの「意味の統一」（誰が優先か等）は v0.5.3 以降。v0.5.2 では集合の導入までにする
- これは振る舞いを変える（12 が直る）。単体テストで赤を確かめてから入れ、v0.5.2 のリリースノートに書く

### 段 3: 寿命の食い違いを 1 件ずつ直す（v0.5.3、振る舞いを変える）

§6 の候補を、**まず再現する単体テストを書いて赤を確かめ**、1 件 1 コミットで直す。段 0 の表の「現状」の列をその行だけ書き換え、「意図」と一致させる。

## 4. 変えないもの

- 同期の判断（シークの判定、補正の計算、しきい値）
- ログの文言（E2E と解析スクリプトが読む）
- ギャップの状態機械（`GapFreezeHandler`）の中身。すでに enum で表されているので、段 1 のできごとを受ける入口を足すだけにする
- 公開 API・設定・環境変数

## 9. 段 1 の実装の記録（2026-09-25）

`src/TimecodeSyncPlayer/SyncLifecycleEvent.cs`。ログは `Sync lifecycle: {Event} source={Source}` の 1 行で固定。
実際の行は Serilog の表示で名前に引用符が付く（例 `Sync lifecycle: "FileLoad" source=load`）。突き合わせのスクリプトは引用符を含めて読む。

**できごと（§3 の一覧からの分け方）**: 今の消し方が入口ごとに違うものは、1 つにまとめると振る舞いが変わるので分けた。
