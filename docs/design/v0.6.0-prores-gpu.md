## 3. shim: `prores-gpu` プロファイル

### 3-1. 表

- `prores-gpu = { media "video/x-prores", parse なし, dec "proresd3d11dec", conv "d3d11colorconvert" }` を **GPU の群の末尾（av1-gpu の後、index 4）** に入れる。件数 10、CPU は index 5〜9
- GPU の群に置く理由: 「GPU が先、CPU が後」の並びを保つ（`prores-cpu` の直前に置くと、GPU と CPU が交互になり software モードの順番の意味が崩れる）。ProRes の素材では GPU の他の 4 つは media の前方一致で外れる（`video/x-h264` など）ので、順番による遅れは無い
- `shim_test` の表の固定（件数 10、`i >= 5` が CPU、復号順の期待）を直す。**期待が変わるのは件数と添字だけで、順番の規則は変えない**ことを試験の説明に書く

### 3-2. アダプタ（`adapter-luid`）

- D16-b（`decoder_matches_shim_adapter`）は d3d11 の既製デコーダの `deviceNdec` の名前の型に依存していて、`proresd3d11dec` には当てはまらない（`adapter-luid` の既定 0 は shim の LUID と一致せず、`decoder-adapter-mismatch` で飛ばされる見込み）
- `prores-gpu` だけ別の扱いにする: 連鎖を組むとき（`build_video_chain_static`）に要素を作った直後、**`adapter-luid` に shim のデバイスの LUID（`device_luid()`）を書く**。READY に上げた後に読み返し、違えば `decoder-adapter-mismatch` としてこの試行を失敗にして次へ進む
- D16（`adapter_supports_profile`）は GUID を持たない dec を常に真とするので変えない
- **プラグイン側の回答（Q4、2026-09-30、v0.1.0 のコードと実測）**:
  - 共有の `GstContext` がもらえればそのデバイスを使い、自分では作らない。自分で作るのは共有が見つからないときだけ（set_context → 下流・上流への context query → バスの NEED_CONTEXT → 無ければ自作して HAVE_CONTEXT）
  - `adapter-luid` ≠ 0 のときは、LUID が一致する context だけを受け入れる（一致しなければ無視して先へ＝自作になる）。0 ならどのデバイスでも受け入れる
  - 出力のプールは常にデコーダのデバイスで作る（下流の提案を使わない）。共有のデバイスを受け入れていれば、出力はそのデバイスのもの
  - 実測: `proresd3d11dec ! d3d11colorconvert` で、LUID が 0 でも指定ありでも、下流から context query で同じデバイスを受け取った
  - デバイスを持った後に `adapter-luid` を読むと、実際に使っているデバイスの LUID が返る
  - **反映**: 読み返しは **preroll の後（PAUSED に達した後）**に行う（start() は READY→PAUSED で走るので、READY の直後では早い）。そこで返る LUID は実際のデバイスの LUID なので判定の根拠に使える。出力バッファのデバイスの比較は段 1 の裏取りとして残す。shim の LUID を書く方針は維持する（Optimus で自作のデバイスに落ちるのを防ぐ）。「書かないと飛ばされる」のは shim 側の D16-b の話で、プラグインは書かなくても共有を受け入れる。段 1 で shim の context の配り方（同期ハンドラの応答か set_context か）を確かめ、自作に落ちていないことをログで見る
- **（回答の前に書いた未確定の記述。記録として残す）**: shim は `GstContext` で共有のデバイスを配っている。`proresd3d11dec` が (a) 配られたデバイスをそのまま使うのか、(b) `adapter-luid` から自分でデバイスを作るのか。(b) なら出力の D3D11Memory は別のデバイスのもので、`d3d11colorconvert` と appsink の共有リングで**デバイスをまたぐコピー**が起きうる（ゼロコピーにならない、または失敗する）。確かめ方: shim のログにデコーダの出力バッファのデバイスのポインタ（`gst_d3d11_memory` の device）と shim のデバイスを並べて出す。**判定の根拠は出力バッファのデバイスと shim のデバイスの比較**とする。`adapter-luid` の読み返しは、共有のデバイスを使う場合は書いた値がそのまま返るだけで「実際に使ったデバイス」の証拠にならないので、補助の記録に留める（TSP-Fable のレビュー (e)）。(b) だった場合の対処はプラグイン側に諮る（11 節の Q4）

- **段 1 の実機の結果（2026-09-30、開発機 RTX 3070、Debug、`agent-a-v060` の `e5ede83`、プラグイン v0.1.0、ProRes 422 HQ 4K 59.94）**:
  - `prores-gpu: context given via=set_context`、`out-mem d3d11=1 ... same=1`、`adapter-luid set=0x1178c read=0x1178c at=first-frame-wait`（RTX の LUID）→ **共有のデバイスのまま、同じアダプタで動く**（Q4 の回答と一致）
  - `first_frame_ms=13.3`、`load.summary total_ms=70.1 profile=prores-gpu`。再生は 2 秒あたり 120 フレーム（4K 59.94 に追いつく）。メタデータ行は `V:proresd3d11dec`
  - 出口の caps: GPU は dec-src `I422_10LE, colorimetry=2:0:0:0`（**訂正 2026-09-30**: 当初「素材に bt709 のタグを付けても unknown」と書いたが誤り。段 1 の素材は ffprobe で color_primaries・transfer・space・range とも unknown で、タグは入っていなかった。PATH の ffmpeg（ImageMagick に同梱の 4.2.3）は `-movflags +write_colr` を付けないと mov に `colr` を書かない。付けて作り直した素材は primaries・transfer・space が bt709）→ sink `BGRA, colorimetry=1:1:5:1`。CPU（`prores-cpu`）は dec-src・sink とも colorimetry の欄なし。両経路の変換器が行列を推定で決めるので、同じ推定になるかは絵の比較で確かめる（8 節）
  - フォールバック: プラグインなし → `chain factory failed` で即座に `prores-cpu`。DLL あり `.cso` なし → `Cannot initialize native D3D11 decoder` → `set-state-fail`（1.5 ms）→ `prores-cpu`（preroll の満了を待たない）
  - 落ち 1 件: `.cso` なしの 1 回目で、`prores-cpu` で開いた約 0.5 秒後に ucrtbase 0xc0000409。同じ時刻に同じツリーで担当のビルドが bin を書き換えていた（DLL 13:45:58・exe 13:46:14、落ち 13:46:06）。最終のバイナリで計 17 回（3 条件 × 5 ＋ 2）は落ち 0。ビルドとの重なりの可能性が高いが断定しない。以後の実機でも数える

### 3-3. 既定の有効・無効（ベンダーの門）

- shim が使っているアダプタ（shim のデバイスのアダプタ）の `DXGI_ADAPTER_DESC.VendorId` を、デバイスを作るときに保存する（いま捨てている値）。判定は shim 側で行う（**実際に復号に使うアダプタ**で決めるため。アプリの表示先のアダプタとは Optimus で違いうる）
- 判定は純関数 `tcs_prores_gpu_allowed(mode, vendorId)` を `include/` に置き、`--policy-only` で真理値表を固定する:

| mode | NVIDIA（0x10DE） | その他 | 不明（0） |
| --- | --- | --- | --- |
| auto（既定） | 使う | 使わない | 使わない |
| on | 使う | 使う（ログに 1 行「未検証のアダプタで ProRes の GPU 復号を使う」） | 使う（同じ 1 行） |
| off | 使わない | 使わない | 使わない |

- 使わないときは試行ループの先頭で `load.skip profile=prores-gpu reason=prores-gpu-<off|vendor> vendor=0x%04x` を出して次へ進む（D16 の skip と同じ形）
- mode の入口は 2 つ。環境変数 `TCS_PRORES_GPU`（auto / on / off、試験用。**設定より優先**）と、アプリからの設定（4 節）。shim はプレイヤーの作成時に環境変数を 1 回読み、値があれば setter の値を上書きする。どちらが効いたかをロードの最初に 1 行（`prores-gpu: mode=auto source=setting vendor=0x10de -> enabled`）
- software モード（`decodeMode=software`）のときは CPU の群が先に試されるので、`prores-cpu` が通れば `prores-gpu` には来ない（今の復号順のまま。`proResGpu` より `decodeMode` が勝つ）。SETUP に 1 行書く

### 3-4. フォールバック

- 全ベンダーで有効（決定 2026-09-25）。`prores-gpu` の試行が D34 のゲートを通らなければ（`caps-missing`・`preroll-timeout`・`chain-fail`・`decoder-adapter-mismatch`）、今のループがそのまま `prores-cpu` へ進む。新しい仕組みは足さない
- **last-good の扱い（11 節の Q2）**: いまは成功したプロファイルが last-good になり、次のロードで先頭に試される。`prores-gpu` が 1 回失敗して `prores-cpu` で開くと、以後のそのプレイヤーでは ProRes が CPU 側から試される（GPU に戻らない）。**変えない**（1 回失敗したアダプタ・ドライバで毎回 GPU を試して落ちるより、その回の起動の間は CPU に留まる方が安全側）。GPU 復旧（プレイヤーの作り直し）と再起動で戻る。**TSP-Fable の判定（2026-09-30、承認）**。SETUP の `proResGpu` の説明に「GPU の復号に 1 回失敗すると、その起動の間は CPU で復号する。GPU 復旧か再起動で GPU をまた試す」を 1 行書く（「有効にしたのに CPU のまま」の誤解を避ける）
- **`.cso` が欠けた型**（プラグイン側の回答 Q7）: 要素の作成は成功し、start()（READY→PAUSED）で RESOURCE/NOT_FOUND「cannot open shader bytecode …\prores_vld.cso」。preroll できない。この失敗が preroll の待ち（100ms×30）の満了を待たずに、バスのエラーで即座に次の試行（`prores-cpu`）へ進むことを段 1 で確かめる（待つなら ProRes のロードが毎回 3 秒遅れる）
- **壊れたフレーム（v0.2.0、Issue #1）**: CPU のパーサーが見つけた破損はそのフレームだけ捨て、GPU の非同期の検査で見つかった破損は最大 3 フレーム遅れて報告する（絵は出力済み）。どちらも GstVideoDecoder の `max-errors` に数え、既定（-1）ではバスに STREAM/DECODE の WARNING を出して続行する。非対応の形式・10 秒の時間切れ・Map の失敗・device lost は今までどおり止まる。
  **TSP-Fable の決定（2026-09-30）**: `max-errors` は既定（-1）のまま（ライブの用途では 1 枚の破損で止まるより続行が正しい）。WARNING は shim がログに出すだけで、画面に出さず、フォールバックもしない。ログは 1 ロードあたり最初の 1 件を行で出し、以後は件数だけを `load.summary` か終了時の集計に足す（他の GPU デコーダの WARNING と同じ経路にできるなら揃える）
- （v0.1.0 の記述）プラグインの既知の制限「エラーの報告が最大 3 フレーム遅れる」: ロード時はゲートが最初のフレームを待つので影響は小さい。再生中の復号エラー（ロードの後）はフォールバックせず、今のバスのエラーの扱い（他の GPU デコーダと同じ）に任せる。既知の制限に書き写す

### 3-5. デコーダ名

- `prores-gpu` の `decoder_name` は `proresd3d11dec`（表の名前）。メタデータ行は `V:proresd3d11dec`、CPU なら `V:avdec_prores` で、どちらで開いたかを画面で見分けられる（決定 2026-09-25 の「確認」）
- `CodecAdvice`: `prores` を含めば「可」のまま。**利用者の決定（2026-09-30、Q3）: v0.6.0 では「可」のまま。RTX で固定の一式が合格した版で「NVIDIA では推奨」に上げる**（SETUP の「素材の推奨」も同じ版で直す）。当初の問い: GPU で開けたときに「推奨」へ上げるかは 11 節の Q3（SETUP の「素材の推奨」を ProRes の推奨側へ戻す計画と関わる）

## 5. フォールバックの判定と記録

- shim のログ（既存の行に足すだけ）:
  - 試行ごと: `load.attempt ... profile=prores-gpu result=<ok|caps-missing|preroll-timeout|chain-fail|skip>`（既存）
  - 門: `load.skip profile=prores-gpu reason=prores-gpu-off|prores-gpu-vendor vendor=0x....`（新）
  - アダプタ: `prores-gpu: adapter-luid set=<shim の LUID> read=<読み返し>`（新、試行ごとに 1 行）
  - 結果: `load.summary ... profile=prores-gpu|prores-cpu`（既存）
- アプリのログ: ProRes の素材を CPU で開いたとき、理由（shim の最後の skip か失敗の reason）をアプリのログに 1 行 `ProRes: CPU で復号（reason=...）`。**同じ理由は起動の間に 1 回だけ**（ロードのたびに出さない。守りすぎの記録を増やさない）
- 画面: メタデータ行の `V:` で分かる（3-5）。警告の表示は足さない（auto で NVIDIA 以外なら CPU が正しい動作なので、警告にしない）
- 試験の判定: E2E とランナーの結果 JSON に「ProRes の素材のロードの profile の内訳」を足す（`prores-gpu` / `prores-cpu` の数）。RTX で `prores-cpu` が 1 件でもあれば FAIL。**この規則は標準の一式と重い素材の回だけに当てる**（8 節のフォールバックの試験 (a)(b)(c) では `prores-cpu` が正解。TSP-Fable のレビュー (b)）

## 6. 既知の制限（v0.6.0 のリリースノートと SETUP）

- ProRes の GPU 復号は NVIDIA（RTX 級）で検証した。他のベンダー（AMD・Intel）は未検証のため、既定（自動）では CPU で復号する。設定で「有効」にできるが、サポート対象外
- 壊れたフレームは捨てるか、そのまま出して続行し、ログに WARNING として記録する。GPU の検査で見つかる破損の報告は最大 3 フレーム遅れる（そのフレームの絵は出力済み。プラグインの既知の制限）
- VC++ 再頒布パッケージ 14.50 以上が要る（インストーラーは自動で入れる。zip の利用者は手で入れる。入っていないときは CPU で復号する）

- **RTX で `prores-gpu`**: shim のログの profile と adapter LUID（出力のアダプタと一致）。結果 JSON の内訳で `prores-cpu` 0
- **絵の一致**: 同じ位置の 1 フレームを `prores-gpu` と `prores-cpu`（`TCS_PRORES_GPU=off`）で取り、参照フレームの判定（既存の E2E の仕組み）で差が許容内。プラグイン側の実測（平均の差 0.3 以内）を基準にする。
  **色の実測と比べ方（2026-09-30、Gst-ProRes の実測を TSP-Fable が転送）**: 段 1 の `2:0:0:0` は素材のヘッダーの色が未指定（`colr` なし）だったためと推定（`ffprobe` の color_primaries / color_transfer / color_space で確かめる）。v0.2.1 は未指定の欄を既定値で埋める。1.28.2 の `d3d11colorconvert` は `2:0:0:0` を同じ既定で推定していたので、GPU 経路の BGRA の画素値は v0.2.0 と v0.2.1 で同じ（修正の意味は推定を caps に明示すること）。GPU と CPU の BGRA の差（試験パターン）: 4K は平均 0.584・p99 14・最大 129、SD は平均 0.166・最大 2（4K の差はクロマの補間の違いが鋭い輪郭に出たものと推定）。
  **反映（TSP-Fable）**: (1) 「平均の差 0.3 以内」は試験パターンの 4K では超える。しきい値は実素材（検証機の M1 か開発機の実写系）で GPU と CPU を比べた分布で決め、合否は平均と p99 の 2 つで見る（最大値は輪郭の 1 画素で跳ねるので使わない）。(2) 色の比較の素材は色のタグ付き（`-color_primaries bt709 -color_trc bt709 -colorspace bt709`、できれば `colr`）で作り、タグ無しはフォールバックの確認にだけ使う。(3) 参照フレームの判定（同期の合否）は、GPU 経路の画素差が判定の許容に入るかを 1 回確かめてから使う
  **注意（TSP-Fable のレビュー (a)）**: プラグインは色タグの無い素材を `colorimetry=2:0:0:0` で出す（v0.1.0 の既知事項）。`prores-cpu`（`avdec_prores → videoconvert`）と GPU（`d3d11colorconvert`）でレンジ・行列の解釈が違えば、系統的な色の差で 0.3 を超えうる。比べる前に両経路の出口の caps（colorimetry・range）をログで並べる（段 1 で出す）。差があるときは「同じ colorimetry を明示してから比べる」か「差を記録して合否から外す」のどちらにするかを、段 1 の結果で決めて TSP-Fable に諮る
- **フォールバック**: (a) `TCS_PRORES_GPU=off` で `prores-cpu`、(b) プラグインのフォルダを外した構成で `chain-fail → prores-cpu`、(b2) DLL はあり `.cso` が無い構成で start() のエラー → `prores-cpu`（待ち時間も記録。別の失敗の経路）、(c) 検証機の内蔵 AMD（出力先なしの既定）で auto → `prores-cpu`（`reason=prores-gpu-vendor`）。`on` の強制は動作確認だけで合否に入れない
- **検証機のハイブリッド GPU**: 出力を RTX に置いたとき、`adapter-luid` が RTX の LUID になり `prores-gpu` で開くこと（実装の後、TSP-TestMachine に依頼）
- **壊れたフレーム**（TSP-Fable の決定 5、2026-09-30）: 破損を含む ProRes（ffmpeg で数バイト壊した 20 秒の素材か、プラグインの smoke の素材）を `prores-gpu` でロードし、止まらずに WARNING が記録されること。合否は「止まらない」「同期の着地・追従が破損のない回と同じ範囲」
- **起動**: プラグインが 1 つ増えるとレジストリの作り直しが要る。インストール直後の最初の起動の時間と `ui.heartbeat` の最初の遅れを v0.5.4 と比べる（v0.5.4 の既知の間欠「インストール直後の最初の起動で数秒反応しない」の悪化が無いこと）
- **同期**: ProRes 4K60 の `prores-gpu` で C-1・L-1 の着地と追従の誤差を `prores-cpu` の回と並べる（v0.4.7 の既知の制限「ProRes 4K60 のロード・シーク遅れ」が GPU で消えるか。消えなくても合否には入れず記録）
