# 出力フレームの生成と公開の分離

## 目的と今回の範囲

通常動画、Black、Frozen、GapFreeze、Buffered の画像を、寿命が明確な共通の出力フレームとして確定してから各出力へ渡す。画像を選ぶ処理が WPF Bitmap 更新や Spout 送信を直接呼び出す構造を解消する。

最初の段階では mpv 描画専用スレッドと、UI スレッド上の Bitmap 更新・Spout 送信・プレビュー処理を維持する。将来の Spout スレッド分離とクリップ内の時間位置に基づく効果処理に備えるが、この段階にはフェード、効果更新タイマー、推測した画像時刻を追加しない。

基点は `refactor/session-lifecycle` の `b66d12b`。公開順序の変更理由と既存測定の限界は [全画面・Spout併用時の公開順序の改善](OUTPUT-CONTENTION-FIX-2026-09-09.md) に記載されている。

## 処理の境界

```text
mpv 専用スレッド
  mpv SW 描画 → 元 snapshot → 最新1枚の mailbox
                                      ↓
UI スレッド                       世代・Gap・順序の確認
                                      ↓
  保存画像／黒画像 ────────────→ 出力フレーム生成
                                      ↓
                               共通の公開処理
                             ┌────────┴────────┐
                        全解像度 Bitmap       Spout
                             ↓
                  プレビュー（縮小・間引き）
```

出力フレーム生成は画像の選択と画素の所有を担当し、WPF と Spout に依存しない。公開処理は確定済み画素を消費する。FrameRenderer は Bitmap の更新を担当する。

プレビューは引き続き、公開済みの全解像度 Bitmap を同じ UI スレッド上で読み取る。出力フレームを別の待ちキューで保持しない。通常30Hz、全画面中10Hz、最大960×540という既存の制限を維持する。

## フレーム所有権

- 幅・高さ・画素・画像種別を一つの出力フレームとして扱う。消費者は画素を書き換えない。
- 通常フレームは元 snapshot の所有権を lease として保持し、出力フレーム化のための全画素コピーを追加しない。
- Black は出力側が所有するゼロ画素を作る。可変の作業バッファを黒く塗ってそのポインタを送信する方式には依存しない。
- Frozen、GapFreeze、Buffered は選択時点の画素を所有コピーにする。元バッファの再利用・クリア・解放が出力フレームを変化させない。
- 最後の所有者が終了するまで配列をプールへ返さない。破棄した所有者からの新しい lease 取得を拒否し、二重 Dispose で返却数を増やさない。
- Spout へ渡すポインタは共通出力フレームの画素を送信呼出し中だけ pin して得る。画素配列と対応関係を保証できない外部ポインタを別引数として受け取らない。
- 送信先から戻った後に pin を解除する。成功・例外のどちらでも、所有フレームは使用範囲の終了時に解放する。

スレッド間の自由な同時利用をこれだけで保証するものではない。今回は生成・公開を既存の UI gate 内で同期実行する。将来並行公開する際は各処理の lease と、両処理の完了・終了処理を追加で管理する。

## 画像選択と既存挙動

| 入力／状態 | 選択と公開 |
| --- | --- |
| 通常 | 世代・sequence確認済みの元 snapshot を使用する |
| Black | 既存のサイズ解決規則で黒画像を作る |
| Frozen | 有効な保存画素を使用し、使用できない場合は既存どおり Black へフォールバックする |
| GapFreeze | 確認済みのキャッシュ画像とその寸法を優先する。確認・Hold の判断は既存 Gap ロジックが担当する |
| Buffered | 完全な画素配列から出力フレームを作る。Bitmapだけを更新する用途は、ポインタの有無ではなく公開側の明示的な選択で表現する |
| Hold | 新しい画像を公開しない |
| capture-only | 元画像を保存する処理だけを行い、公開はしない |

無効寸法や不足した画素の拒否、Gap の再確認、`afterFrameProcessed` の呼出し条件を維持する。Freeze 保存は引き続き元画像の保存であり、Black などの出力結果で保存画像を置き換えない。

今回の通常出力は元 snapshot と同じ画素なので、既存の公開後 Freeze 保存はその画素を使用できる。将来効果を導入する際は、Freeze 保存へ渡す元 snapshot と、効果適用後の出力フレームを明示的に分ける。公開フレームの画素をそのまま Freeze 保存へ流し続ける変更にはしない。

## 公開順序と診断

通常動画で全画面と Spout が有効な場合だけ、現在の併用順序を維持する。

- Bitmap の `TryLock(0)` 成功時はコピー、Spout 送信、Unlock。
- busy 時は Spout 送信、Bitmap Lock、コピー、Unlock。
- 通常の単独経路と特殊画像は、Bitmap 更新、Spout 呼出し、プレビュー通知の順序を維持する。通常経路の統計記録と Freeze 保存の位置も維持する。

Bitmap Lock 内へ新しいログ callback やフレーム生成を持ち込まない。例外時の Unlock、元例外と Unlock 例外の保持、再入拒否、保留プレビュー取消を維持する。

通常フレームの session／generation／sequence による trace 結合と、Bitmap 公開時刻が Unlock 後であることを維持する。特殊画像へ架空の mpv 描画 sequence を付けず、通常フレームの描画統計や初回表示ログに混ぜない。画像種別の既存診断も維持する。

## シーク・停止・終了

この段階では新しいキューや worker を追加しない。既存 RenderSession の世代、公開 gate、mailbox、sequence の逆行防止を使う。

元 snapshot を mailbox から取り出した処理が待機中でも、他の描画による置換でその画素を返却しない。出力フレームが lease を保持している場合も同様に扱う。Black や Freeze の生成時には、可変バッファへの参照を公開側へ持ち越さない。

既存の native worker 停止、render context 解放、mpv 解放の順序を維持する。現在の同期公開から戻る前に、出力フレームの pin や lease を解放しない。

## 次段階の Spout スレッド実証

以下は基盤実装時の当初案。後続の設計議論で、両者の完了を待つ方式は不採用となった。現在の合意は [タイムライン評価・キャンバス合成・周期出力の設計](OUTPUT-PIPELINE-DESIGN.md) を参照する。各出力が独立して最新の合成画像を目標60Hzで公開する方式を検討する。

当初は、Spout の初期化・送信・失敗処理・破棄を一つの専用スレッドへ移し、同じ出力フレームの Spout 送信と UI Bitmap 更新を並行実行して両者の終了後に次の組を開始する方式を候補としていた。

検討を残す事項:

- 実際に使用する Spout/D3D 資源のスレッド要件と、生成から破棄までの所有。
- 実行中フレームと新世代・Black・停止命令の順序。開始済みのネイティブ送信は取消済みと扱わない。
- UI を待つ専用スレッドと、専用スレッドを待つ UI の循環待ち防止。
- 出力別に最新フレームを選択する必要性。当初の検討事項であり、現在は出力間の画像差・時刻差を許容するベストエフォート方式で合意している。
- 既存の GPU 完了待ち期限はネイティブ呼出し全体の最大所要時間を保証しない。待機期限超過を使用中資源の強制解放理由にしない。

## 評価

この段階の合格条件は機能・寿命・公開順序の回帰がないこと。60fps 達成や GPU 競合の改善は主張しない。

管理テストで、lease の最終返却、Dispose と lease 取得の境界、元バッファ変更からの独立、通常の追加画素コピーなし、例外後の解放、Bitmap／Spout の画素一致、画像選択と Gap／trace／プレビューの既存契約を確認する。Windows ネイティブ PowerShell の Debug ビルドと非E2Eテストで検証する。

スレッド実証で実機比較を行う際は、現在版と候補を固定条件で直列実行する。公式 WinSpoutDXreceiver を使い、専用設定・新規ログ先を使用する。既存ログ・通常設定・他アプリを保持し、自分が起動したプロセスだけを終了する。WPR/UAC を伴う GPU 記録採取は自動実行しない。

評価値は公開頻度だけでなく、snapshot準備から各公開までの時間、間隔 p95／p99、同じフレームの出力時刻差、置換数、UI 応答、CPU、継続中のメモリ推移とする。Spout 呼出しの復帰と送信成功も区別する。受信画像の一意性、物理4K60表示、実表示の時間差は、それぞれを直接検証できた範囲だけで報告する。

## 今回の実装と検証結果（2026-09-09）

- `OutputFrame`／`OutputFrameFactory` を追加し、`RenderSession` の通常・特殊画像を `RenderFramePublishPipeline.Publish(OutputFrame, ...)` へ統合した。`FrameRenderer` から画像選択、可変バッファ管理、Spout 直接送信を除去した。
- `RenderedFrameSnapshot.Retain()` で同じ配列の寿命を保持する。元snapshotの破棄後も取得済みleaseは有効で、最後のlease終了時だけ返却する。
- Bitmapだけを更新する特殊画像は `sendSpout: false` で明示する。この指定を通常画像に渡した場合は送信前に拒否する。`spoutEnabled: false` の既存通常経路は、従来どおり無効なSpout出力への呼出しを記録する。
- 親エージェントが設計・ソース／テストレビューと全体検証、サブエージェントが製品コード・関連テストの実装を担当した。
- Windows PowerShell の `dotnet build src/TimecodeSyncPlayer/TimecodeSyncPlayer.csproj --configuration Debug --no-restore` は警告0・エラー0。
- `dotnet test tests/TimecodeSyncPlayer.Tests/TimecodeSyncPlayer.Tests.csproj --configuration Debug --no-restore --filter 'Category!=E2E'` は1,503件成功、失敗0・skip0。追加の15件と、製品からなくなった入口に対するテスト1件の削除により、前回1,489件から差引14件増加した。
- 結果: [非E2EテストのTRX](../TestResults/output-frame-foundation-20260909-101339/non-e2e.trx)。実行時はこの新規結果ディレクトリを指定し、既存結果へ上書きしていない。検証後の製品コード変更は所有者を説明するコメント修正のみ。
- `git diff --check` は問題なし。未追跡 `AGENTS.md` は内容・未追跡状態を保持した。コミットは作成していない。

アプリや受信プロセスを起動する実機試験、ネイティブ Spout 送信、性能測定は今回実施していない。追加の所有コピーが発生する特殊画像を含め、実機の速度と連続運転への影響は未測定。フェードと Spout のスレッド分離は次段階の対象である。
