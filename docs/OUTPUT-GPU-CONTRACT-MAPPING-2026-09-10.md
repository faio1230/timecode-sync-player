# 試作で確定した出力契約と本体所有権の突き合わせ

2026-09-10、[保持区間・再取得実証](GPU-MUTEX-HOLD-RETRY-RESULTS-2026-09-10.md) の結果を、本体の現行所有権（`OutputFrame`／`RenderedFrameSnapshot`／`RenderFramePublishPipeline`／`SpoutFrameTransfer`）と照合した設計メモ。実装変更は含まない。

## 現行本体の所有権（コードから確認した事実）

- mpv専用スレッドが `RenderedFrameSnapshot`（pool配列の所有コピー）を `LatestRenderedFrameMailbox` へ最新1枚として置く。古い1枚は置換時に返却される。
- UIスレッドが `_gate` 内で mailbox から取り出し、世代・Gap・sequence逆行を確認後、`OutputFrame.FromSnapshot`（`Retain()` による同一配列の別lease、画素コピーなし）を作り、`RenderFramePublishPipeline.Publish` を同期実行する。Bitmap更新→Spout送信→プレビュー通知の順で、全画面＋Spout時だけ `TryLock(0)` の結果で順序を入れ替える。
- Spout送信は `SpoutFrameTransfer.SendImage` がUIスレッド上で、送信アクセスmutexを最大100ms待ち、`SendImage`（CPU画素）後にGPU完了を最大100ms確認する。どちらかが超過すると例外となり、`SpoutOutput` は送信機を無効化する（既知の単発無効化問題、今回の範囲外）。
- 出力は「同じ `OutputFrame` を1本の同期呼出しで全出力へ渡す」構造で、出力ごとの最新画像選択や周期は存在しない。

## 試作で確定した契約（実測に基づく事実）

| 項目 | 試作の実装と結果 |
| --- | --- |
| 合成画像の所有 | 3枚のpool。合成側は最新でなく読者0の領域に書き、GPU完了後に最新へ置換。読者はleaseを取り、GPU使用完了までleaseを返さない |
| 出力の独立 | 全画面（GPU worker）とSpout（専用worker・別デバイス）が各自の周期で最新leaseを取る。両者の完了を待たない |
| 読み取り側の排他 | 共有textureのkeyed mutex（key 0、待ちなし取得）。表示側の保持幅は平均0.1〜0.25ms・最大約1ms。コピー失敗は測定分解能の範囲で全件がこの保持区間に対応 |
| 失敗時の扱い | 失敗した出力はその枠を飛ばさず、保持画像を再送する。`signal` では返却通知を最大 min(4ms, 次回予定までの残り) 待って最新画像を1回だけ再取得する。負荷条件で再送175／354→63／33回、年齢最大71／121→約22ms。通常条件で退行なし |
| 位相 | 表示側の取得時刻は起動ごとに0.3〜10msの範囲で変わる（tick約0.3ms、readyは通知次第）。固定位相で競合を避ける設計は起動依存になる |
| 送信待ち | Spoutの送信アクセスmutex要求は8msを上限に、次回予定時刻を期限とする。期限超過は飛ばし、資源は無効化しない |
| 終了 | 新規処理停止→送信workerのjoin→送信側が開いた共有資源の解放→合成側の解放。待機中も強制終了を選べる |

## 対応表

| 試作の要素 | 本体の現行要素 | GPU段階で維持／置換 |
| --- | --- | --- |
| `LatestPool`（3枚、lease、GPU完了） | `LatestRenderedFrameMailbox`（1枚）＋ `RenderedFrameSnapshot.Retain()` | leaseの「最後の所有者が返す」「破棄後の新規lease拒否」は同じ契約。枚数は出力数と保持時間から算定し、CPU側1枚では出力独立にできない |
| 出力ごとの最新取得と周期 | なし（UI gate内の同期公開1本） | 置換対象。各出力は合成済み画像の寸法・公開番号・寿命だけを扱い、タイムライン判断を持たない（合意済み） |
| keyed mutex（別デバイス間） | なし（CPU画素をpinしてSendImage） | Spoutを別デバイス・別スレッドにする場合のみ必要。同一デバイス内の全画面はimmediate contextの直列化で足りる |
| 失敗→返却通知後の1回再取得 | なし | 採用候補。固定位相や固定待ちに依存しない構造として設計に持ち込む |
| 送信mutex要求8ms・期限=次回予定・無効化しない | 100ms待ち・超過で無効化 | 置換対象。ただし単発無効化問題の修正自体は別課題 |
| Freeze保存 | 公開後に元snapshot画素を保存（`_copyFreezeFrame`） | 通常映像レイヤーの合成前画像を保存対象にする。カード合成後や拡大縮小後の画像を保存しない（合意済み） |
| プレビュー | 公開済みBitmapを縮小・間引き | 既存制限維持。GPU化は全画面・Spoutの後 |
| 終了順序 | native worker停止→render context→mpv | 出力worker停止・join→共有資源→デバイスの順を追加。UIと出力workerの循環待ちを避ける |

## 本体へ接続する前に決める事項

1. 出力workerの所有者と、UIスレッド（タイムライン状態・操作）との受け渡し。UIが出力workerを同期待ちしない構造にする。
2. 合成画像poolの枚数。全画面1面＋Spoutで、各出力が1枚ずつGPU完了まで保持し、合成が1枚書く前提なら3枚で足りた（peak occupied 2）。3面時は再算定。
3. Spoutを別デバイスにするかどうか。別デバイスならkeyed mutexと再取得契約が必要。同一デバイス・別スレッドは immediate context の共有になるため採らない（D3D11の直列化要件）。
4. 送信失敗・期限超過時の無効化をやめ、保持画像再送と手動再試行に変える範囲。単発無効化問題の扱いと分けて合意する。
5. mpv画像のGPUアップロード経路（CPU `OutputFrame` → texture）。次の段階の独立実証で、1080p／4K・60Hzのアップロード時間と合成への影響を測る。`hwdec=no` は維持。

## 次の実証（案）

CPU画像アップロード段階: 試作に `--source cpu-upload` を追加し、CPUで生成した画像番号付きBGRA配列（将来のmpv画像と同じ形）を毎枠 `UpdateSubresource`／staging経由でsourceへ載せ、合成・全画面・Spoutを現行条件（split・位相4ms・mutex 8ms・`signal`・tick）で測る。評価はアップロード時間の分布、合成開始遅れ、公開頻度・画像年齢、CPU。合格条件は合成60Hz維持と、GPU生成時と比べた画像年齢増加の説明可能性。mpv接続はその後。

## 追記（2026-09-10 夜）: 走査時刻の計測後

表示通知直後の Present は走査基準で約1フレーム遅いことが分かった（[計測結果](GPU-SCANOUT-STATS-RESULTS-2026-09-10.md)）。対応表の「表示通知駆動（vsync）」行は「vblank 位相基準で次の vblank 直前に最新画像を Present（`vblank`、実証予定）」に置き換える。本体契約の候補: 表示は自分の vblank 時計を持ち、合成・Spout はそれに従属しない。表示遅延の目標は margin（数ms）以内で起動位相に依存しない。

## 追記（2026-09-10 深夜）: vblank 実証後

対応表の「vblank（実証予定）」行は実証済みに更新する。本体契約の候補: (a) 表示は自分の vblank 時計を持ち、予測 vblank − margin で最新画像を Present、失敗した枠は次の vblank へ、(b) 目標到達済みの表示は合成より優先、(c) 合成 tick は主表示の vblank 位相に整列してよい（周期は60Hz固定、Spout は合成に対する位相のまま、他画面は位相差の年齢を許容）。(c) は未実証。

## 追記（2026-09-11）: 合成位相整列後の本体契約候補（出力側の確定版）

- 合成画像 pool（3枚、lease、GPU 完了後に公開）＋ 共有フェンス（書き手→読者）、読者同士は排他しない。
- 表示: DXGI 統計で vblank を予測し、`vblank − margin` に最新画像を Present。目標到達済みの表示は合成より優先。1 vblank 1表示、失敗は次の vblank。
- 合成: 主表示があればその vblank に `vblank − margin − lead` で整列（周期は主表示に追従、slew で逐次補正）。なければ自由走行 60Hz。
- Spout: 合成に対する位相（4ms）で独立に最新画像をコピー・送信。送信アクセス mutex は期限付き、失敗は保持画像の再送。
- 待ち: 高分解能 waitable timer。CPU 側の GPU 完了待ちは lease 返却のために残す。
- 別 worktree の GStreamer 置き換えは、この出力契約に対して「再生位置に対する最適な GPU 画像を供給するソース」として接続する。ソース側の契約は本文の「本体へ接続する前に決める事項」1・5 を参照。
