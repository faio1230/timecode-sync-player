## 3.6 既知の仕様: 表示の落ちが 40 秒に数回起きる（2026-09-15、利用者の判断で仕様として残す）

### 何が起きるか

**全画面表示中、40 秒あたり数回、1 枚だけ提示機会を飛ばす。**
そのフレームは 1 周期分（約 16.7ms）長く表示され、次のフレームに置き換わる。
連続して飛ぶことは無く、飛ぶのは常に 1 枚だけ。

**合格条件（V8）**: 40 秒あたりの落ちが **5 回以下、かつ連続なし**。

> **指標を訂正した（2026-09-15）。** 従来は `present.scanout` の `SyncQPCTime` 間隔 > 25ms で数えていたが、
> これは統計取得タイミングの揺れを含み、**実際の表示欠落を約 2 倍に過大計上していた**。
> 主指標は `PresentRefreshCount` の差が 2 以上（＝実際に飛ばしたリフレッシュ）とする。
> 集計は `scripts/GpuOutputProbeHarness/scanout_drop_summary.py`。

### 実測

同一セッション内で 3 条件を交互に回した結果（2026-09-15、7 run）:

| 構成 | 旧指標 `SyncQPCTime` 間隔 > 25ms | **主指標 `PresentRefreshCount` の飛び** |
| --- | ---: | ---: |
| 優先度なし（**v0.4 の既定**） | 4 / 2 / 2 | **2 / 2 / 1** |
| MMCSS を既定 ON | 2 / 2 | **1 / 2** |
| MMCSS を環境変数で明示 | 1 / 3 | **1 / 1** |

**3 条件に差は無い。** 以前に「MMCSS で 0〜3 回に減る」「既定 ON にすると 6〜9 回へ悪化する」と
読んだ run 群は別セッションのもので、**交互に回すと再現しない**。セッション固有の何かだったが未特定。

**MMCSS の採否は要検討**（2026-09-16、第三者の意見を踏まえ利用者判断で保留）。
現状の既定は優先度操作なしで、それで基準を満たしている。MMCSS の実装はブランチ
`codex/v8c-thread-priority-20260915` に残してあり、観測スクリプトの判定値の訂正（`280c327`、
MMCSS 中の `GetThreadPriority` は相対 15）も同ブランチにある。
落ち同士は最も近くても 25 枚（約 0.42 秒）離れており、連続は観測されていない。

### 原因

**OS のスケジューリングで出力スレッドが数 ms 待たされ、vblank までの余裕を使い切るため。**

- 落ちた tick の合成は**ほとんど予定どおりに始まっている**（起床遅れ 0.2〜0.6ms）。vblank まで約 5ms の余裕があった
- **合成の重さではない**。ProRes の CPU デコードでも、外部 CPU 負荷 12 本でも落ちは増えない
- **アプリ固有ではない**。mpv でも同じ頻度で起きる（3〜5 回 / 40 秒）
- **出力スレッドの優先度を上げても減らない**（上表。MMCSS は効果が確認できなかった）

### なぜ直さないか

**原因がアプリの外側にあり、この環境では両バックエンドとも 0 を達成できない。**
スレッド優先度での対処も効かないことが確認できた（上表）。
利用者の判断で**既知の仕様として残す**。

### 将来の対処の筋道（未検証の候補）

現在の提示は「**次の vblank の時刻を予測し、タイマーでそこまで待つ**」設計
（`OutputEngine` の `vblankTimer.WaitUntilOrStop`）。**起床がタイマー由来なので、OS の遅れをそのまま受ける。**

**OS の起床を待たずに表示側の信号で駆動できれば、この余地は消える可能性がある。** 候補:

| 候補 | 現状 | 見立て |
| --- | --- | --- |
| swapchain の **latency waitable object** で歩調を取る | **既に作ってある**（`SwapchainTarget.cs`、`FrameLatencyWaitableObject`）。ただし即時 Present のタイムアウト付き待ちにしか使っていない（`OutputEngine.cs:1339`） | タイマーではなく**表示パイプラインが起こす**ので、予測とタイマー起床を経路から外せる可能性 |
| `IDXGIOutput::WaitForVBlank` | 未使用 | vblank イベントで直接起きる。ただしこれもカーネル待ちなのでスケジューラの影響は残りうる |
| 合成リードを広げる | 現在約 2.5ms（自動調整） | OS を外すのではなく余裕を増やすだけ。遅延と引き換え |

**いずれも未検証。** 「余地が見えたらそこで対処する」という方針（利用者、2026-09-15）。
**着手するなら、まず latency waitable での歩調取りを試すのが筋**（既に生成済みで、追加の依存が無いため）。

7. **D9: 本物の GPU デバイス消失（TDR）から shim を復旧させるか**（2026-09-16、D8 の調査で判明）。

   死んだ資源への `Signal` でプロセスが落ちる（D8 の二次症状と同じ）。案: shim に `tcs_player_device_removed_reason` を足し、
