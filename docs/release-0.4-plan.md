## 3. リリースノート草案（v0.4.0）

### Added
- GStreamer による再生バックエンドと GPU 合成出力を**既定**にした。D3D11 の共有リングでデコード済み
  テクスチャを直接受け取り、合成・全画面表示・Spout 送信まで GPU 上で完結する
- CPU デコードのコーデック（ProRes ほか）も `d3d11upload` で同じ経路に載せ、リースの扱いを統一
- 音声付き素材の再生（S1）
- MPEG-TS のシークを自前のキーフレーム着地＋再基準化で正確にした（S3）

### Changed
- 既定の `backend` が `1`（Gstreamer）、`outputBackend` が `1`（Gpu）になった。
  従来の mpv／CPU 経路は `settings.json` で `backend=0` / `outputBackend=0` に戻せる（v0.4 では残す）
- パイプラインクロックをシステムクロックに固定し、音声シンクはそれにスレーブする（S3 の副作用）

### Fixed
- 音声トラック付き MP4 が読み込めなかった（S1）
- ProRes ほか CPU デコードのコーデックが読み込めなかった（S2）
- MPEG-TS でシーク後にフレームが数秒届かなかった（S3）

### Known issues（**要判断**、下記 4 参照）
- mpv×Gpu の 4K で合成 p99 が 2.94ms（表示は 59〜60/秒を維持。退避経路のみ）
- 4K 主画面を出力先にすると 40 秒あたり数フレームの落ち（専用ディスプレイ推奨）
- トラック切替時に稀に 100ms 以下の音切れ（60 分試験で 12 回中 4 回）

## 3.5 退避経路の選択肢（V3 の結果次第、判断は利用者）

v0.4 は当初「mpv を完全除去し、退避は GStreamer 内のデコード方式切替が担う」方針だが、
**V3（LTC 同期の精度）を出荷の門とする**。`docs/prompts/2026-09-13-V3-seek-breakdown.md` の
切り分けの結果、GStreamer の回復時間が予算（シーク p95 250ms 以下、ギャップ再入 p95 500ms 以下）に
届かない場合に備え、**選択肢として次を残す**:

- **案 X: mpv を退避経路として 1 リリース残す**（当初計画に戻す）。
  既定は GStreamer×Gpu に切り替えるが、`backend=0` で mpv に戻せる状態を v0.4 では維持し、削除は v0.5 以降。
  この場合 V7（mpv×Gpu×Spout）の条件未達（4K の合成 p99 2.94ms）が再び論点になる。
- **案 Y: 予定どおり mpv を除去**し、退避はデコード方式切替のみ。

**判断は利用者が行う。** 親は V3 の数字と、届かない場合の原因・見込みを揃えて提示する。

## 4. 出荷前に利用者の判断が要る事項

1. **V7（mpv 4K の合成 p99 2.94ms）**: 退避経路のために実装工数を割くか、退避経路に限り基準を分けるか
2. **V8（4K 主画面の落ち）**: 「落ち 0」を主画面にも求めるか、出力先は専用ディスプレイ前提とするか
3. **V6 のトレース上限**: 完全合格にするならトレース上限の可変化か間引き記録が要る
4. **V3／V4 の実施時期**: ケーブルループの接続と現場プロジェクトの提供が前提
5. **現場素材の一覧**: V1 の表に加える。mpv が読めて GStreamer が読めない素材をゼロにするため（v0.5 の撤去判断の根拠）
