## 3. リリースノート草案（v0.4.0）
> **既知の仕様として記載すること**: 全画面表示中、40 秒あたり数回 1 枚だけ提示機会を飛ばす
> （連続しない、飛ぶのは常に 1 枚）。原因は OS のスケジューリングで、mpv でも同様に起きる。
> 詳細は「3.6 既知の仕様」。


### Added
- GStreamer による再生バックエンドと GPU 合成出力を**既定**にした。D3D11 の共有リングでデコード済み
  テクスチャを直接受け取り、合成・全画面表示・Spout 送信まで GPU 上で完結する
- 型付きの再生 API（`IPlaybackApi` / `PlaybackResult` / `IRenderUpdateSource`）を追加し、
  文字列コマンドとプロパティ名をアプリの境界から排除した
- CPU デコードのコーデック（ProRes ほか）も `d3d11upload` で同じ経路に載せ、リースの扱いを統一
- 音声付き素材の再生（S1）
- MPEG-TS のシークを自前のキーフレーム着地＋再基準化で正確にした（S3）
- LTC の fps モード（Auto / Fixed 24・25・29.97・30）と同期オフセット（`syncOffsetMs`、±1000ms）
- 同期補正モード（Smooth / Jump）。着地直後 1.0 秒は Smooth の上限を ±20% にして収束を早める（T9）
- サンプル時計（`TCS_LTC_SAMPLE_CLOCK`、既定 on）。LTC の時刻を音声サンプル位置から出した
  フレーム終端で評価する（T2）
- 解像度変更に共有リングを追従させ、世代（ring epoch）で開き直す（D8）

### Changed
- **mpv を除去した。** 再生は GStreamer のみになり、`backend` 設定は無くなった。
  退避は `decodeMode`（`hardware` / `software`）で行う
- **CPU 合成を除去した。** 出力は GPU 合成のみで、`outputBackend` の既定は `1`（Gpu）。
  `0`（Cpu）は無視して警告ログを出す（設定ファイルは書き換えない）
- ランタイム名を含む型名を役割名へ整理した（旧 `IMpvApi` ほか）
- V3（LTC 同期精度）の正式な解析を sample 解析（フレーム終端基準）にした
- パイプラインクロックをシステムクロックに固定し、音声シンクはそれにスレーブする（S3 の副作用）
- 終了手順の段名からランタイム名を外した（「GStreamer 停止」）
- Single モードでもクリップの `MediaOut` を再生の終端として扱う（Continue と同じ扱い）

### Removed
- mpv バックエンドと `libmpv-2.dll` / `mpv-2.dll` の同梱
- `backend` 設定キーと `outputBackend=Cpu`（v0.3 の値は起動時に無視して警告）
- デバッグ OSD（`showDebugOsd` の OSD 表示。設定キーは互換のため残置）
- 旧 mpv 互換アダプタと文字列コマンド経路（`GstMpvApiAdapter` / `GstCommandTranslator` /
  `MpvPlaybackCommandBuilder` ほか）

### Fixed
- 音声トラック付き MP4 が読み込めなかった（S1）
- ProRes ほか CPU デコードのコーデックが読み込めなかった（S2）
- MPEG-TS でシーク後にフレームが数秒届かなかった（S3）
- 解像度が変わる切替で GPU 復旧後に再生が進まなかった（D8）
- MP4（B フレームあり）の accurate シーク後、qtdemux のタイムスタンプが先頭 DTS 分ずれ、
  アプリが実際より進んだ位置にいると思う問題。shim が segment 写像の stream time を使う（D10）
- ギャップ動作の切替時に、古い LTC フレームの再適用が同期要求を出していた問題（U1）
- E2E `ProjectRoundTrip` の失敗（テスト側のプレイリスト選択待ち。Q1）
- Single モードで EOF へシークした後 seeking が解除されず、LTC を戻しても同期シークが出なかった（D11）
- 一時停止中の位置つきロード直後に位置表示（ラベル・シークバー）が更新されなかった（F1）

### Known issues
- **29.97 ノンドロップの LTC は fps モード「Fixed 29.97」の指定が必要**（Auto は 30 と区別できない）
- **本物の GPU デバイス消失（TDR）からの shim 復旧は未対応（D9）**。この版では対象外（v0.4.1 候補）
- **フレーム 1 枚分の定数は製品では足さない**。現場の遅延は同期オフセット（`syncOffsetMs`）で合わせる
- 4K 主画面を出力先にすると 40 秒あたり数フレームの落ち（専用ディスプレイ推奨。3.6 節）
- トラック切替時に稀に 100ms 以下の音切れ（60 分試験で 12 回中 4 回）
- HAP は未対応（専用分岐の実装まで意図的に拒否）

## 3.6 既知の仕様: 表示の落ちが 40 秒に数回起きる（2026-09-15、利用者の判断で仕様として残す）

### 何が起きるか

**全画面表示中、40 秒あたり数回、1 枚だけ提示機会を飛ばす。**
そのフレームは 1 周期分（約 16.7ms）長く表示され、次のフレームに置き換わる。
連続して飛ぶことは無く、飛ぶのは常に 1 枚だけ。

**合格条件（V8）**: 40 秒あたりの落ちが **5 回以下、かつ連続なし**。

> **指標を訂正した（2026-09-15）。** 従来は `present.scanout` の `SyncQPCTime` 間隔 > 25ms で数えていたが、
> これは統計取得タイミングの揺れを含み、**実際の表示欠落を約 2 倍に過大計上していた**。
> 主指標は `PresentRefreshCount` の差が 2 以上（＝実際に飛ばしたリフレッシュ）とする。
> 集計は `scripts/GpuOutputProbeHarness/scanout_drop_summary.py`。

### 実測

同一セッション内で 3 条件を交互に回した結果（2026-09-15、7 run）:

| 構成 | 旧指標 `SyncQPCTime` 間隔 > 25ms | **主指標 `PresentRefreshCount` の飛び** |
| --- | ---: | ---: |
| 優先度なし（**v0.4 の既定**） | 4 / 2 / 2 | **2 / 2 / 1** |
| MMCSS を既定 ON | 2 / 2 | **1 / 2** |
| MMCSS を環境変数で明示 | 1 / 3 | **1 / 1** |

**3 条件に差は無い。** 以前に「MMCSS で 0〜3 回に減る」「既定 ON にすると 6〜9 回へ悪化する」と
読んだ run 群は別セッションのもので、**交互に回すと再現しない**。セッション固有の何かだったが未特定。

**MMCSS の採否は要検討**（2026-09-16、第三者の意見を踏まえ利用者判断で保留）。
現状の既定は優先度操作なしで、それで基準を満たしている。MMCSS の実装はブランチ
`codex/v8c-thread-priority-20260915` に残してあり、観測スクリプトの判定値の訂正（`280c327`、
MMCSS 中の `GetThreadPriority` は相対 15）も同ブランチにある。
落ち同士は最も近くても 25 枚（約 0.42 秒）離れており、連続は観測されていない。

### 原因

**OS のスケジューリングで出力スレッドが数 ms 待たされ、vblank までの余裕を使い切るため。**

- 落ちた tick の合成は**ほとんど予定どおりに始まっている**（起床遅れ 0.2〜0.6ms）。vblank まで約 5ms の余裕があった
- **合成の重さではない**。ProRes の CPU デコードでも、外部 CPU 負荷 12 本でも落ちは増えない
- **アプリ固有ではない**。mpv でも同じ頻度で起きる（3〜5 回 / 40 秒）
- **出力スレッドの優先度を上げても減らない**（上表。MMCSS は効果が確認できなかった）

### なぜ直さないか

**原因がアプリの外側にあり、この環境では両バックエンドとも 0 を達成できない。**
スレッド優先度での対処も効かないことが確認できた（上表）。
利用者の判断で**既知の仕様として残す**。

### 将来の対処の筋道（未検証の候補）

現在の提示は「**次の vblank の時刻を予測し、タイマーでそこまで待つ**」設計
（`OutputEngine` の `vblankTimer.WaitUntilOrStop`）。**起床がタイマー由来なので、OS の遅れをそのまま受ける。**

**OS の起床を待たずに表示側の信号で駆動できれば、この余地は消える可能性がある。** 候補:

| 候補 | 現状 | 見立て |
| --- | --- | --- |
| swapchain の **latency waitable object** で歩調を取る | **既に作ってある**（`SwapchainTarget.cs`、`FrameLatencyWaitableObject`）。ただし即時 Present のタイムアウト付き待ちにしか使っていない（`OutputEngine.cs:1339`） | タイマーではなく**表示パイプラインが起こす**ので、予測とタイマー起床を経路から外せる可能性 |
| `IDXGIOutput::WaitForVBlank` | 未使用 | vblank イベントで直接起きる。ただしこれもカーネル待ちなのでスケジューラの影響は残りうる |
| 合成リードを広げる | 現在約 2.5ms（自動調整） | OS を外すのではなく余裕を増やすだけ。遅延と引き換え |

**いずれも未検証。** 「余地が見えたらそこで対処する」という方針（利用者、2026-09-15）。
**着手するなら、まず latency waitable での歩調取りを試すのが筋**（既に生成済みで、追加の依存が無いため）。
