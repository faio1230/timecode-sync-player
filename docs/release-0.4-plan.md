## 3. リリースノート草案（v0.4.0）

### Added
- GStreamer による再生バックエンドと GPU 合成出力を**既定**にした。D3D11 の共有リングでデコード済み
  テクスチャを直接受け取り、合成・全画面表示・Spout 送信まで GPU 上で完結する
- CPU デコードのコーデック（ProRes ほか）も `d3d11upload` で同じ経路に載せ、リースの扱いを統一
- 音声付き素材の再生（S1）
- MPEG-TS のシークを自前のキーフレーム着地＋再基準化で正確にした（S3）

### Changed
- 既定の `backend` が `1`（Gstreamer）、`outputBackend` が `1`（Gpu）になった。
  従来の mpv／CPU 経路は `settings.json` で `backend=0` / `outputBackend=0` に戻せる（v0.4 では残す）
- パイプラインクロックをシステムクロックに固定し、音声シンクはそれにスレーブする（S3 の副作用）

### Fixed
- 音声トラック付き MP4 が読み込めなかった（S1）
- ProRes ほか CPU デコードのコーデックが読み込めなかった（S2）
- MPEG-TS でシーク後にフレームが数秒届かなかった（S3）

### Known issues（**要判断**、下記 4 参照）
- mpv×Gpu の 4K で合成 p99 が 2.94ms（表示は 59〜60/秒を維持。退避経路のみ）
- 4K 主画面を出力先にすると 40 秒あたり数フレームの落ち（専用ディスプレイ推奨）
- トラック切替時に稀に 100ms 以下の音切れ（60 分試験で 12 回中 4 回）

## 3.5 退避経路の選択肢（V3 の結果次第、判断は利用者）

v0.4 は当初「mpv を完全除去し、退避は GStreamer 内のデコード方式切替が担う」方針だが、
**V3（LTC 同期の精度）を出荷の門とする**。`docs/prompts/2026-09-13-V3-seek-breakdown.md` の
切り分けの結果、GStreamer の回復時間が予算（シーク p95 250ms 以下、ギャップ再入 p95 500ms 以下）に
届かない場合に備え、**選択肢として次を残す**:

- **案 X: mpv を退避経路として 1 リリース残す**（当初計画に戻す）。
  既定は GStreamer×Gpu に切り替えるが、`backend=0` で mpv に戻せる状態を v0.4 では維持し、削除は v0.5 以降。
  この場合 V7（mpv×Gpu×Spout）の条件未達（4K の合成 p99 2.94ms）が再び論点になる。
- **案 Y: 予定どおり mpv を除去**し、退避はデコード方式切替のみ。

**判断は利用者が行う。** 親は V3 の数字と、届かない場合の原因・見込みを揃えて提示する。

### 未決（利用者の判断待ち）

1. **V8 の「落ち 0」の読み方** — このマシンではどの構成でも達成していない（DISPLAY2 でも 40 秒あたり
   1〜3 秒は present が 59、平均 59.925Hz）。共通条件の「59.9Hz 以上」として読む解釈でよいか。
   **これが決まらないと V8 の合否が確定しない。**
2. **デコード切替の設定形式** — `decodeMode` を settings.json のみ（UI なし）とする案でよいか。
   `backend` / `outputBackend` と同じ扱い。本番中の切替が要るなら UI を検討する。
3. **GStreamer ランタイムの配布方式** — インストーラーは全面的に mpv 前提で GStreamer への言及がゼロ。
   既定にする以上、配布物に無いと動かない。方式は (a) 必要な DLL を同梱、(b) `get-gstreamer.ps1` で
   インストール後にダウンロード（mpv と同じ方式）、(c) 利用者が別途インストール。
   **親の調査では公式ランタイムの ffmpeg は LGPL-2.1-or-later**（`gstlibav.dll` = `avdec_*` の実体）で、
   GPL なのは x264・x265・a52dec（いずれもエンコーダか AC-3 で再生経路では不使用）。
   ただし ffmpeg 側の表示にも「法的助言ではない」とあり、**最終判断は法務的な確認が要る**。
4. **現場素材の一覧** — V1 の表に加える。mpv が読めて GStreamer が読めない素材をゼロにするための
   チェックリスト。**V11-b（ソフトウェアデコードの実力）を実素材で測るのにも要る**
   （合成素材では 4K HEVC が実時間の 3.5 倍だったが、実写ではもっと厳しくなる）。
5. **V4 の実施方法** — 現場のプロジェクトファイル（`TIMECODE_REAL_PROJECT_PATH`）を提供いただくか、
   親が構成したプロジェクトで代替するか。V3 の精度ハーネスが black/freeze のギャップを含むため一部は自動で確認できる。

6. **CPU 合成経路（`outputBackend=Cpu`）を v0.4 で残すか** — V3 の測定で、GStreamer は
   **CPU 合成のときだけ** 60fps 素材で公開が ~320ms 止まる（2 run で再現、mpv には無い、
   GPU 合成では起きない）。詳細は検証記録の「seek-c の 1269ms の正体」。
   - 残すなら: この停滞は残課題として直す必要がある。
   - mpv と一緒に落とすなら: 直す対象ではなくなり、V3 の残る劣位は消える。
   mpv 除去の方針では「退避経路はデコード方式の切替に置き換える」としたが、
   **出力側（合成）の CPU 経路をどうするかは未定**のままだった。
