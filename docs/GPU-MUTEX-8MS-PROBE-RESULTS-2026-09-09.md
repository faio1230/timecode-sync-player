# Spout mutex待ち4ms／8msの実証結果

2026-09-09。[仕様](GPU-MUTEX-8MS-PROBE-SPEC.md)に従い、サブエージェントが独立試作・ハーネスを実装し、親がレビューと直列実機評価を完了した。

## 判断

待ち指定8msではSpout公開59.68〜59.95Hz、取得失敗1／7回となり、4msの54.23〜55.55Hz、取得失敗127／98回から改善した。8msの2試行では失敗の連続もなく、最長公開間隔は30.26〜34.53msだった。公開画像年齢は平均4.90〜4.91msから5.35〜5.66ms、最大約9.5msから約13msへ増えた。

今回の範囲では、この画像年齢の増加と引き換えに公開空白を減らす効果が再現した。**次の比較基準をsplit・送信位相4ms・mutex待ち8ms・公式受信機ありとする。** 試作CLIの既定値は0msのまま、本体への採用や設定変更は行っていない。8msより長い待ちは追加しない。

安定60Hzの達成ではない。8msでも送信見送りが残り、実受信・物理表示を計測したものでもない。全画面は8msの2試行とも60Hzだったが、過去の同じ分離構成で表示準備未完了が多発している。次は送信条件を固定し、全画面の準備確認とPresentのタイミングを切り分ける。今回の正常値だけで表示側の課題を解決済みにしない。

## 実装と条件

- 試作の待ち許容範囲を整数0〜8msへ拡大し、設定値と実効予算の上限を共通化した。既定0ms。ハーネス・解析器も0〜8msに対応。UIは実時間の上限保証と混同しないようmutex request表記にした。
- 待機は1回、実効指定は設定値と次周期までの残り整数msの小さい方。取得後の停止・期限確認、一度だけの返却、GPU完了確認、画像選択・コピー・位相・Present設定・スレッド構成は維持した。
- 全4K試行はsplit／both、位相4ms、公式WinSpoutDXreceiver、GPU生成3840×2160、60Hz、32秒、warmup5秒、解析窓 `[5,27)` の22秒。Debug / x64、同じRTX 3070、同じ実表示先1920×1080。
- 同じ新実行ファイルで、待ち4→8→8→4msの順に比較した。前段階の古い実行ファイルの結果だけを4msの基準にはしていない。

## 解釈と限界

前段階で公式受信機を伴う取得失敗を切り分け、今回は同じ受信機を使い、送信側の待ち予算だけを増やして改善した。GPU処理全体の改修をせずに、受信側の解放を待つ余裕が公開頻度へ影響することを確認できた。一方、受信機内部のどの処理が何ms占有したかは未計測。多数回・長時間の統計試験でもなく、他の受信アプリへの一般化はしない。

公開画像年齢は合成開始から公開成功までの値であり、公開されない期間の受信画像の年齢を表していない。固定1秒区間の最小件数と最長公開空白も併せて判断する。受信機の生存範囲は確認したが、各試行の接続先を画像で検証しておらず、一意画像受信・物理4K60表示を保証しない。入力はGPU生成カードで、CPU画像アップロードやmpv実動画の性能評価ではない。

A2には表示準備未完了6回があった。8msで今回発生しなかったことを、待ち拡大で表示問題も解決した証拠にはしない。過去の表示低下と同じく、準備確認とPresentのタイミングを別に扱う。
