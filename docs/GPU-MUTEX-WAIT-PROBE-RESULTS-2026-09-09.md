# Spout mutex短時間待ちの実証結果

2026-09-09。[実証仕様](GPU-MUTEX-WAIT-PROBE-SPEC.md)に従い、サブエージェントが独立試作と計測を実装し、親がレビュー・実機試験・評価を行った。

後続の[送信位相実証](GPU-SEND-PHASE-PROBE-RESULTS-2026-09-09.md)で画像年齢の改善を確認した。一方、後続のsplit・位相0ms再試験で全画面47.82Hz・表示準備未完了268回が発生した。下記のsplit表示59.95〜60Hzは本資料の試行範囲に限る結果であり、分離すれば表示周期を保証できる意味ではない。

## 判断

4ms待ちの試行ではSpoutの長い公開空白が減ったが、安定60Hzには届かなかった。commonでは表示準備未完了による多数のスキップも発生した。splitは今回の全条件で全画面59.95〜60Hzを維持しており、送信待ちの影響を分離する次段階の候補とする。ただし、スレッドとD3Dデバイスの両方が異なる比較であり、原因や本体への採用を確定する結果ではない。

splitの送信画像年齢は平均約17.5〜17.8ms。最新画像を優先する要件に対し、次は送信周期の位相と画像の選択時点を調べる必要がある。待ち指定を4msより長くする実装は行わず、試作の既定値も0msのまま。本体統合、CPUアップロード、mpv接続、GPUプレビューへはこの結果だけで進めない。

## 条件と測定の意味

- Windows / Debug / x64、RTX 3070、同一アダプター。GPUが3840×2160の画像を生成し、全画面1面とSpoutを併用。実際の表示先・スワップチェーンは1920×1080。各32秒、60Hz、解析窓は `[5,27)` の22秒。
- commonは合成・表示・送信を共通GPUワーカーで処理。splitは送信を別ワーカー・別D3D11デバイスへ分離。両方とも送信用画像へGPUコピーし、コピー完了後に元画像の使用権を返す。
- 待ち指定だけを0／1／2／4msで変更した。同じ新しい実行ファイルを使用し、GPU完了確認、プール、表示設定、送信位相は変更していない。初回実証の古い実行ファイルとの差を待ち時間だけの効果とは扱わない。
- 全画面Hzは成功した `present.return`、Spout HzはGPU完了と外側mutex解放後の `send.publish` 件数／22秒。画像年齢は合成開始からSpout公開まで。受信・走査・出力間の実表示時刻差ではない。
- 公式WinSpoutDXreceiverを非表示で起動し、生存期間を記録した。サンプル受信機はCPU読み戻しとGDI表示を含む。今回の各走行では接続先と一意画像受信を画像で検証していない。前回の別走行の画像確認を今回の受信証明には流用しない。

## 解釈と未確定事項

1. **短い待ちには効果が見えるが、単調には改善しない。** 4msの4試行では最長公開間隔が約116〜119msになった。一方、splitの0msは54.18Hz、1msは50.68Hz、2msは48.86Hz。前回の0msとの差も大きく、受信側と周期の位相・試行間変動を含む。少数試行の最高値で待ち時間を決定しない。
2. **共通構成には表示周期の問題が残る。** C2とC4bで `present.notReady` が350／300回発生した。C2では合成開始の予定時刻からの遅れが小さく、単純なCPUスケジュール遅延だけでは説明できない。表示準備確認とPresentのタイミング、受信処理、GPU内部のどれが原因かは未確定。送信の待ちが直接原因だと断定しない。
3. **splitの画像年齢には約1周期分の差がある。** 待ち時間を0から4msにしても、約17msという基礎的な年齢は残った。合成完了前に前周期の画像を選んでいる可能性を次に検証する。現時点で位相変更による改善を保証しない。
4. **指定timeoutは実測の上限ではない。** 4msでも取得区間が最大5.14msになった。取得区間には小さな予算計算も含む。全試行の解析窓で取得終了が次回期限に達した例は0件、abandonedは0件。実測で期限超過がなかったことは、終了・期限判定の全分岐を実機で検証した意味ではない。管理テストで遅い取得成功・停止・例外時の一度だけの返却を確認した。

次の小実証ではsplitを中心に、合成完了と送信画像選択のQPC・画像番号差を確認し、送信位相だけを変更する比較を設計する。周期60Hz、最新優先、追いつき送信なし、GPU完了前に資源を返さない条件は維持する。commonの表示準備未完了は別の比較項目として残す。待ち方式と位相を同時変更しない。
