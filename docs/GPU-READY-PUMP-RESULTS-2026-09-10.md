# 表示準備通知の待ち受け実証結果（2026-09-10）

## 判断

独立試作に `--display-pacing tick|ready` を追加し、承認済みの1080p動作確認と4Kのtick→ready→ready→tick比較を完了した。本体へのGPU統合は開始していない。実装はサブエージェント、レビュー・実機実行・評価は親が担当した。

ready方式は周期途中の準備通知を待ち受け、通知後に最新画像を選択できた。ただし一貫した性能改善は確認できなかった。ready 1は全画面描画とSpoutコピーの共有画像使用が重なり、Spoutが古い送信用画像を再送した。ready 2は通知がほぼ即時に返り、この滞留は再現しなかった。既定tickを維持し、readyの本体採用は保留する。

次の検討対象は共有sourceの取得・返却と、全画面描画／Spoutコピーの重なり。通知待ちだけで解決したとは扱わず、スレッドやデバイス追加もまだ決めない。

## 実装と条件

[実証仕様](GPU-READY-PUMP-DESIGN.md) に従い、readyはsplit／both／present-wait 0ms／fixedに限定。合成後、画像leaseとkeyed mutexを取得する前に、停止通知と表示準備通知を次回合成予定まで最大1回待つ。期限後に受け取った通知やsource取得失敗時の通知は保持し、次枠で合成を優先して最新画像を選び直す。

待ち時間は残りmsの切捨て。早くtimeoutしても同枠内では再待機せず、端数msの通知を次枠まで見送る限界がある。完全なイベントループではない。GPU完了確認、Present前の共有source返却、所有スレッドでの後片付けを維持。新規スレッド・デバイス・コピー・タイマーは追加していない。

- Windows／Debug／RTX 3070、同一バイナリのGPU生成パターン。mpv・CPUアップロードは含まない。
- 合成・Spout目標60Hz、Spout位相4ms、送信アクセスmutex要求8ms。source keyed mutexは既存の待ちなし取得。
- 公式WinSpoutDXreceiverを各runで起動し直列実行。接続先・画素更新は今回採取していない。
- 1080p：1920×1080、windowed、12秒、解析窓2〜10秒。
- 4K：生成キャンバス3840×2160、全画面1面、各32秒、解析窓5〜27秒の22秒。
- monitor index 1／DISPLAY2、実描画1920×1080／60Hz、Present interval 1、swap buffer 2、maximum frame latency 1。物理4K表示試験ではない。
- 日付は日本時間2026-09-10。run名と保存時刻はUTCの2026-09-09。

## 共有画像の競合を示す記録

ready 1のコピーbusy 59件中50件は、同じ画像IDの `display.draw.start`〜`display.draw.complete` 内に記録された。コード上、この区間でGPUスレッドはsourceのkeyed mutexを保持する。Spoutは最新IDを選択してもsourceを取得できず、保持した前の送信用画像を使う。残り9件は描画区間外だが、取得から描画開始まで・描画完了から返却までの所有時間を含めて測っていないため、競合がないとは判定できない。

最大159.7373msの例では、Spoutは最新ID1582を選択し、コピーbusyとなり、保持していたID1573を送信した。次枠ではID1583のコピーと送信が成功。過去フレームのキューが積み上がったものではなく、コピーできない間に保持画像を再送した挙動である。

ready待機はsource取得前に終わっている。待機中のsource保持ではなく、描画用に取得する時刻が後ろへ動いている。Spout位相4msと重なりやすくなったという説明はログと整合するが、GPU内部全体や全失敗の原因を確定したものではない。
