# Spout送信位相の実証結果

2026-09-09。[位相実証仕様](GPU-SEND-PHASE-PROBE-SPEC.md)に沿ってサブエージェントが実装し、親がレビュー・直列実機試験・評価を完了した。

後続の[受信機対照実証](GPU-RECEIVER-CONTROL-PROBE-RESULTS-2026-09-09.md)では、受信機起動なしの4K対照2回でSpout60Hz・mutex取得失敗0、公式受信機ありで取得失敗が再現した。また公式受信機ありの1回で、位相4msでも全画面46.32Hz・表示準備未完了301回となった。下記の位相4ms・全画面60Hzは本資料の2試行に限る結果であり、安定動作の保証ではない。

## 判断

splitで送信周期を合成周期から4ms後ろへずらすと、当該周期の合成画像を選べた。2試行とも全画面60Hz、コピー元のkeyed mutex取得見送り0、Spout公開時の画像年齢は平均4.86〜5.14ms、最大9.09〜9.45msだった。位相0msの平均17.80〜18.46msに対し、約1周期前の画像を選ぶ状態を改善できた。

ただしSpout公開は51.68〜56.23Hzで、安定60Hzには届いていない。また位相0msの再試験では、splitでも全画面47.82Hz・表示準備未完了268回が発生した。前段階の「分離構成は今回の全条件で全画面59.95〜60Hz」という結果はその測定範囲の事実であり、分離すれば表示周期を保証できるという判断へ一般化しない。

**次の比較基準にはsplit・位相4ms・mutex待ち4msを使う。** これは今回のGPU生成試作における比較条件であり、本体への固定4ms遅延の採用ではない。CLI既定の位相0ms・mutex待ち0msは維持する。次は画像選択の遅れと分けて、残るSpout access mutex取得失敗・長い公開空白を切り分ける。表示準備未完了も独立した未解決項目とする。本体統合やmpv接続、GPUプレビューへは今回進めていない。

## 実装と条件

- `--send-phase-ms` を追加。送信ワーカーのスケジューラー原点だけを変更し、60Hz周期、スキップ、真の次回期限、共通の試験終了時刻を維持した。コピー・GPU完了確認・所有権・Present設定は変更していない。
- `compose.publish/visible` と `send.select.start/end` で、プール公開と画像選択の前後区間を記録した。内部ロックの厳密な線形化時刻ではない。公開と選択が重なるケースは不確定として区別した。
- 4K比較は全てsplit／both、GPU生成3840×2160、32秒、warmup5秒、解析窓 `[5,27)` の22秒。mutex待ち指定4msを固定し、位相0→1→2→4→0→4msの順に実行した。
- 同じDebug / x64実行ファイル、同じRTX 3070、同じ表示先を使用。キャンバスは4Kだが、表示先とスワップチェーンの実寸は1920×1080。通常設定・表示設定を変更していない。
- 公式WinSpoutDXreceiverを非表示で起動し、生存期間を記録。各試行での接続先や一意画像の受信を画像で検証していない。API公開、GPU完了のCPU観測、物理表示・実受信は区別する。

## 分かったこと

1. **画像選択自体が古い候補を優先していた証拠はない。** 確実に可視化済みの候補より古い画像を選んだ例は全試行0。P2に公開・選択の前後関係が不確定な例が1回あった。位相0では、選択時点に当該周期の合成画像がまだ公開されていないことが主因と整合する。4msでは2試行合計2,640回全て当該周期の画像を選択した。
2. **選択した最新画像と、実際に送れた画像は別に見る必要がある。** 位相1／2msでは最新を選べてもコピー元keyed mutexを取れず、保持画像を送る回が残った。P2の最大104.01msの公開は画像353。直前に画像354〜359のコピーを6回連続で見送り、画像353を保持したログと対応する。新画像の選択成功だけで遅延改善を判定しない。
3. **位相4msでは画像年齢の改善は再現したが、送信頻度の改善は確定しない。** 4msのSpout平均51.68〜56.23Hzと、0msの45.41〜54.00Hzの範囲は重なる。受信側との相対位相や試行間変動を制御した多数回の比較ではなく、4msの平均fps向上を確定する結果ではない。
4. **CPUスレッド分離だけで表示を保証できない。** P0bでは合成は60Hzのまま、表示準備未完了が268回発生した。共通構成だけの問題として扱えない。GPU内部、Presentと準備確認の位相、受信処理等の根本原因はこのログだけでは特定しない。
5. **期限と寿命は維持した。** 全解析窓で取得終了の次回期限超過0、GPUエラー0。取得区間の最大は4K試行で約4.93〜5.32msとなり、4ms指定の厳密な復帰保証はない。GPU完了前の資源返却や、遅れた送信の追いつき処理は追加していない。

本体での合成負荷はGPU生成カードとは異なる。4msという数値を普遍的な余裕時間とせず、出力周期に対して合成を先行させ、出力時には準備済みの最新画像を選ぶ設計上の関係を維持して評価する。
