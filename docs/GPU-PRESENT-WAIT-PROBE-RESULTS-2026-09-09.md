# 全画面の準備待ち0／1ms実証結果

1ms待ちの本体採用は保留する。4K生成キャンバスの0→1→1→0ms比較では、1msの2回は全画面60Hzだったが、0msも初回60Hz、再試験56.36Hzと変動した。再試験で準備未完了80回を再現できた一方、1ms側の解析窓では準備確認がほぼ即時に戻った。要求待ち時間による改善と、起動ごとのタイミング差を分離できていない。

## 条件と実装

[実証仕様](GPU-PRESENT-WAIT-PROBE-SPEC.md) に従い、独立試作へ `--present-wait-ms 0|1` を追加した。既定0ms。最新画像選択→source keyed mutex取得→準備確認の順を維持し、native waitを一度だけ行う。成功した準備状態はPresent試行まで保持し、期限・停止で見送った場合は画像を返し、次周期に最新画像を選ぶ。GPU発行後の完了確認と安全なdrainは維持した。0msにも同じ期限確認・計測コードを適用した同一バイナリで比較した。

全試行split・送信位相4ms・Spout mutex要求8ms・公式WinSpoutDXreceiver。Debug/x64、RTX 3070、同一adapter LUID 72428。スワップチェーンはBGRA8、buffer 2、MaximumFrameLatency 1、Present間隔1。合成3枚と送信専用コピーを維持した。本体・mpv・hwdec・GPUプレビューは変更していない。

親がまず1080p/windowedを12秒（解析窓[2,10)秒）確認し、その後4K生成キャンバスを各32秒、解析窓[5,27)秒で4回直列実行した。monitor index 1／DISPLAY2の実描画寸法は1920×1080。4K生成・送信画像の試験であり、物理4K全画面試験ではない。表示設定・通常設定・他アプリは変更していない。

準備確認時間はnative waitを含むCPU観測区間。1ms指定時も既に準備できていれば即時に戻るので、要求1msを各画像へ一律に加えた遅延ではない。B1/B2では実効要求が全1,320回1msだったが、最大でも0.012／0.029ms程度だった。待ってから新たに準備できた画像の救済数を直接測ったものではない。

A2は解析窓の全画面成功1,240回、準備未完了80回。1秒窓の最小成功数は42回で、主に5〜18秒の区間に抜けが集中し、18〜27秒には出なかった。CPU合成は60Hzを維持した。B1/B2の全画面は全1秒窓60回。Spoutの1秒窓最小は4試行とも59回で、1ms条件での明確な改善はない。B2の最長間隔39.06msを含め、常時60Hzの達成とは扱わない。

全試行でコピー見送り0、Spout選択は当該周期の最新画像、画像選択の矛盾0。準備確認の期限超過・保持済み準備状態の再利用・Spout取得終了の期限超過は0。準備状態の保持と再利用は管理テストで確認しており、今回の実機ログでその分岐を通したとは報告しない。

1080pの解析窓は合成・全画面・Spoutとも60Hz、見送り0だった。ただし窓外を含む準備未完了はsmoke 1回、A1 2回、B1 1回、B2 2回、A2 109回。B1/B2を含め、起動直後から見送りが一切ないという結果ではない。

## 評価と次の候補

準備未完了の再現と待ち区間の計測ができた。0msのA1とA2の差が大きく、1msの定常区間で実際に長く待った形跡もないため、今回だけで1msを改善策として確定しない。起動時に決まる出力予定時刻と表示側のタイミング関係は候補仮説だが、GPU内部やDWMの原因は未確定。

次の小実証候補は、同一プロセス・同一スワップチェーンを保ったまま0／1msを区間切替し、境界区間を除外して反復比較すること。起動ごとの状態差を減らし、準備未完了が出る状態で待ちによる差があるかを確認する。今回その切替は実装していない。準備待ちの既定0ms、送信比較条件split・位相4ms・mutex要求8msを維持し、1ms超への拡大やswap設定変更、本体統合は開始しない。

API成功・GPU完了の回数であり、異なる画像が公式受信機へ全て届いたこと、物理表示、画像混在なしを保証しない。受信機は今回も所有プロセスの生存を確認したが、senderへの接続先と画素更新の実測は行っていない。
