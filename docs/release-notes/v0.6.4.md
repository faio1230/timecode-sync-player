# TimecodeSyncPlayer v0.6.4

**安定版（Latest）です。**
観測（ログの行）と試験の基盤を整理した版です。同期の判断・再生の動作は v0.6.3 と同じです。ほかの内容・既知の制限・運用の推奨は v0.6.3 と同じです（[v0.6.3 のリリースノート](https://github.com/faio1230/timecode-sync-player/releases/tag/v0.6.3)、[v0.6.1 のリリースノート](https://github.com/faio1230/timecode-sync-player/releases/tag/v0.6.1)）。

v0.6.3 からの移行の注意: 無し（設定・プロジェクトの形式は変わりません）。

### 振る舞いの変化

- 無し（同期の規則・門・定数は v0.6.3 と同じです）

### 表示の変更

- **LTC の FPS が Auto のとき、補正の状態の欄（表示が空いているとき）に「Auto は確認用です。本番は固定にしてください」と表示します。** 補正の状態の表示があるときはそちらを優先します。FPS の選択にツールチップ「本番では LTC の発生器と同じ fps に固定してください」を付けました（項目の文字列は「Auto」のまま）。既定値（Auto）と設定ファイルの形式は変わりません
- セットアップの文書（`docs/SETUP.md`）の Auto の記述に、停止モードで Auto のときは LTC が乱れると約 2 フレーム止まってから 1 回合わせ直すことがある旨を足しました（試験の層での値）

### 観測と試験基盤の変更（動作は変わりません）

- アプリのログに次の行・値を足しました（記録だけで、動作は変わりません）
  - `Sync hold summary`: 止まった判定から出る後ろ向きのシーク（`backwardSeeksWhileStopped`）を、保持中に確定したジャンプの着地（`heldJumpBackwardWhileStopped`）とその他（`otherBackwardWhileStopped`）から分けて数える。行末に `smoothIneffective`
  - `Playback perf`: 行末に GPU の合成が使った新しいフレームの数（`composedSourceFrames`）
  - `Startup timing`: 起動 1 回に 1 行、起動の各段の開始・終了を起動からの経過（ms）で
- 試験の基盤: アプリのログを日付をまたいで読む、前回読んだ位置から続けて読む、一式の前に当日のログを退避する、L-2 の監査で起点の前に始まる区間を数えない

### 既知の不具合

- 推奨素材の範囲内で既知の不具合は 0 件です（v0.6.3 と同じ）

### 既知の間欠（まれに起きる）

- v0.6.1 のノートの一覧と同じです（v0.6.3 と同様）。加えて、検証機の試験で、一時停止中にシークした直後に目標より先の絵（2〜11 フレーム）が約 3 秒止まって見えたことが 2 回ありました（同じ一式の続けて回した 2 回）。その後の同じ条件の 12 回と、そのシナリオだけを回した 12 回では、v0.6.3・v0.6.4 とも 0 回で、原因は特定できていません。再生中の同期には影響しません

### 検証の概要

公開したビルドは、検証機で試した候補（`0.6.3+13fc092`）と製品のコードが同じで、版番号と文書だけが違います（下の「配布物」）。試験のコードは、検証機で一式を回したもの（`a3fbd52`）と同じで、版の確認のテスト（`ApplicationVersionTests`）の版の文字列だけが違います。

- **開発機**（2026-10-02〜03、RTX 3070）
  - 非E2E 2,965 件合格 / 0 失敗
  - LTC シナリオの一式（標準 ×2・重い素材・ProRes ×2・連続追従 ×2）を v0.6.3 と並べて実行。同期の数（位置の合わせ直しの本数、`Sync hold summary` の数）は v0.6.3 の回と同じ範囲。CRITICAL の行（`gst_segment_do_seek: assertion`、shim のログ `tcs-gst-raw.log`）は 1 回あたり 0〜20 行で、回によって増減がある
  - トラックの保持中の黒（C-2）の診断の回を 20 回、黒 0 回（v0.6.3 の開発機の試験（トレース無し）では 12 回で 1 回）
- **検証機**（2026-10-03 05:1x〜14:01、RTX と内蔵 AMD の Optimus、実素材 M1〜M7 と ProRes の PR1〜PR4、利用者の操作が無いことを確かめてから開始）
  - 標準のシナリオ 3 通り（うち 1 通りは本番と同じ構成: インストール版・トレース無し）: それぞれ 38 件合格 / 0 失敗
  - 連続追従 6 本合格、トラックの切替 2 本合格（映像の止まりの最大 0.017・0.017 秒、0.02 秒を超える区間 0）。切替の回の位置の合わせ直しの本数（80・84）は、同じ条件の v0.6.3 の 3 回（82〜89）と同じ程度
  - ProRes: RTX では 183 回のロードがすべて GPU、CPU 0、アダプタの不一致 0（シナリオ 38 件合格 / 0 失敗）。内蔵 AMD では既定どおり 76 回すべて CPU で、シナリオ 38 件合格 / 0 失敗
  - トラックの保持中の黒 0 回（5 回・100 枚）
  - プロジェクトの保存と復元 10 回: 失敗 0。足した直後の選択の試験 1 件合格。非E2E 2,965 件合格
  - CRITICAL の行（`tcs-gst-raw.log`）: 一式で 82 行（回によって増減がある）
  - 起動直後の UI の止まり（アプリのログの `UI heartbeat summary` の `firstLateMs`）: 一式の起動の中央 約 820ms、最大 2,005ms
- **配布物**: 候補の zip とファイル単位で比べ、違うのは版の表記を含むファイルだけ。shim（`tcs_gstreamer.dll`）と ProRes のプラグインは候補と同じ（v0.6.3 とも同じ）
