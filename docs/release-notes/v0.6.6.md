# TimecodeSyncPlayer v0.6.6

**安定版（Latest）です。**
現場の報告を受けた直しの版です。いちばん大きい直しは、ffprobeが無い機体でクリップの長さが0のままになっていた件です。あわせて、シークバーのスクラブ、オフセットの数値入力、1フレーム送り・戻し、ボタンの見せ方、LTCの入力のメーターを足しました。同期の規則・ゲート・定数はv0.6.5と同じです。ほかの内容・既知の制限・運用の推奨はv0.6.5と同じです（[v0.6.5のリリースノート](https://github.com/faio1230/timecode-sync-player/releases/tag/v0.6.5)、[v0.6.1のリリースノート](https://github.com/faio1230/timecode-sync-player/releases/tag/v0.6.1)）。

v0.6.5からの移行の注意: 設定・プロジェクトの形式は変わりません。1点だけあります。

- Spoutの送信名を環境変数で変えている場合、値の前後の空白を切り捨てて送ります（例「 Stage A 」→「Stage A」）。空白付きの名前を受け側で選んでいた場合は、受け側で選び直してください

### 振る舞いの変化

- **クリップの長さを、再生のエンジン（shim）から読むようにしました。ffprobeは使いません。** v0.6.5までは、長さをffprobeでだけ読んでいました。配布物にはffprobeが入っていないので、ffprobeが無い機体ではプレイリストの各クリップの長さが0のままで、タイムラインの幅とスクロール、追加したときの自動オフセット、Continueの「今どのクリップの時間か」の判定が、長さ0で動いていました。v0.6.6からは、プレイリストに足したときと、開く・プロジェクトを読み込むときに、素材の容器の長さを読みます。長さが読めない素材は、長さを0として使わず「--:--」（長さの欄は「--:--:--:--」）と表示し、読み込んだときに再生のエンジンの長さで埋めます
- **シークバーとタイムラインを、つかんだまま動かすと再生位置がついてくるようにしました（スクラブ）。** v0.6.5までは、離したときにだけその位置へ飛んでいました。前のシークの着地を待ってから次を送ります（送っている途中のシークは1本だけで、離した位置は必ず送ります）。同期の補正は押している間は止まり、離したときは今の手動のシークと同じ扱いに戻ります。タイムラインでは、押したときの行のままで動かし、動かしている間に別の行のファイルを読み込みません
- **1フレーム送り・戻しのボタン（-1F・+1F）を足しました。** 10秒送り（◀◀ ▶▶）は残しています。今の表示のフレームから1フレーム先（前）へ正確にシークします。再生中に押すと、一時停止してから1フレーム動きます。続けて押した数は積み上げ、前のシークの着地の後に次を送ります。先頭と末尾では止まります。経路は今の手動のシークと同じです
- **オフセットを数値で入力できるようにしました。** 単位はmsの整数です。Enterか欄を離れると反映し、Escで前の値に戻します。範囲（-1000〜1000ms）の外は範囲の端に丸め、欄にも丸めた値を戻します。数字以外（小数・単位付き・空など）は反映せず前の値に戻します。全角の数字も読みます。同期が読む値と範囲は今と同じで、設定への保存も今の経路のままです
- **作業中の画面（プライマリ）に全画面を出すときに、確認を出すようにしました。** 毎回出します。ボタンは「出す」「やめる」で、EnterとEscは「やめる」です。全画面に入るのはFULLSCREENのボタンの1か所だけで、プライマリ以外の画面に出すとき、全画面を閉じるとき、起動時の引数・プロジェクトの読み込み・設定の復元・デバイスの復旧など人が操作しない経路では出ません

### 表示の変更

- ボタンの見せ方を直しました。押せないボタンは暗い背景に薄い文字にし、ONのボタン（Sync・Spout・Timeline・Card・LTCの動作中）は緑にしました（文字のON/OFFは残しています）。消音中のMUTEも緑です。LTCの動作中のSTART（押せない）は暗い緑です。主なボタンにツールチップを付け、押せない理由もツールチップに出します
- オフセットの行は、値の文字（「+40 ms」）を外し、つまみと入力欄とmsの1行にしました
- プレイリストの行の「Eff:」の値が右で切れていたのを直しました
- 窓の幅が狭いときも再生の並びが切れないようにしました。狭いときは右側の並び（MUTE・音量・速度・Spout・Card・Timeline）を下の行へ折り返します
- SpoutがONのとき、出力の欄に送信名を「Spout: 名前」で出します（送信の成否は見ていません）
- プレイリストの行に、つかめる印と、ドラッグで並べ替えられることを書いたツールチップを付けました（並べ替えの動作は変えていません）
- LTCの欄に、入力のメーター（ピーク、-60〜0 dBFS）と受信の表示を足しました。受信の表示は3段です
  - 「無音」: ピークが -60 dBFS 未満
  - 「LTC 受信中」: 直近1秒にデコードできたLTCのフレームが、fpsの半分以上（25fpsなら13）
  - 「信号あり・LTC なし」: それ以外
  - 判定のfpsは、LTCの欄で固定にしていればその値、Autoで確定していればその値、未確定なら24です。メーターと受信の表示は、デコーダがすでに数えている値を出すだけで、LTCのデコーダと同期の規則・ゲート・定数には触れていません。表示の判定は同期の側から読まれません

### 観測の変更

- アプリのログの起動時に、ffprobeの有無を1行出します（`ffprobe: not found on PATH ...` か `ffprobe: found on PATH ...`。長さには使いません）。v0.6.5までの「ffprobe is not available, cannot read duration」の警告は出なくなりました
- クリップの長さを読んだときの行を足しました（`Media duration probe`、読み込んだときに埋めたときは `Media duration from the loaded clip`）
- スクラブの行を足しました（`Scrub landed`、離したときに `Scrub summary`）
- 1フレーム送り・戻しの行を足しました（`Seek command sent source=FrameStep`、`FrameStep landed`、`FrameStep queued`、`FrameStep ignored`）
- オフセットの入力を反映しなかったときの行を足しました（`Sync offset input rejected`）
- 全画面の確認の結果の行を足しました（`全画面の確認`）

### 直した不具合

- 起動の直後にProResをGPUで読み込んだ後、まれにアプリが落ちていました（v0.6.2から）。原因はGStreamerに同梱のGLib 2.82.4のGIOが、Windowsのレジストリを読む初期化で終端の無い文字列を読み越すものです。GIOは、ファイルの種類の判定（typefind）のプラグインを読み込むと一緒に読み込まれます。v0.6.6では、クリップの長さとGOP走査の入口でtypefindを使わず拡張子から選ぶようにし、推奨の形式ではGIOが読み込まれなくなりました。推奨外の形式（汎用のデコーダで読むもの）では今も読み込まれ、落ちる窓が残ります。直った根拠はGIOが読み込まれなくなったことで、落ちの回数は直す前が起動72回で2回、直した後は起動60回と一式で0回です

### 既知の不具合

- 推奨素材の範囲内で既知の不具合は0件です（v0.6.5と同じ）

### 既知の制限

- 同梱のGStreamerにMatroskaのdemuxは入れていないため、.mkv/.webmは開けません（長さも不明になります）。推奨の容器はmp4とmovです（v0.6.5以前から同じ）
- 推奨外の形式（汎用のデコーダで読むもの。MPEG-2、MJPEG、DNxHD・DNxHRなどの映像や、拡張子が.mpg・.flvのファイル）を読み込むと、GIOが読み込まれ、起動の直後にまれに落ちる窓が残ります。拡張子が表に無いファイルは、クリップの長さとGOP走査が「対応していない拡張子」として失敗し、長さは再生を始めたときの長さで埋まります

### 既知の間欠（まれに起きる）

- v0.6.5のノートの一覧と同じです

### 検証の概要

公開したビルドは、検証機で試した候補（`0.6.5+91985cd`）と製品のコードが同じで、版番号と文書と試験だけが違います（下の「配布物」）。shim（`tcs_gstreamer.dll`）はv0.6.5から変わりました（v0.6.5: `6266d2042ea97e7cc00e018e7e6066332154fb3e142f2e7e36ca0b31f5e2e7c6`、v0.6.6: `bb5fdcafcfd8556912affb407437b332cda1542c1c006646dc32621b76a97f53`）。ProResのプラグインはv0.2.3のままです。

- **開発機**（2026-10-07〜08、RTX 3070）
  - 非E2E 3,294件合格 / 0失敗。項目ごとの単体とE2E（スクラブ・1フレーム送り・オフセットの入力・全画面の確認・LTCのメーター・ffprobeを外した長さ）は合格
  - LTCシナリオの一式（標準・重い素材・ProRes×2・連続追従×2）と、LTCのループの試験14件: すべて合格。重い素材の合わせ直しが範囲の下に1件（49。保持を繰り返すシナリオで1本ずつ少ない、受け始めの扱いの型）。連続追従の2回目の1回目は、プロセスが一瞬（約0.3〜0.6秒、アプリとshimのログが同時に無音）止まり、戻ったところで古いLTCで後ろへ、続けて前へと合わせ直しが2本増えて範囲の上に外れました。やり直しでは範囲内でした。開発機はほかのアプリと同居しています
  - 起動直後の落ち: 直す前のv0.6.6の一式で2回（GIOのレジストリの読み、ダンプで確認）、直した後の一式と、ProResを先頭に読む起動60回では0回。推奨の素材10本で、`gio-2.0-0.dll`が読み込まれないことをデバッガで確かめました
  - LTCのメーターを出している間のUIの止まり（`ui.heartbeat`の`lateMs`）: LTCの受信に入った後の窓で中央9.4ms・最大14.3ms。起動を含む全体では、起動の最初の1回が約850msです
  - スクラブ（4K59.94のProRes、GPUデコード）: 1秒あたり約60本を送り、1本の着地までは中央3〜4ms・最大8.5ms。そのあいだのUIの止まりは最大14.3ms
- **検証機**（2026-10-08、RTXと内蔵AMDのOptimus、実素材M1〜M7とProResのPR1〜PR4、UACや前面の窓や利用者の操作が無いことを確かめてから開始）
  - 標準のシナリオ3通り（うち1通りは本番と同じ構成: インストール版・トレース無し）: それぞれ38件合格 / 0失敗。同期の数はv0.6.5と同じ範囲
  - 連続追従6本合格、トラックの切替2本合格（映像の止まりの最大0.020・0.017秒）
  - ProRes: RTXでは183回のロードがすべてGPU、CPU 0、アダプタの不一致0（38件合格 / 0失敗）。内蔵AMDでは76回すべてGPU、不一致0（38件合格 / 0失敗、合わせ直しは96でv0.6.5の101と同程度）。アルファ付き（PR4）はGPU・CPUとも読み込み可
  - ffprobeを外した回（アプリのプロセスのPATHだけからffmpeg・ffprobeを外す）: 標準のシナリオ38件合格。起動のログの「ffprobe: not found on PATH」が26回の起動すべてで出て、長さは77回すべて読めました。ffprobeを外した長さの試験も合格
  - 起動直後の落ち: 10/02以降の起動1,690回で0回。候補のアプリでは、`gio-2.0-0.dll`が一度も読み込まれませんでした（26のプロセスで200回の確かめ）
  - プロジェクトの保存と復元10回: 失敗0。非E2E 3,259件合格。足した直後の選択の試験は記録だけ（長さの読みが速くなり、試験で選択を挟めなくなったため）
  - スクラブで同期を合わせ直す試験は、ログのDebugの行を読んでいたため、Releaseのビルドで落ちました。製品の振る舞いではなく試験の作りの問題で、Informationの行で確かめる形に直しました。直した試験は、検証機で候補のReleaseのexeで合格（離した後の同期の合わせ直しの位置6.845秒、離したときのLTC 6.85秒）、開発機でもDebugとReleaseのexeで合格
