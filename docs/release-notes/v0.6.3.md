# TimecodeSyncPlayer v0.6.3

**安定版（Latest）です。**
ランスルーで LTC が止まったときに映像を止まった位置へ戻さないようにし、一時停止中のシークで絵が 1 枚先へずれる件を直しました。ほかの内容・既知の制限・運用の推奨は v0.6.2 と同じです（[v0.6.2 のリリースノート](https://github.com/faio1230/timecode-sync-player/releases/tag/v0.6.2)、[v0.6.1 のリリースノート](https://github.com/faio1230/timecode-sync-player/releases/tag/v0.6.1)）。

v0.6.2 からの移行の注意: 無し（設定・プロジェクトの形式は変わりません）。

### 振る舞いの変化

- **ランスルーでは、LTC が止まったと判定しても映像を止まった位置へ戻さず走り続け、LTC が戻ったときに 1 回だけ合わせます。** v0.6.2 までは、止まったと判定した瞬間に 1 回、止まった位置へ戻していました（LTC が乱れて一瞬止まったと判定されると、映像が 0.5 秒前後止まることがあった。v0.6.2 の既知の間欠）。停止モードは変わりません（止まった位置へ 1 回合わせて一時停止）
- シングルで、LTC がクリップの範囲の外で止まったときにクリップの端で止める動作は変わりません（ランスルーでも、端へ 1 回シークして端で一時停止します）

### 修正

- **一時停止中にシークすると、まれに目標の 1 枚先の絵で止まり、表示の位置も 1 枚先になることがあった。** 一時停止のまま絵を出すために短く再生する間に、2 枚目のフレームまで出していた。検証機の試験で一時停止中のシーク 1,247 回のうち 39 回。1 枚目だけを出すようにした
- **速度の補正を位置の合わせ直しの直後に送ったときに、GStreamer がログに出していた CRITICAL の行（`gst_segment_do_seek: assertion`）を減らした。** 合わせ直しの直後の速度の変更を、そのシークの区切りが届くまで待ってから送る。（開発機の試験では 6〜7 割減。検証機の一式では 141 → 126 行で、回によって増減がある。いずれも shim のログ `tcs-gst-raw.log`。残る行は、合わせ直しより前に送った速度の変更のイベントを、GStreamer の demuxer が合わせ直しの後にもう一度流すために出るもので、合わせ直しの後にこのアプリが送る速度の変更から出るものではない）。この行が出ても速度は指示どおりに変わっていました（v0.6.1・v0.6.2 と同じ shim で、開発機の試験の 180 回すべて。v0.6.1 のノート）。変わるのは診断の行だけです
- 読み込みの直後の「最後に受け取ったタイムコードの再適用」を、時間の期限（1.5 秒）でなく LTC の状態で扱うようにした。読み込みの後に LTC が動いたら再適用はせず、止まったままなら 1 回だけ合わせる（数秒後の保持の始まりに古い値の再適用が走る型を、時間ではなく規則で防ぐ）

### 既知の不具合

- 推奨素材の範囲内で既知の不具合は 0 件です（v0.6.2 と同じ）

### 既知の間欠（まれに起きる）

- v0.6.1 のノートの一覧と同じです。v0.6.2 で足した「ランスルーの入口の合わせで映像が 0.5 秒前後止まる」は、上の振る舞いの変化で無くなりました

### 検証の概要

公開したビルドは、検証機で試した候補（`0.6.2+44cc043`）と製品のコードが同じで、版番号と文書だけが違います（下の「配布物」）。

- **開発機**（2026-10-02、RTX 3070）
  - 非E2E 2,939 件合格 / 0 失敗
  - LTC シナリオの一式を v0.6.2 と並べて実行（標準 ×2・重い素材・ProRes ×2・連続追従 ×2）。ランスルーで LTC が止まったと判定した直後の後ろ向きのシークは v0.6.2 の 1 回あたり 0〜4 本から 0 本、読み込みの後の古い再適用を捨てた行は 7〜16 回から 0 回、ProRes の回の参照の採取の撮り直しは 24 件から 0 件。ProRes の回の 1 回で、トラックの切替の後に約 1.5 秒の黒が 1 回出た（同じ条件の v0.6.2 と v0.6.3 の 10 回ずつ・計 20 回では 0 回。v0.6.1 のノートの既知の間欠の約 1.5 秒の黒と同じ見かけ）
  - shim の試験: 一時停止中のシークで 2 枚目を配信した回は 200 回中 54 回から 0 回（GPU の取り出しを模擬した条件）
  - CRITICAL の行（`gst_segment_do_seek: assertion`、shim のログ `tcs-gst-raw.log`）: 開発機の一式では 1 回あたり 20〜41 行から 5〜14 行（6〜7 割減）
- **検証機**（2026-10-02 15:40〜19:03、RTX と内蔵 AMD の Optimus、実素材 M1〜M7 と ProRes の PR1〜PR4、利用者の操作が無いことを確かめてから開始）
  - インストールと最初の起動、事前確認 5/5
  - 標準のシナリオ 3 通り（うち 1 通りは本番と同じ構成: インストール版・トレース無し）: それぞれ 38 件合格 / 0 失敗
  - 連続追従 6 本合格、トラックの切替 2 本合格（映像の止まりの最大 0.016・0.017 秒、ランスルーの入口の合わせのシーク 0 本）
  - ProRes: RTX では 183 回のロードがすべて GPU、CPU 0、アダプタの不一致 0（シナリオ 38 件合格 / 0 失敗）。内蔵 AMD では既定どおり 76 回すべて CPU で、シナリオ 38 件合格 / 0 失敗。アルファ付き（PR4）は GPU・CPU とも読み込み可
  - 試験の参照の採取の撮り直し 0 件（v0.6.2 は 60 件）。読み込みの後の古い再適用を捨てた行 0 回（アプリのログ）。トラックの保持中の黒 0 回（5 回・100 枚）
  - プロジェクトの保存と復元 10 回: 失敗 0。足した直後の選択の試験 1 件合格。非E2E 2,939 件合格
  - CRITICAL の行（`tcs-gst-raw.log`）: 一式で 141 行（v0.6.2）→ 126 行（v0.6.3）。同じ中身の回だけで数えた値で、回によって増減がある（標準の 1 通りでは 12 → 26）
  - 起動直後の UI の止まり（アプリのログの `UI heartbeat summary`）: 起動 140 回の中央 827ms、最大 1,920ms（一式の最初の起動）
