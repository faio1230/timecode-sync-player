# TimecodeSyncPlayer v0.6.5

**安定版（Latest）です。**
LTCのフレームの検査を加え、ProResのGPUデコードを既定ですべてのGPUで使うようにしました。同期の規則・ゲート・定数はv0.6.4と同じです。ほかの内容・既知の制限・運用の推奨はv0.6.4と同じです（[v0.6.4のリリースノート](https://github.com/faio1230/timecode-sync-player/releases/tag/v0.6.4)、[v0.6.1のリリースノート](https://github.com/faio1230/timecode-sync-player/releases/tag/v0.6.1)）。

v0.6.4からの移行の注意: 無し（設定・プロジェクトの形式は変わりません）。

### 振る舞いの変化

- **規格に合わないLTCのフレーム（桁が9を超える、長さが80ビットでない）は使いません。** 受け始めと、途切れて戻った直後の最初の1つも、長さを確かめられないので使いません。そのため受け取りがLTCのフレーム1つ分（25fpsで40ms）遅れます。止めては流す運用では、そのたびに同じ遅れが出ます。LTCを数フレームだけ流してすぐ止めると、合わせ直しを経ずに止まった位置へ直接着地することがあります（止まる位置は同じ）。受け始めに化けた1つの値で、一瞬ギャップの黒や合わせ直しが入ることを防ぐための変更です
- **ProResのGPUデコードを、既定（自動）ですべてのGPUで使います。** v0.6.4までは、自動のときNVIDIAのGPUでだけ使い、ほかはCPUでデコードしていました。NVIDIA以外のGPUは、検証機の内蔵GPU（AMD）で確かめた範囲です（下の「検証の概要」）。問題があれば、設定の「ProRes の GPU デコード」を「無効」にしてください（再起動の後に反映）。GPUで開けない素材は、これまでどおりCPUでデコードします

### 表示の変更

- FPSの選択の「29.97 fps DF」を「29.97 fps」にしました。ノンドロップの29.97の信号はこれを選んでください。ドロップフレームの信号はAutoでも判定できます（項目のツールチップにも書きました）
- 「ProRes の GPU 復号」を「ProRes の GPU デコード」に、アプリのログの「CPU で復号」を「CPU でデコード」にしました
- インストーラーと配布物のREADME.txtのVC++の再頒布パッケージの名前を、実物の「Microsoft Visual C++ v14 Redistributable (x64)」にしました（旧称 Microsoft Visual C++ 2015-2022）

### 観測の変更

- アプリのログの終了時に `LTC frame check summary` の行を足しました（落としたLTCのフレームの数、受け始めで使わなかった数、受け取った数、極性補正ビットの数）

### 既知の不具合

- 推奨素材の範囲内で既知の不具合は0件です（v0.6.4と同じ）

### 既知の間欠（まれに起きる）

- v0.6.1のノートの一覧と、v0.6.4で足した1行（一時停止中にシークした直後に先の絵が止まって見えることがある件）と同じです。v0.6.4で足した1行の件は、v0.6.5の検証機で1回出ました。出力のトレースでは、合成に使った絵と内部の再生位置は目標どおり（24.968秒）で、画面の再生位置の表示だけが約3秒先（25.1秒）を指していました。表示を作った経路は特定できていません。v0.6.4の2回はトレースが無く、試験の判定も表示の文字列を読んでいたので、同じ型だった可能性があります（推定）。再生位置の表示は同期の確認に使う画面なので、既知の間欠として残します

### 検証の概要

公開したビルドは、検証機で試した候補（`0.6.4+899ee68`）と製品のコードが同じで、版番号と文書だけが違います（下の「配布物」）。shim（`tcs_gstreamer.dll`）はv0.6.4から変わりました（v0.6.4: `251627d33d69b998a6ebe71fad51902014aea783ce166cb56d785b3d734dbccb`、v0.6.5: `6266d2042ea97e7cc00e018e7e6066332154fb3e142f2e7e36ca0b31f5e2e7c6`）。ProResのプラグインはv0.2.3のままです。

- **開発機**（2026-10-05〜06、RTX 3070）
  - 非E2E 3,001件合格 / 0失敗。shimの試験（ProResのGPUデコードの方針の表を含む）は失敗0
  - LTCシナリオの一式（標準・重い素材・ProRes×2・連続追従×2）と、LTCのループの試験14件: すべて合格
  - LTCのフレームの検査: 正しい信号で、桁と長さで落としたLTCのフレームは0、偶奇の不一致は0。25fpsの極性補正ビット（bit 59）は受け取ったLTCのフレームの約半分で1（規格どおり）
  - 保持を繰り返すシナリオで、保持の入口の判定（アプリのログの`Sync hold summary`の`holdEntries`）がv0.6.4より1〜2回少ない回がありました。受け始めの最初の1つを使わないため、短い流れのあとでは入口の判定が省かれることがあります。止まる位置は同じです
- **検証機**（2026-10-06、RTXと内蔵AMDのOptimus、実素材M1〜M7とProResのPR1〜PR4、利用者の操作が無く、UACや前面の窓が無いことを確かめてから開始）
  - 標準のシナリオ3通り（うち1通りは本番と同じ構成: インストール版・トレース無し）: それぞれ38件合格 / 0失敗
  - 連続追従6本合格、トラックの切替2本合格（映像の止まりの最大0.017・0.017秒、0.02秒を超える区間0）
  - ProRes: RTXでは183回のロードがすべてGPU、CPU 0、アダプタの不一致0（シナリオ38件合格 / 0失敗）。内蔵AMDでは76回すべてGPUで開き、CPUへの落ち0、アダプタの不一致0（シナリオ38件合格 / 0失敗）。アルファ付き（PR4）はGPU・CPUとも読み込み可
  - 内蔵AMDのGPUでは、4K60のProRes HQのデコードがCPUより追いつかず、同期の合わせ直しが増えました（同じ試験でv0.6.4のCPUデコード55回 → v0.6.5 99〜101回。GPUデコードを無効にすると54回）。想定は外付けのGPU（NVIDIA・AMDとも）です。内蔵GPUで追いつかないときは、設定の「ProRes の GPU デコード」を「無効」にしてください
  - LTCのフレームの検査（アプリのログの`LTC frame check summary`）: 長さで落としたLTCのフレームは標準の3通りで44・74・46、内蔵AMDで62。桁で落としたもの・偶奇の不一致は0。送出の切り替わりの頭のLTCのフレームを設計どおりに落としたもので、受け取りの挙動（Jumpの診断の数）はv0.6.4と一致しました。極性補正ビットは25fpsの信号でbit 59、30fpsの信号（トラックの切替の試験）でbit 27が約半分で1でした（規格どおり）
  - 試験が参照のフレームを古いと判定した記録が、2つの回で各12行ありました（同じ素材の末尾。v0.6.4の同じ回でも同じ場所で12行）。トラックの保持中の黒は、5回の試験で確かめた100フレームで0
  - プロジェクトの保存と復元10回: 失敗0。足した直後の選択の試験1件合格。非E2E 3,001件合格
  - GStreamerのCRITICALの行のうち`gst_segment_do_seek: assertion`の行（shimのログ`tcs-gst-raw.log`、同じ時刻に`gst_segment_position_from_running_time_full`の行が組で出るが、そちらは数えていない）: 一式で、標準の3通り10・14・16行、ProRes RTX 19行、内蔵AMD 42行（増えた分の大半は、GPUデコードの遅れで合わせ直しが増えたトラックの切替の連続の試験）
  - 起動直後のUIの止まり（`UI heartbeat summary`の`firstLateMs`）: 各回の中央値650〜840ms、最大1,192ms
