# 公式受信機の起動有無によるSpout公開の対照実証

2026-09-09。ユーザーの「次へ進んでください」を受け、[位相実証](GPU-SEND-PHASE-PROBE-RESULTS-2026-09-09.md)で残ったSpout access mutex取得失敗を切り分ける。親が設計・レビュー・実機評価、サブエージェントがハーネスを実装する。

実装・5回の実機試験は完了。[結果](GPU-RECEIVER-CONTROL-PROBE-RESULTS-2026-09-09.md)を参照。受信機を起動しない4K対照2回はSpout60Hz・取得失敗0、公式受信機あり2回は53.50〜56.41Hz・取得失敗143／79回だった。位相4msでの表示準備未完了も再現している。

## 根拠

位相4msの2試行では、取得失敗が最大8／7回連続していた。一方、成功回のSendTexture呼び出しは平均約0.037ms、復帰からGPU完了のCPU観測までは平均約0.13〜0.14msだった。成功時の送信処理が周期を使い切っているという説明だけでは公開空白を説明できない。

SDK 2.007.017の[ReceiveImage](https://github.com/leadedge/Spout2/blob/2.007.017/SPOUTSDK/SpoutDirectX/SpoutDX/SpoutDX.cpp#L903)では、共有画像のアクセス権取得後にstaging textureへのコピーとReadPixelDataを行い、その後にアクセス権を返す。公式[WinSpoutDXreceiver](https://github.com/leadedge/Spout2/blob/2.007.017/SPOUTSDK/SpoutDirectX/SpoutDX/Windows/Receiver/WinSpoutDX.cpp#L121)はReceiveImageとGDI描画を使用する。受信側の処理が競合に関係する可能性を、まず起動有無で比較する。ソースから受信機の実測保持時間やGPU内部原因までは断定しない。

## 変更範囲

試作アプリのソース・実行ファイル・送信処理は変更しない。既存 `GpuOutputProbe.dll` のSHA-256 `1D4ADEFCFC3EEC9649107392F36D927FA6D5D90E2E60D1847B46B489F084B372` を全試行で維持する。

ハーネスへ `-ReceiverMode official|none` を追加する。既定officialは従来どおり公式受信機を起動し、生存範囲・終了を確認する。noneは受信機を起動せず、全画面とSpout送信を通常どおり動かす対照条件。受信機EXEや依存DLLのhash記録は維持する。

解析器はnoneを「所有受信機を起動しない送信側対照測定」と明示する。command.jsonとrunner-result.jsonの両方でnoneが明示され、所有受信機情報がnull・サンプルが空であることを要求する。officialの起動失敗・早期終了・生存範囲不足をnoneとして救済しない。旧ログは従来のofficialとして扱う。対照条件の有効な送信計測と、受信性能の確認を区別する。

他アプリが受信していないことを完全に検証する機能ではない。既存プロセスを記録し、他アプリを終了・設定変更しない。起動前のプロセス名確認ではSpout、OBS、Resolume、TouchDesigner等は見つからなかったが、未知の受信アプリの不在証明にはしない。

## 比較

管理・解析テストと親レビュー後、noneの1080p短時間スモークを行う。正常終了と対照条件のログ分類を確認してから4Kへ進む。

4K試験はsplit／both、位相4ms、mutex待ち4ms、GPU生成3840×2160、60Hz、32秒、warmup5秒、解析窓 `[5,27)`。実表示先・スワップチェーンは既存の1920×1080。A=none、B=officialの順でA→B→B→Aを直列実行する。受信機以外の条件を維持し、単発の最高Hzで判断しない。

合成／全画面／Spout公開頻度、公開間隔と1秒区間最小件数、画像年齢、取得失敗と連続回数、取得区間、表示準備未完了、コピー見送り、期限超過を評価する。noneだけで取得失敗が消えるなら、所有受信機を伴う負荷・同期が関係する根拠とする。ただし受信機のどの内部処理が原因か、他の受信アプリでどうなるかまでは確定しない。両条件で失敗が残るなら、送信側・その他の接続等を追加調査する。

既存ログ・通常設定・表示設定・他アプリを保持し、新規ログへ記録する。終了対象は自分で起動したプロセスのみ。実機は親が直列実行し、WPR/UAC記録やGPUリセットは行わない。GPU異常時は条件を増やす前に停止して確認する。待ち時間の拡大、送信位相変更、本体統合、mpv／hwdec変更、保留中のSpout無効化・OBS混在問題へ範囲を広げない。
