# 表示準備通知を待ち受けるGPUループ案

状態: 2026-09-10、承認済みの最小独立実証を実装・評価済み。[結果](GPU-READY-PUMP-RESULTS-2026-09-10.md) では一貫した改善を確認できず、readyは候補として残し、既定tickを維持する。本体導入は別セッションで開始する。

## 目的と推奨構成

[同一プロセス内の待ち比較](GPU-PRESENT-SEGMENT-PROBE-RESULTS-2026-09-09.md) では待ち0／1msの一貫した改善がなかった。次は周期の冒頭だけで全画面の可否を決める仕組みを見直す。

最初の候補は、既存GPUスレッドが次の合成時刻まで待っている間、全画面の準備通知も待ち受ける方式とする。操作UI、合成と全画面を担当するGPUスレッド、Spoutスレッドという現在の分離構成を維持する。新しいD3D11デバイス、画像コピー、全画面専用スレッドはこの段階では追加しない。

現在は合成直後の準備確認で未準備だと、その出力回を見送り、次の合成時刻まで待つ。候補は未準備でも、その周期の残り時間に準備通知が来れば最新画像を選び直して表示する。例えば周期冒頭で未準備、2ms後に準備が整う場合、次の約16.67ms時点まで丸ごと見送る必要を減らせる可能性がある。通知がそのように到着するか、性能が改善するかは実証対象。

## 周期と処理順

- 合成とSpoutの目標60Hzを維持し、Spoutの位相4ms・mutex要求8msは比較条件として固定する。
- 全画面にも目標60Hzの出力枠を設け、一枠につき表示試行は最大一回。準備できた枠内の時点で表示するので、開始時刻が常に16.67ms間隔になるという意味ではない。
- 同時に処理可能になったら停止確認、期限に達した合成、全画面の順に判断する。表示の直前に利用可能な最新画像を取得する。
- 合成の次回時刻までの待機で、停止通知と表示準備通知を待ち受ける。次回合成時刻で待機を打ち切り、遅れて復帰した場合は通常の周期スキップを適用する。過去の表示枠を貯めない。
- 表示済みの枠では次の枠まで追加表示しない。source取得に失敗した場合もその枠で取得を繰り返さず、次の枠で最新画像を選ぶ。

目標60Hzと物理表示周期は区別する。Present間隔1を維持し、Spoutを表示先の更新周期へ従属させない。全画面を無制限に通知の回数だけ表示する案ではない。

## GPU画像と通知の所有権

準備通知の待機中は合成画像のleaseもkeyed mutexも持たない。通知の受領と画像の取得を分離し、表示できる時点で初めて最新画像を取得する。

通知を受け取ってから合成時刻や停止に達した場合、その準備状態を勝手に失わない。既存の準備状態保持と同じく、実際のPresent試行まで保持し、画像は次の機会に選び直せるようにする。通知の受領と60Hzの出力枠の使用済み状態は別々に管理する。

表示のGPU処理を発行したら既存の完了確認・drainを維持し、完了前に画像を返さない。Present中は共有sourceのkeyed mutexを保持しない。D3D11 immediate contextとPresentは既存GPUスレッドが所有し続ける。

停止通知で待機を解除し、新しい合成・描画・Presentを開始しない。開始済みGPU処理の完了確認後に資源を破棄する。待機中に他スレッドから通知handleやswapchainを閉じない。既存の通常終了・明示的強制終了UIを維持する。

## 技術的な成立条件と限界

Windowsの [WaitForMultipleObjects](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitformultipleobjects) で停止／準備通知と期限付き待機を組み合わせる候補とする。停止handleを優先し、復帰後にQPCと停止状態を再確認する。指定timeoutはOSの実際の復帰時刻を保証しない。短い残時間の待ち方とCPU使用量も実装時に確認する。

Microsoftは [D3D11のマルチスレッド説明](https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-render-multi-thread-intro) で、immediate contextの利用を直列化し、Presentを含むDXGI操作を同じスレッドで行うよう示している。この案では現在の所有関係を維持できる。

この変更で分離するのは通知を待つ時間であり、GPU描画・完了確認・Present自体が長引くと合成への影響は残る。したがって「全画面が合成を一切待たせなくなる」とは扱わない。通知待ちを変えても合成を妨げる実測が残るなら、その結果を根拠に全画面専用スレッド／デバイス等を別段階で設計する。

## 合意後に具体化する実証

実装はサブエージェント、レビューと実機評価は親が担当する。既存の周期冒頭確認を比較基準として残し、候補は独立試作の全画面1面・split出力に限定する。CPUアップロード、mpv、GPUプレビュー、本体統合は含めない。

管理テストでは、準備が周期途中に来る、合成期限と同時に来る、通知受領後に次枠へ遅れる、停止と同時に来る、source取得失敗、保持済み通知、表示済み枠への重複通知を扱う。最新画像選択、追加表示の禁止、catch-upなし、待機中の画像非保持と終了順序を確認する。

計測では出力枠の予定、待機開始／終了理由、通知のCPU観測時刻、画像選択、GPU描画、Present開始／終了、見送りを区別する。通知待機中にまだ選んでいない画像IDを付与しない。現在の解析器が前提とする「画像取得後の準備確認」と異なるため、新経路の所有権検証を明示的に追加する。

全画面・Spoutの公開頻度と間隔、公開画像年齢、合成の開始遅れ、コピー取得失敗、CPU負荷を比較する。通知待ちの単なる長期化で合成や送信が悪化していないかを含めて判断する。具体的な試験時間と比較順序は実装仕様で固定する。

実機は短い1080pから開始し、正常終了確認後に4K生成キャンバスを直列比較する。実描画寸法1080p、公式受信機の使用、既存ログ・通常設定・他アプリの保持、所有プロセスだけの終了、WPR/UAC記録を行わない条件を維持する。

## 2026-09-10の最小実証仕様

`--display-pacing tick|ready` を追加し、既定tickは現行の周期冒頭確認。readyはsplit／both／静的準備待ち0ms／wait-plan fixedに限定する。合成後に次回合成予定と共通終了時刻の小さい方を期限として、停止handleと準備handleを最大1回だけ待つ。実効timeoutは残時間msの切捨て、準備状態保持済みならnative wait不要。通知待ち中に画像leaseとsource keyed mutexを持たない。

最初の比較では複数回の通知待ちを実装しない。timeoutが期限より早く戻った場合、同じ枠内で再待機せず既存のidle待ちへ戻る。端数msを含む残り時間に通知が来ても次枠になる限界を明示し、全残時間を漏れなく扱う完全なイベントループとは呼ばない。タイマー方式やthread数を同時に変えることを避けた限定実証である。

通知成功後に停止・期限を再確認する。遅れて受け取った通知は保持できるが、その枠では新しく描画しない。次枠の合成を優先し、最新画像を再取得する。source取得失敗で同枠の描画を繰り返さない。GPU完了確認・Present前の共有画像返却・通常終了と強制終了の既存動作は維持する。

`display.wait.start/end` は通知待ちを画像IDなしで記録する。予定tick、次回期限、要求timeout、native／保持済みの区別、復帰理由、準備状態保持の有無を記録する。その後の画像取得と既存 `present.ready`、draw、Presentを別段階として全ログで照合する。tickとreadyのログ契約を明示的に区別し、既存ログも引き続き解析できるようにする。

GPU待機のCPU使用量も比較するため、プロセスCPU累計差と対応する実測区間を両条件共通に記録する。全runの近似値は22秒の画像性能窓と混同せず、受信機CPUやGPU使用率とも扱わない。

親がレビューと管理テストを確認後、1080p/windowed readyを12秒・warmup2秒で実行。正常終了と記録確認後、4K生成キャンバスでtick→ready→ready→tickを各32秒・warmup5秒、一回ずつ直列実行する。split、Spout位相4ms、mutex要求8ms、公式受信機、monitor index1を固定する。全条件を同一新バイナリで比較する。
