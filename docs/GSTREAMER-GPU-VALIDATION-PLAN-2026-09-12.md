## V2 の検証方法（親の設計、2026-09-12）

V2 は「音声出力あり」を口頭ではなく**数値で**判定する。理由は再現性で、mpv 撤去の判断材料として記録に残す必要があるため。

### 測り方

既定の再生デバイスを **WASAPI ループバックで録音**し、100ms ごとの RMS（dBFS）を出す。
そのために `scripts/AudioLoopbackProbe`（NAudio 2.2.1 の `WasapiLoopbackCapture` を使う小さな .NET コンソール）を親が用意した。
`AudioLoopbackProbe <seconds> <out.csv> [windowMs=100]` で `t_ms,rms_dbfs,peak_dbfs` を書き、要約（窓数・無音床・再生水準）を出す。
`Invoke-AppGpuTrial.ps1` から run と同時に走らせて `audio-rms.csv` を run ディレクトリへ残す。

**実測で分かった前提**（2026-09-12 20:5x の動作確認）:

- 既定の再生デバイスは `Realtek Digital Output (Realtek(R) Audio)`、IeeeFloat 48000Hz 32bit 2ch。無音時の RMS は −189 dBFS（デジタル無音）。
- **システム全体のミックスを拾う**。動作確認時は Chrome が −5 dBFS で再生しており、そのまま計測すると合否が壊れる。
  **V2 の計測中はブラウザなど他の音をすべて止めること**。上の「前提」行でこれを機械的に確認する。

操作は UIA で行う。runner に次を足す:

| 追加パラメータ | 操作 |
| --- | --- |
| `-MuteAtSeconds` / `-UnmuteAtSeconds` | `BtnMute` を Invoke |
| `-VolumeAtSeconds "12:50,20:100"` | `VolumeSlider`（0〜100）を RangeValue パターンで設定 |
| `-SpeedAtSeconds` | `BtnSpeed` を Invoke（速度は循環） |

### 合格条件

| 項目 | 条件 |
| --- | --- |
| 前提（他の音が鳴っていない） | run 冒頭の無再生区間 2 秒の RMS が **−60 dBFS 以下**。超えていたら計測せず中止する |
| 音声が出ている | 再生中の RMS 中央値が **−40 dBFS 以上** |
| ミュート | Invoke から **200ms 以内**に **−60 dBFS 以下**へ落ち、解除で元の水準（±1.5dB）へ戻る |
| 音量 100→50 | RMS が **−6dB（±1.5dB）** 変化する（`volume` 要素は振幅線形なので 0.5 倍＝−6.02dB） |
| 再生速度 | 速度変更後も音声が途切れず、error 0。映像位置が指定倍で進む。**音程が変わる**のは現行実装の既知の挙動として記録する（`pitch` 要素は入れない） |
| 映像指標 | 共通条件（実フレーム＝素材 fps、表示 59.9Hz 以上、合成 p99 1ms 以下、Spout 60Hz、error 0、exit 0） |

### 「落ち 0」という条件の読み方 — **親の説明が不正確だった（2026-09-14 訂正）**

**訂正前に書いていたこと**: 「このマシンでは落ち 0 をどの構成でも達成していない。
DISPLAY2 でも 40 秒あたり 1〜3 秒は present が 59 になる」。
**これは 2 つの別物を混ぜていた。**

`present.scanout` の**間隔**を直接測り直した結果（`TestResults/v8b`、5〜45 秒の区間）:

| run | present レート | 間隔の平均 | **真の落ち（間隔 > 25ms）** | 最大間隔 |
| --- | ---: | ---: | ---: | ---: |
| DISPLAY1 4K 素材 | 59.981/秒 | 16.679ms | **2 回 / 39 秒** | 33.3ms（vblank 2 回分） |
| DISPLAY1 1080p 素材 | 59.903/秒 | 16.701ms | **4 回 / 39 秒** | 46.6ms（vblank 3 回分） |

- **「present が 59 の秒が 1〜3 回」の大半は落ちではなく、数え方の産物**である。
  実レートが 59.98/秒なので、壁時計の 1 秒ごとに整数個を数えると、たまに 59 になる。
  表示が 60.000Hz ちょうどではないだけ（間隔の平均 16.679ms = 59.95Hz）。
- **本当に飛んでいるのは間隔が 33.3ms 以上になっている箇所**で、39 秒中 2 回（4K 素材）・4 回（1080p 素材）。
- **「DWM が原因」と書いたのも、確かめずに書いた推測だった。** 根拠は無い。

**教訓**: 「落ちた回数」を秒ごとの件数から読むと、実レートが整数 Hz でない限り必ず偽の落ちが出る。
**周期の乱れを見たいときは、件数ではなく間隔そのものを見ること。**
これは `compose.acquire` の `NotReady` を遅延の指標と誤読しかけた S4、
`source.acquire` の `Ready` を「新フレーム取得」と誤読した D5 と同じ種類の誤りである。

## V3 の原因特定（2026-09-13 12:42〜13:14、計測と実装の両方で確認）

### 欠陥 D1: アダプターが `seeking` / `pause` プロパティを実装していない

`MainWindow.IsNativeSeeking()` は `GetPropertyString(mpv, "seeking") != "no"` で判定する。
`GstMpvApiAdapter.GetPropertyString` が扱うのは `path` / `width` / `height` / `video-codec` のみで、
それ以外は `default: return string.Empty`。空文字は `"no"` と一致しないため **常に「シーク中」と判定される**。
同期判定は「シーク中は判断しない」構造なので、**`SyncDecisionEngine` が一度も走らない**。

| 問い合わせされるプロパティ | アダプターの対応 | 影響 |
| --- | --- | --- |
| `seeking` | **なし（空文字）** | `IsNativeSeeking()` が常に true → 同期判定が走らない |
| `pause`（2 箇所） | **なし（空文字）** | `IsNativeGapFreezeTargetReady()` が常に false |
| `audio-codec` | なし（空文字） | メタデータ表示（軽微） |
| `path` / `width` / `height` / `video-codec` | あり | — |

計測もこれと一致した:

| | GStreamer×Gpu | mpv×Gpu |
| --- | --- | --- |

## V3 の判定基準（2026-09-13、利用者の指示で書き直し）

### 定常誤差

連続再生中（シーク・ギャップ再入から **1 秒以上経過**、CSV の `excludedReason` が空）の**符号付き誤差**について、

### 回復時間

ブロックさせない」という目的は達成されている。時間の大半は b'→c、すなわち**パイプラインが

seek-b では mpv の方が遅い（202.8ms 対 113.3ms）。

**1 回のシーク単体では、GStreamer と mpv に本質的な差は無い。**

### `seek.decide` が 1 回しか出ない — これは正常

90 秒の測定を通して `seek.decide` は**起動直後の 1 件だけ**（`delta=-0.648s`）。
以降は同期エンジンが補正を必要としていない。`player.seeking` も `raw=no` 44 件 /
`raw=yes` 3 件と正しく遷移しており、**D1 の修正が効いて一度ロックしたら維持できている**。
定常誤差が mpv と一致した理由がこれである。

（`seek.issue` のうち target≈9.96〜9.98 秒のものはクリップ末尾へのフリーズ用シークで、
同期シークではない。`load.issue` はクリップ境界（タイムライン 12 秒 / 24 秒）での切替。）

## seek-c の 1269ms の正体 — CPU 合成に限った公開の停滞

表 2 のとおり、seek-c でも**正しいフレームは 324ms で公開されている**。
それでも表 1 の回復時間が 1269ms になるのは、**その後に公開が止まるから**である。

### CPU 合成で実際に表示されたフレーム（`d2cpu-gst` の `trace.jsonl`、seek-c）

| 時刻 | gst が表示したもの | mpv が表示したもの |
| ---: | --- | --- |
| 258ms | clip2 frame 286（旧クリップを保持） | clip2 frame 286 |
| 321ms | （まだ来ない） | **clip3 frame 185** |
| 559ms | **clip3 frame 184** | clip3 frame 199 |
| 863ms | clip3 frame 204 | clip3 frame 215 |
| **1186ms** | clip3 frame **223** ← **323ms 公開なし** | clip3 frame 234（連続） |

**フレーム番号は 204→223 と 19 枚（317ms 分）進んでいる。復号は進んでおり、公開だけが止まった。**
表示が frame 204 で固まっていたので誤差が -290ms から -640ms へ発散した。

### 公開間隔の最大値（ms @ フェーズ内経過 ms）

| run | seek-b | **seek-c（60fps）** | seek-back |
| --- | --- | --- | --- |
| `d2cpu-gst` | 201@197 | **323@863**, 301@258 | 134@235 |
| `d2tl-gst` | 203@175 | **328@203**, 313@836 | 137@248 |
| `d2cpu-mpv` | 170@243 | 91@205 | 191@244 |
| `d2tl-mpv` | 111@196 | 100@211 | 64@239 |

**GStreamer は 60fps のクリップでだけ、切替時に加えてもう一度 ~320ms 止まる。2 回の run で再現。
mpv は切替時の 1 回だけ。**

### GPU 合成（v0.4 が出荷する経路）にはこの停滞が無い

| run | フェーズ | `compose.publish` 件数 | 公開間隔の最大 |
| --- | --- | ---: | ---: |
| `tl-gst` | seek-c | 373 | **18ms** |
| `tl-mpv` | seek-c | 373 | 18ms |

`gst.delivery`（実際のフレーム到着）も seek-c で 354 件 / 6.2 秒（≒60fps）、
シーク時の 253ms を除けば最大 34ms。**GPU 合成では両バックエンドとも停滞しない。**

### 機構: CPU 合成は 1 フレームごとに GPU からの同期読み戻しをしている

`GstMpvRenderApiAdapter.RenderContextRender` -> `GstBackendState.RenderInto` ->
`tcs_player_leased_cpu_copy`（`tcs_gstreamer.cpp`）。この最後の関数は
**`frame_lock` を保持したまま**、1 フレームごとに次をやる。

1. GPU テクスチャ -> staging テクスチャへ `CopyResource` / `CopySubresourceRegion`
2. `ID3D11DeviceContext::Flush()`
3. **`Map(staging, D3D11_MAP_READ)`** — GPU の完了を待つ**同期読み戻し**。呼び出しスレッド（UI）がブロックする
4. 1920x1080x4 = **8.3MB** を行ごとに `memcpy`

60fps では毎秒 60 回、**約 500MB/秒の読み戻しとフレームごとの強制同期点**が UI スレッドに乗る。
さらに `frame_lock` を保持している間は `on_new_sample`（ストリーミングスレッド）も待たされる。

**3 つのクリップは全て 1920x1080 で、違いはフレームレートだけ**（24 / 29.97 / 60）。
解像度も形式も同じなので staging テクスチャは作り直されない。**変数は fps だけ**である。
24fps・29.97fps では間に合い、60fps で間に合わなくなる、という観測と一致する。

mpv にこれが無いのは、mpv が SW レンダー API で最初から CPU バッファへ描くからである。
GPU 合成にこれが無いのは、D3D11 テクスチャをそのまま合成して読み戻さないからである。

このコードのコメント自身が `暫定プレビュー通路` と書いている。
**GStreamer x CPU 合成は設計上ここが高コストであり、60fps 素材はその限界を超えている。**

### 結論（V3 の判定ではなく、事実として）

seek-c の劣位は **GStreamer × CPU 合成**の組み合わせに固有で、**GStreamer × GPU 合成には現れない**。
CPU 合成は v0.4 が既定にする経路ではない。

> **利用者への確認事項**: v0.4 で `outputBackend=Cpu`（CPU 合成）を残すのであれば、
> この停滞は残課題として扱う必要がある。mpv と同時に CPU 合成経路も落とすのであれば、
> 直す対象ではなくなる。**この 1 点だけ方針の確認をお願いしたい。**

- 伸びているのは **load 発行後の最初のフレーム到着待ち**。入力側（start→LTC 170〜250ms）と

| --- | ---: | ---: | ---: | ---: |

| mpv | 150.2ms | 76.7ms | **143.0ms** | 235.4ms |

### 同期エンジンはこのずれを見ていない（2026-09-14、親）

`spread/gst` の `seek-c` フェーズ（5 秒間）に記録された制御イベントは**これだけ**だった。

```
  232ms load.issue     value=3080000  start
  240ms load.return
  283ms player.seeking raw=no
 2311ms player.seeking raw=no
 4322ms player.seeking raw=no
```

**`seek.decide` が 1 件も無い。** このイベントは `SyncDecisionEngine.Decide` の中で
`Math.Abs(delta) <= toleranceSeconds` を抜けた**後**・抑止判定より**前**に記録される。
つまり**エンジンは 5 秒間、一度も「ずれている」と判断していない**。

許容は `ToleranceFrames = 6.0`、`max(videoFrameSeconds, timecodeFrameSeconds) * 6` なので
25fps LTC では **240〜250ms**。表示は -274ms ずれており、**本来なら超えているはず**である。

**mpv でも同じ**（seek-c で `seek.decide` 0 件、-147.5ms のまま）。

### コードから確実に言えること

`MainWindow.xaml.cs` の 2 箇所（`SingleModeSyncCoordinator` と継続モード側）で
`SyncPlaybackState` を作っている。どちらも:

```csharp
GetTimePos: () => { int rc = _mpvApi.GetProperty(_mpv, "time-pos", ...); return (rc, playbackSeconds); }
BuildPlaybackState: playbackSeconds => new SyncPlaybackState(
    ...
    IsSeeking: _seekBarInteraction.IsSeeking,
    PlaybackSeconds: playbackSeconds,
    ...)
```

1. **`PlaybackSeconds` は `time-pos`**、すなわち**プレイヤーの自己申告位置**であって、
   **実際に画面へ出ているフレームの位置ではない。** 両者はパイプラインの表示遅延の分だけずれる。
2. **`state.IsSeeking` は `_seekBarInteraction.IsSeeking`**（利用者がシークバーを掴んでいるか）であり、
   `IsNativeSeeking()` ではない。`IsNativeSeeking` は別引数で渡され、**抑止側にしか使われない**。
   ハーネスでは誰もシークバーを操作しないので、**この値は常に false のはず**である。

**2 により、仮説 (b)（`IsSeeking` が真で `Decide` が冒頭で返っている）は成立しにくい。**
残るのは仮説 (a)、すなわち**エンジンの `delta` が許容内**という筋である。

**これはバックエンド固有ではなく、同期の設計そのものの盲点**にあたる。
mpv でも同じ挙動が出ていることと整合する。**V3-B（`docs/prompts/2026-09-14-V3-B-engine-blindness.md`）で
`delta` と表示誤差を同時に記録して確定させる。**

### 確定した連鎖

1. 60fps クリップへシークすると、最初のフレームが出るまで **254.9ms** かかる
   （24 / 29.97fps では 91〜121ms、mpv は同じ 60fps で 143.0ms）
2. その遅れが**そのまま定常オフセット -274ms になる**
3. **その後、誰も補正しない**（5 秒間 -270ms 前後で一定。`HasReachedSeekTarget` の許容内と判断されている）
4. 結果として tol 250ms には原理的に到達せず、回復時間の基準を落とす

**直す道は 2 つある。どちらを採るかは設計判断:**

| 案 | 内容 | 効く範囲 |
| --- | --- | --- |
| (1) 着地を速くする | 60fps で最初のフレームが出るまでの 254.9ms を縮める | 60fps の 1 フェーズ |
| (2) 着地後の残差を補正する | 着地後に残ったオフセットを同期エンジンが詰める | **全フェーズ**（24/29.97fps の -102〜-113ms にも効く） |

**(2) の方が効く範囲が広い。** ただし同期判定の挙動そのものを変えるため、
`TimecodeSyncSeekState.HasReachedSeekTarget` の許容と、再シークの発振を起こさない設計が要る。
これは D3（「sync seek の保留が長く続く」）で見ていた領域と同じ場所である。

> なお `present.scanout` はこのハーネスが全画面表示を開かないため 0 件で、
> **公開→走査の段は測れていない**。実表示までの遅延はこの数字に含まれていない。

### 回復時間が seek-c で基準に到達しない理由もこれ

判定基準の注意書きに書いたとおり、**しきい値が定常誤差より小さい場合は原理的に到達しない**。
seek-c の定常オフセットが -274ms なので、tol 250ms には到達しようがない。
**回復が遅いのではなく、着地位置が遠いまま動かない。**

### CPU 合成で見えた 60fps の停滞とは別の現象

表 1・表 2 で記録した「CPU 合成で 60fps のとき公開が ~320ms 止まる」は、
**公開が止まって誤差が -290 → -640ms へ発散する**という別の挙動だった（GPU 合成では起きない）。
今回のものは GPU 合成で、**発散せず一定**。共通しているのは **60fps 素材でだけ起きる**という点。

## 欠陥 D4: GPU 合成にすると、ロード後 5 秒間 LTC 同期の補正が止まる（2026-09-14）

**V3 の数字より根の深い欠陥。V1〜V10 の前提そのものに関わる。**

### 観測

V3-B（`sync.evaluate` 計測、`TestResults/v3b`）でフェーズごとの評価回数を数えた。

| フェーズ | 長さ | gst の評価回数 | 1 秒あたり | エンジンの \|delta\| | 実際の表示誤差 |
| --- | ---: | ---: | ---: | ---: | ---: |
| black-sweep | 36.3s | 496 | 13.68 | 17.3ms | - |
| freeze-sweep | 36.3s | 371 | 10.23 | 23.5ms | -37〜-53ms |
| seek-a | 6.2s | **1** | **0.16** | 44.8ms | -105.8ms |
| seek-b | 6.2s | **1** | **0.16** | 125.9ms | -112.7ms |
| **seek-c** | 6.2s | **1** | **0.16** | **99.2ms** | **-274.1ms** |
| seek-back | 6.2s | **1** | **0.16** | 40.0ms | -102.1ms |

**mpv でも同じ**（seek-a/c/back が各 1 回、seek-b が 4 回）。**出力経路側の問題であって、プレイヤー側ではない。**

### 原因（コードで確定）

`ContinueOnTrackCoordinator` は `Decide` に入る前に 3 つのゲートを通る。

```csharp
if (_effects.IsNativeSeeking?.Invoke() == true) return SyncRequestResult.Deferred;
(int timePosRc, double playbackSeconds) = _effects.GetTimePos();
if (timePosRc != 0) return SyncRequestResult.Deferred;
if (!_syncService.TryMarkFileLoaded(playbackSeconds, _effects.GetTotalRenderedFrames())) return SyncRequestResult.Deferred;
```

止めているのは 3 番目である。アプリログに証拠が残っていた:

```
Continue mode: waiting for file load stability playback=4.167 mediaPos=4.200 renderedFrames=0
Continue mode: waiting for file load stability playback=5.167 mediaPos=5.240 renderedFrames=0
Continue mode: waiting for file load stability playback=6.167 mediaPos=6.200 renderedFrames=0
```

**`renderedFrames=0`。** `TimecodeSyncService.TryMarkFileLoaded`:

```csharp
private const double FileLoadPlaybackProgressSeconds = 0.08;
private const long FileLoadRenderedFrameProgress = 2;
private static readonly TimeSpan FileLoadTimeout = TimeSpan.FromSeconds(5);
...
long renderedFrameProgress = renderedFrameCount - _fileLoadStartedRenderedFrames;
if (playbackProgress < FileLoadPlaybackProgressSeconds ||
    renderedFrameProgress < FileLoadRenderedFrameProgress)
    return false;
```

`renderedFrameCount` の実体は `MainWindow` の
`GetTotalRenderedFrames: () => _playbackPerformanceStats.TotalRenderedFrames` であり、
これは **CPU の WriteableBitmap 経路で描画したフレーム数**である。
**GPU 合成ではビットマップを描かないので、この値は永久に 0 のまま。**

したがって `renderedFrameProgress` は常に `0 < 2` となり、**ゲートは 5 秒のタイムアウトでしか開かない**。

### 影響

- **`OutputBackend=Gpu` にすると、ファイルロード・トラック切替のたびに LTC 同期の補正が 5 秒間止まる。**
- 精度ハーネスのシークフェーズはちょうど 5 秒なので、**フェーズ全体で同期が効いていなかった**。
  スイープ（35 秒）ではタイムアウト後に毎秒 10〜14 回動くため、この欠陥が見えていなかった。
- **本番では、トラックが切り替わるたびに 5 秒間 LTC からずれても補正されない**ことになる。
  ライブショー用途としては見過ごせない。

### V3 の数字への影響

**V3 の測定値は、この欠陥を含んだ状態のものである。**
seek-c の -274ms が「着地のずれ」なのか「5 秒間補正されないこと」なのかは、
**D4 を直してから測り直さないと分けられない。**

依頼 A で確定した「着地の遅れが定常オフセットを決める」という連鎖自体は変わらないが、
**「その後、誰も補正しない」の理由が、許容内だからではなく、そもそもエンジンが止められていたから**
という可能性が出てきた（seek-c の唯一の評価では \|delta\|=99.2ms で許容 240ms 内だったので、
仮に動いていても補正はしなかったはずだが、それは 1 標本の話であり、
5 秒間動いていればどこかで超えた可能性がある）。

**D4 を直し、V3 を測り直す。それまで V3 の判定は保留とする。**

### D4 が既存の測定値のどこを無効にするか（読み違えないために）

D4 は**シークのフェーズ中だけ**同期を止めていた（スイープは 35 秒あるのでタイムアウト後に動く）。
したがって既存の数字は**列ごとに生死が分かれる**。

| 表 1（回復時間） | `black-sweep` / `freeze-sweep` | `seek-a` / `seek-b` / `seek-c` / `seek-back` |
| 表 2（時系列） | **全部生きている**（着地までの時間の話で、同期の補正とは独立） | - |

| 表 3 の 3(b) | - | seek 列（ただし両条件が等しく影響を受けるので、着地方式の比較としては読める） |

## 欠陥 D5: リース返却漏れで、合成器が同じフレームを返し続ける（2026-09-14）

**GStreamer × GPU 合成でのみ発生。黒ギャップ中にクリップが切り替わると、表示がそのまま固まる。**
固まった先が黒なので「映像が消えて戻らない」ように見える。**精度 run 10 本中 2 本で発生。**

### 原因（OpenCode が特定、親が独立に検証）

`OutputEngine.ComposeTick`:

```csharp
if (!retained && acquired != null) { acquired.Value.Release(); acquired = null; lease = null; }
```

GStreamer の共有リング経路では `LayerImage` が lease を**所有しない**（`Lease = null`）。
そのため `lease = null` はラッパーを **Dispose せずに捨てる**。
`GStreamerSource.active` の参照が残り、**以降 `TryAcquire` は同じ画像を返し続ける**。

shim の契約（`tcs_gstreamer.cpp`）も「リース保持中は同じフレームを返し、release まで進まない」。

**mpv で起きないのは、mpv の `LayerImage` が lease を所有するため `Release()` で返るから。**
実測でも mpv × GPU 合成は `unexpected-black=0` である。

`retained=false` になるのは **`gap==Black` で `KeepHeld` が走らず `held==null`**（世代切替の
`ClearHeld` 直後）のとき。失敗 run のログとも一致する:

```
05:56:20.672 [INF] Continue mode: entered gap, rendering black frame
05:56:22.706        clip2 -> clip3 の切替
（以降、gap 終了の記録が無い）
```

### 親の独立検証

| 指標 | 失敗 `d4-gst` | 正常 `d4-gst-2` |
| --- | ---: | ---: |
| `compose.srv`（切替前 <24s） | 556 | 546 |
| **`compose.srv`（切替後 >=24s）** | **1** | **2604** |
| `lease is still outstanding` 警告 | **3** | 0 |

**切替後に新しいシェーダリソースビューが作られていない。** 合成器は同じ古い画像を描き続けている。

> **親の誤り（記録として残す）**: 親は `source.acquire` が切替後も `Ready` を 60/秒で
> 返していることから「取得は正常、止まっていない」と判断し、「表示ではなく計測の読み戻しの
> 問題かもしれない」と訂正を出した。**これは誤りだった。**
> `Ready` は「取得に成功した」であって「**新しい**フレームを取得した」ではない。
> **同じフレームを返し続けていても Ready になる。**
> `compose.srv`（新しいビューを作った回数）を見れば一目で分かった。
> **「進んでいるか」を見たいときは、成否ではなく“中身が変わったか”を数える指標を選ぶこと。**
> これは `compose.acquire` の `NotReady` を遅延の指標と誤読しかけた S4 と同じ種類の誤りである。

決定的な再現系（狭いテストフックで黒ギャップ中の世代切替を強制する）を作らせている。
**D2 と同じく、決定的に再現させてから直す。**

### E2E 6 件失敗の真因: ディスク枯渇（2026-09-13 19:32〜19:37、撤回済みの疑い）

`ccb3bad`（D2 差し戻し対応）の検証で **E2E が 6 件失敗**した（失敗 6／合格 52／スキップ 5）。
同じバッチの GPU trial も `RUN` 行を出さずに落ちた。落ちたのは `LtcHardwareLoopE2ETests` の
同期シークと黒ギャップ復帰 — D1／D2 が触った領域そのものだったため、いったんは
「アプリ統合レベルの回帰」と読んだ。**これは誤りだった。**

真因は **C ドライブの空き容量が 50 MB まで枯渇していた**こと。

- `GStreamerBackendE2ETests.GStreamerBackend_PlaysAndPublishesGpuFramesToSpout` は
  受信側プロトタイプに **全フレームを無圧縮 BMP で書かせる**（720p60 × 8 秒 × 2 受信 ≒ 3 GB／回）。
- その出力先 `%TEMP%/tcs-gst-e2e-recv{1,2}/<GUID>/` を `finally` で **削除していなかった**
  （消していたのは `workDir` だけ）。2026-09-11 以降の全 run 分が積み上がり **4235 ファイル・10.9 GB**。
- 枯渇の痕跡は明確で、最後に書かれた BMP は**サイズ 1 バイト**で切れていた。
- 同じ枯渇で、直後に走らせた `git checkout` も `Out of diskspace` で失敗している。

**切り分け**: 同じ `ccb3bad` のバイナリで `LtcHardwareLoop` だけを単独実行すると **14/14 合格**。
バッチでは先行する GPU E2E がディスクを食い尽くしてから走るため落ちていた。
失敗は D2 の回帰ではなく、ハーネスの資源リークが引き起こした環境障害である。

**対処**: `GStreamerBackendE2ETests` に (a) `finally` での `recvDir1`/`recvDir2` 削除、
(b) 開始時に `%TEMP%/tcs-gst-e2e-recv{1,2}/` の旧世代を掃除する `PruneStaleTempDirs` を追加した。

**規則に追加**: **テストが落ちたら、まず実行環境の前提（ディスク・メモリ・セッション種別）を確認する。**
テストの失敗内容が「変更した領域」と一致して見えるときほど確証バイアスが働く。今回は失敗した 2 件が
たまたま D1／D2 の担当領域だったため、疑いの方向が固定されかけた。

### 記録の読み方（同じ誤りを繰り返さないために）

アプリのログは **worktree ごと・日ごとに追記され、run をまたいで蓄積する**。E2E は 1 つの日次ログに
何十プロセス分も書き込む。この性質を忘れたために親は 2026-09-12〜13 に 3 回続けて誤った判断をした:

1. **E1 の 1 回目の提出**を「3 回連続成功」で受け入れかけた（実際は過去 run の並びを拾って常に真になる判定だった。これは差し戻せた）
2. **E2「起動時の二重ロード」**（実際は別プロセス。撤回）
3. **S4「切替が mpv の 20 倍遅い」**（`NotReady` の意味の誤読と、バックエンド間で意味が揃わない指標の比較。撤回）

**規則**: ログから run 固有の事実を読むときは、必ず (a) その run のプロセス開始・終了時刻で絞る、
(b) 起動／終了マーカー（`=== TimecodeSyncPlayer 起動 / 終了 ===`）を跨いでいないか確認する、
(c) 指標の定義（何を数えているか）を、切替や操作を一切しない対照データで先に確かめる。

**`app-log-tail.txt` は末尾 400 行の抜粋であって run の全ログではない**（runner が切り出している）。
run の序盤に一度だけ出るログ（起動時の警告など）は含まれないことがある。
2026-09-13 の T1 検証で、上限到達の警告（run 開始 5 秒後に 1 回）をこのファイルで探して
「0 件」と誤読しかけた。**一度しか出ない事象を探すときは日次ログを run の時刻で絞る。**

**期待と違う結果が出たら、実装を疑う前に測り方を疑う。** 「警告が 1 回だけ出る」仕様に対して
0 件という観測が出たなら、まず観測手段の被覆を確認する。今日の 4 件の誤り（E1 の受け入れかけ、E2、S4、
この T1 の誤読）はすべてこの手順を飛ばしたことが原因で、T1 だけは報告前に気づけた。
